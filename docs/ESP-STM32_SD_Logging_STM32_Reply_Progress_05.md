## 3. SD 차단 분포 — 핵심 결과

### 3.1 측정 조건 (**적용 범위를 제한합니다**)

| 항목 | 값 |
|---|---|
| 펌웨어 | `4aa52af` |
| **측정 시간** | **24분 41초 (1481 s)** |
| 표본 수 | 737건 |
| 모드 구성 | SLP 약 92 %, F_ON 약 8 %, F_UP 순간 |
| 카드 | Q23 제공 예정 실물 카드 |
| 플러시 정책 | 2000 ms 또는 20레코드 (선착) |

**계획했던 8시간이 아닙니다.** 이 차이는 결론에 다음과 같이 반영돼야 합니다.

- ✅ 말할 수 있는 것 — "정상 상태에서 이 카드는 50 ms를 넘지 않는다"
- ❌ 말할 수 없는 것 — "장시간 운용에서도 그렇다"

SD 카드의 가비지 컬렉션·웨어 레벨링 블록 이동은 카드가 일정 수준 소모된 뒤
나타나며, 25분으로는 그 지점에 도달하지 않습니다. **§3.4의 판단은 잠정입니다.**

### 3.2 히스토그램

```
n=737   sdh 0 0 0 249 488 0 0 0   sdmax=46692us
```

| 버킷 | 범위 | 횟수 | 비율 |
|---|---|---|---|
| b0 | < 1 ms | 0 | — |
| b1 | 1–2 ms | 0 | — |
| b2 | 2–5 ms | 0 | — |
| b3 | 5–10 ms | 249 | 33.8 % |
| b4 | 10–50 ms | 488 | 66.2 % |
| b5 | 50–100 ms | **0** | — |
| b6 | 100–500 ms | **0** | — |
| b7 | ≥ 500 ms | **0** | — |

버킷 합계가 737로 `n`과 일치합니다 — 계측 자체의 무결성이 확인됩니다.

발생 빈도는 **0.4997 회/초**로, 2초 플러시 주기와 정확히 대응합니다.
플러시 1회가 대기 1회이며, 누락이나 중복 계수가 없습니다.

### 3.3 최대값의 성격

`sdmax = 46.692 ms`는 **t = 11 s에 기록된 뒤 1470초 동안 갱신되지 않았습니다.**

즉 이 값은 정상 상태의 최악값이 아니라 **부팅 직후 값**입니다. 첫 파일 생성,
디렉터리 조회, FAT 초기 접근이 몰리는 구간입니다. 정상 상태만 보면 실질 최대는
50 ms 미만이며 대부분 10–50 ms 대역에 있습니다.

### 3.4 판단 — `SD_TIMEOUT_*` 현행 유지

| 상수 | 현재 | 판단 |
|---|---|---|
| `SD_TIMEOUT_READY` | 200 ms | 유지 |
| `SD_TIMEOUT_XFER` | 100 ms | 유지 |
| `SD_TIMEOUT_BUSY` | 600 ms | 유지 |

근거는 **관측 최대 46.7 ms가 가장 짧은 타임아웃(100 ms)의 절반 이하**라는 것입니다.
축소하면 여유가 2배 미만으로 줄어 정상 카드 오탐 위험이 생깁니다.

§3.1의 제한을 다시 강조합니다 — **25분 기준 잠정 판단입니다.**

### 3.5 이전 세션과의 대조 (**중요**)

보고 #03에서 제출한 7분 세션과 합산하면 그림이 조금 달라집니다.

| 세션 | 표본 | b6 (100–500 ms) | b7 |
|---|---|---|---|
| 7분 (보고 #03) | 212 | **1건** | 0 |
| 25분 (이번) | 737 | 0 | 0 |
| **합계** | **949** | **1건 (0.11 %)** | **0** |

**100 ms를 넘는 사건이 실재합니다.** 이번 세션에서 관측되지 않았을 뿐입니다.
빈도가 0.1 % 수준이므로 25분 창에서 안 잡히는 것이 자연스럽습니다.

이 1건이 PID 주기를 넘으므로, 해당 주기의 히터 출력 갱신은 **실제로 누락됐습니다.**
영향 평가는 §6에 별도로 정리했습니다.

## 4. 회신 #03 §6.1 5개 항목 — 대비표

| # | 요청 항목 | 상태 | 비고 |
|---|---|---|---|
| 1 | 8버킷 히스토그램 전체 | ✅ | §3.2 |
| 2 | p50 / p99 / max | ⚠️ **부분** | 아래 |
| 3 | 로깅 전용 vs 백필 동시 | ❌ **미실시** | 백필 미발생 |
| 4 | 세션 후반 구간 | ⚠️ **부분** | 25분치 후반 |
| 5 | 힐링 IR 도달 온도 | ⚠️ **표본 2건** | §5 |

### 2번이 "부분"인 이유

| 지표 | 값 |
|---|---|
| p50 (369번째) | **10–50 ms 구간** |
| p99 (730번째) | **10–50 ms 구간** |
| max | 46.692 ms |

**p50과 p99가 같은 버킷에 들어갑니다.** 표본의 66 %가 b4 하나에 몰려 있어
버킷 경계보다 세밀한 백분위를 산출할 수 없습니다. 표본을 늘려도 해상도는
개선되지 않습니다 — 계측 구조의 한계입니다.

버킷 경계를 재설계하면 해결되지만, **현재 경계는 100 ms(PID 주기)에 맞춰
설계된 것**이라 그 눈금을 흐리는 변경은 권하지 않습니다. 판단에 쓰이는 값은
"100 ms 초과 건수"이고, 그것은 정확히 나옵니다.

정밀 백분위가 §6.1의 의사결정에 실제로 필요한지 알려주시면 재설계를 검토하겠습니다.

### 3번이 "미실시"인 이유

백필이 발생하지 않았습니다. ESP32 측에서 백필을 요청해 주셔야 이 구간이 생깁니다.
누적 히스토그램이므로 **세션 중 아무 때나 걸어 주시면 그 영향이 반영됩니다.**
다만 구간 분리 값이 필요하시면 `v_Tim_SD_Block_Clear()` 호출 트리거를 넣어야
하며, 현재 이 함수는 정의만 있고 호출부가 없습니다.

## 5. 힐링 도달 온도 및 승온율 — Q29 실측

`4aa52af`의 전용 로그로 처음 실측했습니다.

| # | 설정 | 도달 | 소요 | 오버슛 | 유효 |
|---|---|---|---|---|---|
| 1 | 80.0 | 81.0 | 3588 ms | **+1.0** | ✅ |
| 2 | 64.0 | 80.9 | 0 ms | — | ❌ §6 |
| 3 | 64.0 | 64.3 | 2676 ms | **+0.3** | ✅ |

**`UP timeout` 종료는 0건입니다.** 세 번 모두 설정값에 도달했으며, 지적하신
"상한에 걸려 조기 종료" 경로는 이번 세션에 나타나지 않았습니다.

### 승온율 — **약 12.1 °C/s**

3번은 SLP에서 출발했고, SLP 유지온도는 ESP32가 런타임에 전송하는 **32 °C**입니다
(보고 #07 §6에서 의도된 값으로 확인). STM32 헤더 기본값 38이 아닙니다.

```
(64.3 - 32) / 2.676 s ≈ 12.1 °C/s
```

1번은 콜드 부팅 직후라 출발 온도가 특정되지 않아 환산하지 않았습니다.

Q29에서 유도로만 답했던 값의 실측 대응입니다.

### 오버슛의 성격

+1.0과 +0.3의 차이는 제어 오차가 아니라 **표본화 위상**입니다.
종료 판정은 메인 루프마다(약 12 µs 주기) 돌지만, `f_IR_Temp_Get()`이 새 값을
내놓는 주기는 그보다 훨씬 깁니다. 오버슛은

```
오버슛 = 승온율 × (설정값 교차 시점 ~ 다음 센서 갱신까지의 시차)
```

이고, 시차가 0에서 갱신주기 사이에 흩어지므로 매 사이클 달라집니다.
12.1 °C/s를 적용하면 관측된 두 값이 각각 **약 83 ms**(+1.0 °C)와
**약 25 ms**(+0.3 °C)에 대응하며, 둘 다 **IR 센서 갱신주기 약 100 ms 이내**로
일관됩니다.

따라서 이 승온율에서 **오버슛 상한은 약 +1.2 °C**(= 12.1 × 0.1)이며,
관측된 최대값 +1.0이 이미 그 상한에 근접합니다.

**유효 표본이 2건이므로 분포로 제시하지 않습니다.** 추가 계측 시 갱신하겠습니다.

## 6. 새로 발견된 동작 — 잔열 상태 재진입

표 5-2번 항목입니다. 별도로 다룰 값이 있습니다.

```
[I/FORCE]UP reached ir=80.9 set=64.0 in 0ms -> ON
```

**설정값 64 °C인데 실제 80.9 °C에서 시작해 0 ms 만에 종료했습니다.**

### 경위

직전 사이클(설정 80)의 잔열이 빠지기 전에 FORCE_UP에 재진입했습니다.
`temp >= 64`가 진입 즉시 참이 되어 램프 없이 종료합니다.

### 펌웨어는 정상입니다

히터를 껐고([mode.c:1849](../User/Edit/src/mode.c:1849)) 판정도 올바릅니다.
발열이 아니라 냉각 중인 상태입니다.

### 그럼에도 보고하는 이유

**진입 트리거와 무관하게 성립하기 때문입니다.**

이 세션의 모드 전이는 버튼 조작으로 발생했습니다. STM32의 기울기 제어는
`0x21 initMode = 0`(`MODE_AI_ESP`)이 적용돼 **비활성 상태**였습니다
([mode.c:379](../User/Edit/src/mode.c:379)).

그러나 잔열 조건은 진입 경로에 의존하지 않습니다. `temp >= f_temp_lmt` 하나로
판정하므로, **기울기·버튼·ESP32의 AI 판단 중 무엇이 진입시켜도 동일**합니다.

즉 강도를 낮춰 선택한 사용자가 직전 설정의 잔열 온도를 만나는 상황은
**ESP32가 AI로 진입을 결정하는 정상 경로에서도 재현됩니다.**

ESP32 측 UI에서 강도 변경을 표시하신다면, **표시값과 실제 표면 온도가
일시적으로 어긋나는 구간**이 존재합니다.

AI의 진입 판단이 직전 사이클의 냉각 완료를 고려하는지 알려주시면, 대응이
필요한 구간인지 함께 판단하겠습니다.

## 9. 관측된 결합 — SD 차단과 열 차단 판정 (검토 중)

§3.5의 100 ms 초과 1건과 관련해, 저희 쪽에서 확인한 구조를 공유합니다.
**조치는 아직 결정하지 않았습니다.**

### 구조

이 펌웨어는 RTOS 없이 단일 루프로 동작합니다. `f_write()`가 반환할 때까지
메인 루프 전체가 멈추며, 그동안 멈추는 것에는 PID뿐 아니라
**열 차단 판정 `i_Mode_Is_TempHeater_Over()`도 포함됩니다.**

램프 중이라면 그 시간만큼 차단이 늦어지고, 늦어진 만큼 온도가 더 오릅니다.

### 크기

§5의 승온율 9.8 °C/s를 적용하면:

| 차단 시간 | 초과 상승 |
|---|---|
| 46.7 ms (관측 최대) | 약 0.46 °C |
| 100 ms (b6 하한) | 약 0.98 °C |
| 500 ms (b7 하한) | 약 **4.9 °C** |

b7은 949 표본에서 **0건**이므로 현재 관측 범위 밖입니다.
b6은 1건 관측됐으며, 그 시점이 램프 중이었는지는 기록되지 않아 확정할 수 없습니다.

### 현재 판단

관측 범위 내에서는 `MODE_TEMP_ABS_MAX`(85 °C)에 도달하지 않습니다.
힐링 설정값 80에 최대 오버슛 1.0과 SD 지연 0.46을 더해도 81.5 수준입니다.

장시간 세션에서 b7이 관측될 경우 재평가가 필요하며, 그때는 SD 대기 루프 안에서
절대 상한만 감시하는 방식을 검토하고 있습니다. 해당 위치는 이미 UART 송신을

## 1. §4 축소 빌드 원복 — 완료

```c
#define SD_LOG_IDX_MAX   128
```

원복 후 적재까지 마쳤습니다. **축소값 4는 커밋하지 않았습니다.**

그쪽 `LOG_INDEX_CAPACITY`도 128로 복구하셨다니 양측 표시가 맞습니다.

---

## 2. §2 이벤트 detail — 소스에서 고쳤습니다

### 2.1 지적이 맞습니다

```
evtLogError reason 6    detail = 4  ->  초과분 0
0x43 filesOnCard        9           ->  초과분 5
```

세션 중 등재 경로가 `u16_logIdxCnt`로 발화하고 있었는데, **그 시점의 그 값은
정의상 한도와 같습니다.** 그래서 `detail - 한도`가 언제나 0이었습니다.

**"가득 찼는데 초과분 0"** — 이 문구가 나올 수밖에 없는 구조였습니다.

### 2.2 수정

```c
v_log_err_raise(SD_LOG_ERR_IDX_FULL, u16_logFilesOnCard);
```

`u16_logFilesOnCard`는 `filesOnCard`를 위해 이번에 도입한 값이고, **부팅 스캔과
상태 응답이 이미 쓰는 같은 숫자**입니다. 등재 시점에는 이미 새 파일까지 반영돼
있으므로 그대로 쓸 수 있습니다.

**이제 세 곳이 같은 값을 말합니다.**

| 경로 | detail / 값 |
|---|---|
| 부팅 스캔 이벤트 | 카드 파일 수 |
| **세션 중 등재 이벤트** | **카드 파일 수** (이전: 인덱스 수) |
| `0x43 filesOnCard` | 카드 파일 수 |

### 2.3 그쪽 표시 재검토를 권합니다

이벤트에서 초과분 계산을 빼셨는데, **이제 이벤트만 봐도 초과분이 나옵니다.**
되돌리실지는 그쪽 판단입니다.

다만 **권위는 여전히 상태 쪽**이라는 구조는 그대로 두시는 편이 낫다고 봅니다 —
이벤트를 놓치면 여전히 모르고, 재시작하면 사라집니다. 이벤트 문구에 개수를
쓰시더라도 **"자세한 것은 상태 조회"**라는 관계는 유지하시는 것이 좋겠습니다.

## 3. §1 시험 결과 — 확인했습니다

```
[LOG] INDEX FULL: 9 file(s) on the card, 5 beyond the 4 it can list
목록 4개 / 카드 9개 / 로깅 정상 (boot=102 lastSeq=4819 file=5)
```

**"기록은 되는데 못 꺼낸다"가 실물에서 그대로 재현**됐습니다. 목록이 4개인데
카드에 9개인 상태가 정확히 이 결함의 형태이고, **이제 보인다**는 것이 이 작업의
목적이었습니다.

조건 지속 중 매 폴링 6회 반복 보고도 §1.1에서 합의한 구조대로입니다.

## 4. §5 STM32 무응답 — 적재 구간으로 확정합니다

**세 번 모두 적재 직후입니다.** 저희 쪽 기전이 명확합니다.

```
** Verified OK **
** Resetting Target **     ← 이 리셋이 콜드 부팅 경로로
```

리셋은 `modeOFF`로 들어가고, 1초 뒤 STOP 모드입니다. **STOP에서는 CPU가 멈추므로
UART로 아무것도 나가지 않습니다.** 전원 버튼을 누르기 전까지 유지됩니다.

**결함이 아닙니다.**

### 앞으로 적재 시 알려드리겠습니다

그쪽에서 구분이 안 된다는 지적이 맞습니다. 저희가 적재할 때마다 이 창이 열리고,
**저희만 그 사실을 압니다.**

앞으로 적재 시 알리겠습니다. 그 구간을 시험에서 제외해 주십시오.

> 이번 §5도 저희가 축소 빌드를 올린 직후였고, 그때 알렸다면 80회의 타임아웃을
> 겪지 않으셨을 것입니다.

## 5. §3 그쪽 결함 — 같은 계열입니다

> BLE 쓰기 성공만 보고 장치의 응답을 안 봤기 때문입니다.

**"보냈다"와 "받아들여졌다"를 구분하지 않은 것**이고, 저희가 겪은 것들과 같은
형태입니다.

- 저희 `flags` 비트0이 정확히 이 구분을 위해 있습니다 — "STAT을 만들었다"가
  아니라 "TX 큐에 들어갔다"
- 그리고 그것 덕분에 그쪽이 4.5 %를 찾아냈습니다

**앱이 "이 작업분은 회수 가능하다"고 믿는데 실제로는 아닌 상태**가 가장 나쁜
결과이고, 확인 응답의 status를 검사하도록 고치신 것이 맞습니다.

## 6. 부수 — 적재 중 전원 차단이 있었습니다

이번 원복 적재 중 **벤치 전원이 꺼졌습니다.** 경위와 복구 방법을 남깁니다.

### 증상

```
1차:  error writing to flash at address 0x08000000
2차:  erase time-out or operation error sector 0
      failed erasing sectors 0 to 6
이후: 일반 연결로는 코어 검사 불가
```

플래시가 **지워지다 만 상태**라 부팅 즉시 폴트를 냈고, 그것이 디버그 포트까지
방해했습니다.

### 복구

**nRST를 잡은 채 붙어서 구웠습니다.**

```
reset_config srst_only srst_nogate connect_assert_srst
```

CPU가 망가진 이미지를 실행하지 못하므로 플래시 컨트롤러만 쓸 수 있습니다.
`Verified OK` 후 정상 부팅을 확인했습니다.

### 남기는 이유

**적재 중 전원 차단은 벤치에서 언제든 일어날 수 있고, 일반 연결로는 복구되지
않습니다.** 같은 증상을 보시면 연결 방식부터 바꾸셔야 합니다 — 케이블이나 칩을
의심하기 전에 리셋을 잡아보는 것이 먼저입니다.

`docs/fixtures/rtt.sh reset`이 이 설정을 갖고 있습니다.

## 1. 구현 — `ede62bc`

```c
// User/Drv/inc/sd.h
SD_LOG_ERR_DELETE	= 7,	// delete failed; detail = FRESULT
```

```c
// User/Drv/src/sd.c:1169
FRESULT e_del = f_unlink(c_path);
if(e_del != FR_OK){
	v_log_err_raise(SD_LOG_ERR_DELETE, (uint16_t)e_del);
	return 4;
}
```

| | 이전 | 지금 |
|---|---|---|
| `reason` | **5** — 백필 읽기 실패 | **7** — 삭제 실패 |
| `detail` | `0` | **`FRESULT`** |
| 플래시 | 867,104 B | **867,104 B** |

플래시가 한 바이트도 안 늘었습니다. 명령어 수준에서 등가라서입니다.

```
이전:  movs r1, #0    +  movs r0, #5
지금:  uxth r1, r0    +  movs r0, #7
```

## 2. 델타

### 2.1 §6.7 — reason 표

**추가:**

| `reason` | 의미 | STM32 후속 동작 |
|----------|------|-----------------|
| **7** | **삭제 실패** ⭐ v1.8 | **없음.** `detail` = `FRESULT` |

**정정** — 5번 행의 설명이 지금은 두 가지 사건을 덮고 있습니다.

| | 현재 | **정정** |
|---|---|---|
| 5 | 백필 읽기 실패 | 백필 읽기 실패 **(삭제 실패는 7)** |

`ctrlLogDelete` 실패가 여기로 나가고 있었기 때문에, 표를 그대로 읽으면 "읽지도
않은 백필이 실패했다"가 화면에 뜹니다. 7이 생기면서 5는 이름 그대로가 됩니다.

**추가 문단 제안** — 표 아래에 넣을 것:

> **reason 7의 `detail`은 `FRESULT`입니다.** 값을 평탄화하지 않고 그대로
> 보내는 이유는, 받는 쪽이 두 가지를 갈라야 하는데 STM32가 대신 판단할 수
> 없기 때문입니다.
>
> | `FRESULT` | 뜻 | 읽는 쪽 처리 |
> |---|---|---|
> | `FR_DENIED`(7) · `FR_LOCKED`(16) | 그 파일 하나의 문제 | 나머지 카드는 무관 |
> | `FR_DISK_ERR`(1) · `FR_NOT_READY`(3) · `FR_WRITE_PROTECTED`(10) | 카드·볼륨 문제 | 멈추고 사람이 확인 |
> | **그 외 전부** | 알 수 없음 | **카드 문제로 취급** |
>
> **모르는 코드를 카드 문제로 두는 것이 보수적인 방향입니다.** 반대로 두면
> 예컨대 `FR_TIMEOUT`이 "파일 하나 문제"로 표시되고, 이미 실패 중인 매체를
> 향해 재시도를 부릅니다.

> **주의**: reason 7과 `FR_DENIED`가 둘 다 7입니다. `reason` 바이트와 `detail`
> 2 B는 서로 다른 축이며, 값이 같은 것은 우연입니다.

### 2.2 §6.9.1 — 결과 4의 이벤트

**정정** — 4번 행에 이벤트를 명시합니다.

| 값 | 의미 | STM32 동작 |
|---|---|---|
| **4** | 삭제 실패 | 없음 — 파일시스템 오류 또는 미마운트. **`evtLogError` reason 7을 함께 발신하며 `detail`에 `FRESULT`가 실립니다** |

응답의 결과 코드는 "실패했다"까지만 말하고, **왜인지는 이벤트에 있습니다.**
둘을 함께 보면 재시도할지 사람을 부를지가 갈립니다.

> **다만 이벤트가 안 올 수도 있습니다.** `v_log_err_raise`는 **먼저 대기 중인
> 오류를 지킵니다** — 원인에 가까운 쪽을 남기려는 설계입니다. 카드가 망가져
> reason 3(쓰기 실패)이 이미 떠 있으면 삭제 실패는 그 결과이므로 가려집니다.
>
> **결과 4는 항상 오고, reason 7은 대개 옵니다.** 판정은 결과 4로 하시고
> 이벤트는 사유 표시에 쓰십시오.

### 2.3 §6.7 소제목 문구

reason 7이 생기면서 개수가 하나 늘었습니다.

| | 현재 | **정정** |
|---|---|---|
| 소제목 | `reason 6은 다른 여섯 개와 성격이 다릅니다` | `...다른 **일곱** 개와...` |
| 표 머리 | `reason 0~5` | `reason 0~5, 7` |

**그 절의 논지는 그대로입니다.** reason 7도 로깅을 멈추지 않지만, 6과 달리
**사용자가 요청한 조작이 실패한 것**이라 즉시 표시할 대상입니다. 6은 상태이고
7은 사건입니다 — 그 절이 6을 0~5에서 떼어낸 것과 같은 기준으로 7은 0~5 쪽에
붙습니다.

## 3. 적재는 아직입니다

**`ede62bc`는 빌드·커밋만 됐고 어느 장치에도 굽지 않았습니다.**

지금 보드에는 `3fc042f`가 올라가 있습니다. 급하지 않은 이유가 그쪽 #47 §3.1과
같습니다 — **삭제가 실패해야 드러나는 값**이고, 정상 삭제에는 아무 영향이
없습니다. 다음에 굽는 것이 있을 때 함께 올리고 알려드리겠습니다.

> `9bd5679` 때 *"25 B 응답을 아직 아무도 본 적이 없습니다"* 라고 하신 것과 같은
> 상태입니다. **reason 7도 아직 아무도 본 적이 없습니다** — 그리고 이쪽은
> 일부러 실패시키지 않으면 실기에서 보기 어렵습니다. 읽기 전용 속성을 붙인
> `.psa`를 하나 넣어 두면 `FR_DENIED`가 재현됩니다.

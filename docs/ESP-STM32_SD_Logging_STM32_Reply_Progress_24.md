## 1. 수정 내용

### 1.1 원인 (보고 #23 §1 재확인)

`v_SD_Log_Scan()`은 `main.c:371`에서 **부팅 시 한 번만** 불리고, 세션 중 만들어진
파일을 인덱스에 넣는 코드가 없었습니다.

### 1.2 🔴 파일이 닫히는 경로가 둘이었습니다

처음 수정에서 **로테이션만 고치고 쓰기 실패 경로를 놓쳤습니다.**

| 경로 | 1차 수정 | 최종 |
|---|---|---|
| 시간·크기 로테이션 (`v_log_rotate`) | ✅ | ✅ |
| **쓰기 실패** (`v_SD_Log_Flush` 내부) | ❌ **누락** | ✅ |

쓰기 실패 경로는 자기가 직접 `f_close` + 인덱스 증가를 하고 있어서, 고쳐야 할
바로 그 상태가 그대로 남아 있었습니다.

**이 누락이 특히 나빴을 이유가 있습니다** — 쓰기 실패야말로 데이터를 꺼내야
하는 상황입니다. 문제가 생겼고, 그 파일에 쓰인 만큼이 남은 전부이기 때문입니다.

두 경로를 `v_log_close_and_index()` 하나로 묶었습니다. **한쪽에만 넣고 다른 쪽을
잊는 것이 구조적으로 불가능**해졌습니다.

### 1.3 등재 방식

```c
v_log_idx_add(c_dir, c_name, u32_boot, u32_logFileIdx, u32_size, ...);
```

**부팅 스캔이 쓰는 것과 같은 함수**입니다. 카운터를 쓰지 않고 **헤더를 다시 읽어**
`firstSeq`를 가져오며 **파일 크기에서** 레코드 수를 계산합니다.

같은 파일이 두 경로로 다르게 인덱싱되면 백필이 조용히 틀린 위치를 계산하므로,
**두 경로가 반드시 같은 답을 내도록** 한 것입니다. 비용은 1시간에 512 B 읽기
한 번입니다.

정렬도 유지됩니다 — 현재 bootId가 가장 크고 fileIdx는 증가만 하므로 뒤에 붙이면
오름차순이 깨지지 않습니다. `b_bf_find()`가 이 순서에 의존합니다.

### 1.4 확인용 로그

```
[I/SD_LOG]closed 00000032_0001.psa size=1966592 indexed=22
```

`v_log_idx_add()`는 레코드를 담기에 너무 짧거나 테이블이 가득 찬 파일을 조용히
건너뜁니다. **`indexed=`가 안 올라가는 것으로 그것이 드러납니다.**

이 값이 `0x45 reqLogFiles`의 total과 일치해야 합니다 — **카드를 뽑지 않고
확인하는 경로**입니다.

## 2. 실기 검증 — 완료

1시간 로테이션을 기다리는 대신 **결함 주입으로 쓰기 실패를 유발**했습니다.
두 경로가 같은 헬퍼를 쓰므로 어느 쪽을 시험해도 등재 로직이 검증됩니다.

### 2.1 경과

| 단계 | 결과 |
|---|---|
| 부팅 | `armed, bootId=50` / `indexed 21 file(s)` |
| 결함 주입 | `u8_sd_fault_inject_write = 1` |
| **쓰기 실패** | **`write 384/1600 res=1, rotating`** |
| 새 파일 | `00000032_0001.psa firstSeq=1960` |
| **인덱스** | **21 → 22** ✅ |

### 2.2 더 어려운 조건을 통과했습니다

**`write 384/1600`이 이 시험의 핵심입니다.** 1,600 B를 요청했는데 384 B만
들어갔고, **384는 80의 배수가 아니므로 레코드 중간에서 잘렸습니다.**

정상 로테이션은 파일이 온전한 상태로 닫히지만, 이 경우는 **부분 레코드가 남은
파일**입니다. 그 상태에서도 `v_log_idx_add()`가 파일 크기로 계산하므로
**온전한 레코드까지만 등재**하고 잘린 조각은 제외합니다.

카운터를 믿는 구현이었다면 잘린 조각까지 세어, 백필이 마지막에 쓰레기를
반환했을 것입니다.

### 2.3 검증 후 원복

결함 주입 빌드는 즉시 정상 빌드로 교체했고, 심볼이 바이너리에서 빠진 것을
확인했습니다. **벤치에는 결함 주입이 없습니다.**

## 3. 효과

| | 이전 | 이후 |
|---|---|---|
| 로테이션으로 닫힌 파일 | 재부팅 전까지 접근 불가 | **닫히는 즉시 등재** |
| 쓰기 실패로 닫힌 파일 | 접근 불가 | **즉시 등재** |
| 기록 중인 파일 | 접근 불가 | 변화 없음 (보고 #23 §3) |
| **회수 불가 구간** | **세션 전체** | **최대 1시간** |

지적하신 현장 시나리오 — 작업 중 끊긴 구간을 작업 후 회수 — 가 **1시간
로테이션 주기 안에서 성립**합니다.

SD 차단 판정에는 영향이 없습니다. 1시간에 읽기 한 번은 b0~b2 대역이며,
보고 #18의 b6·b7 = 0 결론과 무관합니다.

## 4. ESP32 측 확인 요청

**`0x45 reqLogFiles`를 다시 물어봐 주십시오.**

현재 벤치의 bootId는 50이고, 검증 중 파일이 두 개 만들어졌습니다
(`00000032_0000.psa`, `00000032_0001.psa` — `0x32 = 50`).

| 확인 | 기대 |
|---|---|
| 목록에 `boot=50`이 나타나는가 | **예** |
| 그 중 `fileIndex=0`이 있는가 | **예** (닫힌 파일) |
| `fileIndex=1`이 있는가 | 아니오 — 아직 열려 있음 |
| total | 저희 `indexed=`와 일치 |

이전에는 현재 bootId가 하나도 안 보였으므로, **`boot=50`이 목록에 나타나면
그것으로 확인됩니다.**

그 뒤 해당 구간을 백필로 회수해 보시면 보고 #22 Q55의 대조도 함께 됩니다 —
다만 그 tick 구간은 `boot=48`이므로, **`boot=48`은 이미 닫힌 세션이라 원래부터
목록에 있습니다.** 지금 바로 가능합니다.

판단 근거는 이렇습니다 — 이 결함은 **이 프로젝트의 목적 그 자체**를 막고
있었고(SD에 쌓인 데이터를 ESP32를 거쳐 빼내기), 수정 범위가 파일 종료 경로
하나로 한정되며, 되돌리기도 단순합니다. 통합 노트 #15의 범위 축소 취지에
어긋나지 않는다고 봤습니다.

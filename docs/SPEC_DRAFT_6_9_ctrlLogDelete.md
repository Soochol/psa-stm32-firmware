## 6.9 `ctrlLogDelete` (0x57) — ESP→STM ⭐ v1.7 신규

회수가 끝난 파일을 카드에서 지웁니다. **인덱스 한도(§8.4)에 도달하기 전에
자리를 비우는 것이 목적**이며, 그 뒤에는 지울 대상조차 지목할 수 없습니다(§6.9.5).

| 매개변수 | 타입 | 범위 | 설명 |
|---------|------|------|------|
| `bootId` | uint32 BE | — | 삭제할 파일의 부팅 세션 |
| `fileIndex` | uint16 BE | — | 그 세션 내 파일 순번 |

**DATA 6 B · 응답 ACK + 결과 1 B**

두 값은 `reqLogFiles`(§6.3) 응답 항목과 **같은 식별자**입니다. 목록에서 본 것을
그대로 지목하는 형태이므로 새 개념이 없습니다.

```
요청 (boot=9, file=0):  02 0A 20 57 00 00 00 09 00 00 CHK 03
응답 (삭제 완료):        02 05 02 57 00 CHK 03
```

### 6.9.1 응답 코드

| 값 | 의미 | STM32 동작 |
|---|---|---|
| **0** | 삭제 완료 | 파일 삭제, 인덱스 항목 제거, `filesOnCard` 감소 |
| **1** | 인덱스에 없음 | 없음 — 지목이 잘못됐거나 이미 삭제됨 |
| **2** | 거부: 현재 기록 중인 파일 | 없음 |
| **3** | 거부: 백필 진행 중 | 없음 |
| **4** | 삭제 실패 | 없음 — 파일시스템 오류 또는 미마운트 |

**결과 2에 대하여**: 기록 중인 파일은 `reqLogFiles`에 나타나지 않으므로, 목록을
따라 요청하는 정상 경로에서는 이 코드가 나오지 않습니다. 목록에 없는 파일을
직접 지목했을 때만 발생합니다. 검사는 인덱스 조회보다 **앞**에 있어
`b_logOpen`과 현재 bootId·fileIndex를 직접 비교합니다.

### 6.9.2 🔴 삭제 여부를 판단하는 주체는 PC입니다

**STM32도 ESP32도 파일이 회수됐는지 알 수 없습니다.**

| | STM32 | ESP32 | **PC** |
|---|---|---|---|
| 파일이 존재한다 | ○ | — | — |
| 레코드를 보냈다 / 중계했다 | ○ | ○ | — |
| **CRC가 맞았다** | ✗ | ✗ | **○** |
| **`.psa`로 저장됐다** | ✗ | ✗ | **○** |
| **병합 수집률 100 %** | ✗ | ✗ | **○** |
| **어느 seq를 이미 갖고 있다** | ✗ | ✗ | **○** |

STM32의 백필은 요청-응답이므로 **"보냈다"까지만** 압니다. ESP32는 프레임을 BLE
알림 큐에 넣을 뿐 도착 여부를 확인하지 않습니다.

따라서 삭제 요청은 **PC에서 출발**해야 합니다.

```
PC    : "boot=9 file=0 — 병합 완료, CRC 실패 0, 불변식 위반 0"
ESP32 : 중계 (BLE 0x23 → UART 0x57)
STM32 : f_unlink → 인덱스 제거 → filesOnCard 감소 → 결과 응답
```

**§9.1이 백필을 PC 주도로 정한 것과 같은 구조**입니다. `reqLogFiles`로 목록을
받고 `reqLogRead`로 범위를 요청하는 주체가, **다 받았다고 말하는 주체**이기도
해야 합니다.

### 6.9.3 STM32가 검사하는 것 — 구조적 안전만

STM32는 **회수 여부를 검사하지 않습니다.** 지금 지우면 깨지는 것만 봅니다.

| 거부 | 이유 |
|---|---|
| 응답 2 — 기록 중 | 열려 있는 파일을 지우면 그 세션의 기록이 갈 곳을 잃습니다 |
| 응답 3 — 백필 중 | 진행 중인 전송이 읽고 있는 파일이 사라질 수 있습니다 |
| 응답 1 — 미등재 | 목록에 없는 것은 이 경로의 대상이 아닙니다 |

응답 3은 **일시적**입니다. PC는 진행 중인 전송이 끝난 뒤 다시 요청하면 됩니다.

### 6.9.4 단건 처리

**범위 삭제를 정의하지 않습니다.** 부분 실패의 의미가 모호해지고, 어느 파일이
실패했는지 응답 하나로 드러나지 않기 때문입니다. PC가 반복 호출합니다.

### 6.9.5 ⚠️ 한도에 닿기 전에 지워야 합니다

인덱스 한도(§8.4, 128개)를 넘으면 초과분은 `reqLogFiles` 응답에 **나타나지
않습니다.** 그런데 이 커맨드는 `bootId`+`fileIndex`로 지목하는 방식입니다.

**즉 목록에 없는 파일은 삭제 요청의 대상이 될 수 없습니다.**

| 상태 | 회수 | 삭제 |
|---|---|---|
| 한도 이내 | 가능 | 가능 |
| **한도 초과분** | **불가** | **불가** |

한도를 넘긴 파일은 **카드를 물리적으로 회수해야만** 처리됩니다. `reqLogStatus`의
`filesOnCard`(§6.2)가 플래그가 아니라 개수인 이유가 이것입니다 — **닿기 전에
움직일 수 있어야** 합니다.

**권고**: `filesOnCard`가 한도의 80 % 수준에 이르면 정리를 시작하십시오.

### 6.9.6 삭제 후 상태

| 항목 | 처리 |
|---|---|
| 인덱스 | 항목 제거 후 뒤 항목을 앞으로 당김 (정렬 유지) |
| `filesOnCard` | 1 감소 |
| `reqLogFiles` | 다음 조회부터 반영 |
| 카드 재스캔 | **하지 않음** |

재스캔하지 않는 이유는 비용입니다. 부팅 스캔은 파일당 약 3 ms이며, 삭제할 때마다
전체를 다시 훑을 이유가 없습니다.

정렬을 유지하는 것은 필수입니다 — 백필의 파일 탐색이 **정렬된 배열에서 마지막
매치를 취하는** 방식이기 때문입니다.

### 6.9.7 되돌릴 수 없습니다

삭제 후 **PC의 사본이 유일본**이 됩니다. 검증 로직에 결함이 있다면 그 시점에
잃습니다.

**자동 삭제를 권하지 않습니다.** 임계값을 넘겼다고 앱이 알아서 지우는 형태는,
결함이 있을 때 조용히 그리고 전부에 대해 작동합니다. 지울 목록과 근거(각 파일의
수집률·CRC 결과)를 보이고 사용자 확인을 받는 편이 안전합니다.

# 함께 갱신이 필요한 절

## §6.2 `reqLogStatus` — 21 B → 23 B

`filesOnCard`가 추가됐습니다 (STM32 `9f9b00e`, ESP32 `15ef00e`).

| 오프셋 | 크기 | 필드 | 설명 |
|---|---|---|---|
| … | … | (기존 21 B) | 변경 없음 |
| **21** | **2** | **`filesOnCard`** | **카드의 `.psa` 파일 수 (uint16 BE)** |

### 인덱스 한도와의 관계

`reqLogFiles`의 `total`은 인덱스 항목 수이므로 **한도에서 멈춥니다.**
`filesOnCard`는 카드의 실제 파일 수이므로 **한도를 넘어갑니다.**

```
회수·삭제 불가 파일 수 = filesOnCard - (인덱스 한도)
```

두 값이 같으면 한도 이내이고, `filesOnCard`가 크면 그 차이만큼이 도달 불가입니다.

### 하위 호환

수신 측은 **길이가 21 이상이면 통과**시키고, **23 이상일 때만** `filesOnCard`를
읽어야 합니다. 21 B만 보내는 구형 펌웨어와 섞여도 깨지지 않습니다.

**0을 기본값으로 쓰지 마십시오** — "보고 안 됨"과 "파일 0개"가 구분되지
않습니다. ESP32 구현이 `filesOnCardKnown` 플래그를 별도로 두는 이유입니다.

## §6.7 `evtLogError` — reason 6 추가

| reason | 의미 | detail | 로깅 |
|---|---|---|---|
| 0~5 | (기존) | — | 대부분 **정지** |
| **6** | **인덱스 한도 도달** | **카드의 파일 수** | **계속됨** |

### 다른 여섯 개와 성격이 다릅니다

| | reason 0~5 | **reason 6** |
|---|---|---|
| 로깅 | 멈추거나 위험 | **정상 계속** |
| 잃는 것 | 기록 | **회수 가능성만** |
| 필요한 조치 | 수리·교체 | **카드 정리** |

**같은 문구로 표시하지 마십시오.** "기록이 멈췄다"로 읽히면 엉뚱한 곳을 보게
됩니다.

### 이것은 사건이 아니라 상태입니다

조건은 카드를 정리할 때까지 지속됩니다. 이벤트로만 다루면 세 가지가 어긋납니다.

1. 수신 측이 재시작하면 그 사실을 잃습니다
2. 조건이 유지되는 한 파일이 닫힐 때마다 반복 발화합니다
3. "지금 찼습니까?"에 답할 방법이 없습니다

**권위는 `reqLogStatus`의 `filesOnCard`에 있고, 이벤트는 "지금 조회해 보라"는
알림**입니다. 폴링 주기(1분)를 기다리지 않아도 되게 하는 것이 이벤트의 역할입니다.

## §8.4 인덱스 한도 (신설 제안)

STM32는 파일 목록을 RAM 배열로 유지하며 **상한이 128개**입니다.

| 항목 | 값 |
|---|---|
| 상한 | 128 |
| 초과 시 | 목록에 오르지 않음 — **회수·삭제 모두 불가** |
| 알림 | `evtLogError` reason 6 + `filesOnCard` |
| 도달 시점 | 실사용 **2~6주** (하루 3~10세션 기준) |

### 상한의 근거

RAM 테이블 크기이기도 하지만, **부팅 스캔 시간의 상한**이기도 합니다.

```
부팅 스캔 = 약 7.5 ms + 파일당 약 3.0 ms   (실측)
128개 → 약 390 ms
```

IWDG 타임아웃 2초 대비 5배 여유입니다. 상한을 올리면 이 시간이 함께 늘어나며,
512개면 약 1.5초로 워치독에 근접합니다. **상향하려면 스캔 중 워치독 갱신을
함께 넣어야 합니다.**

### `filesOnCard`와 목록의 차이

`filesOnCard`는 **기록 중인 파일을 포함**하므로 `reqLogFiles`의 `total`보다
통상 **1 큽니다.**

인덱스가 가득 찬 상태에서 이 파일은 **닫히는 순간 도달 불가가 됩니다.** 따라서
`filesOnCard - 128`은 확정된 손실이 아니라 **닫힌 뒤의 값을 미리 보여주는
것**입니다.

| 시점 | `filesOnCard` | 실제 도달 불가 | `filesOnCard - 128` |
|---|---|---|---|
| 128 등재 + 1 열림 | 129 | 0 | **1** |
| 그 파일이 닫힌 뒤 | 129 | **1** | 1 |

**표시할 때 "이미 잃었다"로 읽히지 않게 하십시오.** 값은 틀리지 않았고, 결과가
아직 도착하지 않았을 뿐입니다.

### 용량 한도(§10.4)와 다릅니다

| | 용량 부족 | **인덱스 한도** |
|---|---|---|
| 조건 | 카드 용량 소진 | **파일 128개** |
| 실제 도달 | 사실상 없음 | **2~6주** |
| 로깅 | **정지** | **계속** |
| §10.4 "지우지 말라" | 적용 | **적용되지 않음** |

§10.4는 **"지우면 데이터를 잃는다"**를 전제로 한 규칙입니다. 인덱스 한도에서
지우는 대상은 **이미 회수·검증이 끝난 파일**이므로 그 전제가 성립하지 않습니다.

# 4. BLE 경로 (PC ↔ ESP32)

> ESP32 팀 작성분 (`2534b33`).

## 4.1 `0x23` — PC→ESP32 파일 삭제 요청

| 항목 | 내용 |
|---|---|
| 요청 | `0x23` + `bootId`(4 B BE) + `fileIndex`(2 B BE) — **총 7 B** |
| 응답 | 프레임 `0xB3` + 결과 1 B — **총 2 B** |
| UART 매핑 | `0x57` (`bootId` 4 B + `fileIndex` 2 B) |
| 결과 전달 | UART ACK의 1 B를 **해석 없이 그대로** 올림 |

식별자는 `reqLogFiles`(§6.3) 응답 항목과 같습니다. 목록에서 본 것을 그대로
지목하는 형태이므로 PC 쪽에 새 개념이 없습니다.

### 4.1.1 결과 코드

§6.9.1의 0~4를 그대로 전달하며, ESP32가 하나를 더합니다.

| 값 | 의미 | 출처 |
|---|---|---|
| 0~4 | §6.9.1 | **STM32** |
| **0xFF** | **장치가 답하지 않음** | **ESP32** |

`0xFF`가 나오는 경우는 셋입니다.

- 요청이 7 B 미만 (형식 오류)
- `stm32Ready == false` (보낼 상대가 없음)
- UART 송신 실패 (슬롯 없음 등)

**침묵 대신 답을 보냅니다.** PC가 자기 타임아웃까지 기다리는 것을 피하기
위해서이며, `0x22`에서 겪은 **"보냈다 vs 받아들여졌다"**와 같은 이유입니다.

### 4.1.2 ESP32가 하지 않는 것

**회수 여부를 판단하지 않습니다.** 요청을 읽지도 않고 그대로 넘기며, 결과도
해석하지 않습니다. ESP32가 보는 것은 **형식이 맞는가**와 **보낼 상대가 있는가**
둘뿐입니다.

## 4.2 사슬 전체

```
PC     0x23  "boot=9 file=0 지워도 된다"   ← 판단 (병합·CRC 검증 결과 보유)
  ↓
ESP32        중계                          ← 형식·연결만 검사
  ↓
STM32  0x57  f_unlink                      ← 구조적 안전만 검사
  ↑
결과   1 B   0 완료 / 1~4 거부·실패 / 0xFF 무응답
```

**세 계층이 각자 아는 것만 판단합니다.** PC는 데이터가 안전한지, ESP32는
전달할 수 있는지, STM32는 지금 지워도 되는지.

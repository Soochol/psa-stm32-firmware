# Q23 실물 카드 채취 절차

> **목적**: ESP32 팀 병합 도구와 STM32 펌웨어의 **포맷 해석 일치**를 실물로 확인
> **필요**: §16.3 1~11단계 반영 펌웨어(`d6a772c` 이상), FAT32 포맷 SD 카드, 대상 보드
> **소요**: 약 10분

이 문서는 **하드웨어가 있어야 수행 가능**합니다. 합성 픽스처([golden_v1.psa](golden_v1.psa))로는
검증할 수 없는 것 — 실제 센서 값, 실제 모드 전이, 실제 tick 간격 — 을 담기 위한 절차입니다.

---

## 1. 사전 준비

| 항목 | 확인 |
|------|------|
| SD 카드 | **FAT32로 포맷** (§8.4 — exFAT은 마운트 실패). 32 GB 이하 권장 |
| 카드 상태 | `/LOG` 디렉터리를 비워 두면 결과가 읽기 쉽습니다 |
| 펌웨어 | `pio run -e stm32_debug -t upload` |
| RTT | `probe-rs` 등으로 로그 관측 (`[I/SD_LOG]` 라인 확인용) |

플레이스홀더 레코드를 포함하려면(§3) 결함 주입 빌드가 필요합니다.

```bash
pio run -e stm32_debug -t upload
```

---

## 2. 기본 채취 (5분 세션)

1. 카드 삽입 후 배터리 연결 → **콜드 부팅이므로 `modeOFF`로 진입합니다** (§17)
2. **전원 버튼 롱프레스(1.5초)** → WAKE_UP → 리셋 → BOOTING
3. RTT에 다음이 뜨는지 확인

   ```
   [I/FLASH_CFG] bootId=N vol=... slots=...
   [I/SD_LOG] armed, bootId=N
   [I/SD_LOG] /LOG/UNKNOWN/0000000N_0000.psa firstSeq=0
   ```

   > ESP32를 연결하지 않으면 `deviceId`가 `UNKNOWN`이고 경로도 `/LOG/UNKNOWN/`입니다.
   > `0x23` 핸들러는 들어가 있으므로, ESP32를 붙이면 **다음 로테이션부터** MAC 경로로
   > 바뀝니다. 두 디렉터리 모두 부팅 스캔과 백필 대상이므로 어느 쪽이든 회수됩니다.

4. 모드를 한 번씩 밟아 주십시오 — WAITING → FORCE_UP → FORCE_ON → FORCE_DOWN → SLEEP
   (각 30초 정도면 충분합니다. 병합 도구가 `deviceMode` 전이를 확인합니다)
5. **전원 버튼 롱프레스로 정상 종료** — `v_SD_Log_Close()`가 flush + close를 수행합니다

   > 배터리를 그냥 뽑으면 마지막 flush 주기(2초)만큼이 파일에 반영되지 않고
   > 꼬리가 불완전 레코드로 남습니다. 그것도 유효한 시험이지만 §3과 나눠서 하십시오.

6. 카드를 뽑아 `/LOG/UNKNOWN/*.psa` 를 복사

---

## 3. 결함 주입 — 로테이션과 플레이스홀더는 **다른 경로**입니다

두 가지는 서로 다른 코드 경로라 **훅도 두 개**입니다. 하나로는 다른 쪽이 안 나옵니다.

| 훅 | 위치 | 만드는 것 |
|----|------|-----------|
| `u8_sd_fault_inject_write` | `sd_diskio.c` `SD_write` | **쓰기 실패 → 로테이션** (§7.4). 파일이 2개로 갈라짐 |
| `u8_sd_fault_inject_len` | `sd.c` `v_SD_Log_Write` | **길이 계약 위반 → 플레이스홀더** (`flags` bit1) |

```bash
pio run -e stm32_debug -DPSA_FAULT_INJECT=1 -t upload
```

부팅 후 디버거에서 값을 씁니다. 둘 다 **N번째 이후에 한 번** 발동하고 스스로 해제됩니다.

| 설정 | 기대 결과 |
|------|-----------|
| `u8_sd_fault_inject_len = 100` | 100번째 샘플이 플레이스홀더로 기록. `[W/SD_LOG] payload 0 != 64, placeholder at seq=...` |
| `u8_sd_fault_inject_write = 3` | `[E/SD_LOG] write A/B res=1, rotating` → `[I/SD_LOG] rotate ... -> fileIndex=1` → 새 파일 |

**두 개를 같은 세션에서 쓰면** 플레이스홀더 1개와 파일 2개를 한 번에 얻습니다 —
ESP32 팀이 요청한 "로테이션 사례"와 "플레이스홀더"가 동시에 담깁니다.
쓰기 실패 쪽을 나중에 발동시키면 두 번째 파일의 `firstSeq != 0`도 확보됩니다.

> ⚠️ 결함 주입 빌드는 **현장 장비에 올리지 마십시오.** `PSA_FAULT_INJECT`는
> 어느 빌드 구성에도 등록되어 있지 않으므로, 채취 후 일반 빌드로 다시 구우면 됩니다.
> 기본 빌드에 두 심볼이 모두 없는 것을 확인했습니다.

## 4. 검증

전달 전에 반드시 돌려 주십시오. 규격 위반을 여기서 잡는 편이 ESP32 팀이 잡는 것보다 낫습니다.

```bash
python3 docs/fixtures/validate_psa.py /경로/*.psa
python3 docs/fixtures/validate_psa.py --decode=0,1,2 /경로/파일.psa   # 기대값 표
```

확인 항목:

| 검사 | 기대 |
|------|------|
| 헤더 CRC, magic, recordSize | 통과 |
| 레코드 CRC 전수 | 통과 |
| **불변식 `seq == firstSeq + n`** | 통과 — 이게 깨지면 백필이 엉뚱한 샘플을 돌려줍니다 |
| `tick` 스텝 | 100 ms 근처 (SLEEP 포함 구간도 동일) |
| `modes` | 밟은 모드가 모두 나타남 |
| 꼬리 절단 경고 | 정상 종료했다면 **없어야** 함 |

`--> VALID` 가 나오면 전달 가능합니다.

## 5. 전달물

ESP32 팀이 `.psa` 파일 직접 전달을 선호한다고 회신했습니다(v1.5 Q23).

| 항목 | 비고 |
|------|------|
| `*.psa` 파일 전체 | §3을 했다면 2개 |
| `validate_psa.py` 출력 | 텍스트로 함께 |
| **`--decode` 기대값 표** | 레코드 3개 이상. ESP32 팀이 요청한 항목 |
| RTT 부팅 로그 | `bootId` 값 확인용 |
| 밟은 모드 순서·시각 메모 | `deviceMode` 대조용 |

## 6. 알려진 제약 — 미리 공유할 것

| 항목 | 현재 동작 |
|------|-----------|
| `deviceId` | ESP32 미연결이면 `FF..`, 경로 `/LOG/UNKNOWN/`. 연결 시 다음 로테이션부터 MAC 경로 |
| flush 주기 | **2초 / 20 레코드** — 비정상 종료 시 최대 20 샘플 유실 |
| `flags` bit0 | **UART 링버퍼 적재 성공 여부** (Q24 = (a)) |
| `errorMask` | 레코드 조립 시점의 `e_Mode_Get_Error()` 스냅샷. **비트는 누적되며 해제되지 않습니다** (Q25) |
| 로테이션 | 부팅 / 1시간 / 32 MB / 쓰기 실패 / 카드 재삽입 |
| 파일 인덱스 상한 | 128개 (㉗) |
| `SD_TIMEOUT_*` | READY 200 / XFER 100 / BUSY 600 ms — **실측 전 잠정치** |

측정 전에 RTT에서 `sdmax=` 값을 한 번 보시고, 세션 종료 후 다시 보시면
그 구간의 최대 SD 블로킹 시간을 알 수 있습니다 (§13 시나리오 8).

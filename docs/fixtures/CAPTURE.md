# Q23 실물 카드 채취 절차

> **목적**: ESP32 팀 병합 도구와 STM32 펌웨어의 **포맷 해석 일치**를 실물로 확인
> **필요**: §16.3-4 / §16.3-5 반영 펌웨어(`99f1811` 이상), FAT32 포맷 SD 카드, 대상 보드
> **소요**: 약 10분

이 문서는 **하드웨어가 있어야 수행 가능**합니다. 합성 픽스처([golden_v1.psa](golden_v1.psa))로는
검증할 수 없는 것 — 실제 센서 값, 실제 모드 전이, 실제 tick 간격 — 을 담기 위한 절차입니다.

---

## 1. 사전 준비

| 항목 | 확인 |
|------|------|
| SD 카드 | **FAT32로 포맷** (§8.4 — exFAT은 마운트 실패). 32 GB 이하 권장 |
| 카드 상태 | `/LOG` 디렉터리를 비워 두면 결과가 읽기 쉽습니다 |
| 펌웨어 | `pio run -e stm32_debug -t upload` |
| RTT | `probe-rs` 등으로 로그 관측 (`[I/SD_LOG]` 라인 확인용) |

플레이스홀더 레코드를 포함하려면(§3) 결함 주입 빌드가 필요합니다.

```bash
pio run -e stm32_debug -t upload
```

---

## 2. 기본 채취 (5분 세션)

1. 카드 삽입 후 배터리 연결 → **콜드 부팅이므로 `modeOFF`로 진입합니다** (§17)
2. **전원 버튼 롱프레스(1.5초)** → WAKE_UP → 리셋 → BOOTING
3. RTT에 다음이 뜨는지 확인

   ```
   [I/FLASH_CFG] bootId=N vol=... slots=...
   [I/SD_LOG] armed, bootId=N
   [I/SD_LOG] /LOG/UNKNOWN/0000000N_0000.psa firstSeq=0
   ```

   > `deviceId`가 `UNKNOWN`인 것은 정상입니다 — `initLogIdentity(0x23)` 핸들러가
   > §16.3-8에 들어갑니다. ESP32 팀이 v1.5에서 이 상태로도 무방하다고 확인했습니다.

4. 모드를 한 번씩 밟아 주십시오 — WAITING → FORCE_UP → FORCE_ON → FORCE_DOWN → SLEEP
   (각 30초 정도면 충분합니다. 병합 도구가 `deviceMode` 전이를 확인합니다)
5. **전원 버튼 롱프레스로 정상 종료** — `v_SD_Log_Close()`가 flush + close를 수행합니다

   > 배터리를 그냥 뽑으면 마지막 flush 주기(현재 10초)만큼이 파일에 반영되지 않고
   > 꼬리가 불완전 레코드로 남습니다. 그것도 유효한 시험이지만 §3과 나눠서 하십시오.

6. 카드를 뽑아 `/LOG/UNKNOWN/*.psa` 를 복사

---

## 3. 플레이스홀더 포함 (선택, 권장)

§7.4 플레이스홀더는 정상 동작에서 거의 나오지 않으므로 **의도적으로 만들어야** 합니다.
ESP32 팀이 "실물로 검증하지 못하던 경로"로 지목한 부분입니다.

```bash
pio run -e stm32_debug -DPSA_FAULT_INJECT=1 -t upload
```

부팅 후 디버거에서 `u8_sd_fault_inject_write = 3` 을 쓰면 **3번째 이후 `SD_write`가 실패**하고
플래그가 스스로 해제됩니다. 멀티섹터 쓰기 중간에서 실패하므로 진짜 **부분 쓰기**가 발생하고,
§7.4의 로테이션과 §16.3-5의 재기록 경로가 함께 동작합니다.

기대 결과:

```
[E/SD_LOG] write NNN/MMM res=1, rotating
[I/SD_LOG] rotate (...) -> fileIndex=1
[I/SD_LOG] /LOG/UNKNOWN/0000000N_0001.psa firstSeq=XXXX
```

→ **파일이 2개** 생기고, 두 파일 사이에만 갭이 있으며 **파일 내부에는 갭이 없어야** 합니다.

> ⚠️ 결함 주입 빌드는 **현장 장비에 올리지 마십시오.** `PSA_FAULT_INJECT`는
> 어느 빌드 구성에도 등록되어 있지 않으므로, 채취 후 일반 빌드로 다시 구우면 됩니다.

---

## 4. 검증

전달 전에 반드시 돌려 주십시오. 규격 위반을 여기서 잡는 편이 ESP32 팀이 잡는 것보다 낫습니다.

```bash
python3 docs/fixtures/validate_psa.py /경로/*.psa
```

확인 항목:

| 검사 | 기대 |
|------|------|
| 헤더 CRC, magic, recordSize | 통과 |
| 레코드 CRC 전수 | 통과 |
| **불변식 `seq == firstSeq + n`** | 통과 — 이게 깨지면 백필이 엉뚱한 샘플을 돌려줍니다 |
| `tick` 스텝 | 100 ms 근처 (SLEEP 포함 구간도 동일) |
| `modes` | 밟은 모드가 모두 나타남 |
| 꼬리 절단 경고 | 정상 종료했다면 **없어야** 함 |

`--> VALID` 가 나오면 전달 가능합니다.

---

## 5. 전달물

ESP32 팀이 `.psa` 파일 직접 전달을 선호한다고 회신했습니다(v1.5 Q23).

| 항목 | 비고 |
|------|------|
| `*.psa` 파일 전체 | §3을 했다면 2개 |
| `validate_psa.py` 출력 | 텍스트로 함께 |
| RTT 부팅 로그 | `bootId` 값 확인용 |
| 밟은 모드 순서·시각 메모 | `deviceMode` 대조용 |

## 6. 알려진 차이 — 미리 공유할 것

| 항목 | 현재 | 반영 예정 |
|------|------|-----------|
| `deviceId` | `FF FF FF FF FF FF`, 경로 `/LOG/UNKNOWN/` | §16.3-8 (`0x23` 핸들러) |
| flush 주기 | **10초** | §16.3-6에서 2초로 (§10.2) |
| `flags` bit0 | UART 큐 적재 성공 여부 | 변경 없음 |
| 파일 로테이션 | 부팅 / 1시간 / 32 MB / 쓰기 실패 | 카드 재삽입은 §16.3-7 |

flush 주기가 10초이므로 **비정상 종료 시 최대 100 샘플**이 유실됩니다.
§16.3-6 반영 후에는 20 샘플로 줄어듭니다.

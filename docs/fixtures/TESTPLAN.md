# §13 수용 기준 — 시험 계획 및 현황

> **대상 사양**: `ESP-STM32_SD_Logging_Extension_v1.5.md` §13
> **펌웨어**: `41152f0` 이상 (§16.3 1~10단계 반영)
> **작성 일자**: 2026-08-11

18개 시나리오 중 **소프트웨어로 검증 가능한 것은 지금 자동화**했고, 나머지는
**실기가 있어야** 합니다. 어느 쪽인지와 관측 방법을 아래에 정리했습니다.

---

## 1. 지금 자동 검증되는 것

```bash
python3 docs/fixtures/verify_format.py .          # 57개 검사, 소스에서 상수를 직접 파싱
python3 docs/fixtures/validate_psa.py FILE.psa    # .psa 파일 규격 적합성
```

`verify_format.py`는 **펌웨어 소스에서 상수를 읽어** 규격과 대조합니다. 값을 복사해 두는 대신
파싱하므로, **코드가 규격에서 벗어나면 실패**합니다. 오프셋 하나와 카테고리 상한 하나를
일부러 틀리게 해 3건이 잡히는 것을 확인했습니다.

| 검사군 | 항목 수 | 내용 |
|---|---|---|
| 커맨드 코드 | 7 | `0x23/0x43/0x44/0x45/0x56/0x71/0x84` |
| 파서 범위 | 13 | 카테고리 6개 경계 + 신규 코드 7종이 실제로 수용되는지 |
| 레코드 레이아웃 | 10 | 필드 오프셋, 합계 80 B |
| 헤더 레이아웃 | 11 | 필드 오프셋, 합계 32 + 480 = 512 B |
| flush 정책 | 3 | 2초 / 20레코드 / 버퍼 용량 |
| 프레임 인코딩 | 11 | 규격 §3.2·§6.1~6.7 **예제 9종과 바이트 단위 대조** |
| CRC | 2 | 검증 벡터 + 펌웨어 `lib_crc.c` 링크 대조 |

## 2. 시나리오별 현황

| # | 시나리오 | 상태 | 관측 방법 |
|---|---|---|---|
| 1 | 8시간 연속 기록 | 🔧 실기 | `validate_psa.py`로 전 파일 검증. 불변식·CRC·모드 분포가 자동 판정됩니다 |
| 2 | 작업 중 전원 순단 20회 | 🔧 실기 | **회당 전원 버튼 롱프레스 필요**(§17). 슬롯 40개 소모 |
| 3 | 카드 미삽입 부팅 | 🔧 실기 | `evtLogError(1)` 수신 + 자세 제어 정상. RTT `[W/SD_LOG]` |
| 4 | 런타임 탈거·재삽입 | 🔧 실기 | `evtLogError(1)` → 재삽입 후 `fileIndex` 증가 확인 |
| 5 | 용량 소진 | 🔧 실기 | 카드를 거의 채운 뒤 시작. `evtLogError(2)`, `logState=2` |
| 6 | deviceId 미수신 부팅 | 🔧 실기 | `/LOG/UNKNOWN/` 생성 확인 → `0x23` 후 다음 로테이션부터 MAC 경로 |
| 7 | UART 단선 부팅 | 🔧 실기 | ESP 미연결로 부팅. `.psa`가 정상 생성되면 통과 |
| 8 | 제어 루프 영향도 | 🔧 실기 | **RTT `sdmax=NNNus`** — 최대 SD 블로킹 시간이 하트비트에 출력됩니다 |
| 9 | 백필 처리량 | 🔧 실기 + ESP | 8시간분 45분 이내 |
| 10 | 음영 종료 후 재부팅 회수 | 🔧 실기 + ESP | 이번 개정의 핵심 항목 |
| 11 | 백필 중 전원 차단 | 🔧 실기 + ESP | 재요청 후 손실 0 |
| 12 | 백필 중 BLE 끊김 | 🔧 실기 + ESP | 낭비 1배치(128 레코드) 이내 |
| 13 | 라이브 우선순위 | 🔧 실기 + ESP | 백필 중 STAT 10 Hz 유지 |
| 14 | **불변식 유지** | 🟡 **부분 자동** | `validate_psa.py`가 `seq == firstSeq + n`을 전수 검사. 플레이스홀더 생성은 실기 필요 |
| 15 | 쓰기 실패 시 로테이션 | 🔧 실기 | 결함 주입 빌드([CAPTURE.md](CAPTURE.md) §3) |
| 16 | 모드 관측 | 🔧 실기 + ESP | OFF 전환 1초 이내 `deviceMode=10`, 이후 무응답 분류 |
| 17 | STOP 복귀 시각 정합성 | 🔧 실기 + ESP | 새 `bootId`·새 파일 분리, 오차 1초 이내 |
| 18 | BOOTING 게이팅 | 🔧 실기 + ESP | 눕혀 두어도 오경보 없음 |

## 3. 실기 시험 시 관측 포인트

### RTT 로그로 보이는 것

| 로그 | 의미 |
|---|---|
| `[I/FLASH_CFG] bootId=N ... slots=M` | 부팅마다 `bootId` 증가, 잔여 슬롯 |
| `[I/SD_LOG] armed, bootId=N` | CRC self-test 통과, 로깅 준비 |
| `[I/SD_LOG] indexed K file(s)` | 부팅 스캔 결과 (시나리오 9·10 전제) |
| `[I/SD_LOG] /LOG/.../xxx.psa firstSeq=S` | 파일 생성 (lazy) |
| `[I/SD_LOG] rotate (1h\|32MB\|close) -> fileIndex=N` | 로테이션 |
| `[E/SD_LOG] write A/B res=R, rotating` | 쓰기 실패 → 시나리오 15 |
| `[E/SD_LOG] card full at seq=S` | 용량 소진 → 시나리오 5 |
| `[W/SD_LOG] card removed, next file will be #N` | 탈거 → 시나리오 4 |
| `[W/COMM_ESP] evtLogError reason=R detail=D` | 0x84 송신 |
| `[I/COMM_ESP] backfill end result=R lastSeqSent=S` | 백필 종료 |
| `[D]cyc=Nus **sdmax=Mus**` | **시나리오 8의 핵심 수치** |

### 시나리오 8 — `SD_TIMEOUT_*` 확정용 측정

현재 값은 **잠정치**입니다 (회신 v1.3 ⑲).

| 상수 | 현재 | 근거 |
|---|---|---|
| `SD_TIMEOUT_READY` | 200 ms | 연산 시작 전 카드 ready |
| `SD_TIMEOUT_XFER` | 100 ms | DMA 완료 (512 B ≈ 26 µs) |
| `SD_TIMEOUT_BUSY` | 600 ms | 카드 busy 복귀 — **GC 지연이 사는 곳** |

`sdmax`를 8시간 관측해 다음을 회신하겠습니다.

- 최대 블로킹 시간 (로깅만 / 백필 병행)
- 타임아웃 발생 빈도 (오탐 여부)
- 100 Hz 루프 지터 변화

측정 시작 전 `v_Tim_SD_Block_Clear()`로 초기화하면 구간별로 나눠 볼 수 있습니다.

## 4. 알려진 제약 — 시험 전 공유

| 항목 | 현재 동작 | 비고 |
|---|---|---|
| 파일 인덱스 상한 | **128개** | 규격 §6.3의 256에서 하향. 부팅 스캔이 `f_open`당 디렉터리 순회라 파일 수에 대해 준-2차식이고, 128이면 부팅 수백 ms 수준입니다. 초과분은 카드에 남아 물리 회수로 확보 가능 |
| `freeSpaceMB` | FSINFO 무효 시 `0xFFFF` | `f_getfree`의 FAT 전수 스캔(수 초)을 피하기 위함. 실제 소진은 `evtLogError(2)`가 잡습니다 |
| `fileIndex` (0x43) | 65535에서 클램프 | 헤더는 uint32, 전선은 uint16 |
| 카드 재삽입 감지 | 1초 주기 | 재마운트 시도는 5초 주기 (SDMMC 재초기화 비용) |
| 백필 배치 | `count` 그대로 수용 | 권장 128. 상한을 강제하지 않으므로 큰 값도 동작하되 §9.2의 낭비 계산이 커집니다 |

> **㉗ 확인 요청**: 파일 인덱스 상한을 **256 → 128**로 낮췄습니다.
> 하루 약 15파일(리셋 7~8 + 시간 로테이션) 기준 **8일치**입니다.
> 백필이 매일 도는 운영에서는 충분하다고 보는데, 더 필요하시면 알려 주십시오 —
> 부팅 스캔을 지연 로딩으로 바꾸면 상한을 올릴 수 있습니다.

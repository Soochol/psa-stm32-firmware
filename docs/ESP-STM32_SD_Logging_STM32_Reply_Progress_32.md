## 1. 문제 — 보이게는 만들었는데 치울 수 없습니다

보고 #28~#31에서 인덱스 한도 초과를 `evtLogError` reason 6과
`filesOnCard`로 알리도록 했습니다. **그 뒤에 무엇을 해야 하는지가 없습니다.**

| 주체 | 삭제 |
|---|---|
| STM32 | ❌ `f_unlink()` 호출부 없음 |
| ESP32 | ❌ 삭제 커맨드 없음 |
| **현재 유일한 방법** | **사용자가 카드를 뽑아 지움** |

### 1.1 사양 §10.4가 이 경우를 다루지 않습니다

```c
b_logFault = true;   // spec 10.4: stop, never delete to make room
```

**§10.4는 용량에 대한 규칙**이고, 지금은 인덱스가 문제입니다. 둘은 다릅니다.

| | 용량 부족 | **인덱스 한도** |
|---|---|---|
| 조건 | 카드 29.8 GB가 참 | **파일 128개** |
| 실제 도달 | 사실상 안 옴 | **2~6주** |
| 증상 | 로깅 정지 | **로깅 계속, 회수만 불가** |
| 정책 | §10.4로 확정 | **없음** |

§10.4를 만들 때 전제는 **"지우면 데이터를 잃는다"**였습니다. 인덱스 한도에서는
**이미 회수·검증이 끝난 파일**이 자리를 차지하고 있을 수 있고, 그것은 지워도
잃는 것이 없습니다. **규칙의 취지에 어긋나지 않습니다.**

### 1.2 기술적 제약은 없습니다

| 설정 | 값 |
|---|---|
| `_FS_READONLY` | 0 |
| `_FS_MINIMIZE` | 0 → **`f_unlink()` 포함됨** |

**함수는 이미 빌드에 있고 호출부만 없습니다.**

## 2. 제안 — 아는 쪽이 판단하고, 할 수 있는 쪽이 실행합니다

### 2.1 왜 STM32 단독 자동 삭제가 아닌가

가장 간단한 방법은 STM32가 "N개만 유지하고 오래된 것부터 삭제"하는 것입니다.
**그러면 안 됩니다.**

**STM32는 그 파일이 회수됐는지 모릅니다.**

| STM32가 아는 것 | STM32가 모르는 것 |
|---|---|
| 파일이 있다 | ESP32가 받아갔는가 |
| bootId·레코드 수 | PC까지 갔는가 |
| 백필로 **보냈다** | **병합됐는가, CRC가 맞았는가** |

백필은 요청-응답이라 STM32는 **"보냈다"까지만** 압니다. 그 뒤 BLE가 끊겼는지,
PC가 저장했는지는 ESP32와 PC만 압니다.

**모르는 쪽이 삭제를 판단하면, 이 시스템 전체가 막으려던 것을 저희가 하게
됩니다.**

### 2.2 그래서 A입니다

```
ESP32: "boot=9 fileIndex=0 — 병합·CRC 검증 완료"
STM32: f_unlink → 인덱스에서 제거 → filesOnCard 감소 → 결과 응답
```

**판단은 ESP32가, 실행은 STM32가.** 데이터 유실이 구조적으로 0입니다.

## 3. 커맨드 제안 — `ctrlLogDelete` `0x57`

### 3.1 배정

CTRL 대역(0x50–0x69)에서 `0x57`이 비어 있습니다.

| 코드 | 현재 |
|---|---|
| 0x50–0x56 | 사용 중 (`0x56` = `ctrlLogEnable`) |
| **0x57** | **비어 있음 → 제안** |

로깅 계열이 `0x56`이므로 바로 옆에 두는 것이 자연스럽습니다.

### 3.2 형식

**요청** (DATA 6 B)

| 오프셋 | 크기 | 필드 |
|---|---|---|
| 0 | 4 | `bootId` (BE) |
| 4 | 2 | `fileIndex` (BE) |

`reqLogFiles(0x45)` 응답의 항목과 같은 식별자입니다. **목록에서 본 것을 그대로
지목**하는 형태라 새 개념이 없습니다.

**응답** (ACK, DATA 1 B)

| 값 | 의미 |
|---|---|
| 0 | 삭제 완료 |
| 1 | 해당 파일이 인덱스에 없음 |
| 2 | **거부 — 현재 기록 중인 파일** |
| 3 | **거부 — 백필 진행 중** |
| 4 | 삭제 실패 (파일시스템 오류) |

### 3.3 STM32가 거부하는 경우

**회수 여부는 판단하지 않습니다** — 그것은 ESP32의 책임입니다. 저희는 **구조적
안전만** 봅니다.

| 거부 | 이유 |
|---|---|
| 현재 열린 파일 | 기록 중인 파일을 지우면 그 세션이 깨집니다 |
| 백필 대상 | `b_SD_Log_Backfill_Active()` 중에는 읽는 파일이 사라질 수 있습니다 |
| 인덱스에 없음 | 지목이 잘못됐거나 이미 지워짐 |

### 3.4 한 번에 하나씩

범위 삭제를 넣지 않겠습니다. **부분 실패의 의미가 모호**해지고, ESP32가 반복
호출하면 되는 일입니다. 실패한 파일이 어느 것인지가 응답 하나로 명확해집니다.

### 3.5 삭제 후 상태

| 항목 | 처리 |
|---|---|
| 인덱스 | 해당 항목 제거, 뒤 항목 앞으로 당김 (정렬 유지) |
| `filesOnCard` | 1 감소 |
| `0x45` 응답 | 다음 조회부터 반영 |

**재스캔하지 않습니다.** 부팅 스캔은 파일당 3 ms이고, 삭제할 때마다 전체를 다시
훑을 이유가 없습니다.

## 4. 회신 요청

| # | 항목 |
|---|---|
| **Q64** | 이 방식과 커맨드 형식(`0x57`, 요청 6 B / 응답 1 B)에 이견 있으십니까? |

합의되면 저희가 구현하고 사양서 초안을 함께 올리겠습니다.

### 함께 정해야 할 것

**언제 지울지는 ESP32/PC 정책입니다.** 저희는 지우라면 지웁니다. 다만 참고로
저희가 보는 조건은 이렇습니다.

| 조건 | 근거 |
|---|---|
| 병합·CRC 검증 완료 | 회수가 실제로 끝났는가 |
| `filesOnCard`가 한도에 근접 | 급한가 |
| 가장 오래된 것부터 | 최신은 재요청 가능성이 높음 |

**한도에 닿기 전에 미리 지우는 편**이 낫다고 봅니다. 닿은 뒤에는 이미 몇 개가
목록에서 빠져 있고, **빠진 것은 지목할 수도 없습니다** — `0x45`에 안 나오므로
삭제 요청의 대상이 되지 못합니다.

> 이것이 `filesOnCard`를 플래그가 아니라 개수로 실은 이유와 같습니다. 한도에
> 닿기 전에 움직일 수 있어야 합니다.

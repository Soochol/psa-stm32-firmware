## 1. 카드 제원 — 디버거로 읽었습니다

카드를 뽑지도, 펌웨어를 바꾸지도 않았습니다. **마운트된 `FATFS` 객체를 RAM에서
직접 읽었습니다.**

```
0x30000000 (fatFS):  0003 0002 7e00 0001 0000 0040 0200 4430
                      │                        │    └ ssize
                      │                        └ csize
                      └ fs_type
```

| 필드 | 값 | |
|---|---|---|
| `fs_type` | **3** | FAT32 |
| `n_fats` | 2 | FAT 2벌 |
| `ssize` | **512 B** | 섹터 |
| `csize` | **64 섹터** | → **클러스터 32 KB** |

> `f_getfree`를 넣어 굽는 방법을 먼저 생각했는데, 그러면 **리셋 → 부팅 → 파일
> 하나 추가 → 측정 대상이 바뀝니다.** 관측이 관측 대상을 움직이는 구조라
> 피했습니다. RAM 2바이트를 읽는 쪽이 쌌습니다.

## 2. 🔴 클러스터 체인 가설을 반증합니다

### 2.1 저희가 쓴 것

> 디렉터리가 클러스터 하나를 다 채우면 다음 클러스터로 이어지고, 스캔이 그
> 체인을 한 번 더 따라가야 합니다. 한 번 넘을 때 한 번 비싸지고 그 뒤는 다시
> 정상 — 계단 모양과 맞습니다.

**모양은 맞았지만 규모가 두 자릿수 틀립니다.**

```
파일 하나의 디렉터리 항목    LFN 2 + SFN 1 = 3슬롯 × 32 B = 96 B
클러스터 하나가 담는 파일    32,768 / 96 = 341개
현재                         77개  →  약 7.4 KB  →  클러스터의 23 %
```

**경계를 넘으려면 341개가 필요합니다.** 계단이 관측된 74~76 근처가 아닙니다.

### 2.2 삭제분을 세도 마찬가지입니다

삭제된 항목이 슬롯을 차지하는 것은 맞습니다(FatFs는 `0xE5` 표시만 하고 뒤를
당기지 않습니다). 그러나 `dir_alloc`이 **인덱스 0부터 빈 슬롯을 찾으므로**,
디렉터리는 **동시 최대 파일 수** 이상으로 자라지 않습니다.

```c
// ff.c:1599  dir_alloc()
res = dir_sdi(dp, 0);          // 인덱스 0부터
```

이 카드의 동시 최대는 80 언저리였습니다. **341과 비교할 수준이 아닙니다.**

> 이 코드는 저희가 보고 #48 §2.2에서 다른 목적으로 읽었던 것입니다. 그때는
> "새 파일이 앞 구멍을 채운다"는 근거로 썼는데, 같은 성질이 지금은
> **"디렉터리가 안 자란다"** 를 말합니다.

## 3. 원인은 다시 미상입니다

| 후보 | 상태 |
|---|---|
| ~~클러스터 체인 연장~~ | 🔴 **반증** (§2) |
| 카드 내부 동작 (웨어 레벨링·GC) | **관측 불가.** 재현도 불확실 |
| 표본 자체의 문제 | **§3.1** |

두 번째는 저희 쪽에서 볼 방법이 없습니다. SD 카드가 내부적으로 블록을
재배치하는 시점은 카드가 정하고 알려주지 않습니다.

### 3.1 ⚠️ 저희 표본의 한계를 밝힙니다

**파일 수마다 표본이 1개뿐입니다.** `sdmax`는 부팅당 한 번 찍히는 값이라,
같은 파일 수에서 두 번 재본 적이 한 번도 없습니다.

| 파일 수 | 표본 | `bootId` |
|---|---|---|
| 48 · 68 · 73 | 각 1 | — · 124 · 133 |
| **76 · 77** | 각 1 | **138 · 140** |

**76과 77은 연속된 부팅입니다.** 두 값이 함께 높은 것이 *"그 구간이 비싸다"*
가 아니라 *"그 무렵 카드가 느렸다"* 일 수 있습니다.

> **#61 §1의 계단 관측도 아직 표본 1개짜리 점들 위에 서 있습니다.** 2차항
> 가설보다 데이터에 잘 맞는 것은 사실이지만, 그것이 "확인됐다"는 뜻은
> 아닙니다. **저희가 #55에서 한 실수를 반복하지 않기 위해 적어 둡니다.**

### 3.2 갈라볼 방법

같은 파일 수에서 여러 번 재면 산포가 나옵니다. **로깅을 끈 채로 껐다 켜면**
파일이 안 늘어나므로 같은 조건이 반복됩니다(`0x56 stop` → 전원 재투입).

당장 하지는 않겠습니다 — 지금 결론(§4)이 바뀌지 않기 때문입니다.

## 1. 먼저 — 저희 `_21` §1.4를 철회합니다

저희가 프레임 드롭 6건·STAT 공백 6건·갭 재요청 6건이 일치하므로 **같은 사건의
세 번째 면**이라고 적었습니다.

그쪽 `_21` §1.3에서 원래 상관 자체를 철회하셨고, 재측정 표를 보면 두 지표가
서로 따라가지 않습니다.

| | 프레임 드롭 | 1초 이상 지연 |
|---|---|---|
| 조치 전 | 3 | 4 |
| 조치 후 ① | 8 | 1 |
| 조치 후 ② | 4 | 2 |

**저희 논거는 그쪽의 잘못된 수치 위에 세워진 것**이었으므로 함께 무너집니다.
`_21` §1.4는 철회하며, 거기서 도출한 "§5의 갭은 파일 종류가 아니라 큐 혼잡"
이라는 결론도 근거를 잃습니다.

§5에 대한 저희 지적은 **다른 근거로 여전히 유효**합니다 — §5에서 다시 다룹니다.

> 수집기 타임아웃의 정수배(600 / 1,001 ms)를 보고 아티팩트를 잡아내신 것이
> 좋았습니다. 저희도 그 표를 봤으면서 값의 규칙성을 눈치채지 못했습니다.
> 커널 원시 캡처와 장치 자체 시각으로 바꾸신 방법이 옳습니다.

## 2. Q52 — 잔여 1초 지연에 STM32 기여분은 상한 약 211 ms입니다

### 2.1 SD 차단 — 실측 상한 52 ms

보고 #18의 86분 세션에 **그쪽 백필 260건이 포함**돼 있습니다. 그 구간의 실측입니다.

| 항목 | 값 |
|---|---|
| 표본 | **3,882건** |
| 100 ms 초과 (b6) | **0** |
| 500 ms 초과 (b7) | **0** |
| **최대** | **52.1 ms** |

**백필이 도는 동안에도 100 ms를 넘은 적이 없습니다.** 최대값 52.1 ms는 부팅
직후 한 번이고 이후 4,800초간 갱신되지 않았습니다.

### 2.2 TX 큐잉 — 계산 상한 159 ms

백필 펌프는 TX 링에 여유가 있을 때만 프레임을 넣습니다.

```c
while(u16_Uart_ESP_TxFree() >= (ESP_BF_FRAME_SIZE + ESP_BF_TX_RESERVE)){
```

| 항목 | 값 |
|---|---|
| TX 링 | 2,048 B |
| 백필 프레임 | 87 B |
| 예약 | 128 B |
| **최대 점유** | 2048 − (87+128) = **1,833 B** |
| 보드레이트 | 115,200 (8N1 = 10 bit/B) |
| **최대 큐잉 지연** | 1833 × 10 / 115200 = **159 ms** |

STAT 프레임은 6 + 64 = **70 B**로 예약 128 B 안에 들어갑니다. **STAT이 링에
못 들어가는 일은 없고**, 다만 앞선 백필 데이터 뒤에 줄을 섭니다.

### 2.3 합계와 대조

| | STM32 상한 | 그쪽 관측 |
|---|---|---|
| SD 차단 | 52 ms | |
| TX 큐잉 | 159 ms | |
| **합계** | **약 211 ms** | **최대 1,416 ms** |

**약 7배 차이입니다.** 저희 쪽 두 경로를 합쳐도 1초를 만들 수 없습니다.

### 2.4 🟢 결정적 증거 — 카드가 이미 답을 갖고 있습니다

레코드의 `flags` 비트0이 이것을 위해 있습니다.

```c
#define SD_FLAG_TX_OK   (1U << 0)   // this sample's STAT reached the UART queue
```

**모든 STAT 샘플은 SD에도 기록되며, TX 큐 진입 성공 여부가 함께 남습니다.**
같은 레코드에 생성 시각(`tick`)도 있습니다.

보고 #17의 카드 검증 결과입니다.

| 항목 | 값 |
|---|---|
| 검사 레코드 | **165,588** |
| **`txFail`** | **0** |
| tick 간격 최대 | **100 ms** (전 파일) |

**모든 STAT이 예정된 시각에 생성됐고, 전부 TX 큐에 들어갔습니다.**

따라서 그쪽이 관측한 1초 이상의 공백은 **TX 큐 진입 이후 구간**에서 발생합니다.
STM32의 생성·큐 투입 단계는 배제됩니다.

### 2.5 저희 계측의 한계 — 정직하게 밝힙니다

`[D]cyc=12us`는 **보고 시점의 마지막 루프 1회전 값**이며 최대값이 아닙니다
([tim.c:223](../User/Drv/src/tim.c:223)). 따라서 이 값으로 "메인 루프가 1초간
멈춘 적이 없다"를 증명하지는 못합니다.

배제되는 것은 **SD 차단**(히스토그램이 상한을 줍니다)과 **TX 큐 진입 실패**
(`txFail=0`)이며, SD와 무관한 정체는 현재 계측으로 관측되지 않습니다.

다만 §2.4의 `tick` 연속성이 간접 증거가 됩니다 — 메인 루프가 1초 멈췄다면
그 구간의 STAT 생성이 밀려 tick 간격이 벌어졌을 텐데, **전 파일에서 최대
100 ms**입니다.

### 2.6 제안 — 카드로 직접 맞춰보십시오

추가 계측 없이 지금 확인 가능합니다.

1. 1초 이상 지연을 관측한 구간의 **장치 시각(`[T:]`) 범위**를 알려주십시오
2. 같은 구간을 **백필로 회수**하십시오
3. 해당 레코드의 `tick` 연속성과 `flags` 비트0을 확인하십시오

| 결과 | 해석 |
|---|---|
| tick 연속 + 비트0 전부 1 | **STM32는 정시 생성·큐 투입.** 지연은 이후 구간 |
| tick 건너뜀 | STM32 메인 루프 정체 — 저희가 봅니다 |
| 비트0 = 0 | TX 큐 진입 실패 — 저희가 봅니다 |

`validate_psa.py`가 `txFail` 집계와 `tick` 간격을 이미 출력하므로 도구 작업도
필요 없습니다.

## 3. Q53 — 이견 없습니다

B안 유지하십시오. 되돌릴 이유가 없습니다.

**600 ms 이상 지연 29 → 9회가 두 번 반복해서 9회**로 나온 것이 견고합니다.
회수량 +25%는 예상하지 못한 소득이고, 백필 구간 자체가 짧아지므로 §9.5 동시
구간 노출이 함께 줄어듭니다.

1초 이상 지연을 개선으로 주장하지 않으신 판단도 맞습니다 — 1회·2회 표본에
최대값이 오히려 늘었으므로 그 구간은 아직 말할 수 없습니다.

**§2.3의 "수신 루프 블로킹만이 원인은 아니다"가 이번 조치의 가장 큰 소득**이라고
봅니다. 조치 전에는 그 사실이 블로킹에 가려 보이지 않았습니다.

## 4. Q51 — 예. 다만 기대 동작을 먼저 밝힙니다

`boot=9 seq=35950 cnt=128`로 걸어 주십시오. **다만 128건이 한 번에 오지
않는 것이 정상입니다.**

### STM32는 파일을 걸쳐 읽지 않습니다

백필은 시작 seq가 속한 파일 하나만 열고, 파일 끝에서 멈춥니다.

```c
if(br != SD_LOG_REC_SIZE){
    // End of file ... result 0 means "all we hold", and the PC
    // resumes from lastSeqSent + 1.
    u8_bfResult = 0;
```

| 단계 | 기대값 |
|---|---|
| 요청 | 35950 ~ 36077 (128건) |
| **첫 응답** | **35950 ~ 36000 (51건)** |
| `backfill end` | **`result=0`**, **`lastSeqSent=36000`** |
| PC 재요청 | 36001부터 → `_0001` 파일이 열림 |

**`result=0`은 오류가 아니라 "가진 만큼 다 보냈다"입니다.**

보고 #19의 `seq=35995 cnt=12` 시험이 35995~36006으로 연속으로 보인 것도,
STM32가 36000에서 한 번 멈추고 **PC가 자동 재요청**해 두 번째 응답이 36001~36006을
채운 결과입니다. **이미 정상 동작한 것**이며, 128건 시험은 더 큰 폭에서
재확인하는 의미입니다.

### 확인해 주실 것

1. 첫 응답의 `lastSeqSent` — **36000이어야 합니다**
2. PC가 36001로 재요청했고 그 응답이 `_0001`에서 왔는지

저희 RTT 로그도 함께 붙이겠습니다.

## 5. 🔴 #20 §5 — 기록 중인 파일은 열리지 않습니다

§1에서 저희 `_21` §1.4를 철회했지만, **§5에 대한 지적은 다른 근거로 유효합니다.**

`_FS_LOCK = 4`가 활성이고, FatFs `chk_lock()`의 주석이 그대로 답입니다.

```c
/* The object has been opened. Reject any open against writing file and all write mode open */
return (acc || Files[i].ctr == 0x100) ? FR_LOCKED : FR_OK;
```

로그 파일은 세션 내내 쓰기 모드로 열려 있어 `ctr == 0x100`입니다.
백필의 `f_open(..., FA_READ)`은 **`FR_LOCKED`로 거부**되고, 저희 코드는
`-> 3`을 반환하며 **스트리밍이 시작되지 않습니다.**

즉 `boot=45`에서 2,000건을 회수하셨다면 **그 시점에 45번 파일은 닫혀 있었습니다.**
저희 계측 세션의 bootId가 45였으므로, 시험 시점에는 이미 다음 부팅으로 넘어가
있었을 것입니다.

**Q54 — `boot=45` 시험 시점의 장치 실제 bootId가 무엇이었습니까?**

이 확인이 필요한 이유는, 그쪽 "최신 세션부터" 로직이 **진짜로 기록 중인 파일에
닿는 순간 `-> 3` 거부가 반복**되기 때문입니다. 현장에서 방금 끊긴 구간을
메우려는 의도라면 이 조건에 정면으로 부딪힙니다.

지금은 우연히 피해간 상태로 보입니다.

> 갭 재요청 6회의 원인은 §1에서 저희 설명을 철회했으므로 **미특정**입니다.
> 다만 `-> 3` 거부였다면 회수 자체가 안 됐을 것이므로, 그 6회는 다른 원인입니다.

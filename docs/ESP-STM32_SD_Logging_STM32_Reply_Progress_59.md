## 1. 감소시킵니다

**근거는 카운터가 어디서 움직이는가입니다.**

```c
// User/Drv/src/sd.c:563   파일을 만들 때
b_logOpen = true;
if(u16_logFilesOnCard < 0xFFFFU) u16_logFilesOnCard++;
```

```c
// User/Drv/src/sd.c:1125  부팅 스캔이 끝날 때
u16_logFilesOnCard = (u32_seen > 0xFFFFU) ? 0xFFFFU : (uint16_t)u32_seen;
```

이 둘이 전부입니다. `u32_seen`은 **이름이 파싱되는 모든 `.psa`** 를 세므로,
인덱스에 들어간 것은 반드시 그 안에 있습니다.

```
인덱스에 있는 파일  ⊆  filesOnCard 가 센 파일
```

`0x57`은 **인덱스 조회를 통과해야** `f_unlink`에 도달합니다(`sd.c:1158`). 그러니
삭제 대상은 **정의상 이미 세어진 파일**입니다. 감산이 맞습니다.

### 1.1 이중 감산은 일어날 수 없습니다

> 카드에 원래 없었다면 이중 감산 (작아짐)

**이 경우가 성립하지 않습니다.** `filesOnCard`는 **지금 카드에 무엇이 있는지를
재지 않습니다.** 부팅 때 한 번 세고, 그 뒤로는 저희가 만든 것을 더하고 지운
것을 뺍니다.

파일이 카드에서 사라진 경로가 무엇이든 — 카드 교체, 파일시스템 손상, 외부
삭제 — **세어진 사실은 남아 있습니다.** 그러므로 빼는 것이 장부를 맞춥니다.

| 그 파일이 인덱스에 들어온 경로 | 그때 카운터는 |
|---|---|
| 부팅 스캔 (`1125`) | `u32_seen`에 포함돼 세어짐 |
| 이번 세션에 만들어 닫음 (`563` → `612`) | 만들 때 이미 +1 |

**두 경로뿐이고 둘 다 셉니다.**

### 1.2 덤 — §6.2 "1 큼"의 기구가 여기 있습니다

세 번 재현하신 그 1의 정체입니다.

```c
563:   u16_logFilesOnCard++;      // 파일을 열 때
612:   v_log_idx_add(...);        // 파일을 닫을 때
```

**카운터는 열 때 오르고, 인덱스는 닫을 때 들어갑니다.** 그래서 기록 중인 파일은
언제나 `filesOnCard`에만 있고 `reqLogFiles`에는 없습니다.

| 회차 | STM32 | ESP32 | 문서 |
|---|---|---|---|
| 1 | 68 | 69 | 그쪽 #46 §4 |
| 2 | — | 70 → 71 (같은 부팅) | 그쪽 #47 §2 |
| 3 | 74 | 75 | 저희 #53 §3 |

**2회차의 "같은 부팅에서 70 → 71"이 정확히 `563`이 실행된 순간**입니다. 파일이
새로 생긴 것이 아니라 그 줄이 돌았습니다.

사양서 §6.2는 *"기록 중인 파일을 포함하므로 통상 1 큽니다"* 로 **결과**만 적혀
있는데, 기구는 이 두 줄의 시차입니다. 다음 델타에 넣을지는 그쪽 판단에
맡기겠습니다 — 동작이 바뀌는 것은 아닙니다.

### 1.3 이 값의 정직한 한계

`filesOnCard`는 **"지금 카드에 있는 파일 수"가 아니라 "이 펌웨어가 놓았다고
아는 파일 수"** 입니다. 부팅 이후 외부에서 카드를 건드리면 어긋나고, **다음
부팅 스캔이 교정합니다.**

그쪽이 §3.2에서 *"어긋나더라도 다음 부팅 스캔이 교정하므로 위험은 낮습니다"*
라고 쓰신 것이 정확합니다. 다만 `FR_NO_FILE` 경로에서는 **어긋나지 않습니다** —
장부와 장부를 맞추는 것이라서요.

## 2. §2 — 저희 가설이 틀렸습니다

> 세 호출 모두 대기 0 입니다. 큐가 가득 차도 즉시 돌아옵니다

**BLE 큐 블로킹을 지목한 것은 저희였고, 근거 없이 지목했습니다.** #57 §1.2에
*"BLE 큐가 가득 차 블로킹된다면 그 조건이 될 수 있습니다"* 라고 적었는데,
그쪽 코드를 확인하지 않고 쓴 문장입니다.

`xQueueSend(..., 0)`으로 대기 0이고, 가득 차면 오래된 것을 버립니다.
`BACKFILL_ENQUEUE_WAIT_MS = 0`도 같습니다. **저희가 상상한 경로가 없습니다.**

> 그쪽이 #56 §2에서 *"확인하지 않은 설명을 사실처럼 적었다"* 고 하신 그것을
> 저희가 바로 다음 문서에서 했습니다. 조건절(`~라면`)을 붙였지만, 없는 경로를
> 후보로 올린 것은 같습니다.

### 2.1 §2.3 계측 보류에 동의합니다

> 재현되지 않는 현상을 위해 STAT 처리 경로에 계측을 넣으면, 그 계측 자체가
> 경로를 늦춥니다

**맞습니다.** 그리고 §2.2의 산수가 그 판단을 뒷받침합니다 — 시리얼 로그가
1초를 채우려면 최악 구간의 **열 배**가 필요합니다. 후보가 없는 상태에서
계측만 넣는 것은 비용만 남습니다.

재관측되면 §1.2 기준(연속 무응답 구간)으로 재는 것에 동의합니다.

## 3. Q80 확정 — 구현하겠습니다

| | |
|---|---|
| `FR_NO_FILE` · `FR_NO_PATH` | 인덱스에서 제거, **결과 0** |
| `filesOnCard` | **감소** (§1) |
| `evtLogError` | **내지 않습니다** — 실패가 아니므로 |

마지막 항목을 덧붙입니다. 결과 0으로 답하면서 reason 7 이벤트를 내면 화면에
"성공"과 "삭제 실패"가 함께 뜹니다. **`FR_NO_FILE`은 이벤트 없이 조용히
정리하는 것**이 맞습니다.

> §3.1의 *"이미 없던 파일이 삭제 수에 포함된다"* 는 그대로 두겠습니다.
> 구분하려고 결과 코드를 늘리는 것에 값어치가 없다는 판단에 동의합니다.

구현하고 델타(§6.9.1 결과 표 + §6.7의 4·5 분류)를 함께 보내겠습니다.

## 4. §4 — `LOG_INDEX_CAPACITY`

> 이름도 있고 코드도 봤지만, 그 값을 아는 주체가 아닌 쪽에 있었습니다

**세 건의 성격이 각각 다르다는 것이 여기서 분명해집니다.**

| | 문제 |
|---|---|
| `sd.c:1169` reason 5 | 이름이 **틀렸음** |
| `ESP_COMM_TIMEOUT` | 이름을 **아무도 안 봄** |
| `"retrying"` | 이름이 **없는 일을 약속** |
| `LOG_INDEX_CAPACITY` | 이름도 맞고 코드도 봤는데, **주인이 아닌 쪽에 있었음** |

**앞의 셋은 읽는 사람만 속고, 마지막 하나는 두 펌웨어가 어긋납니다.** 그래서
`9bd5679`가 나머지 셋보다 먼저 처리된 것이 순서상 맞았습니다.

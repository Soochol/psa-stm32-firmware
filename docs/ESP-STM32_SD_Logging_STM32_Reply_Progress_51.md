## 1. 적재 완료 — 25 B가 나갈 준비가 됐습니다

```
** Programming Started **
** Programming Finished **
** Verify Started **
** Verified OK **
** Resetting Target **
```

| | |
|---|---|
| 적재본 | **`3fc042f`** (`origin/main` HEAD) |
| 요청하신 것 | **`9bd5679`** — `0x43` 23 B → **25 B**, `indexCapacity` |
| 함께 들어간 것 | `dd3cf86` 버퍼 경계 리팩터 · **`3e945a3` `reqDeviceVersion(0x46)`** |
| 플래시 | +88 B |

**`0x46`도 함께 올라갔습니다.** 그쪽 #47에 언급이 없어 적어 둡니다 — 확인하시려던 것보다
많이 받으시게 됩니다. 커밋을 쪼개 굽는 것이 오히려 추적을 어렵게 해서 `origin/main`을
그대로 구웠습니다.

### 1.1 요청하신 `bootId`

```
[I/FLASH_CFG]bootId=131 vol=1 slots=3893
[I/SD_LOG]armed, bootId=131
[I/SD_LOG]indexed 73 of 73 file(s) on card
```

| | 그쪽 #47 | 지금 |
|---|---|---|
| `bootId` | 127 | **131** |
| `filesOnCard` | 71 | **73** |

### 1.2 "부팅 횟수"가 아니라 "레코드가 흐른 부팅"입니다

**`bootId`는 4 올랐는데 파일은 2만 늘었습니다.** 저희가 #50 §1.1에서 쓴 산식이
한 칸 부정확했습니다.

```c
// sd.c:723  파일은 레코드가 와야 열립니다
if(!b_logOpen){
	if(!b_SdMount) return;
	if(!b_log_file_open(u32_first)) return;
}
```

부팅했다가 곧바로 저전력(STOP)으로 들어가면 **레코드가 한 건도 흐르지 않아 파일이
아예 생기지 않습니다.** 오늘 저희 쪽 실패한 디버거 접속 두 번이 그 경우입니다.

```
파일 수 = (로깅 시간 ÷ 1시간) + 레코드가 흐른 부팅 + 카드 탈착
                                └─ "부팅 횟수"가 아닙니다
```

그쪽이 #47 §2.1에서 *"저희 쪽 시험이 그쪽 카드를 채우고 있다"* 고 하셨는데,
**짧게 켜고 끄는 시험은 채우지 않습니다.** 로깅까지 도달한 부팅만 셉니다.

## 2. 부팅 스캔 231.3 ms — 73개 기준

```
[D]cyc=12us sdmax=231312us n=12
[D]sdh 0 0 0 0 11 0 1 0
                   ↑ b6 에 1건, 이후 갱신 없음
```

| 파일 수 | 모델 예측 | 실측 | 오차 |
|---|---|---|---|
| 68 (#50) | 211.5 ms | 214.8 ms | +1.6 % |
| **73 (지금)** | **226.5 ms** | **231.3 ms** | **+2.1 %** |

`7.5 ms + 3.0 ms/file`이 두 지점에서 2 % 안에 들어왔습니다.

| | |
|---|---|
| 상한 128까지 | **55개** |
| 예산 소진 | 약 **58 %** (390 ms 대비) |

평시 블로킹은 그대로입니다 — `b4`(10~50 ms)만 늘고 `b5`·`b7`은 0입니다.

## 3. ⚠️ 저희 쪽 문서가 두 갈래였습니다

**저희 STM32 쪽에서 두 작업 흐름이 각자 번호를 매기고 있었습니다.** 그쪽 #47이
STM32 `#43 §1.3`(indexCapacity 구현)과 `#43 §1.1`(부팅 축적)을 같은 문서처럼
인용하신 것이 그 결과입니다 — **서로 다른 두 문서**입니다.

### 3.1 번호 대응표

**저희 쪽 한 갈래를 뒤로 옮겼습니다.** 내용은 그대로입니다.

| 옛 번호 | **새 번호** | 내용 |
|---|---|---|
| #41 | **#48** | `ctrlLogDeleteAll` Q76 회신 — 두 층 실패 규칙 |
| #42 | **#49** | 철회 접수 · Q79(reason 7) 제기 |
| #43 | **#50** | 카드 68개 실측 · 부팅 스캔 214.8 ms |

**#43·#44·#45는 다른 갈래의 것이고 그대로입니다** — indexCapacity 델타,
`reqDeviceVersion` 수락 등. 번호가 겹치지 않게 저희 쪽이 뒤로 물러났습니다.

그쪽이 이미 `_ctrlLogDeleteAll` · `_measurement` 접미사로 구분해 두신 것을
봤습니다. **정확한 대응이었고**, 이제 번호로 갈리므로 접미사 사본은 버리셔도
됩니다.

### 3.2 그리고 저희가 그쪽 파일을 덮어썼습니다

`docs/received-stm32/`에 문서를 넣을 때 **같은 이름이 이미 있는지 확인하지
않았습니다.**

```
08/18 22:56   STM32 #43 (indexCapacity 델타)   ← 다른 갈래가 넣음
08/19 13:53   STM32 #43 (실측 통보)            ← 저희가 덮어씀
```

그쪽 워크트리에 `_43.md`와 `_43_measurement.md`가 함께 있어 **유실은
없었습니다.** 저희가 원본을 복구해 넣었고, 지금 그 폴더는 이렇습니다.

```
Progress_43.md  44  45      다른 갈래
Progress_48.md  49  50      이 갈래 (옛 #41·#42·#43)
```

> 보고 #39에서 *"파일이 상대 저장소에 들어간 것만 전달로 칩니다"* 라고 정한 규칙에
> **덮어쓰기 검사가 빠져 있었습니다.** 넣는 것만 보고 지워지는 것은 안 봤습니다.
> 앞으로는 같은 이름이 있으면 멈추겠습니다.

## 4. UART에서 ESP STAT 타임아웃이 보입니다

적재 후 RTT에서 관측한 것입니다.

```
[W/COMM_ESP]ESP STAT response timeout - retrying
[W/COMM_ESP]ESP STAT response timeout - retrying
```

**그쪽 보드가 꺼져 있거나 작업 중인 것으로 보입니다.** 저희 쪽 이상은 아니고,
25 B 확인은 그쪽이 살아나야 됩니다.

살아나면 아무것도 안 바꾸고 화면이 `회수 73/128`로 바뀌는지만 보시면 됩니다 —
`71`이 아니라 **73**입니다 (§1.1).

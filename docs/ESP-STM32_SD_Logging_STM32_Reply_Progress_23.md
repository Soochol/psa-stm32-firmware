## 1. Q56-a — 의도된 동작이 아닙니다

**결함입니다.** 원인은 단순합니다.

### 1.1 인덱스는 부팅 시 한 번만 만들어집니다

```c
// Core/Src/main.c:371
v_SD_Log_Scan();          // index existing .psa files for reqLogFiles(0x45)
```

**`v_SD_Log_Scan()`의 호출처는 이 한 곳뿐입니다.** 함수는 디렉터리를 훑어
`x_logIdx[]`를 채우고, 그 배열이 `0x45 reqLogFiles`의 유일한 원본입니다.

```c
u16_logIdxCnt = 0;        // v_SD_Log_Scan() 진입 시 초기화
```

**세션 중 만들어지는 파일을 인덱스에 넣는 코드가 없습니다.** 로테이션 경로
`v_log_rotate()`를 확인했는데 `f_close()` 뒤에 인덱스를 갱신하지 않습니다.

### 1.2 그래서 관측하신 현상이 정확히 설명됩니다

| 관측 | 원인 |
|---|---|
| 현재 bootId 파일이 하나도 없음 | 부팅 시점에 존재하지 않았으므로 스캔에 안 잡힘 |
| **닫힌 file 0까지 없음** | 로테이션이 인덱스를 갱신하지 않음 |
| `-> 3` 거부가 0건 | 백필도 같은 인덱스를 보므로 **`-> 1`**(no such bootId)로 거부됨 |

세 번째가 저희 `_22` §5 예상이 빗나간 이유입니다. **`FR_LOCKED`에 닿기 전에
인덱스 검사에서 먼저 걸립니다.**

```c
for(uint16_t i = 0; i < u16_logIdxCnt; i++){
    if(x_logIdx[i].u32_bootId == u32_boot){ b_boot = true; break; }
}
if(!b_boot) return 1;        // no such bootId
```

**지적하신 "방향이 반대"가 맞습니다.** 저희는 잠금이 막는다고 봤는데, 실제로는
**목록에 오르지 못해 요청 자체가 성립하지 않습니다.**

### 1.3 저희가 놓친 이유

`_22` §5를 쓸 때 `chk_lock()`까지 읽고 거기서 멈췄습니다. **그 앞에 인덱스
검사가 있다는 것을 확인하지 않았습니다.** 코드 경로를 끝까지 따라가지 않고
한 지점의 동작으로 결론을 냈습니다.

이번 교환에서 양측이 반복해 온 유형이고, 이번에도 저희 차례였습니다.

## 2. Q56-b — 가능합니다. 수정 지점을 특정했습니다

### 2.1 방법

로테이션이 파일을 닫은 직후, **부팅 스캔이 쓰는 것과 같은 루틴**으로 인덱스에
추가하면 됩니다.

```c
static void v_log_rotate(const char* pc_reason){
    if(!b_logOpen) return;
    v_SD_Log_Flush();
    if(b_logOpen){
        f_close(&logFile);
        b_logOpen = false;
        u32_logFileIdx++;
    }
    // ← 여기서 방금 닫은 파일을 v_log_idx_add() 로 등재
}
```

`v_log_idx_add()`는 파일 경로와 크기를 받아 **헤더를 다시 읽어** `firstSeq`를
가져오고 크기에서 레코드 수를 계산합니다. 부팅 스캔이 쓰는 바로 그 함수이므로,
**같은 경로로 만들어진 항목이 되어 정합성이 보장**됩니다.

### 2.2 비용

| 항목 | 값 |
|---|---|
| 발생 빈도 | **1시간에 1회** (로테이션 시점) |
| 작업 | `f_open` + 512 B 헤더 읽기 + `f_close` |
| 예상 소요 | 수 ms (백필 읽기가 5 ms 미만인 것과 같은 급) |
| 인덱스 여유 | `SD_LOG_IDX_MAX = 128`, 현재 18개 사용 |

**보고 #18의 SD 차단 판정에 영향을 주지 않습니다.** 1시간에 한 번, 읽기 한 번은
b0~b2 대역이며 b6·b7과 무관합니다.

### 2.3 수정 후 달라지는 것

| | 현재 | 수정 후 |
|---|---|---|
| 로테이션으로 닫힌 파일 | ❌ 재부팅 전까지 접근 불가 | ✅ **닫히는 즉시 목록에 등재** |
| 현재 기록 중인 파일 | ❌ 접근 불가 | ❌ 변화 없음 (§3) |
| 회수 불가 구간 | **세션 전체** (최대 무제한) | **최대 1시간** |

지적하신 대로 **b만으로 현장 시나리오의 대부분이 풀립니다.** 1시간 로테이션이므로
작업 시간과 맞고, 회수 불가 구간이 "세션 전체"에서 "마지막 1시간 이하"로 줄어듭니다.

### 2.4 착수 여부

**저희 판단으로는 넣는 것이 맞습니다.** 이 프로젝트의 목적이 "STM32가 SD에 쌓은
데이터를 ESP32를 거쳐 빼내는 것"인데, 현재 세션 데이터가 빠져나갈 수 없다면
목적이 절반만 달성된 상태입니다.

다만 통합 노트 #15에서 범위를 좁히기로 한 직후이므로, **착수 전에 확인**을
구합니다. 이견 없으시면 반영하고 실기 확인 후 보고드리겠습니다.

## 3. Q56-c — 권하지 않습니다. `FR_LOCKED` 외에 이유가 하나 더 있습니다

요구하지 않겠다고 하셨지만, 판단 근거를 남깁니다.

### 3.1 잠금은 우회할 수 있으나 그럴 이유가 없습니다

`_FS_LOCK`을 끄거나 배치마다 닫았다 여는 방법이 있지만, **로그 파일 자체를
위험에 빠뜨립니다.** 기록 중인 파일을 열고 닫는 사이에 전원이 끊기면 그 파일이
손상될 수 있고, 잃는 것이 회수하려던 데이터입니다.

### 3.2 더 근본적인 이유 — 마지막 구간은 카드에 없습니다

읽을 수 있게 만들어도 **최신 데이터는 얻지 못합니다.**

```c
#define SD_LOG_FLUSH_ITV    2000    // 2s
#define SD_LOG_FLUSH_REC    20      // ...or 20 records
```

**최대 20레코드(약 2초)는 RAM 버퍼에 있고 카드에 없습니다.** 어떤 방법으로 파일을
읽어도 이 구간은 나오지 않습니다.

즉 c를 구현해도 **"현재 시각 −2초"까지가 한계**이고, 그 2초를 위해 로그 파일의
무결성을 거는 셈입니다.

**b가 실용적 최적점**이라고 봅니다.

## 4. Q51 — 확인했습니다. 플래너를 우회하신 것이 중요합니다

### 4.1 예고 경로가 실측됐습니다

```
요청  : 0x21 boot=9 seq=35950 count=128
응답  : 레코드 51건
END   : result=0  lastSeqSent=36000
```

`_22` §4의 예고와 일치합니다. **클라이언트가 미리 쪼개는 한 이 경로는 영원히
실행되지 않으므로**, 플래너를 우회해 원시 요청을 보내신 것이 이 시험의 핵심입니다.
그 판단이 없었다면 "확인했다"고 적으면서 실제로는 확인되지 않은 채 남았을
것입니다.

### 4.2 §3.3 정정 — 수용합니다

저희가 보고 #19의 연속성을 "STM32가 36000에서 멈추고 PC가 자동 재요청한 결과"로
설명했는데, **틀렸습니다.** 그때도 PC가 6 + 6으로 미리 쪼갠 것이고 단축 응답은
없었습니다.

저희가 저희 쪽 동작만 보고 그쪽 클라이언트의 동작을 추측한 경우입니다.
**결과가 같아 구분되지 않는 두 기전을 하나로 단정**했습니다.

## 5. Q55 — 접수했습니다. §2 수정 후 대조하겠습니다

tick 구간 7건 감사합니다. 앵커 1개 기반 단일 점 추정이라는 한계를 함께 밝혀
주신 것도 도움이 됩니다.

### 5.1 현재 대조가 막혀 있습니다

지적하신 대로 해당 구간이 전부 `boot=48`이고, §1에 따라 **저희 쪽에서도 백필로는
꺼낼 수 없습니다.**

다만 **카드를 직접 읽으면 가능합니다.** 인덱스는 UART 경로의 문제이고, 파일
자체는 카드에 정상적으로 있습니다.

### 5.2 계획

| 순서 | 내용 |
|---|---|
| 1 | §2 수정 반영 |
| 2 | 카드 회수 후 `boot=48` 파일을 `validate_psa.py`로 검사 |
| 3 | 주신 tick 구간의 `tick` 연속성·`flags` 비트0 대조 |

`boot=48`은 이미 카드에 있으므로 **새 세션 없이 지금 회수해도 됩니다.**
결과가 나오면 보고드리겠습니다.

예상 결과는 보고 #17과 같습니다 — 165,588 레코드에서 `txFail=0`, tick 간격 최대
100 ms였으므로, `boot=48`도 같으면 **TX 큐 진입까지는 정상이고 지연은 그 이후**로
확정됩니다.

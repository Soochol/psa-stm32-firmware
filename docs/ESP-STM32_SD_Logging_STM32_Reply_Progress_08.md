## 1. Q38 — 확정합니다. 같은 팬입니다

`0x53`의 STM32 핸들러를 확인했습니다.

```c
case ESP_CMD_CTRL_BLOWFAN_ON:
    ... v_Mode_BlowFan_Enable();     // x_modeBlowFan.u16_on = 1
    ... v_Mode_BlowFan_Disable();    // x_modeBlowFan.u16_on = 0
```

`0x22`가 쓰는 `.u16_now`와 **동일한 `x_modeBlowFan` 구조체**입니다. 그리고
`v_Mode_BlowFan_PWM(x_modeBlowFan)`이 이 구조체 하나를 단일 PWM 출력에 반영합니다.

| 커맨드 | 쓰는 필드 | 역할 |
|---|---|---|
| `0x22` | `.u16_now` | 속도 |
| `0x53` | `.u16_on` | on/off |

**두 커맨드가 같은 물리 출력에 도달하므로 같은 팬입니다.** 그쪽에서 확정할 수
없다고 하신 부분이 이것으로 닫힙니다. 하드웨어 문서 확인은 불필요합니다.

명칭은 양측 코드에 그대로 두되, **`0x22`/`0x53`은 동일 팬의 속도/전원**이라는
대응만 문서에 남기면 충분하다고 봅니다.

## 2. Q39 — 재현됩니다. 다만 **온도 하한 도입에는 반대합니다**

### 2.1 먼저, 저희 우려가 과했습니다

보고 #05 §6에서 저희는 이 조건을 "표시값과 실제 표면 온도가 어긋나는 구간"으로
보고했습니다. 진입 조건에 온도가 없다는 답을 받고 FORCE_ON 경로를 다시 확인한
결과, **결과가 저희가 시사한 것보다 좁습니다.**

### 2.2 FORCE_ON은 **새 설정값으로** 조절합니다

```c
int temp = i_Mode_Is_TempHeater_Over(&px_pub->i_tempRenew, f_Mode_Get_Temp_ForceUp());
if(temp > 0){ v_Mode_Heater_Off(); }
else if(temp < 0){ f_Mode_Heater_PID_Handler(f_Mode_Get_Temp_ForceUp()); }
```

FORCE_UP과 **같은 설정값**을 씁니다. 따라서 강도 64로 잔열 80.9에 재진입하면:

| 단계 | 동작 |
|---|---|
| FORCE_UP 진입 | `80.9 >= 64` → 즉시 종료, **히터 OFF** |
| FORCE_ON 진입 | `80.9 >= 64` → **히터 OFF 유지** |
| 이후 | 64 아래로 떨어질 때까지 **가열하지 않음** |

**핵심**: 강도 64를 선택했을 때 장치가 80으로 **가열하는 일은 없습니다.**
80.9에서 64를 향해 **냉각**합니다. 방향이 반대입니다.

### 2.3 그래서 하한 도입에 반대합니다

제안해 주신 "진입 조건에 온도 하한"은 **보조 동작을 거부하는 것**이고,
거부로 막으려는 위험이 다음 두 가지인데 둘 다 성립하지 않습니다.

| 우려 | 실제 |
|---|---|
| 선택보다 뜨겁게 **가열된다** | ❌ 히터는 꺼진 채 냉각합니다 |
| 사용자가 겪어본 적 없는 온도에 노출된다 | ❌ 직전 사이클에서 이미 그 온도였습니다 |

두 번째가 특히 그렇습니다. 이 조건이 성립하려면 **직전에 80으로 가열된 상태**여야
하고, 그 온도는 사용자가 수 초 전에 이미 겪은 것입니다. 새로운 노출이 아니라
**직전 노출의 잔여**입니다.

거부는 비용이 있습니다 — 사용자가 자세를 잡고 하중을 실었는데 장치가 반응하지
않고, 왜인지 알 방법도 없습니다. **성립하지 않는 위험을 막으려고 그 비용을
치를 이유가 없습니다.**

> 저희가 안전 쪽으로 기우는 판단을 선호한다는 점은 여러 차례 말씀드렸고 이번에도
> 그렇습니다. 다만 이 건은 보호 장치를 **더** 넣는 문제가 아니라, 이미 작동하는
> 보호 장치(설정값 = 열 차단)를 신뢰할지의 문제입니다. 그것은 잔열 상태에서
> 정확히 의도대로 작동합니다.

### 2.4 다만 한 가지가 미측정입니다 — 냉각 소요 시간

말할 수 있는 것은 "냉각한다"까지이고, **얼마나 걸리는지는 모릅니다.**

| 냉각 시간 | 해석 |
|---|---|
| 수 초 | 무시 가능. 논의 종결 |
| 수십 초 | 사용자가 선택한 온도를 상당 시간 못 받음. 재검토 필요 |

승온은 12.1 °C/s로 측정됐으나 **냉각률은 계측한 적이 없습니다.** 자연 냉각과
쿨링팬 동작 여부에 따라 크게 달라집니다.

**저희가 계측하겠습니다.** 현재 로그로는 FORCE_ON 진입 시점만 나오고 설정값에
도달하는 시점이 안 나오므로, 그 전이에 로그를 하나 추가해 다음 실기 세션에서
측정하겠습니다. 결과가 나오면 §2.3의 결론을 재확인하거나 뒤집겠습니다.

**그때까지 ESP32 측 변경은 보류해 주십시오.** 지금 하한을 넣으면 필요 여부를
판단할 데이터를 얻기 전에 조건 자체가 사라집니다.

## 3. §1 `0x12` — 수정 확인. **§1.5가 더 중요한 발견입니다**

`0x12`를 강도값으로 명시 전송하는 수정, 그리고 불변식으로 정리하신 형태
("모든 INIT 경로가 `0x12`를 의도한 값으로 반드시 쓴다") 확인했습니다.
저희 쪽 추가 변경은 없습니다.

`0x81` 실패 경로에서도 강도값을 보내는 판단에 동의합니다. `0x12`는 값만 쓰므로
레지스터를 확정된 상태로 두는 편이 방치보다 낫습니다.

### §1.5에 대하여

**setpoint만 고쳤다면 온도는 잡히고 가열은 안 막혔을 것**이라는 발견이
이번 교환에서 가장 중요합니다.

`healingDone`이 `static bool = false`라 재부팅 시 자동으로 "힐링 대기"가 된다는
것은 **저희 쪽에서는 관측할 수 없는 사실**입니다. STM32 입장에서는 정상적인
FORCE_UP 진입 요청으로만 보입니다. 세션 중 착용 상태에서 힐링형 램프가 개시되는
경로였고, 저희가 Q35로 물었던 것보다 결과가 무겁습니다.

저희가 지적한 것은 `0x12`의 값이었고, 그 자리에서 **더 큰 것을 스스로 찾아
같이 고치신 것**입니다. 기록해 둘 가치가 있다고 봅니다.

램프 도중 재부팅 재현 시험이 미검증으로 남아 있다는 점도 확인했습니다.
그 시험은 STM32 쪽에서 도울 수 있습니다 — 필요하시면 `0x12` 수신값을 로그로
남기는 임시 빌드를 올리겠습니다. 복구 후 실제로 어떤 값이 들어왔는지
STM32 쪽 기록으로 교차 확인할 수 있습니다.

## 4. §6 — 승온율 확정. 보고 #05를 갱신했습니다

`initTempSleep = 32`가 의도된 값이라는 확인으로 환산이 확정됐습니다.

```
(64.3 - 32) / 2.676 s ≈ 12.1 °C/s
```

보고 #05 §5를 이 값으로 갱신했습니다. 오버슛 해석도 함께 조정됐습니다.

| 표본 | 오버슛 | 대응 시차 |
|---|---|---|
| set 80 → 81.0 | +1.0 °C | 약 83 ms |
| set 64 → 64.3 | +0.3 °C | 약 25 ms |

둘 다 **IR 센서 갱신주기 약 100 ms 이내**로 일관됩니다. 이 승온율에서
오버슛 상한은 **약 +1.2 °C**이며, 관측 최대값 +1.0이 이미 그 상한 근처입니다.

`MODE_TEMP_ABS_MAX = 85`와의 관계는 다음과 같습니다 — 설정값 85가 들어오면
실제 도달은 약 86입니다. **저희는 이 초과를 수용하기로 결정했습니다.**
히터가 교차 시점에 꺼지므로 발산이 아니라 유한한 열관성이고, 상한을 84로
낮추면 정상 동작점까지 함께 눌리기 때문입니다. 판단 근거를 `mode.h` 주석에
남겼습니다(`ad83adc`).

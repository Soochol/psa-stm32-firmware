# 사양 제안 — SD 로그 색인 "최근 예약" (`logIndexRecentReserve`)

> **제안**: STM32 팀 → ESP32 팀
> **대상 사양**: `ESP-STM32_SD_Logging_Extension` v1.8 — §6.3 `reqLogFiles` 관련
> **성격**: **STM32 내부 동작 변경 — 프레임·필드·길이 변경 없음**
> **그쪽 작업**: 없음. 확인 1건만 부탁드립니다 (§5)

---

## 0. 한 줄 요약

색인 128칸 중 **뒤 64칸을 "최근 파일 전용"으로 예약**해서, 회수가 밀려도
**최근 64개 파일은 항상 목록에 나오고 백필로 꺼낼 수 있게** 합니다.

---

## 1. 문제 — 색인이 차면 **최근 것부터** 가려집니다

색인(128칸)이 차면 그 뒤 파일은 이렇게 됩니다.

| 경로 | 결과 |
|---|---|
| `reqLogFiles(0x45)` | 목록에 나오지 않음 |
| `reqLogRead(0x44)` | **백필 불가** — bootId 조회부터 색인 기반입니다 |
| `ctrlLogDelete(0x57)` | **원격 삭제 불가** — 목록에 없으면 삭제 대상으로 받지 않습니다 |

즉 **보낼 수도, 지울 수도 없는** 상태가 됩니다. (데이터 자체는 카드에 온전히
남고, 카드를 빼면 전부 읽힙니다. 잃는 것은 UART 경로뿐입니다.)

문제는 **어느 파일이 가려지느냐**입니다. 현재 색인은 카드 디렉터리에서 읽히는
순서대로 앞에서부터 128개를 담습니다. FAT은 통상 생성 순서로 디렉터리 항목을
쌓으므로, 실질적으로 **오래된 128개가 색인되고 최신 파일이 잘려 나갑니다.**

현장 이슈를 조사할 때 필요한 것은 대개 최근 기록인데, **정확히 그것이 먼저
사라집니다.**

### 1.1 언제 도달하는가

파일은 **부팅마다 1개** 생기고, 가동 중에는 **1시간마다 1개**씩 늘어납니다.
자동 삭제는 없습니다 (카드가 차도 지우지 않고 기록을 멈추는 정책입니다).

운용 전제는 하루 10~20개 생성, **하루 1회 회수**입니다. 정상적으로 회수되면
카드에 20개 안팎만 남으므로 색인은 차지 않습니다. 회수가 멈추면:

| 하루 생성 | 128 도달 |
|---|---|
| 20개 | **약 6일** |
| 10개 | **약 13일** |

실측 참고로 그쪽 보고 #46이 69개, #65가 80개를 보고했습니다 — 이미 절반을
넘긴 상태입니다.

---

## 2. 제안 — 색인을 두 구역으로 나눕니다

```
현재:   [ ─────────── 앞에서부터 128칸 ─────────── ]   차면 이후 전부 버림
                                                        (버려지는 쪽 = 최신)

변경:   [ ── 오래된 64칸 ── ][ ── 최근 전용 64칸 ── ]
          회수·삭제 큐          항상 최신 64개 유지
```

- **앞 64칸** — 지금과 동일합니다. 오래된 것부터 채우며, 회수·삭제가 진행되는
  큐입니다. 이 구역이 있어야 오래된 파일이 지워질 수 있습니다.
- **뒤 64칸** — 최근 전용입니다. 새 파일이 등록되면 이 구역에서 **가장 오래된
  항목을 밀어내고** 자리를 내줍니다.

### 2.1 새로 생기는 보장

> **최근 64개 파일은 카드 상태와 무관하게 항상 `reqLogFiles`에 나오고
> `reqLogRead`로 꺼낼 수 있습니다.**

밀려난 파일은 사라지지 않습니다. 앞 구역이 회수·삭제되고 다음 부팅에서 색인이
다시 만들어지면 순서대로 올라옵니다. **순번 대기이지 손실이 아닙니다.**

---

## 3. 동작 상세 (STM32 내부 — 참고용)

### 3.1 부팅 스캔 — 2패스로 나눕니다

1. 디렉터리를 훑으며 **이름과 크기만** 읽습니다. 파일명이
   `<bootId:08X>_<fileIndex:04X>.psa`라 **파일을 열지 않고도** 신구를 판정할 수
   있습니다.
2. 앞 64칸은 지금처럼 즉시 담고, 그 뒤로는 **최신 64개 후보만** 유지합니다.
3. 순회가 끝난 뒤 후보 64개만 열어 헤더를 읽습니다.

**부팅 시간은 그대로입니다.** 비싼 작업(파일 열기 + 512 B 헤더 읽기) 횟수가
64+64 = **128번으로 현재와 같고**, 디렉터리 전수 순회는 지금도 하고 있습니다
(카드 파일 수를 세야 하므로 128에서 멈추지 않습니다).

그쪽 v1.8 §8.6 모델(`7.5 ms + 3.0 ms/file`) 기준 128개 = 약 **391 ms**,
변동 없습니다.

### 3.2 세션 중 등록 — 밀어내기를 적용합니다

파일이 닫힐 때(1시간 회전, 쓰기 실패 회전) 색인에 바로 등록하는 경로가
있습니다. 현재는 색인이 차 있으면 **등록이 거부**되어, 가동 중 쌓이는 최신
데이터가 그대로 가려집니다.

변경 후에는 색인이 차 있어도 **최근 구역에서 가장 오래된 항목을 밀어내고
등록**합니다. 앞 구역(회수 대기분)은 건드리지 않습니다. 이 부분이 없으면 예약
구역이 "부팅 시점의 최신 64개"로 굳어버려 §2.1의 보장이 성립하지 않습니다.

### 3.3 삭제 — 변경 없습니다

색인에 있는 파일만 삭제 대상이며, 삭제되면 항목이 빠집니다. 비워진 칸은 다음
부팅 스캔에서 다시 채워집니다 (현재와 동일 — 삭제 즉시 카드의 다른 파일이
그 자리로 올라오지는 않습니다).

### 3.4 유지되는 불변식

- **파일 번호 이어쓰기 검사는 전수 유지합니다.** 같은 bootId가 이미 쓴 최대
  fileIndex를 찾는 검사는 색인 상한과 무관하게 카드 전체를 봅니다. 이걸 64개로
  제한하면 새 파일이 기존 파일 번호를 재사용해 **덮어쓰기**가 발생합니다 —
  숨김이 아니라 실제 데이터 손실입니다. 현재 코드도 같은 이유로 이 검사만
  상한 밖에 두고 있습니다.
- 색인은 `(bootId, fileIndex)` **오름차순 정렬을 유지**합니다.

## 4. 와이어에서 보이는 변화 — 이것만 알아 두시면 됩니다

**프레임·필드·길이 변경이 없습니다.** 관측 가능한 차이는 딱 하나입니다.

> `reqLogFiles(0x45)` 목록의 항목들이 **연속하지 않을 수 있습니다.**
> 앞 구역과 최근 구역 사이에 `(bootId, fileIndex)`가 건너뛰는 구간이 생깁니다.

이미 발생 가능한 상태입니다 — 중간 파일을 삭제하면 지금도 같은 모양이 됩니다.
**새로운 종류의 응답이 아닙니다.**

| 항목 | 변화 |
|---|---|
| `0x45` 응답 형식·페이지네이션 | 변화 없음 |
| `0x43` `filesOnCard` (오프셋 21) | 변화 없음 — 카드의 실제 파일 수 |
| `0x43` `indexCapacity` (오프셋 23) | **계속 128** — "총 칸 수"라는 의미 그대로 |
| "목록 밖 개수" = `filesOnCard` − 목록 수 | **그대로 성립** |
| `0x44`로 구멍 구간을 요청하면 | **result 1 또는 2 (없음)** — 기존과 동일. bootId 자체가 목록에 없으면 1, 해당 seq를 담은 파일이 없으면 2 |
| `evtLogError` reason 6 (색인 넘침) | 그대로. detail은 카드 실제 파일 수 |

백필의 파일 판정은 항목마다 `firstSeq <= seq <= lastSeq` **범위 검사**로
이뤄지므로, 목록 중간의 구멍이 **오조회를 만들지 않습니다.** 구멍에 해당하는
요청은 엉뚱한 파일이 아니라 "없음"으로 정확히 응답합니다.

---

## 5. 그쪽에서 확인해 주실 것 (1건)

목록을 **"가장 오래된 것부터 연속 N개"** 라고 가정한 부분이 있는지만 봐
주십시오.

- 화면 문구에 "오래된 순 N개" 류가 있다면 정확하지 않게 됩니다.
- 목록의 첫 항목과 마지막 항목 사이를 **연속 구간으로 계산**하는 코드가 있다면
  영향을 받습니다.

없으시면 **아무 수정도 필요 없습니다.**

## 6. 왜 64인가

| 예약 칸 | 확보되는 최근분 (하루 20개 기준) |
|---|---|
| 24 | 약 1.2일 |
| 32 | 약 1.6일 |
| **64** | **약 3.2일** |

회수 주기가 하루이므로 하루치(20개)면 최소 요건은 충족됩니다. 다만 이 기능이
필요해지는 상황이 바로 **회수가 밀린 상황**이라, 며칠 비어도 최근 기록이
남도록 여유를 크게 잡았습니다.

**분할 비율은 회수 처리량에 영향이 없습니다.** 목록은 어떤 비율이든 항상
128개이고, 한 회수 주기에 꺼내서 지울 수 있는 양도 **128개로 동일**합니다.
카드가 300개까지 밀렸을 때 정상으로 돌아오는 데 걸리는 회수 횟수도 같습니다.
비율은 "속도"가 아니라 **"무엇을 먼저 보여줄지"** 만 정합니다. 그래서 예약을
늘리는 비용이 사실상 없습니다.

## 7. 호환성·배포 순서

- **그쪽 수정이 필요 없으므로 배포 순서는 무관합니다.**
- 구형 STM32와 섞여도 무방합니다 — 프레임이 동일하고 목록 구성만 다릅니다.
- **아직 구현 전입니다.** 이견이 없으면 다음 릴리스에 넣겠습니다. 버전 규칙에
  따라 개발 중에는 `1.0.1-dev`로 응답합니다 (보고 #68).

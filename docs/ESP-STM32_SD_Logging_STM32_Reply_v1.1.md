## 0. 요약

v1.1의 백필 설계(`0x44` / `0x45` / `0x71`)는 **타당하며 채택합니다.**
운영 조건(배터리 임의 교체, BLE 체류 미보장)에서 물리 회수 전제를 버린 판단이 옳고,
§6.4의 과거 `bootId` 읽기를 필수 요구사항으로 못 박은 것,
§9.2에서 청크별 ACK를 없앤 것, §9.3의 라이브 우선순위 모두 적절합니다.
§13 시나리오 10을 핵심 검증 항목으로 지정하신 것도 정확한 판단입니다.

프레임 예제 7종(`0x45` 요청·응답, `0x44` 요청·ACK, `0x71` END·ACK, §3.2 정답)의
체크섬과 LEN을 전부 재검산했으며 **모두 일치**합니다.

다만 **구현 착수 전에 반드시 해소해야 할 2건**이 있습니다.

| # | 항목 | 성격 |
|---|------|------|
| **A** | **§6.4 산술 오프셋이 §7 길이 계약과 모순됩니다.** 레코드를 하나라도 드롭하면 그 파일의 이후 모든 백필 조회가 어긋납니다 | **원인은 저희 v1.0 회신 §1.5입니다. 해당 문구를 철회하고 대체안을 제시합니다** |
| **B** | **v1.0 회신 갱신본의 정정 ⑧이 반영되지 않았습니다.** 그 결과 §12의 게이팅 조건이 **구현 불가능한 상태**입니다 | 저희 전달 누락 가능성이 있어 재송부합니다 |

Q10~Q13은 전부 답변 가능합니다. 요지만 먼저 적으면:

- **Q10** `_USE_EXPAND = 0`. 활성화는 가능하나 **§10.3 개정이 동반되어야 하며, 1차 구현에서는 비활성 권장**
- **Q11** "읽기는 DMA라 쓰기보다 유리하다"는 전제가 **틀렸습니다.** 호출자는 완료까지 busy-wait합니다
- **Q12** 부팅 시 1회 스캔 + RAM 인덱스 채택. RAM 여유 충분
- **Q13** `_FS_REENTRANT = 0` 유지가 맞습니다. 다만 **`_FS_LOCK = 2`가 백필과 정확히 충돌**합니다

## 1. 🔴 최우선 ① — §6.4 산술 오프셋과 §7 길이 계약이 모순됩니다

### 1.1 문제

§6.4는 백필 조회를 산술로 처리합니다.

```
레코드 오프셋 = 512 + (startSeq - firstSeq) × 80
```

> "고정 크기 레코드이므로 **순차 탐색 없이 산술로 위치를 구할 수 있습니다.**"

이 식이 성립하려면 다음 불변식이 반드시 참이어야 합니다.

> **파일 안의 n번째 레코드의 seq는 정확히 `firstSeq + n` 이다.**

그런데 §7의 길이 계약이 이 불변식을 깨뜨립니다.

> "레코드 조립 시점에 `statPayload` 길이가 64가 아니면 **레코드를 드롭하고** `writeErrorCount` 증가"

레코드를 하나라도 드롭하면 그 지점 이후 **파일 오프셋과 seq의 대응이 80 B씩 어긋납니다.**

### 1.2 왜 조용한 실패가 되는가

STM32는 요청받은 `startSeq` 위치를 산술로 계산해 읽고, 그 자리에 있는 레코드를 그대로 보냅니다.
레코드는 자기 `seq`를 오프셋 0에 갖고 있으므로 **PC가 받는 레코드의 seq는 요청한 값과 다릅니다.**

PC 입장에서 벌어지는 일:

1. `seq = 123456` 요청 → `seq = 123457`부터 시작하는 데이터 수신
2. PC는 `123456`이 여전히 미확보라고 판단 → 재요청
3. 다시 같은 어긋난 데이터 수신 → **무한 재요청 루프**

또는 PC가 seq를 신뢰해 그대로 병합하면 요청 구간과 실제 구간이 어긋난 채
**아무도 눈치채지 못하는 부분 유실**이 됩니다. §13 시나리오 10을 통과하고도 발생할 수 있습니다.

### 1.3 원인은 저희 회신입니다 — v1.0 회신 §1.5 철회

이 "드롭" 규칙은 **저희 v1.0 회신 §1.5에서 제안한 것**이며, v1.1 §7이 그대로 반영한 것입니다.
당시에는 백필이 비범위였기에 드롭이 안전한 선택이었으나,
**§6.4가 산술 조회를 도입한 이상 더 이상 성립하지 않습니다.**

> **v1.0 회신 §1.5의 "레코드를 드롭하고 `writeErrorCount` 증가" 문구를 철회합니다.**
> 아래 §1.4로 대체해 주십시오. ESP32 팀의 기술 오류가 아닙니다.

### 1.4 대체안 — 드롭하지 말고 **플레이스홀더 레코드**를 기록합니다

길이 계약이 위반되면 레코드를 버리는 대신 **자리를 채웁니다.**

| 필드 | 플레이스홀더 값 |
|------|-----------------|
| `seq` (0) | **정상 값** — 불변식 유지의 핵심 |
| `tickMs` (4) | 정상 값 |
| `statPayload` (8..71) | **0x00 채움** |
| `deviceMode` (72) | 정상 값 |
| `flags` (73) | **bit1 = 1 (무효 샘플)** — 신규 정의 요청 |
| `errorMask` (74) | 정상 값 |
| `crc16` (78) | **정상 계산** (레코드 자체는 유효해야 백필 경로가 걸러내지 않음) |

동시에 `writeErrorCount`를 증가시켜 §12 헬스 리포트에 드러나게 합니다.

**효과**

- 파일 오프셋 ↔ seq 불변식이 **어떤 상황에서도 유지**됩니다
- PC 병합 도구는 `flags` bit1로 무효 샘플을 식별해 유실률 통계에 반영할 수 있습니다
  (기존 §10.3의 "CRC 불일치 → 갭으로 계수"와 동일한 취급)
- STM32 구현이 오히려 단순해집니다 — 분기 없이 항상 80 B를 씁니다

### 1.5 검토했으나 기각한 대안

| 대안 | 기각 사유 |
|------|-----------|
| 산술 조회 후 seq를 검증하고 불일치 시 선형 탐색 | 블로킹 diskio 경로에 **상한 없는 읽기**가 실립니다. Q11(제어 루프 부하) 관점에서 채택 불가 |
| 파일 헤더에 갭 테이블 유지 | 기록 완료된 파일을 수정하게 되어 §8.5 "STM32는 로그 파일을 절대 수정하지 않는다"에 위배 |

### 1.6 §1.4와 함께 문서에 명시 요청

§6.4 또는 §7에 다음 한 문장을 넣어 주십시오. 백필 설계 전체가 여기에 걸려 있습니다.

> **불변식**: 파일 내 n번째 레코드의 `seq`는 정확히 `firstSeq + n` 이다.
> 이를 만족시킬 수 없는 상황에서는 **플레이스홀더 레코드를 기록하거나 파일을 로테이션**해야 하며,
> 레코드를 건너뛰어서는 안 된다.

§10.4의 카드 재삽입은 `fileIndex`를 올려 새 파일로 가므로(§8.3) 이 불변식과 충돌하지 않습니다.

## 2. 🔴 최우선 ② — 정정 ⑧ 미반영, §12 게이팅이 구현 불가입니다

### 2.1 전달 경위

v1.0 회신 송부 후 **정정 ⑧을 추가한 갱신본**을 보내드렸는데,
v1.1 변경 이력이 "정정 ①~⑦ 전부"로 기재되어 있어 갱신본이 도달하지 않은 것으로 보입니다.
아래에 재송부합니다.

### 2.2 §7 `deviceMode` 정의가 실제 범위를 담지 못합니다

v1.1 §7 (오프셋 72)은 여전히 **"0=SLEEP ~ 4=FORCE_DOWN"** 입니다.

**(a) 두 개의 서로 다른 열거형이 존재합니다**

| 값 | `e_modeID_t` (STM32 내부, `mode.h:130-140`) | `e_ESP_EVT_MODE_t` (프로토콜, `comm_esp.h:27-35`) |
|---|---|---|
| 0 | `modeBOOTING` | `SLEEP` |
| 1 | `modeHEALING` | `WAITING` |
| 2 | `modeWAITING` | `FORCE_UP` |
| 3 | `modeFORCE_UP` | `FORCE_ON` |
| 4 | `modeFORCE_ON` | `FORCE_DOWN` |
| 5 | `modeFORCE_DOWN` | `TEST` |
| 6 | `modeSLEEP` | `ERROR` |
| 7 | `modeOFF` | — |
| 8 | `modeERROR` | — |
| 9 | `modeTEST` | — |
| 10 | `modeWAKE_UP` | — |

§7이 "0=SLEEP"이라 했으므로 **프로토콜 열거형 기준**입니다.
STM32는 기록 시 내부 ID → 프로토콜 코드로 **변환**해야 하며, 문서에 이를 명시해 주십시오.
변환을 빠뜨리면 `modeWAITING(2)`가 `FORCE_UP(2)`으로 기록되는 등 **조용히 어긋납니다.**

**(b) 상한이 4가 아니라 5입니다** — TEST 모드는 샘플링을 수행하므로(`mode.c:2594`)
`deviceMode = 5 (TEST)` 레코드가 CRC 정상 상태로 카드에 남습니다.

**(c) HEALING은 프로토콜 대응 값이 아예 없습니다** — 부팅 직후 약 1초짜리 전이 상태이며
(`mode.c:1554` 진입, `mode.h:345` `MODE_HEALING_INITIAL_TOUT 1000`),
`v_Mode_Healing()`은 샘플링은 하지만(`mode.c:1667`) `v_ESP_Send_EvtModeChange()`를 호출하지 않습니다.
evtMode 송신 지점은 `mode.c:1698 / 1783 / 1864 / 1951 / 2035 / 2333 / 2455` 7곳뿐이며 Healing은 없습니다.

→ **매 부팅 약 10개 레코드가 대응 코드 없는 상태로 기록됩니다.**

### 2.3 그 결과 §12의 게이팅 조건이 구현 불가능합니다 🔴

v1.1 §12는 다음과 같이 규정했습니다.

> ESP32 측 경보 조건은 `deviceMode ∈ {ERROR, BOOTING, WAKE_UP, OFF}` 일 때 억제로 구현합니다.

**그런데 `BOOTING` / `WAKE_UP` / `OFF`는 `e_ESP_EVT_MODE_t`에 값이 없고,
해당 모드에서 `evtMode(0x82)`가 송신되지도 않습니다.**
ESP32는 이 세 모드를 **관측할 방법이 없으므로** 위 조건을 구현할 수 없습니다.

문제의 실체는 더 나쁩니다. `modeOFF`에서는 센싱이 멈추므로(`mode.c:2074`, `i_mode_off = 1`)
`lastSeq`가 정체되는데, ESP32는 마지막으로 받은 evtMode(예: `WAITING`)를 그대로 믿고 있어
**전원이 켜진 채 OFF 상태로 놓인 장치가 계속 오경보를 냅니다.** §12가 막으려던 바로 그 상황입니다.

### 2.4 해결안 — `reqLogStatus`(0x43) 응답에 `deviceMode`를 추가

evtMode 추적에 의존하지 말고 **STM32가 현재 모드를 직접 보고**하는 것이 근본 해법입니다.

**§6.2 응답 DATA를 20 B → 21 B로 확장**

| 오프셋 | 크기 | 필드 | 비고 |
|--------|------|------|------|
| 0..19 | 20 | *(기존과 동일)* | **변경 없음** |
| **20** | **1** | **`deviceMode`** | **신규.** §7 오프셋 72와 동일한 코드계 |

- STM→ESP 상한 90 B 이내이므로 여유가 충분합니다
- ESP32는 LEN으로 파싱하므로 기존 파서에 영향이 없습니다
- 게이팅이 `evtMode` 추적에서 **완전히 독립**해집니다 — ESP32 재부팅 직후에도 즉시 정확합니다
- §12의 `deviceMode ∈ {…}` 조건이 그대로 구현 가능해집니다

**함께 요청드리는 열거형 확장** (`e_ESP_EVT_MODE_t`)

| 값 | 이름 | 샘플링 | 비고 |
|---|------|--------|------|
| 0~4 | SLEEP / WAITING / FORCE_UP / FORCE_ON / FORCE_DOWN | ✅ | 기존 |
| 5 | TEST | ✅ | 기존. **기록됨 — §7 범위에 포함 필요** |
| 6 | ERROR | ❌ | 기존 |
| **7** | **HEALING** | ✅ | **신규 요청** |
| **8** | **BOOTING** | ❌ | 신규 요청 (0x43 응답 전용, evtMode 송신은 선택) |
| **9** | **WAKE_UP** | ❌ | 상동 |
| **10** | **OFF** | ❌ | 상동 |

7~10을 추가하시면 STM32 측에서 `v_Mode_Healing()`에 `evtMode` 송신도 함께 넣겠습니다.

> **최소안**: 7~10 추가가 부담스러우시면 **`0xFF = UNKNOWN`** 하나만 정의해도 §2.3의
> 오경보는 막을 수 있습니다(샘플링 정지 모드를 전부 `0xFF`로 보고). 다만 관제 해상도가 떨어집니다.
> **권장은 7~10 전체 추가입니다.**

## 3. §14.2 신규 확인 항목 답변 (Q10~Q13)

### Q10. `_USE_EXPAND` 활성 여부 → **비활성. 활성화 가능하나 1차 구현에서는 권장하지 않습니다**

`FATFS/Target/ffconf.h:66`

```c
#define	_USE_EXPAND		0
```

FatFs R0.12c에 `f_expand()` 자체는 포함되어 있으므로(`ff.h:267`) 플래그만 켜면 사용 가능합니다.
다만 **문서 개정이 동반되어야 합니다.**

#### ⚠️ `f_expand()`는 파일 크기를 선할당 크기로 **즉시** 설정합니다

`ff.c:5204-5210`

```c
if (opt) {                          /* opt = 1 : 실제 할당 */
    fp->obj.sclust  = scl;
    fp->obj.objsize = fsz;          /* ← 파일 크기가 곧바로 fsz가 됨 */
    ...
}
```

이 때문에 §10.3의 절삭 공식이 무너집니다.

```
유효 레코드 수 N = (파일크기 - 512) / 80
```

선할당분이 전부 레코드로 계수되고, **Q12의 "파일 크기로부터 `lastSeq` 산출"도 함께 깨집니다.**
전원이 갑자기 끊기면 닫지 못한 파일이 선할당 크기 그대로 남으므로 실제 데이터 경계를 알 수 없습니다.

#### 도입 시 필요한 개정

| # | 내용 |
|---|------|
| 1 | §10.3을 **close 시 `f_truncate()` + CRC 기반 유효범위 판정**으로 개정 |
| 2 | 비정상 종료 파일에 대한 유효 경계 판정 규칙 신설 (선할당 영역은 0x00이므로 CRC 불일치로 걸러짐) |
| 3 | 단편화된 카드에서 `f_expand()` 실패 시 **일반 append로 폴백**하는 경로 명시 |
| 4 | `f_expand()`는 **빈 파일에만** 적용 가능 (`ff.c:5153`, `objsize != 0` 이면 `FR_DENIED`) → 파일 생성 직후 호출 |

#### 권장 — 1차 구현은 비활성 유지

Q5에서 이미 확인했듯 2초 flush는 회당 **1,600 B (3~4 섹터)** 로,
현행 10초/5,600 B 대비 피크가 1/3 이하입니다. `f_sync()`의 FAT·디렉터리 갱신 오버헤드를
얹어도 이 규모에서는 감당 가능한 범위로 판단합니다.

**§13 시나리오 8에서 실측한 뒤, 여유가 부족하면 그때 도입**하는 순서를 제안합니다.
위 4건의 개정 비용이 선불로 발생하므로, 필요성이 확인되기 전에는 도입하지 않는 편이 낫습니다.

### Q11. 백필 `f_read()`의 제어 루프 부하 → **전제가 틀렸습니다. DMA여도 호출자는 블로킹됩니다**

§14.2 Q11은 *"읽기 경로에 DMA가 이미 적용되어 있으니 쓰기보다 유리할 것"* 으로 보셨는데,
**DMA는 CPU가 바이트를 복사하지 않게 해줄 뿐 호출자를 해방시키지 않습니다.**

`FATFS/Target/sd_diskio.c:212-233`

```c
if(BSP_SD_ReadBlocks_DMA(...) == MSD_OK)
{
    ReadStatus = 0;
    timeout = HAL_GetTick();
    while((ReadStatus == 0) && ((HAL_GetTick() - timeout) < SD_TIMEOUT))
    {
        v_SD_BusyWait_Yield();        /* ← busy-wait */
    }
    ...
    while((HAL_GetTick() - timeout) < SD_TIMEOUT)  /* 카드 TRANSFER 복귀 대기 */
```

**제어 루프 관점에서는 읽기도 쓰기와 동일하게 블로킹입니다.**

#### 정상 부하는 문제없습니다

| 항목 | 값 |
|------|-----|
| 백필 목표 | 123.7 레코드/s = **9,896 B/s** |
| SDMMC 4비트 39.2 MHz 이론 대역 | 약 19.6 MB/s |
| 대역 점유율 | **약 0.05%** |
| 섹터 읽기 횟수 (512 B당 6.4 레코드) | 약 19.3 회/s |
| 회당 오버헤드 추정 | 수백 µs |
| **정상 상태 블로킹 점유율** | **1% 미만** |

전송량 자체는 전혀 부담이 아닙니다. **문제는 최악의 경우와 부수 효과 두 가지**입니다.

#### 🔴 위험 ① — `SD_TIMEOUT`이 30초입니다 (IWDG 2초)

`FATFS/Target/sd_diskio.c:41`

```c
#define SD_TIMEOUT 30 * 1000
```

카드가 물리다 멈추면 FatFs 타임아웃(30초)이 오기 **훨씬 전에 워치독 리셋(2초)** 이 발생합니다.
즉 현재 구조에서 SD 이상은 **자세 제어를 끌어안고 리셋되는** 형태로 나타납니다.

**대책 (STM32 측 수정)**: `SD_TIMEOUT`을 **1초 이하로 축소**합니다.
그러면 최악의 블로킹이 IWDG 2초 이내에 들어와 워치독 리프레시 없이도 안전하고,
타임아웃이 `evtLogError(3)` 경로로 자연스럽게 흘러갑니다.

> ⚠️ **busy-wait 안에서 IWDG를 리프레시하는 방식은 채택하지 않습니다.**
> 그렇게 하면 카드가 멈춘 30초 동안 워치독이 계속 먹이를 받아 **자세 제어가 30초간 정지**합니다.
> 로깅보다 안전 기능이 우선이므로, 개를 먹이는 대신 **블로킹 자체를 짧게 자릅니다.**

#### 🔴 위험 ② — SD 블로킹 중 UART TX가 굶습니다

UART 송신은 DMA + 링버퍼 구조인데, **다음 전송을 이어 거는 주체가 메인 루프**입니다.

- `HAL_UART_TxCpltCallback()` (`uart.c:113-120`)은 `e_espTx = COMM_STAT_DONE` 플래그만 세웁니다
- 실제 다음 DMA 기동은 `v_Uart_ESP_Handler()` (`uart.c:243-256`) — 메인 루프에서만 호출 (`main.c:385`)
- TX 링버퍼는 **256 B** (`uart.c:55`)

256 B는 115200 bps에서 **약 22 ms 분량**입니다.
SD 읽기가 22 ms 이상 메인 루프를 잡으면 DMA가 완료된 뒤 후속 전송이 걸리지 않아
**회선이 idle 상태로 낭비**되고, 12.4배 배율이 그만큼 깎입니다.

**대책 (STM32 측 수정, 2건)**

| # | 조치 | 근거 |
|---|------|------|
| 1 | `UART_ESP_TX_ARR_SIZE`를 **256 B → 2 KB**로 확대 | 약 178 ms 분량 확보. RAM_D1 320 KB 대비 무시 가능 |
| 2 | `v_SD_BusyWait_Yield()`에서 **TX 링버퍼 드레인만** 수행 | 블로킹 중에도 회선을 채움 |

`v_SD_BusyWait_Yield()` 훅은 **이미 존재합니다.** `sd_diskio.c:114`에 weak 정의가 있고
`sd_diskio.c:129, 221, 235, 268` 4곳에서 호출되며,
`tim.c:78`에 강한 정의가 있으나 현재는 RTT 하트비트만 찍습니다.

```c
// User/Drv/src/tim.c:77-80 (현재)
void v_SD_BusyWait_Yield(void) {
    v_Tim_1s_Test();
}
```

> ⚠️ **이 훅에서 `v_Uart_Handler()`를 통째로 부르면 안 됩니다.**
> `v_Uart_Handler()` → `v_ESP_Handler()` → 수신 디스패치로 이어지는데,
> 이 훅은 `f_read()`의 busy-wait **안에서** 실행됩니다.
> 그 순간 `reqLogRead`가 도착하면 **FatFs가 재진입**하게 되고,
> `_FS_REENTRANT = 0` 환경에서는 볼륨이 손상될 수 있습니다 (Q13 참조).
> **TX 링버퍼 드레인 코드만 분리해서 호출**해야 합니다.

> ⚠️ **훅이 읽기 경로만 덮고 있습니다.** 4개 호출 지점 중 `sd_diskio.c:221, 235, 268`은
> `SD_read()` 안이고, `:129`는 두 경로가 공유하는 `SD_CheckStatusWithTimeout()`입니다.
> **`SD_write()` 자체의 대기 루프(`sd_diskio.c:353, 366, 400`)에는 훅이 없습니다.**
> flush 쓰기는 회당 1,600 B(3~4섹터)로 짧아 영향이 작지만,
> 대칭성을 위해 쓰기 루프에도 동일 훅을 추가하겠습니다.

#### 결론

| 항목 | 판정 |
|------|------|
| 정상 상태 부하 | ✅ 문제없음 (1% 미만) |
| §13 시나리오 8·12 통과 가능성 | ✅ 위 3건(`SD_TIMEOUT` 축소, TX 버퍼 확대, 훅 강화) 적용 시 가능 |
| 조치 없이 착수 | ❌ 워치독 리셋 및 처리량 미달 위험 |

실측값은 §13 시나리오 8·12에서 확보하여 별도 공유하겠습니다.

### Q12. `reqLogFiles`(0x45) 목록 산출 방식 → **부팅 시 1회 스캔 + RAM 인덱스** (제안하신 방식 채택)

#### RAM 여유 (`STM32H723VGTX_FLASH.ld:51-59`)

| 영역 | 크기 | 현재 용도 |
|------|------|-----------|
| `RAM_D1` | **320 KB** | 일반 BSS/데이터 |
| `DTCMRAM` | 128 KB | |
| `RAM_D2` | 16 KB | `FATFS` 객체 (`sd.c:22`, `.my_d2_section`) |
| `RAM_NOCACHE_D2` | 16 KB | UART DMA 버퍼 |

인덱스 항목은 14 B(`bootId` 4 + `firstSeq` 4 + `lastSeq` 4 + `fileIndex` 2)이므로
**256개 상한을 잡아도 3.6 KB**입니다. 여유는 충분합니다.

> 참고로 `_FS_TINY = 0` (`ffconf.h:206`), `_MAX_SS = 4096` (`ffconf.h:178`) 이므로
> **열린 `FIL` 핸들 하나당 약 4 KB 섹터 버퍼**가 붙습니다.
> 백필 도입으로 핸들이 2개(쓰기 1 + 읽기 1)가 되므로 **약 8 KB**를 추가로 잡아 두겠습니다.

#### 산출 절차

```
부팅 시 1회:
  f_opendir("/LOG/<deviceIdHex>")
  각 항목에 대해:
    - 파일명에서 bootId, fileIndex 파싱
    - f_open + 헤더 512 B 읽기 → magic/headerCrc 검증 → firstSeq 획득
    - lastSeq = firstSeq + (f_size - 512) / 80 - 1
    - f_close
  bootId 오름차순, fileIndex 오름차순 정렬 (§6.3 규정)
```

- 파일 수 N에 대해 `f_open + 512 B + f_close` × N. 항목당 약 1 ms 추정,
  **50개여도 약 50 ms**로 부팅 시 IWDG(2초) 대비 여유가 충분합니다
- 스캔 중에는 핸들을 1개씩만 열고 닫으므로 `_FS_LOCK` 제약에 걸리지 않습니다
- **현재 기록 중인 파일의 `lastSeq`는 RAM에서 실시간 갱신**하고 파일 크기를 신뢰하지 않습니다
- 로테이션 시 인덱스에 1항목 추가 (재스캔 없음)

> ⚠️ `lastSeq`를 파일 크기에서 유도하는 것은 **§1.6의 불변식이 성립할 때만 유효**합니다.
> 플레이스홀더 방식(§1.4)을 채택해야 이 산출이 성립합니다.

#### 상한 초과 시

인덱스가 상한(256)을 넘으면 **가장 오래된 항목부터 인덱스에서만 제외**하고,
`totalCount`에는 인덱스에 담긴 수를 보고합니다.
파일 자체는 삭제하지 않으므로 물리 회수(예비 경로)로는 여전히 회수 가능합니다.
문서 §6.3에 이 동작을 한 줄 명시해 주시면 좋겠습니다.

### Q13. FatFs 동시성 → **`_FS_REENTRANT = 0` 유지가 맞습니다. 단 `_FS_LOCK = 2`가 충돌합니다**

#### `_FS_REENTRANT`은 그대로 둡니다

`FATFS/Target/ffconf.h:241-243`

```c
#define _FS_REENTRANT    0
#define _FS_TIMEOUT      1000
#define _SYNC_t          NULL
```

이 펌웨어는 **RTOS 없는 슈퍼루프**입니다. FatFs 호출이 전부 메인 루프 한 곳에서만
일어난다면 스레드 경합 자체가 없으므로 재진입 지원은 불필요하며,
켜면 `_SYNC_t` 구현(뮤텍스)을 요구해 오히려 부담입니다.

**같은 볼륨에 쓰기 핸들과 읽기 핸들을 동시에 여는 것은 `_FS_REENTRANT = 0`에서도 안전합니다** —
호출이 인터리브되지 않기 때문입니다.

#### 🔴 다만 안전 조건이 있습니다

> **모든 FatFs 호출은 메인 루프에서만 발생해야 합니다.**
> ISR에서 호출 금지, 그리고 **`v_SD_BusyWait_Yield()` 안에서 호출 금지**입니다 (Q11 참조).

이 조건이 깨지는 유일한 현실적 경로가 Q11에서 지적한
"훅에서 `v_Uart_Handler()` 호출 → 수신 디스패치 → `reqLogRead` 처리 → FatFs 재진입"입니다.
훅은 **TX 드레인만** 수행하도록 구현하겠습니다.

#### 🔴 `_FS_LOCK = 2`는 백필과 정확히 충돌합니다

`FATFS/Target/ffconf.h:230`

```c
#define _FS_LOCK    2     /* 동시에 열 수 있는 파일/디렉터리 수 */
```

초과 시 `f_open()`이 `FR_TOO_MANY_OPEN_FILES`를 반환합니다 (`ff.h:233`).

백필 도입 후 동시 오픈 수요:

| 상황 | 필요 핸들 | 판정 |
|------|-----------|------|
| 평상시 로깅 | 쓰기 1 | ✅ |
| 백필 진행 중 | 쓰기 1 + 읽기 1 = **2** | ⚠️ **정확히 한계** |
| 백필 중 파일 로테이션 | 쓰기(구) + 쓰기(신) + 읽기 = **3** | ❌ **초과** |
| `f_opendir` 병용 | +1 | ❌ **초과** |

**대책 (STM32 측 수정, 2건)**

1. `_FS_LOCK`을 **2 → 4**로 상향 (항목당 오버헤드는 12 B 남짓으로 무시 가능)
2. 로테이션은 **"구 파일 close → 신 파일 open"** 순서를 강제
   (신 파일을 먼저 열면 순간적으로 3개가 됩니다)

문서 §8.3 로테이션 규칙에 이 순서를 한 줄 명시해 주시면 구현 계약이 명확해집니다.

## 5. 소소한 정정

### 5.1 §10.3 — "불완전 레코드 → END `result=0`"이 완료와 구분되지 않습니다

> "§6.4 백필 시에도 동일: 불완전 레코드는 송신하지 않고 END(`result=0`)로 종료합니다."

`result=0`은 §6.5에서 **"완료"** 로 정의되어 있습니다. PC는 요청 구간을 전부 받았다고 판단하고
재요청하지 않는데, 실제로는 파일 끝의 불완전 레코드 때문에 조기 종료된 것입니다.

**요청**: 둘 중 하나로 정리해 주십시오.

- `result=0`의 정의를 **"요청 범위 중 장치가 보유한 분량을 전부 송신"** 으로 명확화 (PC는 `lastSeqSent`로 판단)
- 또는 `result=5` (파일 끝 도달 / 보유분 소진) 신설

전자가 더 간단합니다. `lastSeqSent`가 이미 있으므로 PC는 그 값으로 잔여를 계산할 수 있습니다.

### 5.2 §1.4 — 백필 가용 대역 계산에 수신 방향이 섞여 있습니다 (실무 영향 없음)

> 라이브 STAT + ACK: (70 + 6) B × 10 Hz = 760 B/s

UART는 **전이중**이라 STM32 TX와 RX가 물리적으로 별개 선입니다.
ACK 6 B는 ESP→STM 방향이므로 **STM32 TX 대역을 소비하지 않습니다.**

정확히는 TX 가용 대역 = 11,520 − 700 = **10,820 B/s** 입니다.
문서 값(10,760)이 더 보수적이므로 **설계 결론은 그대로 유효**합니다. 참고만 부탁드립니다.

### 5.3 §3.4 STATUS 항목 — 지적 정확합니다

> "STATUS는 등가 비교(`u8_cmd == ESP_CMD_STAT`)라 비교 방식 자체를 범위로 바꿔야 합니다."

`comm_esp.c:173`이 정확히 그렇습니다. 반영하겠습니다.
`v_ESP_RxAck()`(`comm_esp.c:314-318`)도 현재 `ESP_CMD_STAT` 등가 비교이므로 함께 손봅니다.

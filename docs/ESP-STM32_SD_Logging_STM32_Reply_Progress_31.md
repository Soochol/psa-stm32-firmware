## 1. §2 조건 분기 — 실물 검증 없이도 확정할 수 있습니다

미검증으로 남기셨는데, **코드에서 불변식이 성립합니다.**

### 1.1 조건

```
detail > 한도  →  개수 인용
그 외          →  "filesOnCard 를 보라"
```

### 1.2 수정된 펌웨어에서는 항상 `detail > 한도`입니다

발화 지점이 둘이고, 양쪽 다 조건을 만족합니다.

**① 세션 중 등재** ([sd.c:997](../User/Drv/src/sd.c:997))

파일은 **생성 시점에** 카운터를 올립니다 ([sd.c:563](../User/Drv/src/sd.c:563)).

```
파일 생성 → u16_logFilesOnCard++ → 기록 → 닫힘 → v_log_idx_add → 한도 초과 → 발화
```

발화 시점에는 **그 파일까지 이미 세어져 있습니다.** 인덱스가 128로 찼다는 것은
그 파일이 129번째라는 뜻이므로 `detail ≥ 129 > 128`입니다.

**② 부팅 스캔** ([sd.c:1116](../User/Drv/src/sd.c:1116))

```c
if(u32_seen > u16_logIdxCnt){ ... }
```

발화 조건 자체가 `u32_seen > u16_logIdxCnt`이고, 인덱스가 찼다면
`u16_logIdxCnt == 128`이므로 `detail = u32_seen > 128`입니다.

### 1.3 따라서 else 분기는 구형 펌웨어 전용입니다

**수정된 펌웨어로는 그 분기에 들어갈 수 없습니다.** 의도하신 그대로입니다 —
구형 빌드가 섞였을 때만 발동하고, 그때는 개수를 인용하지 않습니다.

**조건을 두신 판단이 맞습니다.** 저희가 `detail`의 의미를 바꿨으므로 구형과 신형이
같은 필드에 다른 것을 싣는 구간이 실재하고, 그것을 값으로 구분하신 것입니다.

실물 확인은 다음에 축소 빌드를 올릴 일이 있을 때 **저희가 함께 보겠습니다.**
그쪽 말씀대로 급하지 않습니다 — 상태 쪽이 계속 정확한 값을 줍니다.

## 2. §3 · §4 · §5 — 확인

### §3 무응답 종결

> 저희가 매번 "재현되면 알리겠다"고만 하고 적재 시점과 대조해 볼 생각을 하지
> 않은 것이 늦어진 이유입니다.

저희도 같습니다. **적재할 때마다 이 창이 열린다는 것을 알면서** 세 라운드 동안
말씀드리지 않았습니다. 보고 #26에서 기전을 설명하면서도 "앞으로 알리겠다"는
말은 보고 #30에 가서야 했습니다.

`bootId 56 → 95`를 단서로 쓰지 않으셨다고 하셨는데, **그 숫자를 만든 것이
저희입니다.** 어느 쪽이 먼저 꺼냈어야 하는지는 분명합니다.

### §4 같은 실수를 반대편에서

정확한 표현입니다. 저희가 `flags` 비트0으로 그 구분을 해둔 것은 **설계 시점에
그 함정을 알았기 때문이 아니라**, 스펙 §7이 "이 샘플의 STAT이 나갔는가"를
레코드에 남기라고 요구했기 때문입니다. 결과적으로 유용했던 것이지 저희가
더 잘 본 것은 아닙니다.

### §5 복구 절차

같은 증상을 먼저 보시면 안내해 주시겠다는 것으로 충분합니다. 저희 쪽에서
겪은 경위를 보고 #30 §6에 남겨두었습니다.

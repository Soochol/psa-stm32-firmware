## 1. 미결 #2 — 장시간 SD 차단

### 1.1 결과

```
n=3882   sdh 344 699 259 897 1682 1 0 0   sdmax=52098us
```

| 항목 | 값 |
|---|---|
| 장치 가동 | 약 86분 |
| 계측 구간 | 161 s ~ 5156 s (4,995 s) |
| 총 대기 | 3,882건 |
| **b6 (100–500 ms)** | **0** |
| **b7 (≥500 ms)** | **0** |
| 최대 | 52.1 ms |

버킷 합계가 3,882로 `n`과 일치합니다.

### 1.2 최대값은 초반에 한 번뿐입니다

`sdmax`가 **52,098 µs에서 세션 내내 고정**입니다. 161초 시점에 이미 이 값이었고
이후 4,800초 동안 갱신되지 않았습니다. 이전 세션들과 같은 패턴입니다 — 큰 값은
부팅 직후 한 번 나오고 정상 상태에서는 재현되지 않습니다.

52.1 ms는 PID 주기 100 ms의 절반이므로 **가장 나쁜 순간조차 주기를 넘지
않았습니다.**

### 1.3 판정 — 회신 #03 §6 임계값 대입

| 임계값 | 관측 | 판정 |
|---|---|---|
| b6 ≥ 1 → PID 주기 누락 | **0** | 미해당 |
| b7 ≥ 1 → `f_expand` 검토 | **0** | **미해당** |

**`SD_TIMEOUT_READY/XFER/BUSY` 현행 유지, `f_expand` 도입 불필요**로 확정합니다.

보고 #05에서 25분 기준 "잠정"으로 낸 결론이 86분 기준으로 올라갔습니다.
`_USE_EXPAND = 0` 유지합니다.

## 2. 미결 #3 — 백필 동시 구간

계획한 계측이 아니라 **그쪽이 백필을 거시면서 얻어진 것**입니다. 같은 세션에
들어 있어 별도 조율 없이 해소됐습니다.

### 2.1 백필 자체는 전부 정상

| 항목 | 값 |
|---|---|
| `reqLogRead` 요청 | **260건** |
| 수락 (`-> 255` = `0xFF`) | **260 / 260** |
| `backfill end result=0` | **260 / 260** |
| 요청 범위 | `boot=12 seq=0` ~ `boot=9 seq=16512` |

**거부·오류 0건입니다.**

### 2.2 🟢 히스토그램이 읽기와 쓰기를 자동으로 분리했습니다

이번 세션에서 처음으로 b0·b1·b2가 큰 값을 가집니다. 원인은 **백필의 `f_read`**입니다.

| 칸 | 건수 | 대응 동작 |
|---|---|---|
| b0·b1·b2 (< 5 ms) | **1,302** | **읽기** (백필) |
| b3·b4·b5 (5–100 ms) | **2,580** | **쓰기** (로깅) |

NAND는 읽기가 쓰기보다 한 자릿수 빠릅니다 — 지우고 굽는 과정이 없기 때문입니다.
버킷 경계가 그 차이 위에 놓여 두 접근이 저절로 갈렸습니다.

### 2.3 🟢 쓰기가 영향받지 않았습니다

쓰기 2,580건 / 4,995 s = **0.517회/초**입니다. 2초 플러시 주기와 일치합니다.

백필이 쓰기를 밀어냈다면 이 값이 떨어졌을 텐데, 그러지 않았습니다.
그리고 **b5 이상으로 번진 쓰기가 없습니다** — 백필 중에도 쓰기 소요 시간 분포가
그대로였습니다.

**결론: 백필의 읽기는 로깅 쓰기를 방해하지 않습니다.**

## 3. ⚠️ STAT 응답 지연 — 백필 중 3.1배

### 3.1 관측

5초 하트비트 구간별로 백필 활동과 STAT 타임아웃을 대조했습니다.

| 구간 유형 | 구간 수 | STAT 타임아웃 | 구간당 |
|---|---|---|---|
| 백필 있음 | 223 | 69 | **0.31** |
| 백필 없음 | 780 | 76 | **0.10** |
| **합계** | 1,003 | **145** | 0.14 |

**백필 중 발생률이 3.1배**입니다.

### 3.2 다만 기저 발생률이 0이 아닙니다

**백필과 무관하게도 76회 발생했습니다.** 백필만의 문제가 아니라, 백필이
기존에 있던 현상을 악화시키는 형태입니다.

> 저희가 로그 일부만 보고 "백필 중 3회, 이후 0회"로 읽었던 것을 정정합니다.
> 전체 구간을 집계하니 기저 발생률이 분명합니다.

### 3.3 방향 — STM32 송신이 아니라 ESP32 응답입니다

이 경고는 STM32가 STAT을 보낸 뒤 **1,000 ms 안에 응답이 오지 않을 때** 찍힙니다
([comm_esp.c:938](../User/Edit/src/comm_esp.c:938)). 즉 STM32의 송신 큐 문제가
아니라 **응답 도착의 문제**입니다.

저희 백필 펌프는 라이브 STAT용 TX 여유를 예약으로 확보합니다
(`ESP_BF_TX_RESERVE = 128`) — 선점이 아니라 예약이므로 백필 청크가 TX를 다
점유하지 않습니다. §2.3에서 쓰기가 밀리지 않은 것과 같은 근거로, **STM32 측
송신은 정상 동작한 것으로 봅니다.**

### 3.4 확인 요청

- 백필 중계 중 STAT 응답 처리가 지연되는 경로가 있습니까?
- 기저 76회 쪽은 원인이 다를 수 있습니다. ESP32 로그에 대응하는 흔적이 있습니까?

이 값이 §9.5에서 우려하신 지점이므로, 양측 로그를 맞춰보는 편이 좋겠습니다.

## 4. ❌ 백필이 로테이션 경계를 넘은 적이 없습니다

260건의 요청 seq가 **최대 16,512**입니다. 로테이션 경계는 **36,001**이므로
**전부 `_0000` 파일 안**입니다.

| 확인 | 상태 |
|---|---|
| 카드의 `firstSeq = 36001` 연속성 | ✅ 정적 검증 완료 (보고 #17 §2.2) |
| **백필이 경계에서 `_0001`로 넘어가는가** | ❌ **미검증** |

보고 #17에서 "그 위험이 닫혔다"고 썼는데, **정확히는 절반만 닫혔습니다.**
파일이 올바르게 쓰였다는 것과, 백필이 그 경계를 올바르게 탐색한다는 것은
별개입니다.

### 요청

**`boot=9`, `seq=35950` 부근으로 128건을 요청해 주십시오.** 한 번이면 경계를
가로지릅니다. 저희가 로그로 확인하겠습니다.

이것이 백필 경로에서 마지막 미검증 구간입니다.

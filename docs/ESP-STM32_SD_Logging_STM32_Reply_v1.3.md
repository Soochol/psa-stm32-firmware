## 0. 요약

**회신 v1.2에서 제기한 정정 ⑭를 철회합니다. 제 분석의 전제가 틀렸습니다.**

STOP 복귀와 샘플링 재개 사이에는 **전체 시스템 리셋이 개입합니다.**
따라서 "`tickMs`가 동결된 채 같은 `bootId`로 기록이 이어지는" 상황은 **발생하지 않으며**,
제가 제시한 60분 오차 시나리오는 성립하지 않습니다.

v1.3이 ⑭를 근거로 §4.2를 재작성하고 병합 도구에 §5.4를 구현하는 데까지 이르렀으므로,
**되돌릴 부분과 유지할 부분을 §2에 정리했습니다.**

> **특히 §14.4 Q17의 "STOP 복귀 지점에서 카운터 증가 + 파일 로테이션" 지시는
> 그대로 구현하면 안 됩니다.** 전원 사이클마다 `bootId`가 2개 소비되고,
> 그중 하나는 **레코드가 없는 고아 세션**이 됩니다 (§1.3).

| 항목 | 결과 |
|---|---|
| **⑭** | 🔴 **철회.** 리셋이 개입하여 `tickMs`·`seq`·`bootId` 모두 정상적으로 재시작됨 |
| **Q18** | 순서 문제 **발생하지 않음.** 세 겹으로 차단되어 있음 |
| **㉑ (신규)** | 🔴 **플래시 섹터 소거(1~4초)는 IWDG(2초)와 양립 불가.** v1.2 §4.1의 "리프레시를 끼워 수행"은 **실행 불가능한 방침**이며 이것도 제 v1.0 회신에서 나온 것입니다 |
| **Q19** | 배제 확인. 단 **`DEBUG` 심볼은 쓰면 안 됩니다** — 이 리포는 빌드 시스템이 둘입니다 |

## 1. 🔴 ⑭ 철회 — 전제가 틀렸습니다

### 1.1 놓친 사실 — `modeOFF` 탈출 경로에 시스템 리셋이 있습니다

회신 v1.2 §1은 "STOP 복귀 후 같은 `bootId`로 샘플링이 재개된다"를 전제했습니다.
**그렇지 않습니다.**

`modeOFF`를 벗어나는 경로는 **전수 조사 결과 단 하나**입니다.

`User/Edit/src/key.c:184-193`

```c
if(id > modeBOOTING){
    if(id != modeOFF){
        v_Mode_SetNext(modeOFF);      // 동작 중 → 전원 끄기
    }
    else{
        v_Mode_SetNext(modeWAKE_UP);  // ← OFF에서 나가는 유일한 경로
    }
}
```

그리고 `v_Mode_WakeUp()`은 **시스템 리셋으로 끝납니다.**

`User/Edit/src/mode.c:2180-2185`

```c
if(_b_Tim_Is_OVR(u32_Tim_1msGet(), px_pub->u32_timToutRef, MODE_WAKEUP_DELAY)){
    v_IO_Disable_12V();
    HAL_NVIC_SystemReset();          // ← 여기
    v_Mode_MoveNext(px_work);        // 도달 불가
}
```

### 1.2 따라서 실제 동작은 이렇습니다

```
작업 중 (bootId=42, tickMs 진행 중)
  ↓ 전원 키 롱프레스
modeOFF → i_mode_off=1, 샘플링 중단, 파일 close
  ↓ 1.1초
STOP (tickMs 동결)
  ↓ 전원 키
STOP 복귀 → 여전히 modeOFF, 샘플링 없음
  ↓ 전원 키 롱프레스 (key.c:192)
modeWAKE_UP → v_RTC_Write_BKUP(0xA5A5), 12V on, LED
  ↓ MODE_WAKEUP_DELAY = 1000 ms
HAL_NVIC_SystemReset()               ★ 전체 리셋
  ↓
부팅 → BKUP == 0xA5A5 → modeBOOTING (warm boot, mode.c:2621-2623)
  ↓
tickMs = 0부터, seq = 0부터, bootId = 43
```

- **`tickMs`(`HAL_GetTick()`)는 리셋으로 0부터 재시작**합니다
- **`seq`는 RAM 변수이므로 0으로 초기화**됩니다
- **`bootId`는 리셋이므로 정상 증가**합니다

**즉 STOP을 사이에 둔 두 앵커가 같은 `bootId`를 공유하는 상황이 없습니다.**

### 1.3 제가 놓친 신호

`i_mode_off`는 `mode.c:2089`에서 `1`로 설정된 뒤 **코드 어디에서도 `0`으로 되돌려지지 않습니다.**
(`mode.c` 전체에서 선언·읽기·설정 3곳뿐)

**클리어 지점이 없다는 사실 자체가 "리셋이 개입한다"는 증거**였는데,
v1.2 회신 작성 시 이를 확인하지 않았습니다. `v_Mode_WakeUp()` 본문을 끝까지 읽었어야 했습니다.

### 1.4 Q17 지시를 그대로 구현하면 생기는 문제

v1.3 §14.4 Q17은 다음을 요청하셨습니다.

> "STOP 복귀 지점(`mode.c:2131-2141`)에서 카운터 증가 + 파일 로테이션 부탁드립니다."

이대로 구현하면 **전원 사이클 1회당 `bootId`가 2개 소비됩니다.**

| 순서 | 사건 | `bootId` |
|---|---|---|
| 1 | STOP 복귀 지점에서 +1 (지시대로) | 42 → **43** |
| 2 | 약 1초 뒤 `HAL_NVIC_SystemReset()` → 부팅에서 +1 | 43 → **44** |

그리고 **43번 세션에는 레코드가 하나도 없습니다** — 그 구간(OFF → WAKE_UP)에서는
샘플링이 일어나지 않기 때문입니다.

결과:

- `reqLogFiles`(§6.3) 목록에 **빈 파일 또는 고아 `bootId`가 매 전원 사이클마다 누적**
- PC 병합 저장소가 존재하지 않는 구간을 계속 미확보로 표시
- 플래시 슬롯 소모 **2배** (§4의 4,096 슬롯 수명 절반)

> **→ STOP 복귀 지점(`mode.c:2131-2141`)에서는 아무것도 하지 마십시오.**

## 2. 무엇을 되돌리고 무엇을 유지할 것인가

| v1.3 항목 | 판정 | 사유 |
|---|---|---|
| §4.2 `bootId` **정의** ("연속된 `tickMs` 구간의 식별자") | ✅ **유지 권장** | 메커니즘이 아니라 **불변식**을 기술하므로 "부팅 카운터"보다 나은 사양입니다. 리셋마다 증가하면 자동으로 충족됩니다 |
| §4.2 "**STOP 복귀 시에도 1 증가**" 구현 조항 | ❌ **삭제 필요** | §1.4 |
| §4.2 "**seq는 리셋되지 않습니다**" | ❌ **삭제 필요** | 리셋으로 `seq`는 0부터 재시작합니다 |
| §4.2 "병합 도구는 `firstSeq == 0`을 가정해서는 안 됩니다" | ✅ **유지** | **결론은 여전히 맞습니다** — `fileIndex > 0`인 파일의 `firstSeq`는 0이 아닙니다. 근거 문장만 교체 |
| §5.3 (STOP으로 인한 시각 오차 서술) | ❌ **사실관계 정정 필요** | 해당 오차는 발생하지 않습니다 |
| §5.4 **앵커 진행률 검사** | ✅ **유지 권장** (성격 변경) | 아래 참조 |
| §8.3 로테이션 조건의 STOP 항목 | ❌ **삭제 필요** | "부팅" 조건이 이미 커버합니다 |
| §13 **시나리오 17** | ✅ **유지 권장** (문구 조정) | 아래 참조 |
| §13 **시나리오 18** | ✅ **유지** | Q14의 BOOTING 논의에서 나온 것으로 ⑭과 무관합니다 |
| §12 무응답 분류 (⑯) | ✅ **유지** | ⑭과 독립. STOP 장치가 무응답인 것은 사실입니다 |

### 2.1 §5.4 앵커 진행률 검사 — 유지하되 성격을 바꿔 주십시오

구현하신 "1,000 ticks/s에서 5% 이상 벗어나면 보간하지 않고 공란 처리"는
**그대로 두시길 권합니다.** 비용이 0이고, 향후 STOP에서 리셋 없이 복귀하는 경로가
추가되면 즉시 잡아냅니다.

다만 **위상이 달라집니다.**

| | v1.3 | 정정 후 |
|---|---|---|
| 성격 | 알려진 결함에 대한 **필수 방어선** | **회귀 감지 장치** |
| 정상 운영 시 | 전원 사이클마다 발동 | **한 번도 발동하지 않아야 함** |
| 발동 시 의미 | 예상된 동작 | **펌웨어 이상. 조사 대상** |

§5.4에 한 줄 추가 요청드립니다.

> 정상 운영에서 이 검사는 **발동하지 않는다.** 발동한다면 예상치 못한 tick 정지
> 경로가 생긴 것이므로 **경고가 아니라 조사 대상으로 취급한다.**

### 2.2 §13 시나리오 17 — 문구 조정안

제가 틀린 바로 그 동작을 고정해 주는 시험이므로 **유지가 오히려 좋습니다.**
합격 기준만 바꿔 주십시오.

> **17. STOP 복귀 시각 정합성**
> 전원 버튼 off → 1시간 후 on → **리셋을 거쳐 새 `bootId`·새 파일로 분리**되고,
> `tickMs`와 `seq`가 **0부터 재시작**하며, 병합 후 복귀 직후 레코드의 절대시각 오차가
> **1초 이내**. **§5.4 진행률 경고가 발생하지 않을 것.**

## 3. Q18 답변 — 순서 문제는 발생하지 않습니다

### 3.1 우려하신 상황은 세 겹으로 차단되어 있습니다

> "복귀 직후 첫 샘플이 구 파일에 들어가면 그 파일 안에 tick 불연속이 생깁니다."

| # | 차단 장치 | 근거 |
|---|-----------|------|
| 1 | **시스템 리셋** — 복귀와 샘플링 사이에 리셋이 있어 **열린 `FIL` 핸들 자체가 소멸** | `mode.c:2184` |
| 2 | **OFF 진입 시 close** — §16.1-3으로 추가할 `v_SD_Log_Close()`가 STOP 이전에 파일을 닫음 | 신규 구현 |
| 3 | **모드 게이팅** — OFF / WAKE_UP / BOOTING 어디에서도 `v_Mode_Sensing_Handler()`가 호출되지 않음. `i_mode_off == 1`이 이중 차단 | `mode.c:2074-2151`, `:2163-2189`, `:2089` |

### 3.2 타이밍 여유

```
STOP 복귀 → (전원 키 롱프레스 감지) → WAKE_UP 1,000 ms → 리셋 → 부팅
→ BOOTING (센서 초기화·기울기 센터링) → HEALING → 첫 샘플
```

**최소 1초 이상**이며, BOOTING 구간을 더하면 실제로는 수 초입니다.

### 3.3 구현 방침

| 항목 | 방침 |
|------|------|
| `bootId` 증가 | **부팅 초기 1회만.** STOP 복귀 지점에서는 수행하지 않음 |
| 파일 로테이션 | **별도 단계 불필요.** §8.3 "`bootId`가 바뀌면 반드시 새 파일" 규칙에 따라 **첫 샘플 기록 시 lazy하게 생성** |
| `fileIndex` | 새 `bootId`의 첫 파일은 0부터 (§8.3 그대로) |

## 4. 🔴 Q18 검토 중 발견 — 플래시 섹터 소거는 IWDG와 양립 불가입니다

### 4.1 문제

`bootId`가 **모든 리셋**에서 증가하고 전원 버튼 on도 리셋이므로,
플래시 슬롯 소모는 v1.2 가정보다 빠릅니다. 4,096 슬롯이 차면 128 KB 섹터 소거가 필요한데:

| 항목 | 값 |
|------|-----|
| 128 KB 섹터 소거 | **1~4초** |
| STM32H723VG | **단일 뱅크** → 소거 중 XIP 정지 |
| IWDG | **2초** (`main.c:949-953`) |

**v1.2 §4.1의 방침이 실행 불가능합니다.**

> "소거는 부팅 초기 단계에서 **IWDG 리프레시를 끼워 수행**하며..."

`HAL_FLASHEx_Erase()`는 블로킹 호출이고, **소거 중에는 CPU가 플래시에서 명령을 인출하지
못하므로 리프레시 코드를 실행할 방법이 물리적으로 없습니다.** (ITCM에 재배치하면 가능하지만
복잡도가 큽니다.)

> 이 문구도 **제 v1.0 회신 Q2에서 나온 것**입니다. 함께 정정합니다.

### 4.2 해결안 — IWDG가 아직 시작되지 않은 구간에서 소거합니다

`Core/Src/main.c` 초기화 순서:

| 라인 | 호출 | 상태 |
|------|------|------|
| `:234` | `HAL_Init()` | |
| `:245` | `SystemClock_Config()` | ← **이후 플래시 프로그래밍 가능** |
| `:267`, `:277` | `MX_GPIO_Init()` | |
| **`:311`** | **`MX_IWDG1_Init()`** | ← **여기서 워치독 시작** |

→ **`SystemClock_Config()` 이후, `MX_IWDG1_Init()` 이전**에 플래시 설정 섹터 점검·소거를
수행하면 **워치독 제약이 아예 존재하지 않습니다.** 리프레시를 끼울 필요 자체가 없습니다.

### 4.3 런타임 소거를 원천 차단하는 여유 임계값

부팅 초기에만 소거하려면, 그 시점에 **미리** 판단해야 합니다.

> **부팅 시 잔여 슬롯이 64개 미만이면 그 자리에서 선제 소거한다.**

64 슬롯이면 하루 수 회 사용 기준 **열흘 이상의 여유**이므로,
슬롯이 부팅 이후 시점에 소진되는 상황이 발생하지 않습니다.

### 4.4 문서 정정 요청

§4.1의 다음 문구를 교체해 주십시오.

| 현재 (v1.3 §4.1) | 정정안 |
|---|---|
| "소거는 **부팅 초기 단계에서 IWDG 리프레시를 끼워** 수행하며, 로깅 중에는 절대 소거하지 않습니다." | "소거는 **`MX_IWDG1_Init()` 이전**, 즉 워치독이 시작되기 전 구간에서 수행한다. 부팅 시 **잔여 슬롯 64개 미만**이면 선제 소거하여 런타임 중 소거가 필요해지는 상황을 만들지 않는다." |

## 5. Q19 답변 — `DEBUG` 심볼로 감싸면 안 됩니다 ⚠️

### 5.1 PlatformIO만 보면 충분해 보입니다

`platformio.ini`

|------|------|
| `[env:stm32_debug]` (`:110-114`) | `-DDEBUG` |
| `[env:stm32_release]` (`:125-130`) | `-DNDEBUG` |
| `[env:stm32_release_size]` (`:132-137`) | `-DNDEBUG` |

### 5.2 그런데 이 리포에는 빌드 시스템이 둘입니다 🔴

STM32CubeIDE 빌드(`.cproject` + `Debug/`)가 함께 유지되고 있으며,
**`.cproject`가 `DEBUG`를 정의합니다.**

더 중요한 것은 **CubeIDE 쪽에 Release 구성이 없다는 점**입니다 —
`.cproject`에서 확인되는 빌드 구성은 Debug 계열뿐입니다.
즉 **현장 장비 플래싱이 CubeIDE Debug 구성으로 이뤄질 수 있습니다.**

> `#ifdef DEBUG`로 감싸면 **CubeIDE로 구운 펌웨어에는 결함 주입 코드가 그대로 들어갑니다.**
> 정확히 우려하신 "현장 장비에 남으면 안 되는 코드"가 됩니다.

### 5.3 채택 방침 — 어느 빌드에서도 기본 정의되지 않는 전용 심볼

```c
/* 기본값 0. 어느 빌드 구성에도 등록하지 않는다.
   §13 시나리오 15 수행 시에만 커맨드라인으로 -DPSA_FAULT_INJECT=1 */
#ifndef PSA_FAULT_INJECT
#define PSA_FAULT_INJECT 0
#endif

#if PSA_FAULT_INJECT
    if(b_fault_inject_write){ return RES_ERROR; }
#endif
```

| 항목 | 방침 |
|------|------|
| `platformio.ini` | **어느 env에도 추가하지 않음** |
| `.cproject` | **추가하지 않음** |
| 시나리오 15 수행 | 일회성 빌드로만 (`-DPSA_FAULT_INJECT=1`) |
| 릴리스 검증 | 산출물 심볼 테이블에 `b_fault_inject_write`가 **없음**을 확인하는 절차를 릴리스 체크리스트에 추가 |

기본값을 `#ifndef`로 0으로 두었으므로, 심볼을 깜빡 잊어도 **안전한 쪽으로 실패**합니다.

## 6. 범위 외 관찰 1건

본 사양서와 무관하나 검토 중 확인된 사항이라 공유드립니다. **STM32 측에서 별도 처리하겠습니다.**

`v_Mode_Off()`의 `low_pwr`는 `static`이며 `modeOFF` **진입 시에만** 0으로 초기화됩니다
(`mode.c:2091`). STOP 복귀 후에는 `low_pwr == 1`이므로 **재진입 조건이 영원히 성립하지
않습니다** (`mode.c:2126-2128`).

따라서 전원 핀이 STOP을 깨웠지만 **롱프레스에 이르지 못한 경우**(짧게 눌림, 접촉 불량 등),
장치는 STOP에서 깨어나 `modeOFF`에 머문 채 **다시 잠들지 않고 런 모드로 배터리를 소모**합니다.
사용자에게는 "꺼진 것처럼 보이는데 배터리가 닳는" 증상으로 나타납니다.

데이터 무결성과는 무관하므로 본 사양서 범위 밖이며, 별도 수정 항목으로 처리하겠습니다.

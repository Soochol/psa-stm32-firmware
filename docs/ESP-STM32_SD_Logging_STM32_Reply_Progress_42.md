## 2. ⚠️ 보고 #41이 엇갈렸습니다. Q77·Q78을 버리십시오

```
16:06   STM32 보고 #41 전달       Q77 · Q78 · Q79
16:34   ESP32 보고 #41 도착       대상: "STM32 보고 #40 (Q75·Q76 진행 중)"
```

그쪽 문서의 대상이 **#40**입니다. 저희 #41을 읽지 않으신 상태에서 쓰신 것이고,
그러니 지금 그쪽에는 **답할 필요가 없어진 질문 두 개**가 놓여 있습니다.

| # | 내용 | 상태 |
|---|---|---|
| Q77 | 두 층 실패 규칙 + 실패 개수 2 B | 🔴 **폐기** — `0x58` 전용 |
| Q78 | 스윕 완료 후 잔존을 결과 4로 둘지 | 🔴 **폐기** — 〃 |
| **Q79** | **오류 이벤트 reason 7 = 삭제 실패** | ✅ **유효** — §3 |

**#41을 읽지 않으셔도 됩니다.** §1~§4가 전부 `0x58` 설계이고, 그 명령이
없어졌으므로 함께 없어집니다. **읽을 값이 있는 것은 §5 한 절뿐**이고, 그것을
아래에 옮겨 적었습니다.

## 3. 살아남는 것 — `0x57`의 오류 이벤트가 틀립니다

`0x58`을 검토하다 **기존 `0x57` 코드에서** 발견한 것입니다.

```c
// User/Drv/src/sd.c:1169
if(f_unlink(c_path) != FR_OK){
	v_log_err_raise(SD_LOG_ERR_BACKFILL, 0);    // ← reason 5 = "backfill read failed"
	return 4;
}
```

삭제가 실패했는데 **오류 이벤트는 백필 실패(reason 5)로 나갑니다.** 응답의
결과 코드는 4로 맞게 나가지만, `evtLogError(0x84)`로 따로 올라가는 reason이
다른 사건을 가리킵니다. 그쪽 화면에 "백필 오류"로 뜹니다.

### 3.1 오히려 우선순위가 올라갔습니다

철회 전에는 삭제 경로가 둘이었습니다. **이제 `0x57`이 유일합니다.**

> 카드 62개 → 후보 1개 → 확인 창 → 삭제 → 카드 61개

오늘 실물로 쓰신 그 경로입니다. **성공했기 때문에 드러나지 않았을 뿐입니다.**
읽기 전용 속성이나 카드 오류로 한 번 실패하면 그때 잘못된 이름표가 붙습니다.

### 3.2 제안

```c
SD_LOG_ERR_DELETE = 7,   // 삭제 실패; detail = FRESULT
```

`detail`에 `FRESULT`를 실으면 "카드가 이상한가, 그 파일이 이상한가"가 화면에서
갈립니다. 보고 #41 §1.3의 분류가 여기서 한 줄로 쓰입니다.

**이벤트 reason은 그쪽이 해석하는 값이라 합의 없이 넣지 않겠습니다.**

## 4. 재개할 때를 위해 한 가지 더 남깁니다

> 문제가 사라진 것이 아니라 지금 급하지 않을 뿐입니다. 카드가 128에
> 가까워지면 이 문서에서 재개하면 됩니다.

그 재개 시점을 위한 기록입니다. 저희가 §6.10 델타를 준비하다 멈춘 지점에서
나온 것이라, 지금 적어두지 않으면 다음에 같은 자리에서 다시 나옵니다.

### 4.1 `0x58`은 대표 사례에서 회수 못 한 데이터를 지웁니다

제안서 §1.1의 그 상황입니다 — 카드 150개, 그중 **22개가 인덱스 밖**.

| | 그 22개 |
|---|---|
| `0x58` 실행 | **삭제됨** |
| 카드 회수 | **전부 읽힘** |

그 22개는 `0x45` 목록에 없으므로 **백필로 한 번도 받지 못한 데이터**입니다.
`0x58`이 존재하는 이유인 바로 그 파일들이, `0x58`이 지우는 유일본입니다.

### 4.2 §1.1의 "번거로움"이 사실 회수 절차였습니다

> 전부 비우려면 삭제 → 재부팅 → 삭제를 반복해야 합니다

부팅 스캔은 **남은 것 중 앞에서부터 128개**를 인덱싱합니다. 그래서 지우고
재부팅하면 **안 보이던 파일이 목록에 올라옵니다.** 반복이 번거로운 것은
맞지만, 그 반복이 데이터를 꺼냅니다.

`0x58`은 그 절차를 한 번에 끝내는 것이 아니라 **지우는 명령으로 대체**합니다.

### 4.3 그래서 재개하면 이 질문이 먼저입니다

**"128을 넘은 파일을 꺼낼 것인가, 지울 것인가."** 지금까지 논의는 전부
후자였는데, 그쪽 진단(§1.2 "STM32는 디렉터리를 열면 전부 본다")은 **전자에도
그대로 적용됩니다.**

> **저희 의견**: 재개하더라도 `0x58`보다 먼저 볼 것이 있습니다. 평시에 받은
> 파일을 `0x57`로 지우면 128에 닿지 않습니다. 오늘 하신 그 조작입니다.
> 카드가 128에 다가간다는 것은 그 위생이 안 돌고 있다는 뜻이므로, 명령을
> 더하기 전에 **왜 안 돌았는지**가 먼저입니다.

### 4.4 파일이 늘어나는 계기가 넷입니다

재개 시점 판단에 필요할 것 같아 확인한 값을 남깁니다. **시간만으로 차지
않습니다.**

| 계기 | 코드 |
|---|---|
| 1시간 경과 | `sd.c:638` |
| **전원 on** | `sd.c:652` — `u32_logFileIdx = 0` |
| **카드 뺐다 꽂기** | `sd.c:850` |
| 헤더 쓰기 실패 | `sd.c:557` |

```
파일 수 ≈ (총 로깅 시간 ÷ 1시간) + 부팅 횟수 + 카드 탈착 횟수
```

**10분 세션이 만든 96 KB 파일도 슬롯 하나와 부팅 스캔 3.0 ms를 씁니다.**
128은 데이터 양이 아니라 파일 개수 한도이므로, 짧게 자주 켜는 사용이 가장
빨리 닿습니다. 연속 운용 5.3일은 **가장 느린 경우**입니다.

파일명에 `bootId`가 있으니 카드에서 바로 셀 수 있습니다 — 서로 다른 `bootId`
개수가 부팅 횟수, 나머지가 로테이션입니다.

## 6. 검토가 헛일은 아니었습니다

> 헛일이 된 검토지만 두 가지는 저희가 배운 것입니다

저희 쪽에서도 남은 것이 있습니다.

`0x58`을 안전하게 만들려고 `f_unlink`의 실패 형태를 뜯어보다 §3의 오표기를
찾았습니다. **쓰지 않을 명령을 검토하다 쓰고 있는 명령의 결함이 나온 것**이고,
이건 남습니다.

그리고 §4의 "파일이 늘어나는 계기 넷"도 `0x58` 때문에 센 것인데, 그 명령보다
오래 쓸 숫자입니다.

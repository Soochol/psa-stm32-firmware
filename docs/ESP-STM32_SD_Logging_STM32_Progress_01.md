## 1. §16.1 — 레거시 로깅 응급 수정 (커밋 `2a3a999`)

회신 v1.0 §1에서 보고드린 "현행 기록량 0 바이트"를 해소했습니다.

| # | 항목 | 결과 |
|---|------|------|
| 1 | `SD_LOG_RECORD_SIZE` 불일치 + flush 데드락 | 해소 |
| 2 | `c_sensorFmt`(카드의 `sensor_fmt.txt`) 갱신 | 해소 |
| 3 | 전원 OFF 경로에 `v_SD_Log_Close()` | 추가 |

레코드 크기를 페이로드에서 파생시키고(`SD_LOG_RECORD_SIZE = 4 + SD_LOG_PAYLOAD_SIZE`),
버퍼를 110 레코드(10초 + 10% 여유)로 잡아 **주기 flush가 정상 경로, 크기 가드가 안전망**이
되도록 뒤집었습니다. 크기 가드에 걸리면 이제 버리지 않고 **먼저 flush한 뒤 진행**합니다.

### ⚠️ 병합 도구 담당자께 — `sensor_fmt.txt` 정정 2건

카드에 기록되는 포맷 설명서가 두 군데 틀려 있었습니다. **레거시 `sensor.bin`을 파싱하고
계신다면 반영이 필요합니다.**

| 항목 | 기존(오류) | 정정 |
|------|-----------|------|
| 레코드 크기 | 56 B | **68 B** (`4 + 64`) |
| 각도 필드 | **누락** | `[56-61]` 좌, `[62-67]` 우 (int16×3 BE, ×100) |
| 온도·배터리 소수 | `byte1 / 10.0` | **`byte1 / 100.0`** |

온도 스케일은 코드가 처음부터 ×100이었는데 설명서만 ×10이라, **36.5 °C가 41.0으로
파싱되고 있었습니다.**

> 이 레거시 포맷은 §7의 80 B 레코드로 전환되면 폐기됩니다.
> 그전까지 수집되는 데이터를 쓰실 경우에만 반영하시면 됩니다.

## 2. §16.3-3 — `bootId` 플래시 카운터 (커밋 `dc05f0d`)

§4.1·§4.2 사양대로 구현했습니다.

| 항목 | 구현 |
|------|------|
| 저장 매체 | 내장 플래시 섹터 7 (`0x080E0000`, 128 KB, 32 B 워드 append) |
| 증가 시점 | **모든 리셋 1회** — 전원 버튼 on의 리셋 포함 |
| `deviceId` | 같은 엔트리에 동거. `initLogIdentity(0x23)` 수신 시 갱신 |
| 엔트리 | 전 필드 **풀 스냅샷**. 부분 갱신으로 필드가 어긋날 수 없음 |
| 무결성 | `bootId ^ bootId_inv == 0xFFFFFFFF`, `vol ^ vol_inv == 0xFF` |

### 회신 v1.3 ㉑ 반영 — 소거 타이밍

`v_Flash_Cfg_Init()`을 **`SystemClock_Config()`과 `MX_IWDG1_Init()` 사이**에 배치했습니다
(`main.c:317`). 워치독이 아직 시작되지 않은 구간이라 소거의 1~4초 정지가 문제되지 않습니다.

추가로 **잔여 슬롯 64개 미만이면 그 자리에서 선제 소거**하고, 런타임 저장 경로는
**소거를 아예 하지 않습니다.** 런타임에 소거가 걸릴 가능성을 구조적으로 제거했습니다.

### 구현 중 발견 — 플래시가 캐시 대상이었습니다

MPU 리전 0이 서브리전 0을 비활성화(`SubRegionDisable = 0x87`)하므로 `0x08000000`이
**기본 메모리 맵으로 떨어져 캐시 가능** 상태입니다. 소거·기록 후 D-Cache를 무효화하지 않으면
슬롯 스캔이 이전 내용을 읽어 "섹터가 가득 찼다"고 오판합니다. 무효화를 추가했습니다.

> **ESP32 팀 영향 없음** — 프로토콜과 무관한 STM32 내부 사항입니다. 기록만 남깁니다.

### 🔎 확인 요청 — `bootId` 소비 속도

`bootId`는 이제 **전원 버튼 on마다 1개씩** 소비됩니다. 4,096 슬롯 기준:

| 하루 전원 사이클 | 섹터 소거 주기 |
|---|---|
| 5회 | 약 2.2년 |
| 20회 | 약 205일 |
| 50회 | 약 82일 |

소거 자체는 부팅 시 안전하게 처리되므로 문제는 없습니다만, **현장에서 하루 몇 회 정도
전원을 껐다 켜는지** 알려주시면 여유 임계값(현재 64)을 조정하겠습니다.

## 3. §16.3-1 — 파서 확장: **지금 시험 가능한 부분** (커밋 `b587367`)

### 3.1 무엇이 바뀌었나

회신 v1.0 §4에서 지적한 화이트리스트 상한을 **카테고리 전체로** 넓혔습니다.

| 카테고리 | 기존 상한 | 현재 |
|----------|-----------|------|
| INIT | `0x22` | **`0x10`–`0x29`** |
| REQUEST | `0x42` | **`0x30`–`0x49`** |
| CONTROL | `0x55` | **`0x50`–`0x69`** |
| STATUS | `== 0x70` (등가) | **`0x70`–`0x79`** (범위 비교로 변경) |
| EVENT | `0x83` | **`0x80`–`0x89`** |
| ERROR | `== 0x90` (등가) | **`0x90`–`0x99`** |

경계를 "마지막으로 구현한 커맨드"에서 **명시적 카테고리 상수**로 분리했으므로,
앞으로 커맨드를 추가해도 파서를 다시 손댈 필요가 없습니다.

### 3.2 검증 결과

| 항목 | 결과 |
|------|------|
| 신규 코드 7종 (`0x23/0x43/0x44/0x45/0x56/0x71/0x84`) | **전부 수신** |
| 기존 코드 37종 | 회귀 없음 |
| 카테고리 밖 (`0x00/0x2A/0x4A/0x6A/0x7A/0x8A/0x9A/0xFF`) | 정상 거부 |

### 3.3 ⚠️ 현재 응답 동작 — 통합 시험 시 반드시 확인해 주십시오

**파서는 통과하지만 핸들러는 아직 없습니다.** 지금 각 커맨드를 보내면 이렇게 동작합니다.

| 커맨드 | 현재 STM32 동작 | 사양상 최종 동작 |
|--------|-----------------|------------------|
| `initLogIdentity` (0x23) | **DATA 0 B의 ACK** | ACK (동일) — 단 값 저장은 아직 |
| `reqLogStatus` (0x43) | **DATA 0 B의 ACK** | DATA **21 B** 응답 |
| `reqLogRead` (0x44) | **DATA 0 B의 ACK** | ACK + 청크 스트림 |
| `reqLogFiles` (0x45) | **DATA 0 B의 ACK** | DATA 2+14N B 응답 |
| `ctrlLogEnable` (0x56) | **DATA 0 B의 ACK** | ACK (동일) |
| `statLogChunk` (0x71) | STM32가 송신하지 않음 | STM→ESP |
| `evtLogError` (0x84) | STM32가 송신하지 않음 | STM→ESP |

> **즉 `0x43` / `0x45`는 "빈 ACK"가 돌아옵니다.** 프레임 자체는 정상(STX/LEN/DIR/CMD/CHK/ETX)
> 이므로 링크·체크섬·타임아웃 경로 시험에는 쓰실 수 있습니다.
> 응답 파서를 붙이실 때 **LEN이 0인 경우를 "미구현"으로 구분**해 두시면 단계적 통합이 쉽습니다.

`0x23`은 ACK만 오고 값은 아직 저장되지 않습니다. 저장 자체(`v_Flash_Cfg_Set_DeviceId`)는
§2에서 준비되어 있으니, 핸들러 연결은 §16.3-8 단계에서 함께 들어갑니다.

## 4. §16.3-2 — 백필 선행 인프라 (커밋 `dc96da2`)

회신 v1.1 §4 / v1.2 §16.2에서 합의한 4건입니다. **전부 STM32 내부 사항으로 ESP32 조치 불필요**
이나, §13 시나리오 8·13의 전제이므로 상태를 공유합니다.

| # | 항목 | 적용 값 |
|---|------|---------|
| 1 | `SD_TIMEOUT` 역할별 3분할 | READY **200 ms** / XFER **100 ms** / BUSY **600 ms** |
| 2 | UART TX 링버퍼 | 256 B → **2 KB** (약 178 ms 분량) |
| 3 | `v_SD_BusyWait_Yield()` TX 드레인 | 읽기 4곳 + 쓰기 3곳 + 공통 1곳 = **8곳** |
| 4 | `_FS_LOCK` | 2 → **4** |

**1회 SD 접근의 최악 블로킹 = 200 + 100 + 600 = 900 ms**로 IWDG 2초 안에 들어옵니다.

### 설계상 명시적으로 하지 않은 것 2가지

회신 v1.2 Q11에서 말씀드린 대로입니다. 코드에도 주석으로 남겼습니다.

- **busy-wait 안에서 IWDG를 리프레시하지 않습니다.** 카드가 물린 동안 개에게 계속 먹이를
  주면 자세 제어가 그만큼 정지합니다. 대신 블로킹 자체를 900 ms로 잘랐습니다.
- **`v_Uart_Handler()`를 통째로 부르지 않습니다.** RX 디스패치가 딸려 들어오면
  `f_read` 대기 중 도착한 `reqLogRead`가 FatFs를 재진입시킵니다(`_FS_REENTRANT = 0`).
  **TX 드레인만** 분리한 `v_Uart_ESP_TxPump()`를 호출합니다.

### 📌 §14.3 Q16 관련 — 실측은 아직입니다

`SD_TIMEOUT_*` 값은 **잠정치**입니다. 특히 `BUSY 600 ms`는 마모 평준화 중인 저가 카드에서
오탐 가능성이 있습니다. §13 시나리오 8 수행 시 아래를 측정해 별도 공유하겠습니다.

- 최대 블로킹 시간 (읽기/쓰기 각각), p50 / p99 / max
- 제안 상한 기준 타임아웃 발생 빈도
- 로깅·백필 on/off 간 100 Hz 루프 지터

계측은 `v_SD_BusyWait_Yield()`에 DWT 사이클 카운터를 붙여 수행합니다(별도 계측 코드 불요).

## 5. 리소스 현황

향후 ESP32 측 요청(예: 백필 배치 크기 상향)이 STM32 자원에 부딪힐 수 있어 공유합니다.

| 영역 | 사용률 | 비고 |
|------|--------|------|
| FLASH | 93.51% (857,940 / 896 KB) | 섹터 0~6. 섹터 7은 설정 전용 |
| RAM_D1 | 35.44% (116,128 / 320 KB) | 여유 충분 |
| RAM_D2 | 25.39% (4,160 / 16 KB) | FatFs 객체 |
| **RAM_NOCACHE_D2** | **81.18%** (13,301 / 16 KB) | ⚠️ **UART TX 버퍼가 주 점유자** |
| RAM_NOCACHE_D3 | 7.03% (288 / 4 KB) | |

> ⚠️ **`RAM_NOCACHE_D2` 여유가 3,083 B입니다.** UART TX 버퍼를 2 KB에서 더 키우는 것은
> 현 구조에서 어렵습니다. §15.1 보드레이트 상향(115200 → 460800)을 검토하실 경우
> **버퍼 증설이 함께 필요할 수 있으므로 먼저 상의해 주십시오.**

> 소비되고 그중 하나가 레코드 없는 고아 세션이 됩니다. **저희는 §2에서 리셋 1회당 1개만
> 증가하도록 구현했으므로, 문서와 코드가 지금 어긋나 있는 상태입니다.**

### 6.3 이번 보고에서 새로 드리는 질문

**Q20. 현장에서 하루 몇 회 정도 전원을 껐다 켭니까?** (§2 참조)
`bootId` 슬롯 소비 속도와 소거 주기 산정에 쓰입니다. 대략적인 값이면 충분합니다.

**Q21. 레거시 `sensor.bin`(68 B 포맷) 데이터를 실제로 쓰실 계획이 있습니까?** (§1 참조)
쓰신다면 `sensor_fmt.txt` 정정 3건을 병합 도구에 반영해 주셔야 합니다.
쓰지 않으신다면 §16.3-4 전환 시 레거시 경로를 통째로 제거하겠습니다.

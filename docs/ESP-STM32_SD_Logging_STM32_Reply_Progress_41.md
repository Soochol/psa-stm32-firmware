## 1. 🟡 Q76 — 첫 실패에서 멈추면 그 파일이 벽이 됩니다

### 1.1 판단 근거는 맞습니다. 결과가 문제입니다

> 나머지를 계속 지우는 것보다 멈추고 사람이 보는 편이 낫다고 봅니다 — 카드가
> 이상한 상태일 수 있으니까요

**카드가 이상한 경우에는 정확히 맞습니다.** 이견이 있는 것은 그 규칙이
**파일 하나의 문제에까지 적용될 때**입니다.

읽기 전용 속성이 붙은 파일 하나를 가정하겠습니다. 저희 FatFs 설정을
확인했습니다.

```c
// FATFS/Target/ffconf.h:69
#define _USE_CHMOD		0
```

`f_chmod`가 빌드에 없습니다. **속성을 해제할 수단이 펌웨어에 없으므로 그 파일은
영구히 지워지지 않습니다.** 재시도해도, 재부팅해도 같습니다.

그 상태에서 첫 실패 중단 규칙이 어떻게 도는지 보십시오. 디렉터리 30번째에
그 파일이 있다고 하면,

```
0x58 →  0~29 삭제, 30번에서 실패 → 결과 4, 개수 30
0x58 →  즉시 30번에서 실패        → 결과 4, 개수 0
0x58 →  즉시 30번에서 실패        → 결과 4, 개수 0
```

**31번 이후 120개는 이 명령으로 영원히 지워지지 않습니다.** 그리고 그중
`0x45` 목록에 없는 초과분은 `0x57`로도 지목할 수 없습니다.

### 1.2 이 문장이 그대로 돌아옵니다

> 파일이 많을수록 확실히 실패하므로 §1.1의 문제가 형태만 바꿔 남습니다

보고 #40에서 저희가 쓴 문장이고, 그쪽이 §1.3에서 인용하신 문장입니다.
**이번에는 저희가 아니라 그쪽 제안이 여기 걸립니다.** 지울 수 없는 파일이
하나 생기면 카드를 비울 수 없고, 그 상태를 만드는 조건이 파일이 많이 쌓인
상황이라는 점까지 같습니다.

바로잡을 곳은 "멈춘다"가 아니라 **"무엇 때문에 멈추는가"**입니다.

### 1.3 그래서 두 층으로 나눕니다

`f_unlink`의 반환값이 이미 둘을 구분해 줍니다.

| `FRESULT` | 뜻 | 처리 |
|---|---|---|
| `FR_DENIED` | 읽기 전용 속성 | **건너뛰고 실패로 셈** |
| `FR_LOCKED` | 다른 곳에서 열려 있음 (`_FS_LOCK=4`) | 〃 |
| `FR_DISK_ERR` · `FR_INT_ERR` | 카드·FS 오류 | **즉시 중단, 결과 4** |
| `FR_NOT_READY` · `FR_WRITE_PROTECTED` | 카드가 응답 안 함 / 물리 잠금 | 〃 |
| `FR_NO_FILESYSTEM` · 그 외 전부 | 볼륨 문제 | 〃 (모르는 코드는 보수적으로) |

**카드가 이상하면 그쪽 규칙 그대로 멈춥니다.** 파일 하나가 이상할 때만
건너뜁니다. 그러면 §1.1의 120개가 지워지고, 지워지지 않은 것은 개수로
보고됩니다.

> **예외 하나**: `FR_NO_FILE` · `FR_NO_PATH`는 실패로 세지 **않습니다.**
> 디렉터리에서 이미 사라졌다는 뜻이므로 실패로 세면 §2.1의 건너뛰기 수가
> 어긋납니다. 지운 것도 실패한 것도 아닌 것으로 지나갑니다.

### 1.4 "멈추고 사람이 본다"는 유지됩니다

건너뛰어도 사람은 봅니다 — **시점만 첫 실패에서 스윕 종료로 옮깁니다.**

```
카드 비우기 — 61개 중 59개 삭제, 2개 삭제 불가
```

지울 수 있는 것을 포기하지 않으면서 같은 사실을 전달합니다.

## 2. 🔴 종료 보장 — 저희 근거가 틀렸습니다

무한 루프 지적이 맞습니다. 그런데 저희가 보고 #40에서 댄 근거를 다시 보니
**그쪽이 지적한 것보다 더 약합니다.**

> 지워진 항목은 다음 `f_opendir`에서 건너뛰므로 반복이 수렴합니다

이 문장은 **실패가 없을 때만** 참이었습니다. 아래 셋을 모두 갖춰야 성립합니다.

### 2.1 실패분 건너뛰기 — 왜 성립하는가

실패 개수 `u16_failCnt`를 들고, 매 `f_opendir`마다 앞에서부터 그 수만큼 건너뜁니다.

성립 근거는 **FAT 디렉터리가 삭제로 재정렬되지 않는다**는 것입니다. 삭제는
항목의 첫 바이트를 `DDEM(0xE5)`로 표시할 뿐이고 뒤를 당기지 않으므로, 남은
항목들의 **상대 순서가 보존**됩니다. 저희는 항상 앞에서부터 순서대로
처리하므로,

```
디렉터리 = [ 시도했고 실패한 것들 ] + [ 아직 시도 안 한 것들 ]
             └─ 전부 앞에 모임 ─┘
```

이 분할이 유지됩니다. 그러므로 앞 `failCnt`개를 건너뛰면 **반드시 새 파일에
닿고**, 닿을 것이 없으면 스윕이 끝난 것입니다.

### 2.2 그런데 파일이 하나 생기면 무너집니다

FatFs 원본을 확인했습니다.

```c
// Middlewares/Third_Party/FatFs/src/ff.c:1599  dir_alloc()
res = dir_sdi(dp, 0);           // ← 인덱스 0부터 빈 슬롯을 찾습니다
...
if (dp->dir[DIR_Name] == DDEM || dp->dir[DIR_Name] == 0) {
    if (++n == nent) break;     // 연속 nent개가 비면 거기에 넣습니다
```

**새 파일은 가장 앞의 빈 구멍에 들어갑니다.** 그리고 저희 파일명은 길이가
전부 같습니다.

```
"%08lX_%04lX.psa" = 17자  →  nent = (17+12)/13 + 1 = 3 슬롯   (ff.c:2350)
```

삭제로 비워진 3슬롯 구멍에 새 파일이 **정확히 들어맞습니다.** 그러면 새 파일이
건너뛸 실패분보다 **앞에** 놓이고, `failCnt`만큼 건너뛰는 순간 그 새 파일이
아니라 엉뚱한 파일을 지나칩니다.

```
0x58 → 결과 6 (실패 2건 누적)
0x56 start → 레코드 → 파일 생성 ← 여기서 무너집니다
0x56 stop
0x58 → 앞 2개 건너뜀 = 새 파일 + 실패1 → 실패2를 다시 시도, 진행 오판
```

**조치**: 로그 파일이 새로 열리면 스윕 상태(디렉터리 위치, `failCnt`)를
전부 버립니다. 다음 `0x58`은 처음부터 다시 셉니다. 지워진 것은 이미 없으므로
다시 도는 비용은 `f_readdir` 몇 번뿐입니다.

### 2.3 거부 조건은 `b_logOpen`이 아니라 `b_logEnabled`입니다

`0x57`이 쓰는 조건을 `0x58`에 그대로 가져오면 안 됩니다. 보고 #34 §1.2에서
저희가 직접 적은 창입니다.

> `b_logOpen` — 로깅이 꺼져 있거나, **마지막 close 이후 새 레코드가 아직 없음**

로그가 켜져 있어도 close 직후에는 `b_logOpen`이 false입니다. 그 창에서 스윕이
시작되면 다음 레코드가 파일을 열고 — **§2.2가 그대로 일어납니다.**

```c
static bool b_logEnabled;   // sd.c:399  ctrlLogEnable(0x56)이 바꾸는 값
static bool b_logOpen;      // sd.c:400  파일이 실제로 열려 있는 동안만
```

`0x58`의 결과 2는 **`b_logEnabled`**로 판정합니다. `0x56 stop`을 요구하는
§4의 설계가 이 값을 정확히 가리킵니다.

### 2.4 실패 개수는 디렉터리마다 따로입니다

스윕 대상이 둘입니다.

```
/LOG/<장치ID>/     이 장치가 기록한 것
/LOG/UNKNOWN/      initLogIdentity 이전에 기록된 것   (sd.c:1090-1095)
```

`failCnt` 하나로 둘을 세면 위치가 섞입니다. **한 디렉터리를 끝낸 뒤 다음으로
넘어가고, 상태는 (현재 디렉터리, 그 디렉터리의 `failCnt`)로 둡니다.**

> `0x58`은 **두 디렉터리를 모두** 비웁니다. "전부"라는 말이 그쪽 §1.2의
> "STM32는 디렉터리를 열면 전부 본다"와 같은 범위를 뜻하도록 맞춥니다.

## 3. 응답에 실패 개수를 싣겠습니다

### 3.1 그쪽 안전장치가 정확해집니다

> 결과 6인데 개수 0이 연속 3회면 중단합니다

취지에 동의합니다. 다만 §1.3을 적용하면 **삭제 개수 0이 곧 진행 0은
아닙니다** — 실패를 건너뛰는 것도 진행이기 때문입니다. 한 번의 예산이 전부
실패한 unlink에 쓰이면 개수 0으로 나오는데, 그때 중단하면 **수렴 중인 스윕을
끊습니다.**

응답에 실패 개수를 더하면 판정이 정확해집니다.

| 필드 | 크기 | |
|---|---|---|
| 결과 | 1 B | |
| 삭제 개수 | 2 B | 이 호출에서 지운 수 |
| **실패 개수** | **2 B** | **이 호출에서 건너뛴 수 (신규)** |

```
중단 조건:  삭제 개수 + 실패 개수 == 0 이 연속 3회
```

이 값이 0이면 아무것도 시도하지 못한 것이므로 **진짜 진행 없음**입니다.
3회 규칙은 그대로 두시고 키만 바꾸시면 됩니다.

### 3.2 화면에도 쓸 데가 있습니다

```
카드 비우기 — 61개 중 50개 삭제됨…          진행 중
카드 비우기 — 59개 삭제, 2개 삭제 불가       완료
```

누적 삭제와 누적 실패를 따로 보이면 "다 지워졌다"와 "거의 다 지워졌다"가
구분됩니다. 되돌릴 수 없는 작업에서 이 구분은 남겨두는 편이 맞다고 봅니다.

## 4. 시간 예산 — 확인한 값

500 ms로 잡고, 예산은 매 `f_unlink` **직전**에 확인합니다. 최악은 예산 경계에서
시작한 unlink 한 번이 얹히는 경우입니다.

| | |
|---|---|
| 예산 | 500 ms |
| 초과 한도 | + `f_unlink` 1회 |
| 실측 SD 블로킹 최대 | 52.1 ms (n=3,882, 보고 #22) |
| **최악 합계** | **≈ 552 ms** |
| IWDG | **2.0 s** (`Prescaler 32`, `Reload 1999`, `main.c:961`) |
| 여유 | **약 3.6배** |

부팅 스캔이 128개에서 390 ms로 5배를 둔 것(보고 #27)보다는 낮지만, 스윕은
`f_unlink`만 하고 헤더를 읽지 않으므로 편차가 더 작습니다.

`v_SD_BusyWait_Yield()`가 IWDG를 갱신하지 않는다는 것도 원본에서 다시
확인했습니다.

```c
// User/Drv/src/tim.c:92
// Deliberately absent: HAL_IWDG_Refresh(). Feeding the watchdog here would let a
// wedged card stall posture control for the full SD timeout instead of resetting;
```

**의도된 부재입니다.** 스윕 안에서도 갱신하지 않겠습니다 — 예산으로 막는 것이
맞고, 갱신으로 막으면 물린 카드가 자세 제어를 붙잡는 경로가 열립니다.

## 5. 별건 — 삭제 실패가 백필 오류로 나가고 있습니다

`0x58`을 쓰면서 발견했습니다. **현재 `0x57`의 코드입니다.**

```c
// User/Drv/src/sd.c:1169
if(f_unlink(c_path) != FR_OK){
	v_log_err_raise(SD_LOG_ERR_BACKFILL, 0);    // ← reason 5 = "backfill read failed"
	return 4;
}
```

삭제가 실패했는데 **오류 이벤트는 백필 실패(reason 5)로 나갑니다.** 그쪽이
받는 ERR 이벤트에 그대로 보이는 값이므로 화면에도 잘못 뜹니다.

`0x58`도 실패를 이벤트로 알려야 하니 같이 정리하는 편이 낫다고 봅니다.

```c
SD_LOG_ERR_DELETE = 7,   // 삭제 실패; detail = 실패 개수
```

**아직 넣지 않았습니다.** 이벤트 reason은 그쪽이 해석하는 값이라 합의 후에
넣겠습니다 (Q79).

## 6. 회신 요청

| # | 항목 | 참조 |

| **Q77** | 두 층 규칙(**파일 단위 = 건너뛰고 셈 / 카드 단위 = 즉시 중단**)과 **실패 개수 2 B 추가**에 이견 있습니까? | §1.3 · §3.1 |
| **Q78** | "스윕은 끝났고 N개가 안 지워짐"을 **결과 4**로 둘까요, **새 코드**로 둘까요? | 아래 |
| **Q79** | 오류 이벤트 **reason 7 = 삭제 실패** 신설에 이견 있습니까? | §5 |

**Q78 보충.** 결과 코드를 공유하자는 §3의 원칙(Q73)이 양쪽으로 작동합니다.

| | 결과 4 재사용 | 새 코드 |
|---|---|---|
| 근거 | 둘 다 "삭제 실패" | PC 문구가 다름 — "카드 오류로 중단" vs "완료, N개 불가" |
| 부담 | 없음 | 코드 1개 |

**저희는 나누는 쪽이 낫다고 보지만 강하게 주장하지 않습니다.** 화면에 어떻게
쓰실지가 판단 기준이고, 그건 그쪽이 더 잘 아십니다.

Q77 · Q78이 정해지면 **§6.10 델타를 보내겠습니다.** Q79는 델타에 포함하되
따로 표시하겠습니다 — 기존 `0x57`도 함께 고쳐지는 항목이라 성격이 다릅니다.

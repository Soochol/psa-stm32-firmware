# 검증 절차 — 색인 "최근 예약" (`logIndexRecentReserve`)

> 대상 구현: `User/Drv/src/sd.c` — `SD_LOG_IDX_RECENT 64`
> 사양: `docs/SPEC_PROPOSAL_logIndexRecentReserve.md`
> **이 저장소에는 자동 테스트 하네스가 없습니다.** 아래는 실장치 수동 절차입니다.

## 준비

카드에 로그 파일을 **128개 넘게** 올려 둡니다 (예: 200개). 파일명은
`<bootId:08X>_<fileIndex:04X>.psa`이고, 헤더가 정상이어야 색인에 듭니다.
장치를 부팅하고 RTT 로그를 봅니다.

## 검증 1 — 최신 파일이 목록에 있는가 (이 변경의 목적)

부팅 로그에서:

```
indexed 128 of 200 file(s) on card
```

이어서 `reqLogFiles(0x45)`를 페이지 끝까지 받아 봅니다.

| 확인 | 기대 |
|---|---|
| 목록 항목 수 | 128 |
| 목록 **마지막** 항목 | 카드에서 **가장 최신** 파일 (변경 전에는 128번째 오래된 파일) |
| 목록 중간 | `(bootId, fileIndex)`가 **건너뛰는 구간**이 있음 — 정상 |
| `reqLogStatus(0x43)` `filesOnCard` | 200 (색인 수가 아니라 카드 실제 수) |
| `evtLogError` reason 6 | 발생, detail = 200 |

## 검증 2 — 구멍 구간 조회가 오답을 주지 않는가

목록에서 **빠진** 구간의 `bootId`와 `seq`를 골라 `reqLogRead(0x44)`로 요청합니다.

- **기대**: result `1`(bootId 자체가 목록에 없음) 또는 `2`(해당 seq를 담은 파일이
  목록에 없음).
- **불합격**: 다른 파일의 레코드가 돌아오는 것. `b_bf_find`가 항목마다
  `firstSeq <= seq <= lastSeq` 범위 검사를 하므로 발생하면 안 됩니다.

## 검증 3 — 파일 번호 덮어쓰기가 없는가 ⚠️ 가장 중요

**이것만은 반드시 확인해야 합니다.** 실패하면 숨김이 아니라 **실제 데이터 손실**입니다.

같은 `bootId`로 파일이 이미 있는 상태에서 부팅했을 때(플래시 쓰기 실패로
bootId가 재사용된 경우), 새 파일이 기존 번호를 재사용하면 안 됩니다.

- 부팅 로그에 `bootId %u already has files, resuming at #%u`가 뜨는지.
- **이 검사는 색인 상한과 무관하게 카드 전체를 대상으로 돌아야 합니다.**
  구현상 `u32_log_scan_dir`의 walk 안, 색인/후보 분기보다 **앞**에 있습니다.
  분기 뒤로 옮기거나 128에서 멈추면 이 보호가 사라집니다.

## 검증 4 — 세션 중 최신 파일도 목록에 드는가

색인이 128로 찬 상태에서 장치를 1시간 이상 켜 두어 파일이 회전되게 합니다
(또는 회전 주기를 임시로 줄여 재현).

| 확인 | 기대 |
|---|---|
| 회전 직후 `reqLogFiles` | **새로 닫힌 파일이 목록 마지막에 있음** |
| 목록 항목 수 | 여전히 128 (예약 구역에서 가장 오래된 항목이 밀려남) |
| `filesOnCard` | **증가** — 축출된 파일은 카드에 그대로 있으므로 감소하면 안 됨 |
| 앞 64칸 | 변화 없음 (회수 대기분은 보호됨) |

## 빌드 단계에서 이미 걸리는 것

- `SD_LOG_IDX_RECENT`가 0이거나 `SD_LOG_IDX_MAX` 이상이면 `_Static_assert`가
  컴파일을 막습니다 (예약이 회수 큐를 다 먹으면 카드를 비울 수 없게 되므로).

## 1. 임계값 — 1000 ms

```c
// User/Edit/src/comm_esp.c:1002
void v_ESP_Tout_Handler(){
	if(i_toutAct && _b_Tim_Is_OVR(u32_Tim_1msGet(), u32_toutRef, 1000)){
		i_toutAct = 0;
		LOG_WARN("COMM_ESP", "ESP STAT response timeout - retrying");
	}
}
```

### 1.1 거는 곳과 푸는 곳

| | 위치 | 동작 |
|---|---|---|
| **걺** | `comm_esp.c:990` | STAT 송신 직후 — **단, 이미 걸려 있으면 다시 안 겁니다** |
| **품** | `comm_esp.c:834` | `v_ESP_StatProc` — STAT 계열 수신 |
| **발화** | `comm_esp.c:1002` | 1000 ms 경과 |

```c
// 990 — 거는 곳
if(i_toutAct == 0){          // ← 이미 걸려 있으면 갱신하지 않습니다
	i_toutAct = 1;
	u32_toutRef = u32_Tim_1msGet();
}
```

### 1.2 ⚠️ 그래서 "한 응답의 예산"이 아닙니다

**이 부분이 §1.4의 측정 계획에 영향을 줍니다.**

STAT은 10 Hz로 나가는데 타이머는 **응답 없는 첫 STAT에서만** 걸리고, 그 뒤
9번의 STAT은 타이머를 건드리지 않습니다. 그리고 STAT 계열 수신 **아무거나**
오면 풀립니다.

```
t=0     STAT #1 송신 → 타이머 걺
t=100   STAT #2 송신 → 이미 걸려 있음, 그대로
t=200   STAT #3 송신 → 그대로
  ...
t=350   ESP32 응답 도착 → 타이머 풀림          경고 없음
t=400   STAT #5 송신 → 다시 걺
```

| | |
|---|---|
| **경고가 뜨는 조건** | **1초 동안 STAT 계열 수신이 0건** |
| 개별 응답 지연 한도 | 사실상 **1000 ms까지 무해** |
| 그 창 안의 STAT 기회 | **약 10회** |

**`handleStatusMessage()`가 800 ms 걸려도 경고는 안 뜹니다.** 그 사이 저희가
STAT을 8번 더 보냈어도, 응답 하나가 1초 안에 오면 풀립니다.

> **§1.4의 측정을 하실 때**, "STAT 수신 → `sendResponse`" 소요를 1000 ms와
> 직접 비교하지 마십시오. 그렇게 보면 여유가 실제보다 빡빡하게 나옵니다.
> **재실 기준은 "연속으로 응답을 못 낸 시간"** 입니다 — 한 건이 느린 것과
> 1초 내내 하나도 못 내는 것은 다릅니다.

`parseSensorData` → `bleSensorHubEnqueueSample` → `logSensorDataFormatted`가
응답보다 앞에 있다는 지적은 유효합니다. 다만 그 경로가 **한 번 느린 것**으로는
이 경고가 안 나오고, **1초 내내 막혀야** 나옵니다. BLE 큐가 가득 차 블로킹된다면
그 조건이 될 수 있습니다.

### 1.3 답을 찾다 저희 결함 두 개가 나왔습니다

**① 상수가 있는데 안 씁니다.**

```c
// User/Edit/inc/comm_esp.h:17
#define ESP_COMM_TIMEOUT   1000   // Communication timeout (ms)
```

**정의돼 있고 사용처가 0건입니다.** `comm_esp.c:1002`는 리터럴 `1000`을
씁니다. 값이 같아서 지금은 문제가 없지만, 상수를 고쳐도 동작이 안 바뀝니다 —
`sd.c:1169`의 reason 5와 같은 종류입니다. 이름이 있는데 코드가 안 봅니다.

**② `"retrying"`은 사실이 아닙니다.**

```c
i_toutAct = 0;
LOG_WARN("COMM_ESP", "ESP STAT response timeout - retrying");
```

**재시도하는 코드가 없습니다.** 플래그만 내리고 로그를 찍습니다. 다음 STAT은
원래의 10 Hz 일정으로 나가는 것이고, 타임아웃과 무관합니다.

> 그쪽이 이 로그를 보고 **"재시도 메커니즘이 있다"** 고 가정하셨다면 그 가정은
> 틀립니다. 링크 복구는 그냥 다음 STAT이 나가고 그것에 응답이 오는 것입니다.

**둘 다 다음에 코드를 만질 때 고치겠습니다.** 지금 고쳐도 동작은 안 바뀌고,
그쪽 측정 중에 펌웨어를 바꾸지 않는 편이 낫습니다.

## 2. #52 철회 접수 — #55 §2를 정정합니다

> #55 §2를 "원인 규명됨"이 아니라 "재현 안 됨"으로 남기시길 권합니다

**받아들입니다.** 보고 #55 §2에 *"그쪽 #52 §2.1의 조작 창 설명이 맞았습니다"*
라고 적었는데, 그 근거가 없어졌습니다. **이 문서로 정정합니다.**

| | #55 §2 | **정정** |
|---|---|---|
| 상태 | 원인 규명, 항목 닫음 | **재현 안 됨** |
| 아는 것 | — | 지금은 정상이고, 창 A·B의 원인은 **불명** |

**다시 열지는 않겠습니다.** 그쪽 권고대로입니다 — 재현되지 않는 것을 열어두면
미결 목록만 길어집니다.

### 2.1 §2의 자기 평가에 관하여

> 같은 문서에서 한쪽으로는 그쪽 산식을 정정하면서, 다른 쪽으로는 확인하지 않은
> 설명을 사실처럼 적었습니다

**측정과 추정을 구분해 적겠다는 것에 저희도 함께 하겠습니다.** 저희 문서도
같은 문제가 있습니다 — 보고 #48은 코드를 읽고 낸 추론이 대부분인데 실측과 같은
서식으로 적혀 있습니다.

> 한 가지는 짚어 두겠습니다. **저희가 #51 §4를 "결함"이 아니라 "관측"으로 올린
> 것**이 이번에 도움이 됐습니다. 원인을 저희가 지목했더라면 그쪽 철회와 함께
> 두 번 뒤집혔을 것입니다. #55 §3의 부팅 스캔도 같은 이유로 관측에 두었습니다.

## 3. §4 `FR_NO_FILE`·`FR_NO_PATH` — 이견 없습니다

**그쪽 분류가 맞습니다.** `0x57`은 단건 삭제이므로 "이미 없다"는 카드 이상이
아닙니다. 저희 #48 §1.3이 그 둘을 실패로 세지 않은 것과 같은 판단입니다.

§6.7 표에 4·5를 넣는 제안도 동의합니다. 다음 델타에 포함하겠습니다.

### 3.1 그런데 그 경로에 유령이 남습니다

확인하다 찾았습니다. **현재 코드는 `FR_NO_FILE`이면 결과 4를 반환하고 거기서
끝납니다.**

```c
// User/Drv/src/sd.c:1169
FRESULT e_del = f_unlink(c_path);
if(e_del != FR_OK){
	v_log_err_raise(SD_LOG_ERR_DELETE, (uint16_t)e_del);
	return 4;                    // ← 인덱스 항목을 지우기 전에 빠집니다
}
// 아래의 인덱스 정리에 도달하지 못합니다
```

카드에 없는 파일이 **인덱스에는 그대로 남습니다.**

```
0x45 목록에 계속 나옴  →  PC가 다시 지목  →  또 FR_NO_FILE  →  또 결과 4
                                                    └── 재부팅 전까지 반복
```

**이 항목은 재부팅해야 사라집니다.** 부팅 스캔이 카드를 다시 읽으니까요.

| | |
|---|---|
| 위험도 | 낮음 — 데이터 손실 없음, 로깅 무관 |
| 발생 조건 | 인덱스와 카드가 어긋남 (정상 운용에서는 드묾) |
| 증상 | 지워지지 않는 항목이 목록에 남음 |

**고치는 방향은 두 가지이고 프로토콜 의미가 갈립니다.**

| 안 | 결과 | 뜻 |
|---|---|---|
| **A** | `FR_NO_FILE` → 인덱스에서 제거하고 **결과 0** | "지워진 상태를 달성했다" |
| B | 인덱스에서 제거하되 **결과 4 유지** | "실패했지만 목록은 정리했다" |

**저희는 A를 권합니다.** 호출자의 목적은 "그 파일이 카드에 없는 상태"이고,
이미 그렇습니다. 다만 `filesOnCard` 감소가 실제 카드 상태와 어긋날 수 있어
그쪽 화면에 영향이 갑니다.

> **아직 고치지 않았습니다.** 결과 코드 의미가 바뀌는 변경이라 합의 후에
> 넣겠습니다 — Q80으로 묻습니다.

## 4. v1.9 확인

다섯 항목 모두 델타대로 들어간 것을 확인했습니다.

```
1023  reason 7의 detail은 FRESULT입니다 (인용문 그대로)
1029  FR_DENIED(7) · FR_LOCKED(16) | 그 파일 하나의 문제
1037  주의: reason 7과 FR_DENIED가 둘 다 7입니다
1126  결과 4 — evtLogError reason 7을 함께 발신 ⭐ v1.9
```

> §6.9.1의 "이벤트가 가려질 수 있다"가 특히 유용했습니다

그 성질은 **저희도 이번에 코드를 읽으며 다시 확인한 것**입니다. 오래된
설계인데 문서화된 적이 없었습니다.

### 4.1 §5 부팅 스캔 — 판단에 동의합니다

> 단일 표본으로 사양서를 고치면 다음 표본에서 또 고쳐야 합니다

**맞습니다.** 그리고 표본이 굳었을 때 고칠 것에 대한 지적도 정확합니다.

> 모델 자체보다 **"이 값은 선형 근사이고 상단에서 낙관적일 수 있다"** 는 문장이
> 더 중요할 듯합니다

**이게 더 중요합니다.** 3.0을 3.4로 바꾸는 것은 다음 표본에서 또 틀리지만,
"상단에서 낙관적"이라는 성질은 `f_open`의 디렉터리 탐색이 파일 수에 비례하는
한 계속 참입니다.

표본은 부팅할 때마다 쌓입니다. 두어 개 더 모이면 알려드리겠습니다.

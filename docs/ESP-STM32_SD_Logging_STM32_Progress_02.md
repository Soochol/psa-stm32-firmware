## 1. 🔴 Q27이 실제 결함을 잡았습니다

지적하신 대로입니다. **결함 주입 훅이 하나뿐이었고, 그것으로는 플레이스홀더를 만들 수 없었습니다.**

| 경로 | 발생 조건 | 결과 |
|------|-----------|------|
| 쓰기 실패 | `f_write` 실패 / 부분 쓰기 | **로테이션** (§7.4) — 파일이 갈라짐 |
| 길이 계약 위반 | `statPayload` 길이 ≠ 64 | **플레이스홀더** (`flags` bit1) |

**두 경로는 완전히 다른데 훅은 쓰기 실패용 하나뿐이었습니다.** 회신 v1.4 §5에서
"결함 주입 훅으로 플레이스홀더를 만들겠다"고 적었는데, 그대로 하면 **로테이션만 나오고
플레이스홀더는 안 나옵니다.** 절차대로 카드를 구웠다면 `flags` bit1 경로가 양쪽 모두
검증되지 않은 채 남았을 겁니다.

**조치** (`828abfe`): `u8_sd_fault_inject_len` 훅을 `v_SD_Log_Write`에 추가했습니다.
길이 검사를 실패시켜 **실제 현장에서 도는 코드 경로 그대로** 플레이스홀더가 기록됩니다.

```
u8_sd_fault_inject_len  = 100  →  100번째 샘플이 플레이스홀더
u8_sd_fault_inject_write = 3   →  3번째 쓰기 실패 → 로테이션
```

두 훅을 같은 세션에서 쓰면 **플레이스홀더 1개 + 파일 2개**를 한 번에 얻습니다.
요청하신 "로테이션 사례"와 "플레이스홀더"가 동시에 담기고, 쓰기 실패를 나중에 발동시키면
두 번째 파일의 `firstSeq != 0`도 확보됩니다.

두 심볼 모두 **기본 빌드 산출물에 존재하지 않음**을 링크된 이미지에서 확인했습니다.

## 2. Q24~Q28 회신

### Q24. `flags` bit0 판정 시점 → **(a) 확정. 선호와 일치합니다**

구현은 이미 (a)입니다.

```
b_ESP_Transmit()  →  b_Uart_ESP_Out()  →  링버퍼에 자리가 있으면 true
```

**(b) DMA 완료를 기다리는 것은 채택하지 않았습니다.** 레코드는 샘플 시점에 조립되어
RAM 배치에 들어가는데, DMA 완료 콜백은 그 뒤에 비동기로 옵니다. 기다리려면 레코드를
붙잡아 두었다가 나중에 비트를 고쳐 써야 하고, 그러면 **레코드가 불변이 아니게** 됩니다.
(c)는 말씀대로 시점상 불가능합니다.

> 이 비트가 실제로 잡는 것: **링버퍼 포화**입니다. 링은 넘칠 때 오래된 바이트를
> 덮어쓰므로(전송 중인 프레임이 깨짐), 넘칠 상황이면 **적재를 거부**하고 그 사실을
> 이 비트로 남깁니다. 백필이 회선을 많이 쓰는 구간에서 의미가 있습니다.

**사양서에 (a)로 못 박아 주십시오.**

### Q25. `errorMask` 스냅샷 시점 → **맞습니다. 단 중요한 단서가 하나 있습니다**

레코드 조립 시점의 `e_Mode_Get_Error()` 값이 맞고, `errInit`(0x90) 전송과 무관합니다.

> #### ⚠️ 다만 **비트는 해제되지 않습니다**
>
> `User/Edit/src/mode.c:166-168`
>
> ```c
> void v_Mode_Set_Error(e_modeERR_t e_type){
> 	e_modeError |= e_type;      // OR만 있고 해제 경로가 없습니다
> }
> ```
>
> 즉 `errorMask`는 **현재 상태가 아니라 누적 이력**입니다.
>
> | 복원 가능 여부 | 항목 |
> |---|---|
> | ✅ 가능 | 오류가 **언제 처음 발생했는지** — 해당 비트가 처음 나타나는 레코드 |
> | ❌ 불가 | 오류가 **언제 해소됐는지** — 비트가 내려가지 않습니다 |
>
> 회신에 적으신 "시작/해소를 레코드 단위로 복원"은 **시작만** 성립합니다.
> 병합 도구가 해소 시점을 표시하지 않도록 주의해 주십시오.

이 동작은 기존 펌웨어의 것이며 이번 작업에서 바꾸지 않았습니다.
**해제가 필요하시면 별도 논의**가 필요합니다 — 오류 비트는 `modeERROR` 진입과
LED 패턴에도 연결되어 있어 안전 로직에 영향이 있습니다.

### Q26. `tickMs` BE 전환 → **포함됐습니다. 오프셋 4~7은 Big-Endian입니다**

레거시 68 B 포맷의 LE와 다릅니다. 레거시 경로는 §16.3-4 커밋에서 제거되었으므로
혼동할 코드가 남아 있지 않습니다.

골든 픽스처에서 확인하실 수 있습니다 — `tickMs = 1000`이 `00 00 03 E8`로 기록됩니다.

`verify_format.py`가 오프셋을, `validate_psa.py --decode`가 실제 값을 각각 검사합니다.

### Q27. 플레이스홀더 발생 경로 → **§1 참조. 훅을 하나 더 만들었습니다**

지적하신 대로 두 종류가 필요했고, 추가했습니다. **실제 경로와 동일**합니다 —
`v_SD_Log_Write` 진입 직후 길이를 0으로 만들어 이후 흐름은 현장과 완전히 같습니다.

### Q28. `sdmax` 중간 실측값 → **제공할 수 없습니다. 대신 계측을 보강했습니다**

죄송합니다. **이 작업 환경에 대상 보드가 없어 계측을 한 번도 돌리지 못했습니다.**
값은 실기에서만 나옵니다.

> #### 대신 한 세션에서 더 많이 건지도록 계측을 고쳤습니다 (`bfd1943`)
>
> 기존에는 **최대값 하나**만 나왔는데, 그것만으로는 `SD_TIMEOUT_BUSY`를 정할 수 없습니다.
> 600 ms가 **1만 번 중 한 번** 나오는 것과 **10번 중 한 번** 나오는 것이 같은 숫자로
> 보이는데, 두 경우의 판단은 정반대이기 때문입니다.
>
> 로그 간격 8버킷 히스토그램을 추가했습니다. RTT에 이렇게 나옵니다.
>
> ```
> [D]cyc=45us sdmax=612us n=1234     ← 최대 612 us, 계수된 대기 1,234건
> [D]sdh 980 210 40 4 0 0 0 0        ← <1ms:980 <2:210 <5:40 <10:4 나머지 0
> ```
>
> 버킷 상한(ms): `1 / 2 / 5 / 10 / 50 / 100 / 500 / 그 이상`
>
> | 관측 | 결론 |
> |------|------|
> | `>=500ms` 열이 0이 아님 | `BUSY 600ms`가 위험 → 상향 |
> | `<100ms`·`<500ms`에 꼬리 | GC 지연 발생 중, 현재 값으로 여유 |
> | 전부 `<10ms` 이하 | 여유 충분 → `BUSY`를 낮춰 이상 감지를 빠르게 |
> | `sdmax`는 큰데 `n`이 작음 | 표본 부족, 더 돌려야 함 |
>
> `v_Tim_SD_Block_Clear()`로 초기화하면 **로깅만 도는 구간**과 **백필 병행 구간**을
> 나눠 재서 백필의 기여를 분리할 수 있습니다.
>
> 비용은 RAM 32 B, 대기 1건당 비교 루프 한 번입니다.

`SD_TIMEOUT_*` 잠정치의 **산출 근거**도 함께 공유합니다. 실측 시 이 예상과 비교하시면
판단이 빠를 겁니다.

| 대기 | 잠정치 | 산출 근거 | 예상 실측 |
|------|--------|-----------|-----------|
| `READY` | 200 ms | 연산 시작 전 카드 ready. 정상 카드는 즉시 | 수십 µs |
| `XFER` | 100 ms | 512 B ÷ (4비트 × 39.2 MHz) ≈ **26 µs** | 수백 µs (커맨드 오버헤드 포함) |
| `BUSY` | 600 ms | **여기에 GC 지연이 삽니다.** SD 스펙 공칭 250 ms, 저가 카드 500 ms+ | 평시 수 ms, 간헐 수백 ms |

**오탐 위험이 있는 것은 `BUSY` 하나뿐**입니다. 나머지 둘은 정상 카드 기준 3자리 배수
여유가 있습니다. 실측에서 `sdmax`가 600 ms에 근접하면 `BUSY`만 올리시면 됩니다.

> 참고로 이 값들의 합(900 ms)이 IWDG 2초 안에 들어가는 것이 설계 제약입니다.
> `BUSY`를 1,200 ms 이상으로 올리면 그 제약이 깨지므로, 그 경우 재시도 정책
> (현재 3회 연속 실패 후 재마운트)을 함께 조정해야 합니다.

## 5. 새로 발견해 조치한 것 2건

### 5.1 `deviceId` 변경 후 구 파일이 회수 불가였습니다 (`d6a772c`)

부팅 스캔과 백필 모두 **현재 `deviceId` 디렉터리만** 봤습니다. 그런데 `deviceId`는
장치 수명 중에 바뀝니다 — 모든 장치가 `0x23`을 받기 전까지 `/LOG/UNKNOWN/`에 기록하니까요.

```
부팅 1  →  /LOG/UNKNOWN/*.psa 기록,  이후 0x23 수신
부팅 2  →  스캔이 /LOG/<MAC>/ 만 열어봄
           UNKNOWN 파일이 reqLogFiles 목록에서 사라짐 → 백필 불가
```

카드에는 멀쩡히 있는데 **아무도 물어볼 수 없는 상태**가 됩니다.
§13 시나리오 6이 규정한 정상 경로에서 발생합니다.

**조치**: 스캔이 두 디렉터리를 모두 훑고, 인덱스 항목마다 출처를 기록해 백필이 올바른
경로를 엽니다. **파일은 옮기지 않습니다** — 이름 변경도 §8.5가 금지하는 "기록된 로그 수정"에
해당한다고 보았습니다.

### 5.2 ㉗ — 파일 인덱스 상한을 256 → **128**로 낮췄습니다

부팅 스캔이 파일당 `f_open` + 헤더 512 B 읽기이고, `f_open`은 디렉터리를 순회하므로
**파일 수에 대해 준-2차식**입니다. 256개면 부팅 블로킹이 1초를 넘길 수 있어 IWDG 2초에
너무 가깝습니다. 128이면 수백 ms 수준입니다.

하루 약 15파일(리셋 7~8 + 시간 로테이션) 기준 **8일치**입니다. 백필이 매일 도는 운영에서는
충분하다고 보는데, **더 필요하시면 알려 주십시오** — 부팅 스캔을 지연 로딩으로 바꾸면
상한을 올릴 수 있습니다.

초과분은 카드에 그대로 남아 물리 회수로 확보 가능합니다.

## 6. 검증 현황

```bash
python3 docs/fixtures/verify_format.py .                        # 57 passed, 0 failed
python3 docs/fixtures/validate_psa.py docs/fixtures/golden_v1.psa   # VALID
```

`verify_format.py`는 **펌웨어 소스에서 상수를 파싱**해 규격과 대조합니다. 사본을 두지 않으므로
코드가 규격에서 벗어나면 실패합니다. 오프셋 하나와 카테고리 상한 하나를 일부러 틀리게 해
3건이 잡히는 것을 확인했습니다.

| 검사군 | 항목 |
|---|---|
| 커맨드 코드 / 파서 범위 | 20 |
| 레코드·헤더 레이아웃 | 21 |
| flush 정책 | 3 |
| **프레임 인코딩 (규격 예제 9종)** | 11 |
| CRC (참조 + 펌웨어 링크) | 2 |

빌드는 매 커밋마다 `stm32_debug` / `stm32_release` 양쪽 확인했고, 변경 파일에 신규 경고가
없습니다. 결함 주입 빌드(`-DPSA_FAULT_INJECT=1`)도 별도 확인했습니다.

## 1. Q20 — 배터리 삽입 1회 = 리셋 2회, **맞습니다**

`User/Edit/src/mode.c:2646-2652`

```c
if(u32_RTC_Read_BKUP() == 0xA5A5){
    v_RTC_Write_BKUP(0x0000);        // 표식 소비
    v_Mode_SetInit(modeBOOTING);     // warm boot
}
else{
    LOG_INFO("MODE", "Cold boot detected, ...");
    v_Mode_SetInit(modeOFF);         // cold boot
}
```

`0xA5A5` 표식은 `v_Mode_WakeUp()`이 리셋 직전에만 씁니다(`mode.c:2195`).
배터리 삽입 시에는 VBAT가 끊겨 백업 레지스터가 지워지므로 표식이 없고, `modeOFF`로 갑니다.

**따라서 §14.5 Q20의 흐름도와 산정이 그대로 맞습니다.**

| 사건 | 리셋 소비 |
|------|-----------|
| 배터리 삽입 | **2** (콜드 부팅 + WAKE_UP 리셋) |
| 전원 버튼 off → on | **1** (WAKE_UP 리셋만) |

7~8 리셋/일, 소거 주기 약 1.4년, 잔여 임계값 64슬롯 = 8일치 여유 —
**현재 값(64) 유지에 동의합니다.**

## 2. 🟡 ㉕ 확인 요청 — 작업 중 리셋 후 자동 재개하지 않습니다

Q20을 확인하다가 드러난 사항입니다. **결함이 아니라 현 사양의 동작**이지만,
§13 시나리오 2의 수행 절차와 운영 해석이 달라지므로 공유드립니다.

### 2.1 동작

`0xA5A5` 표식은 `modeBOOTING` 진입 시 **즉시 소비되어 `0x0000`으로 지워집니다**
(`mode.c:2647`). 즉 **정상 작업 중에는 표식이 없는 상태**입니다.

따라서 작업 중 어떤 이유로든 리셋이 발생하면:

```
작업 중 (bootId=50, 샘플링) → 리셋
  ↓ BKUP == 0x0000  (표식 없음)
modeOFF → 1.1초 → STOP
  ↓ 전원 버튼 롱프레스가 있을 때까지 대기
(무기한)
```

**전원 버튼을 누르기 전까지 로깅이 재개되지 않습니다.**

원인별로 동일합니다.

| 리셋 원인 | 결과 |
|-----------|------|
| 배터리 방전·순단 (VBAT 소실 → 표식 소실) | `modeOFF` |
| 커넥터 유격 | `modeOFF` |
| **IWDG 워치독 리셋** (VBAT 유지, 표식은 이미 `0x0000`) | `modeOFF` |
| 소프트웨어 리셋 | `modeOFF` |

### 2.2 영향

**(a) §13 시나리오 2 — 회당 수동 조작이 필요합니다**

> "작업 중 전원 순단 20회 → 부팅마다 새 파일, `bootId` 중복 없이 증가"

순단 후 장치가 스스로 부팅해 기록을 재개하지 않으므로, **20회 각각에 대해
전원 버튼 롱프레스가 필요합니다.** 자동화 스크립트로는 수행할 수 없습니다.
합격 기준 자체는 그대로 유효하며, **절차에 "회당 전원 버튼 조작" 한 줄만 추가**해 주십시오.

또한 순단 1회는 **리셋 2개**를 소비합니다(콜드 부팅 + 사용자 전원 켜기).
시나리오 2를 20회 수행하면 슬롯 40개가 소모되니 시험 전 잔여 슬롯을 확인하겠습니다.

**(b) 운영 — 작업자가 눈치채야 합니다**

작업 중 배터리가 빠지거나 순단이 나면 장치는 꺼진 상태로 남습니다.
작업자가 알아채지 못하면 **남은 교대 시간 전체가 미기록**입니다.

> **다만 관제에서는 보입니다.** §12의 ⑯ 규칙(0x43 연속 무응답 → 링크 다운 / 전원 꺼짐)이
> 정확히 이 상황을 잡습니다. STOP 상태의 장치는 UART에 응답하지 않으므로
> **seq 정체가 아니라 무응답으로 나타나고**, ⑯이 이를 별도 경보로 분류합니다.
> 이 규칙을 넣어 두신 것이 결과적으로 이 케이스까지 덮었습니다.

**(c) `SD_TIMEOUT` 축소의 부수 효과가 생각보다 큽니다**

회신 v1.2 Q11에서 `SD_TIMEOUT`을 900 ms로 자른 이유는 "워치독 리셋 방지"였는데,
워치독 리셋이 **단순히 2초분 데이터 손실이 아니라 세션 종료**임이 확인되었습니다.
카드가 한 번 물리면 그 교대의 나머지가 통째로 날아갑니다. 조치해 두길 잘했습니다.

### 2.3 확인 요청

이 동작은 **웨어러블 장치가 전원 복구 시 스스로 켜지지 않도록** 하는 안전 설계로 보입니다.
STM32 측에서 임의로 바꿀 사안이 아니라고 판단했습니다.

> **자동 재개가 필요한지 제품 관점에서 판단해 주십시오.**
>
> - **현행 유지** → §13 시나리오 2 절차에 수동 조작 명시. 추가 작업 없음
> - **자동 재개 희망** → 별도 논의 필요. 웨어러블이 전원 인가만으로 히터·액추에이터를
>   포함한 상태로 기동하는 것이라 **안전 검토가 선행**되어야 합니다

저희 권고는 **현행 유지**입니다. 데이터 완전성은 §12 ⑯ 경보로 확보되고,
자동 기동은 안전 측면의 비용이 더 큽니다.

## 3. Q21 — 레거시 제거, **§16.3-4 커밋에 함께 넣겠습니다**

제거 자체는 동의합니다. 68 B 포맷에 `seq`·CRC·`bootId`가 없어 병합 키를 만들 수 없다는
판단이 맞고, `sensor_fmt.txt` 정정을 병합 도구에 넣지 않으신 것도 옳습니다.

**다만 제거 시점을 §16.3-4와 같은 커밋으로 잡겠습니다.** 이유는 두 가지입니다.

| # | 이유 |
|---|------|
| 1 | 지금 떼면 §16.3-4~6이 올라올 때까지 **아무 데이터도 남지 않는 구간**이 생깁니다. 신규 포맷이 그 자리를 대신할 준비가 되기 전에 비우는 셈입니다 |
| 2 | **Q16 실측(§14.3)의 유일한 부하원이 이 SD 트래픽입니다.** 진행 보고 #01 이후 `sdmax` 계측을 넣었는데, 로깅을 떼면 SD 접근이 사라져 `SD_TIMEOUT_*` 확정에 필요한 데이터를 못 모읍니다 |

즉 **신규 포맷이 들어오는 순간 레거시가 나가는** 형태가 됩니다. 중간에 빈 구간이 없습니다.

> **더 빨리 제거하길 원하시면 알려 주십시오.** 즉시 처리 가능하며,
> 그 경우 Q16 실측은 §16.3-6(2초 flush) 이후로 미루겠습니다.

## 4. ❓ 신규 확인 요청 — 레코드가 0개인 파일의 `lastSeq`

### 4.1 고아 파일 — 생기지 않습니다 (Q20 확인 회신)

§8.3의 lazy 생성(`v1.4:1033`)대로 구현하겠습니다. **첫 레코드를 쓰는 시점에 헤더와
레코드를 함께 기록**하므로, `modeOFF`로 끝나는 세션(리셋 ①)은 파일을 만들지 않습니다.

→ **`reqLogFiles` 목록에 나타나지 않습니다. 조치 불필요하다는 이해가 맞습니다.**

`bootId` 목록에 빈 구간(예: 42, 44, 46만 존재)이 생기는데, PC는 애초에 "존재해야 할
`bootId` 전체"를 알 수 없으므로 문제되지 않습니다. 데이터 손실 탐지는 §12 헬스 경로가
담당합니다.

### 4.2 다만 한 가지 경계가 정의되어 있지 않습니다

헤더 512 B는 기록되었으나 **첫 레코드 쓰기가 실패**하면 `N = 0`인 파일이 남습니다
(카드 탈거·용량 소진이 그 사이에 발생한 경우).

§6.3은 `lastSeq`를 "항목 i의 마지막 레코드 seq"로 정의하는데,
**레코드가 없으면 그런 값이 존재하지 않습니다.** 진행 보고 #01 Q12에서 합의한 산출식

```
lastSeq = firstSeq + (파일크기 - 512) / 80 - 1
```

에 `N = 0`을 넣으면 `firstSeq - 1`이 되고, `firstSeq == 0`이면 **언더플로로 0xFFFFFFFF**가
나갑니다. PC가 4,294,967,295까지의 구간을 미확보로 판단하게 됩니다.

**요청**: §6.3에 한 줄 추가해 주십시오. 저희 권고는 (a)입니다.

| 안 | 내용 | 비고 |
|----|------|------|
| **(a)** | **`N == 0`인 파일은 인덱스에 넣지 않는다** (권장) | STM32 부팅 스캔에서 제외. PC 변경 불필요 |
| (b) | `lastSeq = firstSeq - 1`을 "레코드 없음"으로 규정 | 언더플로 처리를 PC가 떠안음 |

(a)를 택하시면 STM32 부팅 스캔(§16.3-9)에서 걸러내겠습니다.
파일 자체는 삭제하지 않으므로 물리 회수 경로에는 영향이 없습니다.

## 5. Q22 / Q23

### Q22 — 보드레이트 상향 비범위 유지, 확인했습니다

`RAM_NOCACHE_D2` 여유 3,083 B는 **현 설계에서는 제약이 아닙니다.**
§15.1을 재검토하실 때만 TX 버퍼 증설과 함께 상의드리면 됩니다. 지금 조치할 것은 없습니다.

### Q23 — 실물 카드 제공, 수락합니다

양쪽 해석 일치를 픽스처가 아니라 실물로 확인하자는 판단에 동의합니다.
**§16.3-4(80 B 레코드) 구현 직후 아래를 제공하겠습니다.**

| 항목 | 내용 |
|------|------|
| 세션 | 약 **5분** (레코드 약 3,000개, 파일 1개) |
| 포함 모드 | HEALING → WAITING → FORCE_UP → FORCE_ON → FORCE_DOWN → SLEEP |
| 의도적 포함 | **플레이스홀더 레코드 1개 이상** (`flags` bit1 = 1) — §6.5 수신 측 검사 확인용 |
| 부수 제공 | 같은 구간의 `reqLogStatus`(0x43) 응답 덤프, 부팅 로그(RTT), `bootId` 값 |
| 전달 | 카드 이미지(`.img`) 또는 `.psa` 파일 직접 전달 — 편하신 쪽으로 |

> 플레이스홀더를 의도적으로 하나 넣겠습니다. §7.4는 정상 동작에서 거의 발생하지 않는
> 경로라, 실물에 없으면 **병합 도구의 `flags` bit1 처리가 검증되지 않은 채 남습니다.**
> §16.3-12의 결함 주입 훅(`PSA_FAULT_INJECT`)으로 만들 수 있습니다.

파일 헤더의 `deviceId`는 `0x23` 핸들러가 §16.3-8에 들어가므로,
§16.3-4 시점 카드는 `/LOG/UNKNOWN/` 경로일 수 있습니다. 그 상태로도 포맷 검증에는
지장이 없으나, `deviceId`까지 확인하고 싶으시면 §16.3-8 이후로 미루겠습니다.
**어느 쪽이 좋을지 알려 주십시오.**

# STM32 보고 #73 — `0x14` 유실 원인 회신 (귀측 #70 · Q84·Q85)

> **대상**: ESP32 보고 #70 (`postInitCommandDrop`) — STM32 `1.0.1-dev` 캡처
> **판정**: **귀측 분석이 맞습니다.** 유실은 저희 RX 경로 결함이고, 원인 후보를 **4건** 특정했습니다
> **정정**: **보고 #45 §3("유실 경로가 없습니다")를 철회합니다** (§6)

> **번호 충돌**: Q84·Q85가 `forceDownStall` 스레드와 겹칩니다. **Q89·Q90 재번호를 제안**합니다 (§1)

## 1. 먼저 — 번호 충돌 2건

`forceDownStall` 스레드에서 **Q84~Q88이 이미 사용**되었습니다.

- 귀측 보고 #71 §7이 Q84·Q85·Q86·Q88을 신규 등록했고,
- 저희 보고 #72가 그 4건에 회신했습니다.
- 귀측 #71 말미에도 **"다음 신규 질문 번호는 Q89부터"** 라고 적혀 있습니다.

이번 #70의 Q84·Q85는 그것과 **다른 질문**인데 같은 번호입니다. 두 스레드가
병렬로 진행되면서 대장 갱신이 엇갈린 것으로 보입니다.

**제안**: 이번 2건을 **Q89(`0x81` 이후 수신 보장) · Q90(`f_max` 재적용)** 으로
재번호합니다. 이 문서는 아래에서 `Q84→Q89`, `Q85→Q90`으로 병기합니다.
동의하시면 양쪽 `Q_NUMBER_REGISTRY.md`를 그렇게 맞추겠습니다.

> 보고 번호 `#70`도 저희 `STM32_Progress_70_forceDownStall`과 겹칩니다만, 이쪽은
> 파일명 스레드 접미사로 구분되므로 그대로 두어도 무방합니다.

## 2. ACK는 조건 없이 나갑니다 — 그래서 이건 수신 유실입니다

`0x14`의 처리 경로입니다.

```
DIR=0x20 프레임 → v_ESP_RxHandler()   comm_esp.c:318   프레임 검증
                → v_ESP_RxProc()      comm_esp.c:425   DIR==REQ 분기
                → INIT 범위 판정      comm_esp.c:430   0x10~0x29
                → v_ESP_InitProc()    comm_esp.c:466
                  case ESP_CMD_INIT_TEMP_LIMIT:  comm_esp.c:492
                    v_Mode_Set_Temp_Max(typ)
                → b_ESP_Transmit(ESP_DIR_ACK, u8_cmd, NULL, 0)   comm_esp.c:545
```

핵심은 **`comm_esp.c:545`의 ACK가 `switch` 바깥**이라는 점입니다. 데이터 내용,
길이, 처리 성공 여부와 무관하게 **INIT 범위 프레임이 핸들러에 도달하기만 하면
ACK가 나갑니다.** 값 적용(`v_Mode_Set_Temp_Max`)이 먼저 끝나고 ACK가 나가므로,
귀측은 이 ACK를 "받았다"가 아니라 **"적용됐다"** 로 읽으셔도 됩니다.

따라서 **ACK가 없었다 = 프레임이 `v_ESP_InitProc`에 도달하지 못했다**가 되고,
온도·전압으로 값이 적용되지 않았음을 증명하신 귀측 §3·§5.1과 완전히 일치합니다.
**"ACK만 유실"이 아니라는 판단이 맞습니다.**

> 참고로 송신 실패 경로도 하나 있긴 합니다. TX 링(2 KB)에 자리가 없으면
> `b_Uart_ESP_Out()`이 `false`를 반환하는데(`uart.c:224`) `comm_esp.c:545`가 그
> 반환값을 버립니다. 다만 이번 캡처는 부팅 직후라 TX 링이 비어 있었을 것이므로
> **이 경로는 아닙니다.** 그래도 §8-(5)에서 같이 고칩니다.

## 3. 확정된 유실 메커니즘 4건 (+1)

전부 코드에 실재합니다. 파일:라인을 답니다.

### M1. 메인루프 1회당 프레임 1개 — 역동기화 중에는 **1바이트**

`v_ESP_RxHandler()`는 메인루프에서 **호출이 1회**이고(`comm_esp.c:157`,
`v_ESP_Handler()` → `v_Uart_ESP_Handler()` → `main.c`의 `v_Uart_Handler()`),
호출 1회에 **프레임 1개만** 처리합니다. 반복 배수(drain loop)가 없습니다.

더 중요한 것은 **실패 경로**입니다. STX 불일치 / LEN 이상 / CMD 범위 이탈 /
체크섬 불일치 / ETX 불일치 — **다섯 경로 모두** `b_Jmp(espRx, 1)`로 **정확히 한
바이트만** 버리고 `return`합니다 (`comm_esp.c:334, 345, 361, 374, 390, 399`).

즉 **바이트 하나가 어긋나면, 재동기화 비용이 "바이트당 메인루프 1주기"** 입니다.

여기서 귀측 로그가 이 모델을 그대로 확인해 줍니다. §2.1의 ACK 러시 간격입니다.

```
13603 → 13638 → 13688 → 13715 → 13741 → 13767 → 13793 → 13820 → 13847 → 13876 → 13902
   35     50      27      26      26      26      27      27      29      26   (ms)
```

**26~27 ms 등차** — 저희 메인루프 1주기입니다. 프레임 하나에 정확히 한 주기가
쓰이고 있습니다. 그리고 `0x14` 송신(≤13095)부터 첫 ACK(13603)까지의 **508 ms
침묵**은 이 주기로 **약 19회분**입니다. 정상 배수라면 그 사이에 12개를 전부
처리했어야 합니다. **그 구간에서 파서가 정상 배수 상태가 아니었다**는 뜻입니다.

### M2. LEN 검증 순서 — 쓰레기 LEN 하나로 파서가 멈춥니다

`v_ESP_RxHandler()`의 LEN 처리입니다 (`comm_esp.c:342~362`).

```c
static uint8_t len;                                   // ← 호출 간 유지
...
len = p_arr[out];
if(len < ESP_FMT_LEN_MIN || len > mask){ ...버리고 return... }   // mask = 127
len -= ESP_FMT_LEN_MIN;
if(ESP_FMT_SIZE_MIN + len > espRx->u16_cnt){
    return;                                           // ← 더 받을 때까지 대기
}                                                     //    len은 유지된 채
...
data_len = len;
if(data_len > ESP_RX_DATA_BUF_SIZE){ ...버리고 return... }       // ← 32 검사는 여기
```

문제는 **순서**입니다. LEN은 **127까지 통과**하는데, 실제 상한인
`ESP_RX_DATA_BUF_SIZE`(32) 검사는 **"더 받을 때까지 대기" 뒤에** 있습니다.
그래서 쓰레기 LEN이 들어오면 **먼저 대기부터 합니다**:

| 쓰레기 LEN | 파서가 기다리는 바이트 수 | 결과 (링 128 B) |
|---|---|---|
| 0x25 (37) | 39 | 39 B 쌓일 때까지 정지 |
| 0x60 (96) | 98 | 98 B 쌓일 때까지 정지 |
| **0x7F (127)** | **129** | **영구 정지** — 128 B 링에서 절대 충족 불가 |

`len`이 `static`이라 함수 진입부(`comm_esp.c:321`)의
`if(espRx->u16_cnt < ESP_FMT_SIZE_MIN + len){return;}`도 같은 값으로 계속
막습니다. **정지 중에도 ISR은 계속 링을 채웁니다.**

### M3. `HAL_UART_AbortReceive()` — 수신 데이터를 버립니다

`v_Uart_ESP_DisableIT()`의 실체입니다 (`uart.c:198`).

```c
void v_Uart_ESP_DisableIT(){
	HAL_UART_AbortReceive(p_uart1);
}
```

저장소 안의 HAL 소스(`Drivers/STM32H7xx_HAL_Driver/Src/stm32h7xx_hal_uart.c`)를
확인했습니다.

```c
  /* Clear the Error flags in the ICR register */
  __HAL_UART_CLEAR_FLAG(huart, UART_CLEAR_OREF | UART_CLEAR_NEF | ... );

  /* Discard the received data */
  __HAL_UART_SEND_REQ(huart, UART_RXDATA_FLUSH_REQUEST);   // ← RDR를 비웁니다
```

그리고 이 abort는 **프레임을 정상 소비할 때마다, 그리고 재동기화 1바이트마다**
호출됩니다 (`comm_esp.c:334~406`, 6곳). USART1은 FIFO 비활성(`main.c:1518`,
`HAL_UARTEx_DisableFifoMode`)이라 RDR는 1바이트 깊이입니다. **abort 시점에 RDR에
들어와 있던 바이트는 그대로 사라집니다.**

원래 이 abort의 목적은 `b_Jmp()`가 링 인덱스를 만지는 동안 ISR을 막는 것인데,
그러자고 **수신기 자체를 껐다 켜는 것**은 과합니다 (§8-(2)에서 임계구역으로
바꿉니다).

### M4. 링버퍼 오버플로 — **가장 오래된 것부터** 조용히 버립니다

RX 링은 128 B입니다 (`comm_esp.c:115, 148`). `v_Put`의 구현입니다
(`lib_ringbuf.c`, `_RING_PUT_FN_DEF`).

```c
px->p_arr[px->u16_in] = src;
px->u16_in = (px->u16_in + 1) & px->u16_mask;
if(px->u16_cnt > px->u16_mask)                       // 가득 찼으면
{
    px->u16_out = (px->u16_out + 1) & px->u16_mask;  // ← 가장 오래된 바이트를 덮어씀
}
```

**가득 차면 거절하지 않고 가장 오래된 바이트를 덮어씁니다.** 그리고 아무 신호도
남기지 않습니다. M1·M2로 배수가 막힌 상태에서 이게 발동하면, **먼저 도착한
프레임부터** 사라집니다.

> 이것이 **"12개 중 첫 번째 하나만 없어졌다"** 는 귀측 관측과 정확히 맞는
> 부분입니다. 무작위로 하나가 빠진 게 아니라 **가장 오래된 것이 빠지는 구조**입니다.

### M5. (부수 발견) ORE 시 수신이 멈춥니다 — 이번 캡처의 원인은 아닙니다

저희는 `HAL_UART_ErrorCallback()`을 재정의하지 않았습니다(전 소스 grep 0건).
H7 HAL은 오버런(ORE)을 **blocking error**로 분류해 `UART_EndRxTransfer()`로
수신을 중단하고 빈 weak 콜백을 부릅니다. **`HAL_UART_Receive_IT()`를 다시 걸어
주는 코드가 없습니다.**

지금은 M3의 abort/재개가 **우연히** 재무장 역할을 해서 자가 복구됩니다 — 링에
남은 백로그를 처리하다 `v_Uart_ESP_EnableIT()`가 불리기 때문입니다. 이번 캡처가
18139에 복구된 것도 이 경로로 설명됩니다.

**그래서 §8-(2)로 abort를 없애면, §8-(4)의 에러 콜백 재무장이 선택이 아니라
필수가 됩니다.** 둘은 반드시 같이 들어가야 합니다. 명시해 둡니다.

### 3.6 이번 캡처의 방아쇠는 특정하지 못했습니다

정직하게 적습니다. 위 4건은 **메커니즘으로 확정**되었지만, 13095 시점에 최초
1바이트를 어긋나게 만든 것이 M3의 flush인지, ORE인지, 부팅 구간의 라인 노이즈인지는
**캡처 1건으로 가릴 수 없습니다.** 바이트 단위 산술로 역산해 하나를 지목하는 것은
과적합이라 하지 않겠습니다. **넷을 전부 닫는 것으로 대신합니다.**

## 4. Q84 (→ **Q89**) 회신 — `0x81` 직후 수신 보장

### 4.1 답: **(a)도 (b)도 아닙니다**

귀측 §4.2의 두 가설에 대한 답입니다.

| 가설 | 판정 | 근거 |
|---|---|---|
| **(a)** `0x81` 후 짧은 구간 RX 미무장 | **아닙니다** | RX는 `v_Uart_ESP_Init()`(`uart.c:189`)에서 무장되며, 이는 `main.c:301`의 주변장치 초기화 시점입니다. `0x81`(`mode.c:1661`)은 그보다 **수 초 뒤**입니다. `0x81` 전후로 무장 상태가 달라지는 구간이 없습니다 |
| **(b)** 부팅 후 첫 프레임을 재동기화에 소모 | **아닙니다** | "첫 프레임"이라는 특별 취급이 코드에 없습니다. `v_ESP_RxHandler()`는 부팅 이후 매 루프 동일하게 동작합니다 |

**진짜 성질은 이겁니다: 유실은 `0x81`로부터의 시간이 아니라 "역동기화 사건"에
묶여 있습니다.** 바이트 하나가 어긋나거나(M3/M5), 쓰레기 LEN이 파서를
멈추면(M2), 그때부터 배수가 마비되고(M1) 링이 넘치면서 **그 창에 들어온
프레임**이 사라집니다(M4).

**그래서 귀측 §4.3의 판단이 맞습니다 — 지연 상수를 뽑아도 소용없습니다.**
`0x81 + X ms`를 지켜도 그 시점에 역동기화가 진행 중이면 똑같이 사라지고, 반대로
동기가 맞아 있으면 `+1 ms`에 보내도 무사합니다. **숫자를 드리지 않겠습니다.
드리면 그게 오히려 다음 릴리스에서 조용히 깨질 상수입니다.**

### 4.2 계약 — 귀측 선택지 2번(구조적 보장)으로 답합니다

**§8의 수정이 랜딩된 시점부터** 다음을 보장합니다.

> **STM32는 `evtInitStart(0x80)`·`evtInitResult(0x81)`을 보내기 훨씬 전인
> 주변장치 초기화 단계에서 UART1 수신을 무장하며, 그 이후 어떤 경로에서도
> 수신기를 해제하지 않습니다. 프레임 소비·재동기화는 수신기를 건드리지 않는
> 임계구역에서만 인덱스를 조작합니다. 따라서 `0x81` 이후 도착분에 대한 시간
> 하한은 필요하지 않습니다.**

여기에 배수 보장을 덧붙입니다.

> **메인루프 1회에 수신 링을 소진할 때까지 프레임을 처리합니다(상한 있는 배수
> 루프). 역동기화 시에도 바이트 폐기가 같은 루프 안에서 이어집니다. 따라서
> "메인루프 1주기당 1프레임" 상한은 사라집니다.**

**단서를 분명히 합니다: 이 계약은 §8의 수정이 들어간 빌드부터 성립하며, 이
문서 이전의 `1.0.1-dev`에는 해당하지 않습니다.** 와이어에서 구분할 방법이
없으므로 **릴리스 `1.0.1` 이상**을 기준으로 삼아 주십시오 (§8 말미).

### 4.3 현재 펌웨어의 위험 창 — 그리고 귀측이 검증할 수 있는 예측

수정 전까지의 위험 창은 **"`0x81` 직후"가 아닙니다.** **직전 프레임을 소비하는
중에 도착하는 모든 프레임**입니다. 부팅과 무관합니다.

**이것은 귀측 로그로 판별 가능한 예측입니다.** 저희 모델이 맞다면:

- 부팅과 **무관한** 시점에도 `retryCount > 0`인 ACK가 드물게 관측되어야 합니다.
  특히 **연속 송신 구간**(설정 변경 배치, 로그 파일 조회 직후 등)에서요.
- 가설 (b)가 맞았다면 **부팅 직후에만** 나타나야 합니다.

기존 세션 로그에서 `retryCount > 0` ACK를 부팅 여부와 함께 집계해 주시면
**저희 모델이 반증되는지 바로 갈립니다.** 귀측 §7-4의 "ESP32 단독 리셋 반복"
실험보다 이쪽이 (a)/(b)를 더 잘 가릅니다 — 저희 모델은 (a)·(b) 둘 다 부정하므로,
**부팅 외 유실이 하나라도 나오면 저희가 맞고, 수백 회 부팅에서만 나오면 저희가
틀린 겁니다.**

### 4.4 귀측 §7-3(수신 링버퍼 확인)에 대해

`0x81` 송신 직후 링에 프레임이 쌓이는지 보는 것으로는 판별이 안 됩니다 —
**M1~M4 어느 경우에도 프레임은 링에 쌓입니다.** 문제는 쌓인 것을 꺼내는
쪽입니다. 대신 저희는 **링 오버플로 카운터와 재동기화 바이트 카운터**를 넣어
(§8-(3)) 다음 캡처에서 **숫자로** 확인하겠습니다. 이쪽이 훨씬 결정적입니다.

## 5. Q85 (→ **Q90**) 회신 — `f_max` 상승 시 setpoint 재적용

### 답: **재적용합니다. 귀측 실측이 맞고, 사양서 문구가 낡았습니다.**

```c
/* Re-derives the setpoints from what was requested, for a new f_max. */
static void v_Mode_Temp_Reapply(void){                          // mode.c:241
	float f_max = x_modeTempLmt.f_max;
	x_modeTempLmt.f_sleep   = (f_tempReqSleep   > f_max) ? f_max : f_tempReqSleep;
	x_modeTempLmt.f_waiting = (f_tempReqWaiting > f_max) ? f_max : f_tempReqWaiting;
	x_modeTempLmt.f_forceUp = (f_tempReqForceUp > f_max) ? f_max : f_tempReqForceUp;
}

void v_Mode_Set_Temp_Max(float f_temp){                         // mode.c:248
	x_modeTempLmt.f_max = f_Mode_Temp_Clamp(f_temp, "temp limit");
	// Raising f_max lifts anything that was clamped against the old one. Without
	// this the result depends on the order 0x14 and 0x12 happen to arrive in.
	v_Mode_Temp_Reapply();
}
```

핵심은 **`f_tempReqSleep` / `f_tempReqWaiting` / `f_tempReqForceUp`** 입니다.
`0x10`·`0x11`·`0x12`로 **요청받은 원본 값**을 별도로 보관하고, 실제 동작
setpoint는 매번 `min(요청값, f_max)`로 **파생**시킵니다. 그래서 `f_max`가
올라가면 **잘려 있던 값이 원본까지 되살아납니다.**

귀측 §5.2의 관측 — `0x12` 재전송 없이 18139의 `0x14` ACK 이후 70.7 → 80.5 °C —
가 정확히 이 동작입니다.

**도입 시점**: 커밋 `e18f3ce` (*fix(mode): clamp UART temperatures to an absolute
ceiling*). 그 이전 펌웨어는 사양서 문구대로 "잘린 채 남는" 동작이었습니다.
**`1.0.1-dev` 이상에서 재적용이 보장됩니다.**

### 사양서 정리

§`0x12`의 **"이후 `f_max`가 올라가도 잘린 채 남습니다"** 는 지금 구현과 반대이니
삭제/수정 부탁드립니다. 대신 이렇게 적어 주시면 정확합니다.

> `0x10`·`0x11`·`0x12`의 요청값은 원본 그대로 보관되고, 동작 setpoint는
> `min(요청값, f_max)`로 파생된다. 따라서 `0x14`가 나중에 도착해 `f_max`가
> 올라가면 **잘려 있던 setpoint가 요청값까지 자동 복원된다.** `0x14`와
> `0x12`의 도착 순서는 최종 결과에 영향을 주지 않는다.

> **다만 §`0x12`의 🔴 순서 제약(`0x14`를 먼저) 자체는 유지해 주십시오.**
> 최종 상태는 순서 무관이지만, **`0x14`가 늦으면 그 사이 구간이 낮은 천장에서
> 동작**합니다 — 이번 캡처의 1.8초 정체가 바로 그것입니다. 순서 제약은 여전히
> 의미가 있습니다.

### 귀측 §6 완화책에 대해

**Q90이 "재적용한다"로 답해졌으므로 귀측 완화책은 멱등한 중복 전송이 되어
무해합니다. 그래도 유지해 주시길 권합니다.** 이유는 두 가지입니다.

1. §4.3의 위험 창은 부팅 전용이 아닙니다. `retryCount > 0`을 신호로 쓰는 로직은
   부팅 외 구간에서도 그대로 값을 합니다.
2. 저희 §8이 랜딩되기 전까지는 그게 유일한 2차 방어선입니다.

`0x14` 선행 여부 경고가 "보냈는가"만 보고 "전달됐는가"를 안 봤다는 자체 진단도
정확합니다. 저희 쪽 `1.0.1-dev`가 그 침묵을 유발한 원인 제공자입니다.

## 6. 보고 #45 §3 철회

당시 이렇게 답했습니다.

> **§3. Q81 — 문제없습니다. 준비 시점이라는 것이 없습니다**
> 수신 경로는 UART ISR → 링버퍼 → 메인루프 파싱입니다. … **유실 경로가 없습니다.**

**"유실 경로가 없습니다"는 틀렸습니다. 철회합니다.**

앞 문장("준비 시점이라는 것이 없다")은 지금도 맞습니다 — §4.1대로 `0x81` 전후로
무장 상태가 달라지지 않습니다. **틀린 것은 뒷 문장입니다.** ISR이 링에 넣는
데까지만 보고, **링에서 꺼내는 쪽(M1·M2)과 링 자체의 넘침 정책(M4), 그리고
수신기를 껐다 켜는 경로(M3·M5)를 보지 않았습니다.**

경로가 있다는 것을 §3에 넷 열거했습니다. 그게 철회의 근거입니다.

## 8. 저희 쪽 수정 — **구현 완료**

| # | 수정 | 닫는 메커니즘 |
|---|---|---|
| **(1)** | `v_ESP_Handler()`가 **상한 있는 배수 루프**로 수신 링을 소진합니다. `b_ESP_RxHandler()`가 `bool`을 반환하도록 바꿔(진행 있음/없음), 링에 온전한 프레임이 없을 때만 빠져나옵니다. 상한은 `ESP_RX_ARR_SIZE`(128) — 매 반복이 최소 1바이트를 소비하므로 **링 1회분**이고, 폭주 프레임이 메인루프의 나머지(워치독·모드·ADC)를 굶기지 못합니다 | **M1** |
| **(2)** | `v_Uart_ESP_DisableIT()`/`EnableIT()`를 **삭제**하고, `b_Jmp()` 둘레를 **PRIMASK 임계구역**(`v_ESP_RxDrop()`)으로 바꿨습니다. 경합 대상은 `u16_cnt` 하나뿐이라 이게 맞는 크기의 락입니다. **수신기를 끄지 않으므로 RDR flush가 사라집니다** | **M3** |
| **(3)** | LEN 상한 검사를 **"더 받을 때까지 대기" 앞으로** 옮겼습니다. 이제 `ESP_FMT_LEN_MIN + ESP_RX_DATA_BUF_SIZE`(36)를 넘는 LEN은 **즉시** 1바이트 재동기화로 갑니다 — 대기 자체가 불가능해집니다. 허용 범위는 이전 `data_len > 32` 검사와 **정확히 동일**하므로 정상 프레임에는 변화가 없습니다 | **M2** |
| **(4)** | `HAL_UART_ErrorCallback()`을 정의해 ORE/FE/NE에서 **`HAL_UART_Receive_IT()`를 재무장**하고 카운트합니다. **(2)와 같은 커밋으로 들어갔습니다** — (2)가 지금의 우연한 자가복구를 없애기 때문입니다 | **M5** |
| **(5)** | 링 오버플로 바이트·재동기화 바이트·UART 에러 **카운터 3종**을 추가하고, 1초 간격 **에지 트리거 로그**(`rx damage: overflow=… resync=… uartErr=…`)로 노출합니다. 값이 변할 때만 한 줄 나갑니다 | **M4** (가시화) |
| **(6)** | ACK 송신의 `b_ESP_Transmit()` 반환값을 확인해 TX 링 포화로 ACK가 못 나간 경우를 기록합니다 — 그동안 이건 "명령을 못 받은 것"과 구별이 안 됐습니다 | (부수) |

**(2)와 (4)의 결합은 협상 대상이 아니었습니다.** 따로 랜딩하면 (2)만으로 ORE 한 번에
ESP 링크가 영구히 죽습니다. 같은 커밋에 들어갔습니다.

**M4(링 오버플로 자체)는 정책을 바꾸지 않았습니다.** 오버플로 시 가장 오래된
바이트를 버리는 동작은 그대로입니다 — (1)~(3)이 오버플로에 이르는 경로를 막는
쪽이 맞는 순서이고, 그래도 넘친다면 그건 **숨기지 말고 보여야 할 사건**이라
(5)의 카운터로 드러냅니다. 다음 캡처에서 `overflow`가 0이 아니면 링 확대를
검토하겠습니다.

### 검증 상태

| 항목 | 상태 |
|---|---|
| 빌드 | `pio run -e stm32_debug` **통과** (신규 경고 0건) |
| 정적 검토 | 허용 LEN 범위가 변경 전과 동일함을 확인 (≤ 32 B DATA) |
| **실기 검증** | **아직입니다.** 부팅 후 `rx damage` 로그 추이와, 귀측 §4.3 집계와의 대조가 남았습니다 |

**로그를 읽으실 때 두 가지 주의사항이 있습니다.**

1. **카운터는 "바이트" 수이지 "사건" 수가 아닙니다.** 역동기화 한 번이 링을
   바이트 단위로 훑기 때문에 **단일 사건이 `resync=19`로 보고될 수 있습니다.**
   `19`를 19건으로 읽지 마십시오.
2. **리셋 이후 누적이고, 부팅 핸드셰이크에서 초기화하지 않습니다.** 그래서
   `evtInitStart` 이전의 라인 노이즈도 그대로 잡힙니다 — 그 노이즈가 방아쇠
   후보 중 하나라 일부러 숨기지 않았습니다. **부팅 직후 한 줄이 나오는 것 자체는
   수정 실패가 아닙니다. 핸드셰이크 이후에도 숫자가 계속 늘어나는지**가
   판단 기준입니다.

> **STAT(`0x70`) 페이로드에는 넣지 않았습니다.** 와이어 포맷 변경은 사양서
> 왕복이 필요한 별건이라 이번 스레드에서 같이 처리하지 않았습니다. 필요하시면
> 별도 제안으로 올려 주십시오.

**버전**: 이미 `1.0.1-dev`이므로 추가 범프는 없습니다. 다만 STM32 응답에는 빌드
시각 필드가 없어서 **서로 다른 `1.0.1-dev` 빌드를 와이어에서 구분할 수
없습니다.** 그래서 §4.2 계약은 **릴리스 `1.0.1` 이상**을 기준으로 삼아
주십시오. 그 전의 `1.0.1-dev` 빌드가 어느 쪽인지는 저희가 개별로 통지하겠습니다.

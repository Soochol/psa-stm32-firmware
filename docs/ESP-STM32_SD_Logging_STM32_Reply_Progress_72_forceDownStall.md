## 0. 판정 회신

P1~P3 채택과 정련 2건 모두 동의합니다. 특히 두 가지는 저희 원안보다 낫습니다:

- **`cycleMaxTilt` 기반 재분류(§2)** — 매 샘플 라이브 각도 대신 사이클 최대값을
  쓰면 각도가 순간적으로 임계 아래로 떨어져도 재분류가 풀리지 않습니다. 상태
  변수도 늘지 않고, `canControlSTM()`이 닫힌 구간에 눈멀지 않도록 추적 블록을
  FD 밖에 둔 배치도 맞습니다.
- **batWarnActive를 게이트에서 선차단(§4-2)** — 저희 원안(FD 지점 `|| batWarnActive`
  분기)이 FU 트리거 쪽 스팸 창을 놓쳤다는 지적이 정확합니다. 네 발화 지점을
  한 곳에서 막는 쪽이 옳습니다. WAITING 보고 시 동기화가 생략될 수 있다는
  분석도 맞고, 배터리 교체 전까지 FORCE_*가 전면 차단되므로 실질 영향이
  없다는 결론에 이견 없습니다.

P4 미채택도 수용합니다. 15–35° 저굽힘 하중이 hybrid·deep 양쪽 사각에 빠진다는
지적은 저희가 제안 시 고려하지 못한 커버리지 손실입니다.

§1의 F1~F3 선행 구현 고지 감사합니다. 최종 릴리즈 규칙표(§1)의 ④ 55 s 무조건
FD를 P2 채택 후에도 남긴 판단에 동의합니다 — ②~④가 모두 각도를 전제하므로
IMU 오프셋으로 15° 미만을 영영 못 보는 경우의 최후 탈출구가 필요합니다.

## 1. Q84 — 0x16 타임아웃 단위·범위

**(a) 실단위는 초입니다. 공식 확인합니다.**

수신 파싱은 `comm_esp.c:503-512` — 4개 필드를 각각 uint16 빅엔디언으로 읽어
`v_Mode_Config_Tout(waiting, forceUp, forceOn, forceDown)`에 그대로 전달합니다
(스케일링·환산 없음). 각 모드가 이 값을 쓸 때 `MODE_TOUT_TO_MS_MULT`(=1000,
`mode.h:427`)를 곱해 ms로 만듭니다:

| 용도 | 위치 |
|------|------|
| WAITING | `mode.c:1728` — `u32_Mode_Get_Waiting_Tout() * 1000` |
| FORCE_UP | `mode.c:1811` |
| FORCE_ON | `mode.c:1908` |
| FORCE_DOWN | `mode.c:1994` |

따라서 그쪽이 보낸 `(5, 60, 60, 250)`은 forceUp 5 s / forceOn 60 s /
forceDown 60 s / waiting 250 s입니다. §6-(c)의 실측 252.1 s는 250 s 설정에
샘플링·MP3 종료 대기가 더해진 값으로, 초 단위 해석과 일치합니다.

**(b) 범위 밖 값은 클램프도 거부도 하지 않고 그대로 수용합니다.**

`v_Mode_Config_Tout`(`mode.c:192-197`)은 네 필드를 검증 없이 대입만 합니다.
수용 범위는 와이어 폭 그대로 **1~65535 s**이며, 250은 정상 동작합니다.

다만 **0은 병리적입니다**: `_b_Tim_Is_OVR`이 `u32_std >= u32_itv`로 비교하므로
(`lib_tim.c:11`) itv=0이면 항상 참 — 해당 모드가 진입 즉시 타임아웃합니다.
그쪽이 `initTimeoutConfiguration`에서 0을 거부하고 계셔서(`uartMaster.cpp:3227`)
현재는 도달하지 않는 경로입니다. 저희 쪽 하한 가드는 이번 스레드 범위 밖으로
두고, 별도 건으로 추가하겠습니다 — 링크가 유일한 입력원인 값에 수신측 가드가
없는 것은 그 자체로 정리 대상입니다.

**(c) 사양서 §0x16 표기 정정에 이견 없습니다.** "단위: 초, 범위: 1~65535
(구현상 무클램프 수용)"이 코드 사실입니다. ×100 ms 표기는 오기이며, 정정
초안을 그쪽에서 잡아 주시면 검토하겠습니다.

## 2. Q85 — forceOn 타임아웃 폴백의 능동 냉각

**능동 냉각은 없습니다. 다만 "냉각 없음"보다 중요한 사실이 있습니다 —
SLEEP은 38 °C를 능동 유지합니다.**

먼저 팬: 쿨링 팬을 켜는 지점은 `v_Mode_ForceDown`의 `v_Mode_CoolFan_Enable()`
(`mode.c:2031`)과 JIG TEST 경로(`mode.c:2609`·`2642`)뿐입니다. FORCE_UP 진입 시
`v_Mode_CoolFan_Disable()`(`mode.c:1823`)로 꺼진 뒤 FORCE_ON·SLEEP 어느 쪽도
다시 켜지 않으므로, 폴백 경로의 팬 PWM은 0입니다.

그런데 SLEEP 핸들러(`mode.c:2091-2098`)는 방치가 아니라 **온도 유지 루프**입니다:

```
temp = i_Mode_Is_TempHeater_Over(&i_tempRenew, f_Mode_Get_Temp_Sleep());  // 38 °C
if(temp > 0)      v_Mode_Heater_Off();              // 38 이상 → 히터 off, 자연 냉각
else if(temp < 0) f_Mode_Heater_PID_Handler(...);   // 36.5 미만 → PID로 재가열
```

즉 52 °C에서 자연 냉각으로 내려오다 **38 °C에서 멈추고 그 온도를 유지**합니다
(히스테리시스 1.5 °C, `mode.h:358`). 상온까지 내려가지 않습니다. WAITING도
동일한 38 °C 유지이고(`mode.c:1761-1767`), FORCE_DOWN의 냉각 목표도 38 °C
(`mode.c:2024`)이므로 **시스템 전체의 아이들 온도가 38 °C**입니다.

**이 사실이 §5 질문 2에 갖는 의미**: 사이클 종료 후에도 구동기는 상온이 아니라
38 °C에 머뭅니다. SMA가 이 온도에서 어느 정도 확장 이력을 유지하는지에 따라
ToF가 사이클 사이에 180 mm 아래로 남을 수 있고, 그렇다면 재잠금 해석이
"한 사이클 내 잔류"가 아니라 "세션 전반의 기준선 이동"이 됩니다. 기구 담당
조회 시 이 38 °C 유지 조건을 함께 제시하시길 권합니다.

## 3. Q86 — FORCE_ON 거동의 최근 변경 여부

**FORCE_ON 자체의 제어 로직은 최근 수 개월간 실질 변경이 없습니다. 다만 그쪽
트리거가 소비하는 "각도"의 산출 방식은 4월에 크게 바뀌었습니다 — 발현율 변화의
후보는 이쪽입니다.**

**(1) FORCE_ON 잔열 냉각 작업 — 추가 후 당일 되돌림, 실기 미실행**

| 커밋 | 날짜 | 내용 |
|------|------|------|
| `b22319d` | 08-12 | FORCE_ON 잔열 배출 시간 계측 |
| `9508917` | 08-12 | FORCE_ON 중 쿨팬 가동 |
| `9f0520f` | 08-12 | 위 둘 되돌림 |

`git diff 4aa52af 9f0520f -- User/Edit/src/mode.c`가 **빈 출력**이므로 되돌림은
완전합니다. 되돌림 커밋 메시지는 "Neither ran on hardware"라고 적고 있어
(저희 기록상의 진술이며 배포 이력으로 재확인한 것은 아닙니다) 08-12 이후 main
빌드에는 이 작업이 전혀 포함되지 않습니다.

**(2) 실질 변경 2건 — 정상 동작에는 영향 없음**

- `e18f3ce`(08-11) UART 수신 온도의 절대 상한 85 °C 클램프. 그쪽이 보내는 값
  (80/72/64/54/52)은 모두 하한이라 무영향.
- `4aa52af`(08-11) FORCE_UP 램프 도달 온도 로깅 — 로그만 추가.

**(3) 발현율 변화의 유력 후보 — 4월 각도 산출 대개편**

- `d06fe12`(04-07) **Mahony → accel-only 전환**. 이때 적응형 LPF가 함께
  들어왔습니다(동적 가속 시 α=0.001, 사실상 동결 —
  `icm42670p_platform.c:1965-2006`). 보고 #70 §2-1의 캡처 레이스는 이 특성이
  재료입니다.
- `1531489`(04-13) **`acos` → `atan2`, baseline 90→0**. 각도가 부호 있는 값이
  되었고 기준점이 이동했습니다. 그쪽 `computeWaistTilt()`는 부호를 그대로
  쓰므로, 같은 자세가 만들어내는 수치 궤적이 이 시점 전후로 다릅니다.

ESP32 판정 로직이 동일한데 발현율이 달라졌다면, STM32 빌드가 이 4월 경계를
넘었는지가 첫 확인 지점입니다. 대상 유닛의 `reqDeviceVersion(0x46)` 응답과
플래시 시점을 대조해 주시면 좁힐 수 있습니다.

## 4. Q88 — TESTING 이탈 시 evtMode

**전제 정정이 필요합니다: 이탈 경로는 존재하고, 이탈 시 `evtMode`도 전송됩니다.
잠금이 안 풀리는 원인은 다른 데 있습니다.**

**(1) JIG의 `EXIT_TEST`는 모드를 떠나지 않습니다 — 이것이 실제 원인입니다.**

`DBG_CMD_EXIT_TEST` 처리(`comm_dbg.c:281-284`)는 `v_Mode_Set_DBG_Act(modeTEST_WAITING)`
만 호출합니다. 이는 **modeTEST 내부의 action을 WAITING으로 바꾸는 것**이지
모드 전이가 아닙니다(`mode.c:2504-2510`). 따라서 `e_Mode_Get_CurrID()`는 계속
`modeTEST`이고, `u8_Mode_Get_ProtoMode()`도 계속 TEST(5)를 반환합니다
(`mode.c:2131`). 이름과 동작이 어긋나는 지점입니다.

**(2) 실제 이탈 경로는 2개이고, 둘 다 `evtMode`를 보냅니다.**

| 경로 | 코드 | 결과 |
|------|------|------|
| 전원키 롱프레스(1.5 s) | `key.c:182-194` — `id > modeBOOTING && id != modeOFF` → `v_Mode_SetNext(modeOFF)`. `modeTEST`(9)가 조건을 만족 | modeOFF 진입 시 `v_ESP_Send_EvtModeChange(ESP_EVT_MODE_OFF)` 전송 (`mode.c:2160`) |
| 그쪽 `ctrlRst(0x50)` | `comm_esp.c:758` — 무조건 `v_Mode_SetNext(modeOFF)` | 동일 |

`resetDevice()`(`uartMaster.cpp:3573`)가 `stm32Ready`만 확인하고 `canControlSTM()`을
거치지 않으므로, TESTING 잠금 중에도 0x50은 발신 가능합니다. **잠금 해제
설계는 evtMode(OFF, 코드 10) 수신을 트리거로 삼으시면 됩니다.**

**(3) 검사 중 비-TESTING 모드의 일시 보고 구간은 없습니다.** TEST action이
FORCE_UP/DOWN/WAITING으로 바뀌어도 모드 자체는 `modeTEST`이므로 보고값은
TEST로 고정입니다.

**(4) 남는 실사용 문제**: JIG로 검사한 유닛은 `EXIT_TEST`를 보내도 TEST에
머물고, 전원 재인가나 0x50 없이는 그쪽 잠금이 풀리지 않습니다. `EXIT_TEST`가
실제로 modeTEST를 떠나도록 고치는 것이 정공법이나, JIG 검사 절차·치구 쪽
기대 동작과 맞물려 있어 이번 스레드에서 단독 변경하지 않았습니다. 필요하시면
별도 스레드로 올리겠습니다.

## 5. 우리 몫 — IMU 세션 재초기화 완료

보고 #70 §4에서 "별도 처리 예정"이라 한 증폭기 결함을 **구현·빌드 완료**했습니다
(커밋 `d03e84d`).

- **문제**: `v_IMU_Tout_Handler`가 3회 버스 복구 실패 후 `e_imu_config`를 READY로
  되돌리지만, `e_IMU_Ready`의 호출자가 BOOTING뿐이라 아무도 그 요청을 처리하지
  않았습니다. 결과적으로 남은 세션 내내 각도가 0으로 고정 스트리밍되고, 0은
  하류에서 "직립"으로 읽히므로 그쪽 각도 기반 FU(>35° 필요)가 영영 발화하지
  못해 **모든 사이클이 ToF 단독 경로로 몰립니다**.
- **수정**: `v_IMU_Reinit_Handler()` 신설 — `e_imu_config != DONE`이면 10 s 간격으로
  재초기화를 시도하고, 한 시도는 3 s로 상한을 둡니다. 재시도는 무제한으로,
  다른 센서의 복구 정책(`bba945c`)과 같습니다. BOOTING 중에는 호출하지 않습니다
  (`mode.c` 호출부) — 같은 상태머신을 두 주체가 밀면 어느 쪽도 끝내지 못합니다.
- **부수 수정**: `e_IMU_Ready`는 진행 위치를 static에 담고 있어, 재시도 시
  `interface`가 "전송 계층 설정 완료"로 남아 방금 리셋된 버스에서 그 단계를
  건너뛰는 문제가 있었습니다. 진입부 되감기 플래그로 해결했습니다.
- **앵커 보존**: accel-tilt 기준점은 재초기화 시에도 유지합니다. 여기서 다시
  잡으면 0°의 의미가 세션 중간에 바뀝니다.
- **빌드**: `pio run -e stm32_debug` SUCCESS (FLASH 82.7 %).
- **펌웨어 버전**: `1.0.1-dev` 유지 — 이미 개발 사이클 중이라 추가 범프 없음.

## 6. 실기 캡처 (§6 요청) — 보류

§3 시그니처와 §5 질문 2를 함께 닫을 하중 굽힘→기립 반복 캡처는 **현재 세션에서
수행하지 못했습니다** — 실기 접속이 필요한 작업입니다. 다음 실기 세션에서
확보해 SD 백필을 전달하겠습니다. 그쪽 분석 스크립트가 준비되어 있다니, 캡처
후 파일만 넘기면 될 것으로 이해했습니다. 캡처 시 §2의 38 °C 유지 조건 때문에
**사이클 사이 ToF 기준선**도 함께 보시길 권합니다.

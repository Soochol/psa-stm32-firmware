## 1. 🔴 §5 — 기록 중인 파일은 백필로 열리지 않습니다

### 1.1 FatFs가 거부합니다

`_FS_LOCK = 4`로 파일 잠금이 활성입니다
([ffconf.h:233](../FATFS/Target/ffconf.h:233)). FatFs `chk_lock()`의 주석이
그대로 답입니다.

```c
/* The object has been opened. Reject any open against writing file and all write mode open */
return (acc || Files[i].ctr == 0x100) ? FR_LOCKED : FR_OK;
```

로그 파일은 세션 내내 쓰기 모드로 열려 있으므로 `ctr == 0x100`입니다.
백필은 `f_open(&bfFile, path, FA_READ)`로 여는데, 읽기라 `acc = 0`이지만
**`ctr == 0x100` 쪽이 참이 되어 `FR_LOCKED`**가 됩니다.

저희 코드는 이것을 오류로 처리합니다.

```c
if(f_open(&bfFile, c_path, FA_READ) != FR_OK){
    v_log_err_raise(SD_LOG_ERR_BACKFILL, 0);
    return 3;                     // reqLogRead -> 3
}
```

즉 **기록 중인 파일을 요청하면 `-> 3`으로 거부되고 스트리밍이 시작되지 않습니다.**
조용히 잘못된 데이터를 주는 일은 없습니다.

### 1.2 그래서 §5의 관측이 설명되지 않습니다

`boot=45`에서 **2,000건을 회수하셨다면 그 파일은 쓰기로 열려 있지 않았던
것**입니다. 저희 계측 세션의 bootId가 45였으므로, 시험 시점에 이미 다음 부팅으로
넘어가 45번 파일이 닫혀 있었을 가능성이 높습니다.

그쪽 백필 로직이 "최신 세션부터"로 바뀐 것과, 그 최신 세션이 **직전 세션**인
것은 다릅니다. 장치가 재부팅하면 직전 bootId의 파일은 닫힌 파일이 됩니다.

### 1.3 확인 요청

**`boot=45` 시험을 하실 때 장치의 실제 bootId가 무엇이었습니까?**

- 45였다면 → 저희 분석이 틀렸으므로 `chk_lock` 경로를 다시 보겠습니다
- 46 이상이었다면 → **닫힌 파일을 읽으신 것**이고, §5의 "기록 중" 전제가 성립하지
  않습니다

이 구분이 필요한 이유는, 그쪽 로직이 실제로 기록 중인 파일에 닿게 되면
**`-> 3` 거부가 반복**되기 때문입니다. 현재 코드에서는 그때 회수가 되지 않습니다.

### 1.4 갭 6회는 BLE 드롭 6건과 같아 보입니다

§5에서 `boot=45`의 갭 재요청을 **6회**로 보고하셨는데, §1.3에서 프레임 드롭도
**6건**입니다.

| 출처 | 건수 |
|---|---|
| §1.3 `backfill frame dropped` | **6** |
| §1.3 1초 이상 STAT 공백 | **6** |
| §5 `boot=45` 갭 재요청 | **6** |

세 값이 같습니다. §1.3에서 "드롭 1건 = 약 1초의 루프 기아가 같은 사건의 양면"으로
정리하셨는데, **갭 재요청도 같은 사건의 세 번째 면**일 가능성이 높습니다.

그렇다면 §5의 "기록 중인 파일은 재요청이 잦다"는 결론이 성립하지 않습니다 —
파일 종류가 아니라 **BLE 큐 혼잡이 원인**이고, 그것은 §1.5 조치로 해소됩니다.

닫힌 파일(`boot=27`·`boot=39`)에서 0회였던 것은 그 시점에 큐 혼잡이 없었던
것으로 설명됩니다.

## 2. Q50 — B(별도 태스크 분리)를 지지합니다

| 안 | 평가 |
|---|---|
| A 재시도 축소 | 창을 좁힐 뿐, 혼잡이 심해지면 재발 |
| **B 태스크 분리** | **✅ 근본** |
| C 재시도 중 양보 | 루프 구조를 건드리면서 보장은 약함 |

A는 8×4 ms를 3×2 ms로 줄여 프레임당 32 ms를 6 ms로 낮추지만, **연달아 쌓이는
구조 자체는 그대로**입니다. §1.3에서 "30개쯤 이어지면 약 1초"라고 하셨는데,
6 ms여도 170개가 이어지면 같은 1초가 됩니다. 큐 혼잡의 길이에 비례하는 성질이
남습니다.

B는 그 비례 자체를 끊습니다. 수신 루프가 BLE 큐 상태와 무관해지므로 **STAT 처리율이
백필 부하와 분리**됩니다.

**§9.5 재계측은 저희 쪽 준비가 끝나 있습니다** — 계측 코드가 이미 벤치에 올라가
있고 별도 작업이 필요 없습니다. 조치하신 뒤 백필을 걸어주시면 같은 방식으로
집계해 드리겠습니다. 일정은 그쪽에 맞추겠습니다.

## 3. Q51 — 예. 다만 기대 동작을 먼저 알려드립니다

`boot=9 seq=35950 cnt=128`로 다시 걸어 주십시오.

### 3.1 STM32는 파일을 걸쳐 읽지 않습니다

**이것이 이 시험의 핵심이고, 미리 밝혀둡니다.** 백필은 시작 seq가 속한 파일
하나만 열고, 파일 끝에 닿으면 거기서 멈춥니다.

```c
if(br != SD_LOG_REC_SIZE){
    // End of file ... result 0 means "all we hold", and the PC
    // resumes from lastSeqSent + 1.
    u8_bfResult = 0;
    v_bf_close();
```

따라서 `seq=35950 cnt=128` 요청의 기대 동작은 다음과 같습니다.

| 단계 | 결과 |
|---|---|
| 요청 | 35950 ~ 36077 (128건) |
| STM32 응답 | **35950 ~ 36000 (51건)** — `_0000` 파일 끝 |
| `backfill end` | `result=0`, `lastSeqSent=36000` |
| **PC 재요청 필요** | `seq=36001`부터 — `_0001` 파일이 열림 |

**한 번의 요청으로 128건이 다 오지 않는 것이 정상입니다.** `result=0`은 오류가
아니라 "가진 만큼 다 보냈다"입니다.

### 3.2 그래서 `cnt=12` 시험이 연속으로 보인 이유

35995~36006이 끊김 없이 이어졌다고 하셨는데, STM32는 35995~36000에서 한 번
멈췄을 것입니다. PC 클라이언트가 `lastSeqSent + 1`로 자동 재요청해 두 번째
응답이 36001~36006을 채웠고, 병합 결과만 보면 연속으로 보입니다.

**즉 이미 정상 동작한 것**이며, 128건 시험은 그것을 **더 큰 폭에서 재확인**하는
의미입니다. 51건에서 끊기는지, `lastSeqSent`가 정확히 36000인지가 확인 지점입니다.

### 3.3 확인해 주실 것

시험 후 그쪽 로그에서 두 가지를 알려주십시오.

1. 첫 응답의 `lastSeqSent` 값 (**36000이어야 합니다**)
2. PC가 36001로 재요청했는지, 그 응답이 `_0001`에서 왔는지

저희 쪽 로그도 함께 붙이겠습니다.

## 4. §1 원인 규명 — 확인했습니다

`handleLogChunkMessage()`와 `handleStatusMessage()`가 같은 수신 루프에 있고,
BLE 알림 재시도(8회 × 4 ms)가 그 루프를 최대 32 ms 잡는다는 구조 —
명확합니다.

**드롭 6건과 1초 공백 6건이 일치한다는 관측이 특히 좋습니다.** 두 지표가 같은
사건의 양면이라는 것을 수치로 보이셨고, 그 덕분에 §1.4처럼 세 번째 지표까지
같은 원인으로 묶어볼 수 있게 됐습니다.

### 재시도 도입 경위에 대하여

> 원래는 `notify()`의 반환값을 무시했고, 배치 96건에서 29건이 조용히 사라졌습니다.
> 재시도를 넣어 유실을 0으로 만들었는데, 그 대가가 지금 보시는 지연입니다.

저희 쪽에서도 같은 형태가 있었습니다 — 잘못된 레코드를 **버리는** 대신
플레이스홀더로 자리를 지키게 바꾼 것입니다(보고 v1.1). 유실을 없애는 대신
파일에 무의미한 레코드가 들어가는 비용을 받았습니다.

두 경우 모두 **유실을 막는 쪽이 옳았고**, 그 대가를 나중에 계측으로 발견한
것도 같습니다.

## 5. §2 기저 76회 — 우선순위에 동의합니다

65초 표본에서 기댓값이 1.3회라 0건이 이상하지 않다는 계산, 동의합니다.
저희도 그 수치로 기저를 단정하지 않겠습니다.

**§1.5 조치를 먼저 하고, 그 뒤 남는 발생분을 기저로 보는 순서**가 맞습니다.
조치 후 재계측 때 저희 쪽 카운트도 함께 내겠습니다 — 양측 수치를 맞춰보면
그쪽 로그에 흔적이 없는 발생분이 무엇인지 좁혀집니다.

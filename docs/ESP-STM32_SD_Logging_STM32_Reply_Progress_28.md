## 1. Q61 — 조용한 실패를 없앴습니다

### 1.1 (a) 의도된 동작이 아닙니다

```c
if(u16_logIdxCnt >= SD_LOG_IDX_MAX) return;   // 조용히
```

`SD_LOG_IDX_MAX`는 **RAM 테이블 크기 제한**으로 넣은 값이고, 넘쳤을 때의 처리는
설계된 적이 없습니다. 그냥 반환합니다.

지적하신 대로 **이것만 아무 신호가 없습니다.** 다른 실패는 전부 알립니다 —
마운트 실패, 카드 없음, 용량 부족, 쓰기 실패, 파일시스템 손상, 백필 실패.
여섯 개 코드가 있는데 이 경우만 빠져 있었습니다.

> 보고 #24 §1.4에서 저희가 "`indexed=`가 안 올라가는 것으로 드러난다"고 쓴 것도
> 정정합니다. **RTT를 보고 있을 때만 유효한 이야기**이고, 현장 조건을 고려하지
> 않은 서술이었습니다.

### 1.2 (b) `evtLogError` reason **6**을 추가했습니다

기존 채널을 그대로 씁니다. **프레임 형식 변경 없습니다.**

```c
SD_LOG_ERR_IDX_FULL = 6,   // index cap reached; that file is unreachable
```

| 필드 | 값 |
|---|---|
| reason | **6** |
| **detail** | **카드의 실제 파일 수** (16비트, 상한 0xFFFF) |

**detail을 플래그가 아니라 개수로 한 이유**가 있습니다. 한도 안에서 보면
`0x45` total은 언제나 128이므로, **한 개가 못 들어갔는지 마흔 개가 못 들어갔는지
구분할 방법이 없습니다.** 개수를 실으면 `detail - 128`이 곧 도달 불가 파일 수입니다.

### 발생 지점 두 곳

| 시점 | detail |
|---|---|
| **부팅 스캔** — 한도를 넘는 파일을 발견 | 카드의 전체 파일 수 |
| **세션 중 등재** — 로테이션·`0x56` close 시 한도 초과 | 현재 인덱스 수 (128) |

부팅 스캔은 이미 `u32_seen`(실제 파일 수)을 세어 경고 로그로 쓰고 있었습니다.
**값은 있었고 전선에 안 실렸을 뿐**입니다.

### 1.3 ESP32 측 요청

`evtLogError` 수신부에 **reason 6** 처리를 추가해 주십시오. 나머지는 그대로입니다.

의미는 **"기록은 정상, 회수만 불가"**입니다 — 로깅은 계속되고 데이터도 카드에
정상적으로 쌓입니다. 사용자에게 알릴 성격이라기보다 **정리가 필요하다는 신호**로
쓰시면 되겠습니다.

## 2. Q61-c — 닫기를 줄이지 마십시오

**빈 상태에서 닫는 것은 비용이 0입니다.**

```c
static void v_log_rotate(const char* pc_reason){
    if(!b_logOpen) return;
```

파일은 **첫 레코드가 생길 때 지연 생성**됩니다. 마지막 로테이션 이후 기록이
없으면 열린 파일이 없고, `v_SD_Log_Close()`는 즉시 반환합니다. **파일이 생기지
않습니다.**

제안하신 "기록이 있을 때만 닫기"는 이미 저희 쪽에서 그렇게 동작합니다.
ESP32에서 조건을 추가하실 필요가 없습니다.

**세션 종료마다 보내는 현재 방식을 그대로 유지하십시오.** 파일 수가 늘어나는 것은
실제로 기록이 있었던 세션에 한하며, 그것은 회수되어야 할 데이터가 있다는 뜻입니다.

## 3. §1 `0x56` 사용 — 좋은 판단입니다

**"파일은 닫혀야 목록에 오른다"**는 제약을 정면으로 푸신 것이 맞습니다.
저희가 보고 #23 §3에서 "기록 중인 파일은 읽을 수 없다"고만 답하고 **닫을 방법이
이미 있다는 것은 말씀드리지 못했습니다.**

`v_SD_Log_SetEnabled(false)`가 `v_SD_Log_Close()` → `v_log_rotate("close")` →
`v_log_close_and_index()`로 이어지므로, 보고 #24에서 합친 경로를 그대로 탄다는
분석도 정확합니다. **새 경로를 만드신 것이 아니라 기존 경로를 부르신 것**이고,
그래서 저희 쪽 검증이 그대로 적용됩니다.

### 즉시 재개하는 판단에 동의합니다

> 카드가 무선과 무관하게 기록한다는 것이 이 시스템의 안전판이고, 명령 하나
> 아끼자고 그걸 PC 의존으로 바꾸지 않겠습니다.

맞습니다. 그리고 `RESTART COMMAND NOT SENT`를 콘솔에 남기고 PC에 실패로
답하도록 하신 것도 — **로깅이 꺼진 채 조용히 진행되는 것**이 이 시스템에서
가장 나쁜 상태이기 때문입니다.

**20,433에서 닫혔으므로 1시간 로테이션(36,000)이 아니라 이 명령이 닫은 것**이라는
검증 논리도 명확합니다.

## 4. §3 카드 초기화 — 저희가 했습니다

의도한 초기화가 맞습니다. **보관이 필요한 데이터는 없었습니다.**

경위는 이렇습니다. 보고 #27 §3에서 보고드린 `sdmax = 150.9 ms`의 원인을
확인하려고, 파일 수를 바꿔 대조하기 위해 비웠습니다.

| 파일 수 | 부팅 후 첫 SD 대기 |
|---|---|
| 1개 | **10.5 ms** |
| 8개 | 19.0 ms |
| 48개 | **150.9 ms** |

**같은 카드·같은 펌웨어에서 파일 수만 바꾼 대조**이고, 결과는 §5입니다.

지워진 데이터는 벤치 시험분이며 포맷 검증(보고 #17, 165,588 레코드)이 이미
끝난 것들입니다. 로테이션 1시간 복구도 확인해 주신 대로입니다.

## 5. 부수 발견 — 파일 수는 부팅 스캔에만 영향합니다

보고 #27 §3에서 "미해석"으로 남긴 항목이 풀렸습니다.

### 5.1 원인은 파일 생성이 아니라 부팅 스캔입니다

`n=1`의 큰 값은 `v_SD_Log_Scan()`입니다. 스캔의 연속 읽기가 서로 2 ms 안쪽이라
계측기가 **한 번의 긴 대기로 병합**합니다.

```
고정 약 7.5 ms + 파일당 약 3.0 ms
  1개 -> 10.5 (실측 10.5)
 48개 -> 151.5 (실측 150.9)
```

파일당 3 ms는 `f_open` + 512 B 헤더 읽기 + `f_close` 비용과 맞습니다.

### 5.2 다른 경로는 영향받지 않습니다

| 동작 | 파일 수 영향 | 근거 |
|---|---|---|
| 일반 로깅 쓰기 | **없음** | 302회 실측, 5~50 ms 고정 |
| 로테이션 파일 생성 | **없음** | 4회 실측, b6 불변 |
| 백필 `f_open` | **없음** | 48개 상태에서 3회, 전부 2 ms 미만 |
| `0x45` 응답 | **없음** | RAM 인덱스만 읽음 |

부팅 스캔이 디렉터리를 훑으며 **카드 내부 읽기 캐시**를 데워놓기 때문으로 봅니다.

### 5.3 상한이 걸려 있습니다

```c
while(u16_logIdxCnt < SD_LOG_IDX_MAX){   // 128
```

스캔 루프가 128개에서 멈추므로 **최악 약 390 ms**이며, IWDG 2초 대비 5배
여유입니다. 부팅이 워치독에 걸릴 위험은 없습니다.

발생 시점도 `BOOT(0)` — 히터가 꺼져 있는 구간이라 제어 영향이 없습니다.

### 5.4 미시험으로 남는 것

로테이션·백필이 빨랐던 것은 **카드 캐시** 덕이고, 그것은 보장된 동작이 아닙니다.
**긴 유휴 뒤 첫 백필**은 재본 적이 없습니다. 캐시가 밀려났다면 그때 `f_open`이
150 ms를 낼 수 있고, 그 시점은 세션 중입니다.

크기는 램프 중 기준 약 1.8 °C 상당으로, 이미 수용한 오버슛(+1.0~1.2 °C)과 같은
자릿수입니다. 급한 항목으로 보지 않습니다.

**장시간 세션에서 한참 놀린 뒤 백필을 걸어주시면** 확인됩니다. 다음 기회에
부탁드립니다.

## 1. §5 `indexed=` 대조 — 일치합니다

저희 RTT 캡처입니다. `0x5F = 95`로 bootId도 맞습니다.

```
[I/SD_LOG]armed, bootId=95
[I/SD_LOG]indexed 48 file(s)
[I/SD_LOG]closed 0000005F_0000.psa size=96592 indexed=49
[I/SD_LOG]closed 0000005F_0001.psa size=96592 indexed=50
[I/SD_LOG]closed 0000005F_0002.psa size=96592 indexed=51
[I/SD_LOG]closed 0000005F_0003.psa size=96592 indexed=52
```

| | 저희 `indexed=` | 그쪽 `0x45` total |
|---|---|---|
| 부팅 직후 | 48 | — |
| 1차 로테이션 후 | **49** | **49** ✅ |
| 3차 로테이션 후 | **51** | **51** ✅ |
| 최종 | 52 | — |

**조회 시점의 두 값이 그대로 맞습니다.**

### 파일 크기도 교차 확인됩니다

```
size = 96,592 B = 512(헤더) + 1,201 × 80
```

그쪽이 센 **1,201 레코드**와 정확히 일치합니다. 저희는 크기를, 그쪽은 레코드 수를
본 것인데 같은 답입니다.

## 2. 검증 통과 — 전제 확정에 동의합니다

**재부팅이 없었음을 먼저 확정하신 것이 이 검증의 핵심**입니다. bootId 95 동일,
tick 129 s → 311 s 연속, ESP32 리셋 흔적 0건. 이 셋이 없으면 부팅 스캔과
구분되지 않습니다.

세 파일이 전부 1,201 레코드로 **반복 재현**된 것도 중요합니다. 한 번의 우연이
아니라는 것을 보여줍니다.

### §3 회수까지 하신 것

**"목록에 나타나는 것과 읽히는 것은 다르다"** — 맞습니다. 등재만 되고 읽기가
안 되면 소용이 없습니다. 진행 중인 세션에서 방금 닫힌 파일을 200건 회수해
수집률 100 %가 나온 것이 실질적 완결입니다.

### §4 `firstSeq` 동적 확인

`1200 → 1201`, `2401 → 2402`. 보고 #17에서 카드를 뽑아 정적으로 본 것을
**동작 중에 경계가 만들어지는 순간**으로 확인하신 것입니다.

`v_log_idx_add()`가 카운터가 아니라 헤더를 다시 읽는 이유가 여기 있습니다 —
두 경로가 같은 값을 내야 하고, 이번에 그것이 실측으로 확인됐습니다.

## 3. 🔴 신규 — 처음으로 100 ms를 넘었습니다

이번 세션에서 저희 히스토그램에 **b6(100–500 ms) 1건**이 찍혔습니다.

```
[D]cyc=12us sdmax=150899us n=293
[D]sdh 5 2 0 100 184 1 1 0
                      ↑ b6
```

**150.9 ms입니다.** 이전 모든 세션의 최대가 52.1 ms였고 b6는 항상 0이었습니다.

이 값은 **PID 주기 100 ms를 넘습니다** — 그 주기의 히터 출력 갱신이 누락됐다는
뜻입니다. 보고 #18에서 "b6 = 0이므로 지연이지 누락이 아니다"라고 확정했던
판정이 이 관측으로 **부분적으로 흔들립니다.**

### 3.1 발생 시점 — 로테이션이 아닙니다

2분 로테이션 빌드였으므로 첫 로테이션은 **120초** 시점입니다. 그런데
`sdmax = 150899`는 **96초 하트비트에 이미 찍혀 있었습니다.**

**첫 로테이션 전입니다.** 부팅 직후 파일 생성 구간에서 발생했습니다.

### 3.2 🟢 인덱스 등재는 무해합니다 — 확인했습니다

저희가 가장 먼저 의심한 것이 **이번에 추가한 `v_log_idx_add()` 호출**이었습니다.
로테이션마다 512 B 헤더를 다시 읽으므로 비용이 늘어납니다.

**아닙니다.** 같은 세션에서 로테이션이 **4회** 일어났는데 b6는 **1에서 늘지
않았습니다.**

| 시점 | b6 |
|---|---|
| 96 s (로테이션 전) | 1 |
| 로테이션 4회 후 (n=293) | **1** |

**로테이션 경로는 100 ms를 넘지 않습니다.** 2분 빌드가 그것을 30배 자주
실행시켰는데도 b6가 그대로인 것이 근거입니다. 1시간 빌드에서는 더욱 문제가
되지 않습니다.

### 3.3 유력한 원인 — 디렉터리가 커졌습니다

`/LOG/D0CF1336A1A4/`에 파일이 **48개**였습니다(부팅 스캔 기준). 이전 세션들에서는
15~23개였습니다.

FAT 디렉터리 조회는 항목 수에 비례합니다. 파일 생성(`f_open` + `FA_CREATE_ALWAYS`)이
빈 디렉터리 항목을 찾는 데 걸리는 시간이 파일 수와 함께 늘어납니다.

**즉 카드가 채워질수록 부팅 시 파일 생성이 느려집니다.** 2분 로테이션으로
파일을 시간당 30개씩 만든 것이 이 상태를 앞당겼습니다.

### 3.4 저희 계획

**단발 관측이므로 아직 단정하지 않겠습니다.** 1건은 사건 하나이지 비율이
아닙니다(보고 #18에서 저희가 같은 실수를 했습니다).

다음 장시간 세션에서 두 가지를 보겠습니다.

| 확인 | 의미 |
|---|---|
| 부팅 시 1회만 발생하는가 | 정상 상태에는 영향 없음 |
| 파일 수에 따라 커지는가 | 카드 수명 동안 악화 — 대응 필요 |

**그쪽에서 하실 것은 없습니다.** 다만 파일이 계속 쌓이면 이 값이 커질 수 있으므로,
회수 완료된 오래된 파일의 정리 정책을 언젠가 논의해야 할 수 있습니다.

## 4. STM32 무응답 — 적재 중으로 정리합니다

bootId가 56 → 95로 올라 있었다는 관측이 결정적입니다. **그 사이 저희가 여러 차례
적재했고**, 적재할 때마다 리셋 → `modeOFF` → STOP으로 무응답 창이 열립니다
(보고 #26 §2).

39회의 bootId 증가는 적재·부팅 반복과 정합적입니다. **결함으로 보지 않습니다.**

적재 중이 아닌 시점에 재현되면 알려주십시오. 그때는 RTT를 붙여두겠습니다.

## 5. 로테이션 주기 원복 — 완료

```c
#define SD_LOG_ROTATE_ITV   (60UL * 60UL * 1000UL)   // 1 hour
```

원복 후 빌드·적재까지 마쳤습니다. **2분 값은 커밋하지 않았습니다** — 검증용
임시 빌드로만 올렸고, 저장소에는 처음부터 1시간 값만 있습니다.

파일이 51개까지 늘어난 것은 이 검증의 대가입니다. §3.3의 관측도 그 부산물이므로,
결과적으로는 **평소보다 빨리 도달할 상태를 미리 본 셈**입니다.

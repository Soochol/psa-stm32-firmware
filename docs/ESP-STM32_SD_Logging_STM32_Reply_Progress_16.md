## 1. Q44 — 이견 없습니다

### 1.1 되돌림 완료

```
9f0520f  Revert the FORCE_ON residual heat work
         ← 9508917 (팬 정책) + b22319d (계측 로그)
```

두 커밋 모두 **실기 미검증이고 SD 로깅과 무관**하다는 판단에 동의합니다.
잔열 냉각은 자연 냉각으로 복귀하며, 히터는 그 구간 내내 꺼져 있으므로
되돌아오는 것은 **위험이 아니라 대기 시간**입니다.

### 1.2 되돌림이 깨끗합니다

두 커밋 이후의 커밋은 **전부 문서**이며 코드 의존이 없습니다. 충돌 없이
적용됐고, 흔적도 남지 않았습니다.

| 확인 항목 | 결과 |
|---|---|
| `MODE_TEMP_RESIDUAL_MARGIN` | 제거됨 |
| `ON settled` / `ON unsettled` 로그 | 제거됨 |
| FORCE_ON의 쿨링팬 참조 | `v_Mode_CoolFan_Handler()` 호출 1건 — **되돌림 이전부터 있던 것** |
| 빌드 | SUCCESS |

`9508917`이 함께 넣었던 "FORCE_ON 종료 시 팬 해제"도 같이 빠졌는데,
**이것이 정상입니다.** 그 해제는 같은 커밋의 팬 활성화가 만든 누수를 막기 위한
것이었고, 활성화가 없으면 FORCE_ON은 진입 시점의 OFF 상태를 그대로 유지하므로
해제할 대상 자체가 없습니다.

### 1.3 유지 대상 2건 확인

| 커밋 | 상태 |
|---|---|
| `e18f3ce` `MODE_TEMP_ABS_MAX = 85` | ✅ 유지. 순서 의존도 제거 포함 |
| `4aa52af` FORCE_UP 도달 온도 로그 | ✅ 유지 |

되돌림 후 코드는 `4aa52af` 시점과 **주석 7줄만 다릅니다**(`ad83adc`).
그 주석은 `MODE_TEMP_ABS_MAX`가 setpoint를 제한할 뿐 도달 온도를 제한하지
않는다는 것과, 그럼에도 85를 낮추지 않는 이유를 남긴 것입니다.
**유지 대상인 클램프를 설명하는 주석**이므로 함께 남겼습니다. 기능 변경은 없습니다.

### 1.4 범위 이탈에 대하여

> 그 발단은 ESP32 측이 Q39 답변에서 묻지도 않은 "온도 하한 도입" 제안을 한
> 것이었습니다. 저희 잘못입니다.

**한쪽 잘못이 아닙니다.** 잔열 재진입을 처음 보고서에 올린 것은 저희입니다
(`STM32_Reply_Progress_05` §6). 그때 저희가 "표시값과 실제 표면 온도가 어긋난다"로
서술했고, 그 서술이 Q39를 부르고 하한 제안을 불렀습니다.

관측 자체는 기록할 가치가 있었다고 봅니다. 문제는 그것을 **SD 로깅 보고서 안에서
계속 끌고 간 것**이고, 별건으로 분리했어야 했습니다.

## 2. 운영 사항 — 그쪽에서 볼 수 없는 것

### 2.1 🔴 벤치에 되돌리기 전 펌웨어가 올라가 있습니다

카드 회수 세션 전에 **재적재가 필요합니다.**

| | 커밋 |
|---|---|
| 현재 벤치 | `9508917` (팬 정책·계측 로그 **포함**) |
| 저장소 HEAD | `9f0520f` (되돌림 반영) |

이 상태로 세션을 돌리면 팬 정책이 동작하고, 벤치와 저장소가 어긋납니다.
**카드 검증 세션 전에 `9f0520f`를 적재**하겠습니다.

SD 로깅 동작 자체는 두 빌드가 동일하므로 **이미 받으신 백필 20개 레코드의
유효성에는 영향이 없습니다.**

### 2.2 문서 3건이 팬 정책을 "반영 완료"로 서술하고 있습니다

`STM32_Reply_Progress_12` · `_13` · `_14`입니다. 되돌림으로 사실과 어긋나게
됐으나, **수정하지 않고 그대로 둡니다.** 발송된 문서를 소급 수정하면 그쪽이
읽으신 판본과 갈리며, 그것은 보고 #11에서 함께 정리한 판본 문제를 다시 만드는
일입니다.

**이 문서(#16)가 그 3건의 후속 정정**입니다. 인용 시 #16을 함께 참조해 주십시오.

## 3. Q45 — 준비 상태

일정은 별도로 회신드리겠습니다. 준비된 것은 다음과 같습니다.

| 항목 | 상태 |
|---|---|
| 펌웨어 | `9f0520f` 빌드 완료, 적재 대기 |
| 검증 도구 | `docs/fixtures/validate_psa.py`, `verify_format.py` |
| 절차 | `docs/fixtures/CAPTURE.md` |

### 검증 대상 — 백필로 확인되지 않은 것

지적하신 대로 백필 20개 레코드는 **레코드 단위 CRC만** 통과한 것이고,
카드 전체 구조는 미확인입니다. 실물 카드에서 확인할 항목입니다.

| 항목 | 백필로 확인됨 | 카드에서 확인할 것 |
|---|---|---|
| 레코드 80 B 구조 | ✅ | — |
| CRC-16/CCITT | ✅ (20/20) | 전체 레코드 |
| 512 B 파일 헤더 | ❌ | **헤더 필드 전체** |
| `seq == firstSeq + n` 불변식 | 부분 | **파일 전체 연속성** |
| 로테이션 경계 | ❌ | **1시간 / 32 MB 경계의 파일 분할** |
| 플레이스홀더 레코드 | ❌ | **`SD_FLAG_INVALID` 비트1** |
| 파일명 규칙 | ❌ | `<bootId>_<idx>.psa` |

**로테이션 경계와 플레이스홀더가 핵심**입니다. 둘 다 골든 픽스처로만 맞춰봤고
실물에서 발생한 적이 없습니다.

## 4. Q43 종결 — 지적이 맞았습니다

> 96초 기준값은 과대추정이었고 실측 기준 약 50초입니다.

`STM32_Reply_Progress_13` §3에서 제기한 불일치가 이것입니다. 인용하신 기울기
(0.45 / 0.20 °C/s)가 피팅 `k = 0.00400`에서 유도되는 값(0.20 / 0.144)의 약 2배였고,
**기울기 쪽이 맞다면 96초보다 빠르다**고 적었습니다. 약 50초면 그 방향입니다.

계측을 취소하므로 사용처는 없습니다. **Q43은 종결합니다.**

> 다만 기록해 둘 값이 하나 있습니다 — 저희가 §2.4에서 "수십 초면 재검토"라는
> 판정 기준을 먼저 세우고 96초를 대입해 조치에 들어갔습니다. 실제가 50초였어도
> 같은 구간이라 판정은 바뀌지 않았을 것입니다. 즉 **되돌림의 근거는 숫자가
> 틀려서가 아니라 범위 밖이기 때문**이며, 그 점에서 조정에 동의합니다.

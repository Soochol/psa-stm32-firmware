## 1. 🔴 ⑭ 신규 — STOP 모드가 `tickMs`를 정지시키는데 `bootId`는 그대로입니다

### 1.1 현상

`modeOFF`는 종착 상태가 아니라 **STOP 모드로 가는 경로**입니다.

`User/Edit/src/mode.c:2098-2141`, `User/Edit/inc/mode.h:346-347`

```
modeOFF 진입 (i_mode_off = 1, 센싱 중단)
  ↓ MODE_POWEROFF_DELAY = 100 ms
12V 차단, I2C 디이니트
  ↓ MODE_LOWPWR_ENTRY_DELAY = 1000 ms
HAL_SuspendTick();
HAL_PWR_EnterSTOPMode(PWR_LOWPOWERREGULATOR_ON, PWR_STOPENTRY_WFI);   ← 여기서 정지
  ↓ (전원 키 입력)
v_WakeUp_Clock_Config()  →  HAL_ResumeTick()
```

세 가지가 동시에 성립합니다.

| 사실 | 근거 |
|------|------|
| **STOP은 리셋이 아닙니다** | `HAL_PWR_EnterSTOPMode()` 반환 후 인라인으로 실행이 이어집니다 (`mode.c:2131-2141`) |
| **`tickMs`가 동결됩니다** | `HAL_SuspendTick()`으로 SysTick 정지. `u32_Tim_1msGet()`은 `HAL_GetTick()` 그대로입니다 (`tim.c:36-38`). 복귀 시 `HAL_ResumeTick()`으로 **같은 값에서 재개** (`main.c:1827-1833`) |
| **`bootId`는 바뀌지 않습니다** | 리셋이 아니므로 부팅 카운터가 증가하지 않습니다 |

### 1.2 IWDG 분기는 코드로 확정됩니다 — 무기한 STOP입니다

"STOP 중 IWDG가 돌아 2초 뒤 리셋되지 않는가"를 확인했습니다. **그렇지 않습니다.**

`Core/Src/main.c:960-979`가 부팅마다 옵션 바이트를 검사해 **강제로 freeze로 되돌립니다.**

```c
HAL_FLASHEx_OBGetConfig(&OBInit);
if(OBInit.USERConfig & FLASH_OPTSR_FZ_IWDG_STOP){
    ...
    OBInit.USERType   = OB_USER_IWDG_STOP;
    OBInit.USERConfig = OB_IWDG_STOP_FREEZE;   /* = 0 */
    HAL_FLASHEx_OBProgram(&OBInit);
    HAL_FLASH_OB_Launch();
    HAL_NVIC_SystemReset();
}
```

`OB_IWDG_STOP_FREEZE = 0x00000000` (`stm32h7xx_hal_flash_ex.h:333`),
`OB_IWDG_STOP_ACTIVE = FLASH_OPTSR_FZ_IWDG_STOP` (`:334`).

→ **STOP 중 워치독은 정지하며, 장치는 전원 키가 눌릴 때까지 무기한 STOP에 머뭅니다.**
리셋 루프 가능성은 배제됩니다.

### 1.3 그 결과 앵커 방식이 무너집니다

작업자가 **배터리를 빼지 않고 전원 버튼만** 쓰는 시나리오입니다.

| 시각 | 사건 | `bootId` | `tickMs` |
|------|------|----------|----------|
| 09:00 | 전원 on, 작업 시작 | 42 | 0 |
| 11:00 | 전원 버튼 off | 42 | 7,200,000 |
| 11:00~12:00 | **STOP (UART 무응답)** | 42 | **7,200,000 동결** |
| 12:00 | 전원 on, 작업 재개 | **42 (그대로)** | 7,200,000부터 재개 |

ESP32가 확보하는 앵커:

- `A1 = (tick 7,200,000 ↔ 11:00)` — STOP 직전 마지막 폴링
- STOP 중에는 무응답이므로 **앵커 없음**
- `A2 = (tick 7,260,000 ↔ 12:01)` — 복귀 후 첫 폴링

복귀 직후 레코드 `seq = 72001`, `tickMs = 7,200,100`을 A1~A2 사이에서 선형 보간하면:

```
비율 = (7,200,100 - 7,200,000) / (7,260,000 - 7,200,000) = 100 / 60,000 = 0.00167
추정 시각 = 11:00 + 0.00167 × 61분 = 11:00:06
실제 시각 = 12:00:00.1
────────────────────────────────────────
오차 ≈ 60분
```

오차는 A2에 가까워질수록 줄어 0이 되므로, **복귀 직후 약 1분 분량(600 레코드)이
1시간 폭으로 뭉개집니다.**

### 1.4 왜 위험한가 — 어떤 검증에도 걸리지 않습니다

| 검사 | 결과 |
|------|------|
| `seq` 연속성 | ✅ 통과 — 72000 다음이 72001, 갭 없음 |
| `tickMs` 스텝 | ✅ 통과 — 정확히 +100 ms |
| CRC | ✅ 통과 |
| `flags` bit1 | ✅ 통과 — 유효 샘플 |
| §13 시나리오 1~16 | ✅ **전부 통과** |

**데이터는 완벽해 보이는데 시각만 틀립니다.**

§5의 다음 문구가 문제를 키웁니다.

> "앵커 밀도: 부팅 세션당 **최소 2개**(시작·종료 근처)면 수정발진자 드리프트까지
> 선형 보정되어 오차가 100 ms 이하로 유지됩니다."

2점 선형 fit을 쓰면 STOP 불연속이 **세션 전체로 번집니다.**

### 1.5 빈도 — 예외가 아니라 정상 운영입니다

- **콜드 부팅 자체가 `modeOFF`로 시작합니다** (`mode.c:2627`).
  배터리를 끼우면 곧바로 OFF → STOP이며, 전원 키를 눌러야 깨어납니다.
- `ESP_CMD_CTRL_RST`(0x50)도 `modeOFF`로 보냅니다 (`comm_esp.c:510`).
- 작업자가 점심시간에 전원 버튼으로 끄고 오후에 다시 켜면 **매번 발생**합니다.

§4는 "작업자는 하루에도 여러 번 배터리를 교체합니다"를 전제했지만,
**전원 버튼만 쓰는 경우가 오히려 자연스럽습니다.**

### 1.6 해결안 — `bootId`를 STOP 복귀 시에도 증가시킵니다

이것은 `bootId`의 의미를 **바꾸는 것이 아니라 복원하는 것**입니다.

§4가 `bootId`를 요구한 근거는 이것이었습니다.

> "seq는 부팅마다 0으로 리셋되므로 **seq만으로는 같은 장치의 오전 데이터와
> 오후 데이터를 구분할 수 없습니다.**"

그런데 **전원 버튼으로 나뉜 오전/오후 세션은 현재 정의로 같은 `bootId`를 공유합니다.**
즉 v1.2의 `bootId` 정의는 이미 자신의 목적을 달성하지 못하고 있습니다.

**재정의 요청**

> `bootId` = **연속된 `tickMs` 구간의 식별자.**
> 리셋뿐 아니라 **STOP 모드 복귀 시에도 1 증가**한다.

**효과**

| 항목 | 효과 |
|------|------|
| §8.3 로테이션 | "`bootId`가 바뀌면 반드시 새 파일" 규칙이 **파일 경계를 공짜로 제공** |
| §5 앵커 | "세션당 앵커 2개" 주장이 **다시 참**이 됨 |
| 병합 도구 | **변경 불필요** — 기존 `(deviceId, bootId, seq)` 키가 그대로 동작 |
| §6.3 `reqLogFiles` | 세션이 파일로 분리되므로 목록만 봐도 불연속이 드러남 |

**비용**: 전원 버튼 사이클마다 플래시 쓰기 1회 추가.
하루 2~5회 수준이면 §4의 4,096 슬롯 대비 무의미한 수준이며,
섹터 소거 주기(4,096 부팅)에도 사실상 영향이 없습니다.

> **참고**: `seq`는 STOP을 넘어 계속 증가하므로(센싱만 멈출 뿐 카운터는 유지),
> `bootId`가 바뀌면 새 파일의 `firstSeq`는 0이 아니라 **재개 시점의 seq**가 됩니다.
> §8.1 `firstSeq` 정의("이 파일 첫 레코드의 seq")와 이미 일치하므로 문서 변경은 없습니다.
> 다만 §8.3의 "`fileIndex`는 0부터"는 그대로 적용합니다.

### 1.7 병합 도구 측 방어선 (권장)

`bootId` 재정의만으로 충분하지만, 이중 안전장치로 한 줄 추가를 권합니다.

> 인접 앵커 쌍이 함의하는 tick 진행률이 **1,000 ticks/s에서 크게 벗어나면**
> 그 구간을 불연속으로 표시하고 **넘어서 보간하지 않는다.**

STM32 펌웨어에 예상치 못한 tick 정지 경로가 남아 있더라도 데이터가 조용히 틀리지 않습니다.

## 2. §14.3 Q14~Q16 답변

### Q14. `deviceMode` 7~10 확정 → **이의 없습니다. 수용합니다**

`0xFF` 최소안 기각 사유(§7.1)에 동의합니다. 저희가 대안으로 제시했으나,
§12의 "미지 값은 억제하지 않는다" 원칙과 양립하지 않는다는 지적이 정확합니다.
`v_Mode_Healing()`의 `evtMode` 송신도 함께 구현하겠습니다.

다만 문서에 명시해 주셔야 할 관측 범위 단서가 **2건** 있습니다.

#### (a) SD 레코드에는 `{0~5, 7}`만 나타납니다

§7.1 표의 "샘플링" 열이 이미 답을 담고 있지만, 결론이 명시되어 있지 않습니다.

| 값 | 모드 | SD 레코드 | 0x43 응답 |
|---|------|-----------|-----------|
| 0~5 | SLEEP ~ TEST | ✅ 나타남 | ✅ |
| **6** | ERROR | ❌ **없음** | ✅ |
| **7** | HEALING | ✅ 나타남 | ✅ |
| **8~10** | BOOTING / WAKE_UP / OFF | ❌ **없음** | ✅ (단서 (b) 참조) |

`6`과 `8~10`은 샘플링이 정지하는 모드이므로 **레코드가 생성될 수 없습니다.**
이를 §7.1에 한 줄 적어 주시지 않으면 **병합 도구가 영원히 오지 않는 값을 기다리게 됩니다.**

#### (b) `OFF(10)`은 약 1.1초만 관측 가능합니다 ⚠️

§1.1에서 확인했듯 `modeOFF` → STOP 진입까지는
`MODE_POWEROFF_DELAY(100 ms) + MODE_LOWPWR_ENTRY_DELAY(1000 ms)` = **약 1.1초**입니다.
그 이후 STM32는 UART에 **일절 응답하지 않습니다.**

0x43 폴링 주기가 1분이므로 **이 1.1초 창에 폴링이 걸릴 확률은 약 1.8%** 입니다.

> **따라서 "전원이 켜진 채 OFF로 놓인 장치"의 정상 상태는 `deviceMode=10`이 아니라
> `0x43 무응답`입니다.**

**요청 2건**

1. **§12에 무응답 처리 규칙 추가**
   > 0x43이 연속 N회 무응답이면 **링크 다운 / 전원 꺼짐 상태로 분류**하고
   > 별도 경보를 냅니다. **seq 정체 경보로 흘려보내지 않습니다.**

   이 규칙이 없으면 STOP에 들어간 장치가 "seq가 안 늘어난다"가 아니라
   아예 응답이 없는 상태로 남아, §12의 어느 조건에도 걸리지 않습니다.

2. **§13 시나리오 16의 창 한정**
   > "OFF 전환 **직후 1초 이내** 0x43 조회 시 `deviceMode=10` 보고" 로 수정.
   > 그 이후는 무응답이 정상이며, 시나리오 16의 후반부는
   > **"무응답이 링크 다운으로 분류되고 seq 정체 오경보가 발생하지 않음"** 을 검증합니다.

#### (c) 실질적으로 가장 유용한 값은 `BOOTING(8)`입니다

`modeBOOTING`은 센서 초기화·MP3 준비·기울기 센터링을 기다리며 **무기한 유지될 수 있고**
(`mode.c:1550-1560`), 그동안 메인 루프가 돌기 때문에 **0x43은 정상 응답합니다.**
장치를 눕혀 두면 BOOTING에 머무는데 seq는 늘지 않으므로, 게이팅이 없으면 지속 오경보가 납니다.

`WAKE_UP(9)`도 `MODE_WAKEUP_DELAY = 1000 ms`(`mode.h:348`)로 짧지만 관측 가능합니다.

### Q15. 쓰기 실패·부분 쓰기 시 로테이션 → **구현 가능합니다**

#### FatFs 의미론 확인 완료

| 항목 | 근거 |
|------|------|
| `*bw`는 청크마다 누적됨 | `ff.c:3625` (`*bw = 0`), `ff.c:3636` (`*bw += wcnt`) |
| 디스크 오류 시에도 `*bw` 보존 | `ABORT` 매크로는 `fp->err` 설정 후 반환 (`ff.c:455`) — `*bw`를 되돌리지 않음 |
| `fp->fptr`도 같은 루프에서 동기 갱신 | `ff.c:3636` |

→ **`f_write()` 반환 후 `bw != btw`만 보면 부분 쓰기를 정확히 감지할 수 있습니다.**
`res != FR_OK` 와 함께 판정하면 디스크 오류와 용량 부족을 모두 잡습니다.

#### 다만 §7.4보다 **더 단순한 규칙**을 제안합니다

문서는 "새 파일의 `firstSeq`는 실제로 기록되는 첫 레코드의 seq"라고만 했는데,
이를 `floor(bw / 80)` 산술로 풀면 경계 조건이 늘어납니다. 그럴 필요가 없습니다.

**근거**: 모든 flush는 `f_write` + `f_sync` 쌍이므로,
구 파일의 **디렉터리 엔트리에 반영된(=읽을 수 있는) 내용은 항상 마지막 성공 sync 지점**,
즉 **레코드 경계**에서 끝납니다. 부분 쓰기로 넘어간 바이트는 sync되지 않았으므로
파일 크기에 잡히지 않습니다.

**제안 규칙**

> 쓰기 실패 또는 부분 쓰기가 감지되면:
> 1. 구 파일 핸들을 포기하고 close (`fp->err` 때문에 어차피 재사용 불가)
> 2. 새 파일을 열고 **현재 RAM 배치 전체를 다시 기록**
> 3. 새 파일의 `firstSeq` = **그 배치의 첫 레코드 seq**

`floor(bw/80)` 계산이 불필요하고, **유실이 0**이 됩니다
(배치가 아직 RAM에 그대로 있으므로).

#### 이 규칙이 만드는 모호성 1건 — 닫아 주십시오 ⚠️

용량 부족으로 `FR_OK` + 부분 쓰기가 난 경우, 구 파일의 읽기 가능 범위와
새 파일의 범위가 **최대 1배치(20 레코드)만큼 겹칠 수 있습니다.**

병합 저장소는 `(deviceId, bootId, seq)` 키로 중복을 제거하므로 문제가 없지만,
**`reqLogRead`(§6.4)의 파일 선택 규칙이 없습니다.** 같은 seq를 담은 파일이 둘이면
STM32가 어느 쪽을 열어야 할지 정해져 있지 않습니다.

**요청**: §6.4에 한 문장 추가

> 실패 로테이션 이후 파일 간 seq 범위가 겹칠 수 있다.
> 이 경우 **`fileIndex`가 큰 파일을 우선**한다.

#### §13 시나리오 15에는 결함 주입 훅이 필요합니다

"강제 쓰기 실패 주입"을 하려면 수단이 있어야 합니다.
diskio 래퍼(`sd_diskio.c`의 `SD_write`)에 **디버그 플래그로 `RES_ERROR`를 강제**하는
경로를 넣겠습니다. 릴리스 빌드에서는 컴파일 아웃합니다.

### Q16. `SD_TIMEOUT` 축소 시 오탐 → **단일 상수를 줄이는 대신 역할별로 분리합니다**

우려는 타당합니다. 마모 평준화·GC 중인 카드는 실제로 수백 ms를 멈춥니다.
다만 현재 `SD_TIMEOUT` 하나가 **성격이 전혀 다른 세 대기**에 공용으로 쓰이는 것이 문제입니다.

#### (a) 역할별 분리

| 대기 | 위치 | 자연 소요 | 제안 상한 |
|------|------|-----------|-----------|
| 카드 ready 대기 (연산 시작 전) | `sd_diskio.c:119-133` `SD_CheckStatusWithTimeout()` | 보통 즉시 | **200 ms** |
| **DMA 완료 대기** | `sd_diskio.c:219`, `:266` | **µs 스케일** (512 B @ 39.2 MHz ≈ 26 µs) | **100 ms** |
| **카드 busy 복귀 대기** | `sd_diskio.c:233`, `:352` 등 | **여기에 GC 지연이 삽니다.** SD 스펙 공칭 250 ms, 저가 카드 500 ms+ | **600 ms** |

DMA 완료 대기를 100 ms로 잡아도 정상 카드에서는 3,800배 여유입니다.
**오탐이 날 수 있는 곳은 사실상 busy 복귀 대기 하나뿐**이므로, 여기만 넉넉히 잡으면 됩니다.

#### (b) 재시도 예산이 같은 2초 천장을 씁니다 ⚠️

§10.4는 "쓰기 실패 → **재시도** → 실패 지속 시 재마운트"로 규정했는데,
이를 **인라인 루프로 돌리면 `타임아웃 × 재시도 횟수`가 그대로 블로킹**입니다.
600 ms × 3회 = 1.8초로 IWDG 2초를 거의 다 씁니다.

**구현 방침**

> 재시도는 **메인 루프 반복에 분산**합니다. 한 번의 `v_SD_Log_Flush()` 호출 안에서
> 연속 재시도하지 않고, 실패하면 반환한 뒤 다음 주기에 다시 시도합니다.
> **K회 연속 타임아웃 후에만 `evtLogError(3)`으로 승격**합니다.

K회 연속 조건이 Q16이 걱정하신 오탐을 직접 억제합니다 —
GC 지연은 단발성이므로 연속 K회를 채우지 못합니다.

#### (c) 측정은 거의 공짜입니다

`DWT_Init()`이 이미 구현되어 있습니다 (`tim.c:89-93`, CYCCNT 활성화).
`v_SD_BusyWait_Yield()`가 **모든 busy-wait에서 호출되므로**, 여기서 최대 블로킹 시간을
누적 계측하면 별도 계측 코드 없이 실측값을 얻을 수 있습니다.

**§13 시나리오 8 실측 시 다음을 함께 보고하겠습니다.**

| 항목 | 내용 |
|------|------|
| 최대 블로킹 시간 | 읽기 / 쓰기 각각 |
| 분포 | p50 / p99 / max |
| 타임아웃 발생 빈도 | 제안 상한 기준 |
| 100 Hz 루프 지터 | 로깅·백필 on/off 비교 |

이 실측 후 (a)의 상한값을 확정하겠습니다. **문서에는 상한값을 못 박지 말고
"실측 후 확정"으로 남겨 주십시오.**

## 3. 소소한 정정

### 3.1 §6.4 예제가 `count = 1000`인데 권장값은 128입니다

`02 0E 20 44 ... 03 E8 AF 03` — `03 E8` = 1000이고 설명도 "1000개"입니다.
같은 절의 필드 표는 "권장 128"이라 읽는 사람이 혼란스럽습니다.

프레임 자체는 유효하며 체크섬 `0xAF`도 맞습니다(재검산 완료). **표기만 정리 요청드립니다** —
예제를 128(`00 80`)로 바꾸시면 체크섬도 함께 바뀌니, 설명 문구만 손보시는 편이 안전합니다.

### 3.2 §6.2 21 B 응답 예제 — 체크섬 `0xB6` 유효 확인

LEN이 `0x18` → `0x19`로 바뀌면서 XOR 차이 `0x01`이 발생하는데,
새로 추가된 `deviceMode = 0x01` 바이트와 정확히 상쇄됩니다.

```
A5^02=A7 ^19=BE ^02=BC ^43=FF ^01=FE ^00^00^00=FE ^2A=D4 ^00=D4 ^01=D5
^E2=37 ^40=77 ^00=77 ^BC=CB ^61=AA ^4E=E4 ^1D=F9 ^4C=B5 ^00=B5 ^03=B6
^00=B6 ^00=B6 ^01=B7 ^01=B6                                    → 0xB6 ✅
```

전체 27 B, LEN `0x19` = 25 = 4 + 21 도 일치합니다. **수정 불필요**이며 확인 결과만 공유합니다.

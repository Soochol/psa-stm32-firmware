## 1. §1.3 초기화 타이밍 — 예상과 일치합니다

`0x80` 5.2초 / `0x81` **13.1초**는 정상 범위입니다.

`MODE_BOOTING_TOUT = 20000` (20초, `mode.h:133`)이 상한이고, BOOTING은 센서 초기화·
MP3 준비·기울기 센터링을 모두 기다린 뒤 종료합니다. 13.1초면 **타임아웃에 걸리지 않고
정상 완료**한 것입니다.

INIT 커맨드를 `0x81` 핸들러에 모으신 근거로도 타당합니다 — 그 이전에는 STM32가
센서 파라미터를 받아도 적용할 대상이 아직 초기화되지 않았습니다.

## 2. §4 질의 ① — **B를 권합니다. A는 의미가 어긋납니다**

### 2.1 A의 문제 — 일어나지 않은 사건을 재생하는 것

`0x81`은 **상태가 아니라 사건**입니다. "STM32가 방금 부팅을 마쳤다"는 뜻이고,
ESP32 단독 재부팅 시 그 사건은 **일어나지 않았습니다.**

STM32가 요청에 응해 `0x81`을 다시 보내면 ESP32는 "STM32가 방금 부팅했다"고 결론짓는데,
그건 사실이 아닙니다. 그리고 그 잘못된 결론 위에서 **안전 초기화가 재실행**됩니다 —
지적하신 "이미 힐링을 마친 장치에 재무장" 문제가 정확히 여기서 나옵니다.

> 이 교환에서 같은 유형의 오류가 이미 두 번 있었습니다.
>
> | 항목 | 이름이 약속한 것 | 실제 |
> |---|---|---|
> | `errorMask` "스냅샷" | 현재 상태 | 누적 이력 |
> | `initTempLimit` "상한" | 과열 보호 | 설정 클램프 |
>
> `0x81`을 상태 조회로 쓰는 것은 **세 번째 사례가 됩니다.**

### 2.2 필요한 것은 상태 조회이고, **`0x43`이 이미 그것입니다**

ESP32가 실제로 알고 싶은 것은 "STM32가 준비됐는가"이지 "방금 부팅했는가"가 아닙니다.
그리고 `reqLogStatus`(0x43)가 바로 그 질문에 답합니다.

| 근거 | 확인 |
|---|---|
| **BOOTING 중에도 응답합니다** | `v_Uart_Handler()`가 메인 루프(`main.c:394`)에 있고, 모드 핸들러도 같은 루프입니다. 모드와 무관하게 응답합니다 |
| **`deviceMode`가 현재 상태를 직접 알려줍니다** | §16.3-8에서 21 B 응답에 넣은 필드입니다 |
| **무응답도 정보입니다** | STOP 모드 = UART 무응답. ⑯ 규칙이 이미 이를 "링크 다운/전원 꺼짐"으로 분류합니다 |

즉 **`0x81`보다 많은 정보를 이미 주고 있습니다.** `0x81`은 "부팅했다" 한 비트지만,
`0x43`은 "지금 어느 상태인가"를 말합니다.

### 2.3 안전 초기화 재실행 — 멱등성으로 갈립니다

물어보신 "재무장이 맞는가"는 항목마다 답이 다릅니다.

| 항목 | 성격 | ESP32 단독 재부팅 시 |
|---|---|---|
| `initLogIdentity`(0x23) | **멱등** — STM32가 이미 플래시에 보유 | 재전송 무해. 보내셔도 됩니다 |
| `initTempLimit`(0x14) | **멱등** — STM32 RAM에 유지됨 | 재전송 무해 |
| `initTempForceUp`(0x12) | **멱등** | 재전송 무해 |
| 히터 활성화 | STM32가 모드에 따라 스스로 관리 | **불필요** |
| **힐링 재무장** | **비멱등 — 실제 가열 사이클을 시작합니다** | **게이팅 필요** |

파라미터 3종은 STM32 RAM/플래시에 그대로 남아 있으므로 재전송이 no-op입니다.
**보내는 편이 낫습니다** — STM32가 실제로 재부팅한 경우까지 같은 코드로 덮이니까요.

문제는 힐링뿐이고, **`deviceMode`로 정확히 갈립니다.**

```
0x43 응답의 deviceMode:
  BOOTING(8) / HEALING(7)  → STM32가 갓 부팅함 → 전체 초기화 적절
  WAITING(1)/FORCE_*/SLEEP → 세션 진행 중      → 파라미터만, 힐링 재무장 금지
  무응답                    → ⑯ 규칙 (링크 다운/전원 꺼짐)
```

### 2.4 권고

> **B를 채택하되, 판정 근거를 "일정 시간 STAT 수신"이 아니라 **`0x43` 응답 + `deviceMode`**로
> 하십시오.**

"STAT이 일정 시간 오면"은 휴리스틱이라 임계값을 정해야 하고 경계 사례가 생깁니다.
`0x43` 응답은 **결정적**입니다 — 응답이 오면 STM32는 요청을 처리할 수 있는 상태이고,
`deviceMode`가 어느 상태인지까지 말해줍니다.

ESP32 측 변경은 다음과 같습니다. **STM32 변경도 프로토콜 추가도 없습니다.**

1. 자체 부팅 직후 `0x43`을 **즉시 1회** 폴링 (1분 주기를 기다리지 않음)
2. 응답이 오면 → 파라미터 3종 전송 + 폴링/앵커 시작
3. `deviceMode`가 BOOTING/HEALING일 때만 → 힐링 재무장 포함
4. 무응답이면 → ⑯ 규칙으로 분류하고 재시도

`0x81`은 그대로 두십시오. 정상 경로에서는 여전히 가장 빠른 신호이고,
B는 그것을 대체하는 게 아니라 **놓쳤을 때의 복구 경로**입니다.

### 2.5 그래도 A를 원하시면

구현은 어렵지 않습니다. 다만 **새 커맨드 코드가 필요하고**(`0x81` 재전송을 요청하는
REQUEST), §2.1의 의미 문제가 남습니다. 그 경우 최소한 **재전송임을 구분할 수 있는
표식**(예: `evtInitResult` DATA에 "재전송" 플래그)을 넣어, ESP32가 진짜 부팅과
재전송을 구별할 수 있게 해야 한다고 봅니다.

**저희 권고는 B이며, 판단은 그쪽에 맡깁니다.** A로 결정하시면 커맨드 코드를 배정해
주십시오 — REQUEST 범위(`0x46`~`0x49`)가 비어 있습니다.

## 3. §5 질의 ② — **이미 2회/교체 기준입니다. 닫아 주십시오**

회신 v1.4 §1에서 확정한 표가 그대로 2회/교체입니다.

| 사건 | 리셋 소비 |
|---|---|
| **배터리 삽입** | **2** (콜드 부팅 + WAKE_UP 하드 리셋) |
| 전원 버튼 off → on | 1 (WAKE_UP 리셋만) |

그리고 Q20에서 그쪽이 산정하신 **7~8 리셋/일**이 바로 이 기준입니다 —
배터리 삽입 3회 × 2 + 휴게 조작 1~2회 × 1 = 7~8.

### 수명 계산

```
슬롯 수 = FLASH_CFG_SIZE / FLASH_WORD_SIZE = 128 KB / 32 B = 4,096
소비    = 8 슬롯/일  (부팅 7~8 + 설정 변경 소수)
수명    = 4,096 / 8 ≈ 512일 ≈ 1.4년
```

여유 임계값 `FLASH_CFG_ERASE_MARGIN = 64`는 **8일치**입니다
(`flash_cfg.c:32`). 소거는 그 전에 부팅 초기 단계에서 선제 수행되므로
런타임 중 소거가 발생하지 않습니다.

**이 항목은 닫아 주셔도 됩니다.**

## 4. §3.2 벤치 빌드 확인 — 일부만 확정할 수 있습니다

### 확정되는 것

`flash_cfg.c`를 열람하고 확인하신 내용은 **현재 워크트리와 일치합니다.**
`v_Flash_Cfg_Init()`가 유일한 증가 지점이고 `i_state_loaded` 가드가 있으며
STOP 복귀 경로에 증가 코드가 없습니다. ⑭ 철회가 코드에 반영돼 있습니다.

관측하신 동작(`bootId` 전원 사이클당 +2, 고아 세션이 파일을 만들지 않음)도
이 코드의 동작과 정확히 일치합니다.

### 확정되지 않는 것

**§4 캡처 시점(2026-08-12 12:00경)의 벤치 빌드에 아래 두 커밋이 포함됐는지는
확인되지 않습니다.** 둘 다 그 이후 커밋입니다.

| 커밋 | 내용 | 캡처에 미치는 영향 |
|---|---|---|
| `e18f3ce` | `MODE_TEMP_ABS_MAX = 85` 클램프 + 순서 재적용 | 온도 동작. 로깅/`bootId`와 무관 |
| `4aa52af` | FORCE_UP 도달 온도 로그 | 로그 1줄 추가. 동작 변경 없음 |

즉 **§3의 `bootId` 분석과 §1의 앵커 검증에는 영향이 없습니다.**
다음 세션은 `4aa52af`로 적재해 진행하며, 그때 `[I/FORCE] UP reached ...` 줄이
로그에 새로 나타나는 것으로 적재 여부를 확인하실 수 있습니다.

## 5. §7 `MODE_TEMP_ABS_MAX` — **완료했습니다** (`e18f3ce`)

보고 작성 시점 이후에 반영됐습니다. 확정해 주신 값 그대로입니다.

```c
#define MODE_TEMP_ABS_MAX   85.0f
```

네 개 온도 세터가 모두 이 값으로 클램프하며, 클램프 시 `LOG_WARN`을 남깁니다.

### 순서 의존도 함께 제거했습니다

§5.1에서 ESP32 측에 경고 가드를 넣으신 그 문제입니다. STM32 쪽에서 근본적으로
해결했습니다 — **요청값을 클램프된 값과 분리해 보관하고, `f_max`가 바뀔 때마다
재적용**합니다.

| 시나리오 | 결과 |
|---|---|
| `0x14`=85 → `0x12`=80 (현행 순서) | f_max 85 / forceUp **80** ✅ |
| `0x12`=80 → `0x14`=85 (역순) | forceUp 70 → **80** ✅ **순서 무관** |
| `0x14`=200 → `0x12`=150 (이상값) | **85 / 85** ✅ |
| 힐링 80, 강도 72·64·54 | **전부 그대로 통과** ✅ |

§5.1의 ESP32 경고는 이제 **이중 안전장치**가 됩니다 — 순서가 뒤바뀌어도 최종 상태는
같지만, 경고가 뜨면 전송 순서가 바뀐 것이므로 그 자체로 유용한 신호입니다.

## 6. 8시간 세션 — 현황

**아직 실시하지 않았습니다.** 현재 단계는 다음과 같습니다.

| 단계 | 상태 |
|---|---|
| RTT 접속 환경 구축 | ✅ 완료 (§7 참조) |
| 7분 예비 계측 | ✅ 완료 — 보고 #03에 보고한 212건 |
| `4aa52af` 적재 | ⏳ 진행 중 |
| Q23 실물 카드 회수 | ⏳ 적재 후 |
| **8시간 세션** | ⏳ 카드 회수 후 |

순서를 이렇게 잡은 이유는 실물 카드가 먼저 나오면 **포맷 검증과 8시간 세션을
분리**할 수 있기 때문입니다. 8시간을 돌린 뒤 포맷 문제가 발견되면 다시 8시간이
필요해집니다.

회신 #03 §6.1의 5개 항목은 그대로 챙기겠습니다. 5번(힐링 IR 도달 온도)은
`4aa52af`에서 전용 로그를 넣었습니다 — 기존 5초 하트비트로는 5~10초짜리 램프에서
표본이 1~2개뿐이라 도달값을 말할 수 없었습니다.

```
[I/FORCE] UP reached ir=79.8 set=80.0 in 6240ms -> ON      ← 도달
[I/FORCE] UP timeout ir=71.2 set=80.0 after 10000ms -> ON   ← 미도달
```

두 종료 경로를 구분합니다. 지적하신 "힐링이 상한에 걸려 조기 종료되면 SD 부하 패턴이
달라진다"가 후자이고, 하류에서는 둘이 똑같아 보이므로 구분이 필요합니다.
경과 시간도 나오므로 **Q29에서 유도로만 답했던 승온율이 실측으로 나옵니다.**

## 8. §3.3 문서 정오 — 동의합니다

§16.3-3에 철회 전 지시가 남아 있었다는 지적이 맞습니다.

**변경 이력 표를 그대로 두고 §16.3만 고치신 판단에 동의합니다.** 이력은 시점의 기록이고
§16.3은 지금 따라야 할 체크리스트라는 구분이 정확합니다.

> 다행히 **구현은 §4.2를 따랐고 §16.3-3을 따르지 않았습니다.** `dc05f0d` 커밋 메시지에
> "bootId identifies one contiguous tickMs span... every reset"으로 적혀 있고,
> 그쪽이 §3.2에서 코드로 확인하신 대로입니다.
>
> 다만 지적하신 위험은 실재합니다 — 저희가 보고 #02에서 **단계 번호로 진척을 보고**했으므로,
> 다음 사람이 그 표를 따라 작업하면 철회된 지시를 구현하게 됩니다. 잡아주셔서 감사합니다.

절 번호와 단계 번호를 유지하신 것도 좋습니다. 기존 회신 문서들의 인용이 전부 그대로
유효합니다.

## 1. 🔴 Q65 — 결과 2는 도달 가능합니다

### 1.1 검사 순서가 인덱스 조회보다 앞입니다

```c
if(!b_SdMount) return 4;
if(b_SD_Log_Backfill_Active()) return 3;
if(b_logOpen && u32_boot == u32_Flash_Cfg_Get_BootId()
        && (uint32_t)u16_idx == u32_logFileIdx){
    return 2;                                   // ← 여기
}
for(i = 0; i < u16_logIdxCnt; i++){ ... }       // ← 인덱스 조회는 그 다음
if(i >= u16_logIdxCnt) return 1;
```

**"인덱스에 없음"이 먼저 답하는 구조가 아닙니다.** 기록 중인 파일 검사가
인덱스 조회보다 앞에 있고, 인덱스를 참조하지도 않습니다.

> 그쪽 추론("인덱스에 있으면 정의상 닫힌 것")은 **인덱스에 대해서는 맞습니다.**
> 다만 결과 2는 인덱스를 보지 않고 `b_logOpen`과 현재 bootId·fileIdx를 직접
> 비교합니다. 목록에 없어도 지목만 하면 걸립니다.

### 1.2 그렇다면 왜 1이 나왔나

세 조건의 AND이므로 하나라도 어긋나면 통과해서 인덱스 조회로 갑니다.

| 조건 | 어긋나는 경우 |
|---|---|
| `b_logOpen` | **로깅이 꺼져 있거나**, 마지막 close 이후 새 레코드가 아직 없음 |
| `bootId` 일치 | 다른 세션을 지목 |
| `fileIdx` 일치 | **`0x43`을 읽은 뒤 그 사이에 로테이션·close가 일어남** |

**가장 유력한 것은 세 번째와 첫 번째입니다.** 시험 1에서 `0x56`으로 파일을
만드셨는데, close 직후에는 `u32_logFileIdx`가 이미 다음 번호로 올라가 있고
새 레코드가 오기 전까지 `b_logOpen`이 false입니다.

그 창에서 이전 번호를 지목하면 **그 파일은 이미 인덱스에 있으므로 결과 0**,
다음 번호를 지목하면 **아직 없으므로 결과 1**이 됩니다.

### 1.3 재현 방법

**`0x43`을 읽고 곧바로** 그 `bootId` + `fileIndex`로 `0x57`을 보내십시오.

| 전제 | |
|---|---|
| 로깅이 **켜져 있을 것** | `0x56`으로 멈춘 상태면 열린 파일이 없습니다 |
| 그 사이 close가 없을 것 | `0x56`을 보내지 말고, 로테이션(1시간)도 피해서 |
| 레코드가 흐르고 있을 것 | SLEEP이면 10 Hz로 들어오므로 충분합니다 |

`0x43`의 `fileIndex`는 **지금 쓰고 있는 파일의 번호**이므로, 그 값이 곧
결과 2를 부르는 값입니다.

### 1.4 그래도 사양서에 적겠습니다

재현이 까다로운 것은 사실입니다 — **정상 운용에서 이 조건에 닿는 것은
사고에 가깝습니다.** PC가 목록에 없는 파일을 지목할 이유가 없기 때문입니다.

§6.9.1에 한 줄 넣겠습니다.

> **결과 2**는 `reqLogFiles`에 나타나지 않는 파일을 지목했을 때만 발생합니다.
> 목록을 따라 요청하는 정상 경로에서는 나오지 않습니다.

**검사를 지우지는 않겠습니다.** 목록에 없는 것을 지목하는 경로가 존재하는 한
(PC가 직접 만든 요청, 오래된 목록으로 요청, 시험) 가드는 필요합니다.

## 2. Q66 — 적어둡시다. 다만 "예보"보다 정확한 설명이 있습니다

### 2.1 관측이 맞습니다

`filesOnCard`는 **기록 중인 파일을 포함**하고 `0x45 total`은 포함하지 않으므로,
정상 운용에서 **1 차이가 납니다.**

### 2.2 그 1은 "아직 아닌 것"이 아니라 "곧 그렇게 될 것"입니다

**예보에 가깝다**고 하셨는데, 조금 더 정확히는 이렇습니다.

기록 중인 파일도 **닫힐 때 등재를 시도**합니다. 그 시점에 인덱스가 여전히
가득 차 있으면 **그 파일도 도달 불가가 됩니다.**

| 시점 | `onCard` | 도달 불가 | `onCard − 128` |
|---|---|---|---|
| 128 등재 + 1 열림 | 129 | 0 | **1** |
| 그 파일이 닫힌 뒤 | 129 | **1** | 1 |

**계산값 1은 처음부터 맞았고, 실제가 뒤늦게 따라온 것**입니다. 열린 파일은
이미 자리가 없는 상태에서 쓰이고 있으므로, 닫히는 순간 밀려납니다.

즉 **한 칸 앞서는 것이 아니라, 결과를 미리 말하는 것**입니다.

### 2.3 제안 문구

§8.4에 이렇게 넣겠습니다.

> `filesOnCard`는 기록 중인 파일을 포함하므로 `reqLogFiles`의 `total`보다
> 통상 1 큽니다. 인덱스가 가득 찬 상태에서 이 파일은 **닫히는 순간 도달
> 불가가 되므로**, `filesOnCard - 128`은 확정된 손실이 아니라 **닫힌 뒤의
> 값을 미리 보여주는 것**입니다. 표시할 때 "이미 잃었다"로 읽히지 않게
> 하십시오.

**표시 문구는 그쪽 판단에 맡기겠습니다.** "1 beyond"를 그대로 쓰셔도 틀리지
않습니다 — 다만 그 1이 아직 열려 있는 파일이라는 것을 아는 상태에서 쓰는 것과
모르고 쓰는 것이 다릅니다.

## 3. 시험 결과 — 나머지 4건 확인

| # | 결과 | 확인 |
|---|---|---|
| 1 | 0, 17 → 16 | ✅ `file=3`만 제거, 0·1·2·4·5·6 유지 |
| 3 | 3 | ✅ 백필 중 거부 |
| 4 | 1 | ✅ 없는 세션 |
| 5 | `0x45` 16→15, `onCard` 17→16 | ✅ 두 값 함께 감소 |

**1번의 "다른 인덱스가 그대로"가 중요합니다.** 배열 중간을 지우고 뒤를 당기는
처리가 순서를 깨지 않았다는 뜻이고, 백필의 파일 탐색이 그 순서에 의존합니다.

### `filesOnCard`가 안 보이던 것

> 한도 초과일 때 말고는 찍지 않고 있었습니다.

저희가 값을 실어놓고 **그것이 보이는지는 확인하지 않았습니다.** 상태 줄에
넣으신 것이 맞습니다 — 평상시 값을 봐야 한도에 다가가는 것도 보입니다.

## 4. §5 삭제 UI — 판정 기준이 특히 좋습니다

> 판정 기준은 요약 수치가 아니라 보유입니다 — 장치가 말한 그 파일의 모든 seq를
> 갖고 있어야 목록에 오릅니다.

**"수집률 100 %"가 아니라 "모든 seq 보유"**로 잡으신 것이 정확합니다.
요약 수치는 계산 결과이고, 보유는 사실입니다. 계산에 결함이 있으면 요약은
틀릴 수 있지만 보유는 틀리지 않습니다.

`load_existing`이 CRC 실패 레코드를 버리므로 **보유 = 온전히 도착**이라는
연결도 맞습니다.

되돌릴 수 없다는 것과 사본이 유일본이 된다는 것을 화면에 그대로 적으신 것도
좋습니다.

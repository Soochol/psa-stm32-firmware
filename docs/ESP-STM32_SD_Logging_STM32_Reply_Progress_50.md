## 1. `filesOnCard`가 68입니다

오늘 펌웨어를 재적재하고 RTT로 확인한 값입니다.

```
[I/FLASH_CFG]bootId=124 vol=1 slots=3900
[I/SD_LOG]armed, bootId=124
[I/SD_LOG]indexed 68 of 68 file(s) on card
```

**`0x43`의 `filesOnCard`로 보이는 값이 68입니다.** 그쪽 화면에 61로 남아 있다면
`reqLogStatus`를 한 번 받아보시면 맞춰집니다.

### 1.1 7개가 어디서 왔는가

| | |
|---|---|
| 그쪽 시험 시점 | `boot=114` (삭제 시험의 대상 파일) |
| 지금 | **`bootId=124`** |
| 그 사이 | **10회 부팅** |

로깅 시간이 아니라 **부팅 횟수**로 늘었습니다. 저희 쪽 작업 — 펌웨어 재적재,
디버거 붙이기 시도, 전원 조작 — 이 각각 한 번씩 셌습니다.

**보고 #49 §4.4에 적은 산식이 그대로 나왔습니다.**

```
파일 수 ≈ (총 로깅 시간 ÷ 1시간) + 부팅 횟수 + 카드 탈착 횟수
```

그때는 코드를 읽고 낸 값이었고, 이번에는 실물이 같은 답을 냈습니다. **하루 만에
61 → 68**이고, 그동안 로깅한 시간은 몇 분입니다.

> 삭제 시험이 62 → 61로 하나 줄인 그 날, 저희 쪽 부팅이 7개를 얹었습니다.
> `0x57` 위생이 **부팅 빈도를 따라가야** 한다는 뜻입니다.

## 2. 부팅 스캔 214.8 ms

같은 부팅에서 SD 블로킹 측정값입니다.

```
[D]cyc=12us sdmax=214786us n=12
[D]sdh 0 0 0 2 9 0 1 0
                    ↑ b6 (100~500 ms) 에 1건
```

이 `sdmax`는 표본이 12건에서 37건이 될 때까지 **한 번도 갱신되지 않았습니다.**
단발 사건이고, 정체는 **부팅 스캔**입니다.

### 2.1 보고 #27 모델이 맞았습니다

| | |
|---|---|
| 모델 (보고 #27) | `7.5 ms + 3.0 ms/file` |
| 68개 예측 | **211.5 ms** |
| **실측** | **214.8 ms** |
| 오차 | **+1.6 %** |

48개에서 150.9 ms를 재고 세운 모델인데, **20개 늘어난 지점에서 1.6 % 안에
들어왔습니다.** 파일당 비용이 선형이라는 가정이 이 구간에서 유지됩니다.

### 2.2 상한 예산의 절반을 넘었습니다

| 파일 수 | 부팅 스캔 | IWDG 2.0 s 대비 |
|---|---|---|
| 48 (이전 실측) | 150.9 ms | 13배 |
| **68 (지금)** | **214.8 ms** | **9.3배** |
| 128 (상한) | 약 390 ms | 5.1배 |

**아직 여유는 충분합니다.** 다만 128을 "아직 먼 곳"으로 두기에는 오늘 하루의
증가폭이 작지 않았습니다.

### 2.3 평시 블로킹은 그대로입니다

```
[D]sdh 0 0 0 12 24 0 1 0     (n=37)
        b3 ┘  b4 ┘     b6 ┘
```

`b3`(5~10 ms)와 `b4`(10~50 ms)만 계속 늘어납니다. **`b5`·`b7`은 0이고 `b6`은
부팅 스캔 1건에서 멈춰 있습니다.**

평시 플러시는 **50 ms 안**이고, 보고 #22의 52.1 ms(n=3,882)와 같은 대역입니다.
그쪽 백필이 부딪히는 것은 이쪽 값이지 `sdmax`가 아닙니다.

> **`sdmax` 하나만 보면 오해합니다.** "이 장비는 최대 214 ms 멈춘다"로 읽히지만
> 부팅에 한 번 그렇고 운용 중에는 50 ms 안입니다. 버킷을 나눠 두지 않았으면
> 이 구분이 안 보입니다.

Q79(`SD_LOG_ERR_DELETE = 7`)는 **아직 넣지 않았습니다** — 합의 전이라서입니다.

> **대상**: ESP32 `SPEC_PROPOSAL_logIndexCapacity` (Q77)

> **성격**: 정본 소유 합의(#39 §3) 이후 **첫 델타**입니다 — 사양서 본문은 손대지 않았습니다

## 1. Q77 — 예. 넣었습니다

### 1.1 진단이 맞습니다

> 주석이 스스로 인정하고 있습니다 — 한도의 주인은 STM32인데 값은 저희가 들고 있습니다.

맞습니다. 그리고 **#29에서 실제로 어긋난 것**이 결정적입니다. 저희가 축소 빌드로
`SD_LOG_IDX_MAX`를 4로 내렸을 때, 양쪽이 맞은 이유는 그쪽이 손으로 4를 넣으셨기
때문입니다. 다음에 저희가 이 값을 건드리면 **연락하는 것 말고는 맞출 방법이 없는**
구조였습니다.

한 가지 덧붙이면, 이 값은 얼어 있는 상수가 아닙니다. §8.6에 적어 둔 대로 **부팅
스캔 블로킹 시간 예산**이고, 워치독 갱신을 스캔 안에 넣으면 올릴 수 있다고
이미 써 두었습니다. **올릴 계획이 생기면 그때 또 어긋날 값**이었습니다.

### 1.2 §3.4에 동의합니다 — 이유를 하나 보탭니다

매 응답에 상수를 싣는 것에 대한 그쪽 논거 셋 모두 맞습니다. 저희 쪽 이유를
하나 더 답니다.

**펌웨어가 따로 올라갑니다.** STM32와 ESP32는 같이 교체되지 않습니다. 별도 조회
커맨드로 부팅 때 한 번만 받으면, **저희가 먼저 업데이트된 구간에서 그쪽이 들고 있는
값은 낡은 값**입니다. 같은 응답에 실려 오면 그 구간이 아예 없습니다.

### 1.3 구현

| 파일 | 변경 |
|---|---|
| `User/Drv/inc/sd.h` | `u16_SD_Log_Idx_Capacity()` 선언 |
| `User/Drv/src/sd.c` | 정의 — **`SD_LOG_IDX_MAX`를 그대로 반환** (리터럴 아님) |
| `User/Edit/src/comm_esp.c` | 0x43 응답 끝에 2 B 적재 |

```c
uint16_t u16_SD_Log_Idx_Capacity(){
	return SD_LOG_IDX_MAX;
}
```

**리터럴을 쓰지 않은 것이 요점입니다.** 매크로를 반환하므로 축소 빌드에서
자동으로 따라갑니다 — #29 같은 상황에서 저희가 손댈 곳이 한 군데로 줄었고,
그쪽은 손댈 곳이 없습니다.

빌드 확인: `stm32_debug` SUCCESS, FLASH +16 B (실측). 프레임 버퍼 여유는 충분합니다
(`b_ESP_Transmit` DATA 상한 90 B, 0x45가 이미 86 B를 씁니다).

## 2. 델타 — §6.2, §8.6

#39 §3에서 **"앞으로 변경은 델타로"** 를 수락했고 **이번이 그 첫 적용**입니다.
저희 쪽 `v1.7` 파일은 건드리지 않았습니다. 아래를 v1.8에 반영해 주시고,
발행하실 때 저희 `docs/received/`에도 넣어 주십시오.

### 2.1 §6.2 오프셋 표

```diff
  | 20 | 1 | `deviceMode` | 현재 모드 (§7.1) |
  | 21 | 2 | `filesOnCard` | 카드의 `.psa` 파일 수 (uint16 BE) ⭐ v1.7 |
+ | 23 | 2 | `indexCapacity` | 인덱스 상한 = `SD_LOG_IDX_MAX` (uint16 BE) ⭐ v1.8 |
```

머리말 `**응답 DATA**: 21 B` → **25 B**.

> ⚠️ 이 줄은 **v1.7에서 이미 갱신이 누락됐습니다.** 본문에는 "응답 길이 21 B → 23 B
> (v1.7)"라고 따로 적혀 있는데 머리말은 21 B 그대로입니다. 이번에 함께 고쳐 주십시오.

### 2.2 길이 게이팅

그쪽이 §3.2에 쓰신 그대로입니다. 이견 없습니다.

```
길이 >= 21  →  기존 필드
길이 >= 23  →  filesOnCard 유효
길이 >= 25  →  indexCapacity 유효
```

§3.3의 처리(값이 없으면 0이 아니라 `indexCapacityKnown = false`)도 맞습니다.
**0은 "상한 0"이라는 유효한 값**이라 기본값으로 쓰면 안 됩니다 — `filesOnCard`
때 저희가 §6.2에 적은 것과 같은 이유입니다.

### 2.3 예시 프레임 — v1.7부터 틀려 있습니다

§6.2의 예시가 **`filesOnCard` 추가 때 갱신되지 않았습니다.** 지금 실려 있는
프레임은 21 B 시절 그대로입니다.

```
현재 (§6.2):  02 19 02 43 ... 01 01 B6 03      ← LEN=0x19(21 B), filesOnCard 없음
```

저희 `b_ESP_Transmit` 구현으로 재계산했습니다. 체크섬은 `0xA5`에서 시작해
STX·LEN·DIR·CMD·DATA를 XOR합니다 — **위 21 B 예시의 `B6`가 이 식으로 재현되므로
알고리즘은 검증된 것**입니다.

```
정정 (25 B, filesOnCard=61, indexCapacity=128 추가):

02 1D 02 43 01 00 00 00 2A 00 01 E2 40 00 BC 61 4E 1D 4C 00 03 00 00 01 01 00 3D 00 80 0F 03
 │  │        │  └─ bootId ─┘ └─ lastSeq ┘ └ currentTick┘ └free┘ └idx┘ └err┘ │  │  └files┘ └cap┘ │
 │  └ LEN = 4 + 25 = 29 (0x1D)                                        fmt ──┘  │              chk┘
 └ STX                                                          deviceMode ────┘

체크섬 = 0x0F · 전체 31 B
```

중간 단계인 23 B(v1.7)가 필요하시면 `LEN=0x1B`, 체크섬 `0x89`입니다.

### 2.4 §8.6 — 한 줄

```diff
  | 상한 | 128 |
+ 
+ **이 값은 v1.8부터 `reqLogStatus`의 `indexCapacity`로 보고됩니다(§6.2).**
+ 수신 측은 128을 상수로 갖지 마십시오 — 축소 빌드나 상한 조정에서 어긋납니다.
```

§8.6의 "상향하려면 스캔 중 워치독 갱신을 함께 넣어야 합니다" 문단이 곧 이 필드가
필요한 이유이므로, 그 근처에 두시는 것이 읽기 좋을 듯합니다.

## 3. 표시 문구 — 3건

**제안을 반대하는 것이 아닙니다.** 필드도 게이팅도 맞습니다. 다만 그쪽 §1과 §2.2에
적힌 **화면 문구**가 이 숫자의 의미와 어긋나 있어, 사용자에게 나가기 전에 적습니다.

### 3.1 `SD 카드 61 / 128 개` — 128은 카드의 한도가 아닙니다

이 라벨은 **카드가 128개까지 담긴다**로 읽힙니다. 그렇지 않습니다.

`SD_LOG_IDX_MAX`는 저희 소스 주석대로 **RAM이 아니라 부팅 시간 예산**입니다.

```
부팅 스캔 = 약 7.5 ms + 파일당 약 3.0 ms  (실측, §8.6)
128개 → 약 390 ms   ·   IWDG 2 s 대비 5배 여유
```

항목 하나가 `f_open` + 512 B 헤더 읽기 한 번이고, `f_open`의 디렉터리 탐색은 파일
수에 비례해 늘어납니다. **128은 그 시간이 워치독 안에 들어오는 지점**이지, 카드가
차는 지점이 아닙니다. 카드에는 수천 개가 들어갑니다.

§8.6이 §10.4(용량)와 다르다고 표까지 만들어 구분해 둔 것이 이 때문입니다.

| | 용량 부족 (§10.4) | 인덱스 한도 (§8.6) |
|---|---|---|
| 지표 | **`freeSpaceMB`** (§6.2 오프셋 13) | `filesOnCard` vs `indexCapacity` |
| 로깅 | **정지** | **계속** |
| "지우지 말라" | 적용 | **적용 안 됨** |

**"카드가 얼마나 찼는가"를 보여주고 싶으시면 그 값은 이미 `freeSpaceMB`로 가고
있습니다.** 두 축을 하나의 라벨로 합치지 마시길 권합니다. 예를 들어

```
SD 카드     여유 7,500 MB          ← freeSpaceMB
회수 가능   61 / 128 개            ← filesOnCard / indexCapacity
```

라벨은 그쪽 영역이니 문구까지 정해 드릴 생각은 없습니다. **다만 "SD 카드"라는
말이 붙는 쪽은 위여야 합니다.**

### 3.2 초과는 데이터 손실이 아닙니다

> 저희 코드는 `filesOnCard > LOG_INDEX_CAPACITY`를 **ESP_LOGE + 회수 불가 경고**로
> 처리합니다. 분모가 틀리면 **멀쩡한 장비가 데이터 손실을 보고**합니다.

분모 걱정은 맞고, 그래서 이 필드를 넣었습니다. 다만 **"데이터 손실"은 분모가
맞아도 틀린 표현**입니다. §8.6:

> **로깅은 계속됩니다.** 초과분도 카드에 정상 기록되며, 잃는 것은 **UART 경로로
> 꺼낼 수 있는가**뿐입니다. 카드를 물리적으로 회수하면 전부 읽힙니다.

코드도 그렇게 되어 있습니다 — 인덱스가 가득 차면 `v_log_idx_add`가 등재만 건너뛰고
**파일은 열리고 기록되고 닫힙니다.**

`ESP_LOGE`는 그대로 두셔도 됩니다(운영자가 봐야 할 상태가 맞습니다). **사용자에게
나가는 문구만** "손실"이 아니라 **"원격 회수 불가 — 카드에는 남아 있음"** 쪽으로
잡아 주십시오. 사용자가 "이미 잃었다"로 읽으면 **정반대 행동(초기화·교체)**을
합니다.

§8.6에 *"표시할 때 '이미 잃었다'로 읽히지 않게 하십시오"* 라고 적어 둔 것이
정확히 이 문장을 향한 것입니다.

### 3.3 `filesOnCard - indexCapacity`는 열려 있는 동안 1 큽니다

§4의 계획에 **"초과 시 '목록 밖 N개' 경고"** 라고 쓰셨는데, 그 N이 이 값이라면
**기록 중인 파일 하나를 미리 세고 있습니다.**

`filesOnCard`는 §6.2대로 **기록 중인 파일을 포함**합니다. 인덱스가 가득 찬 상태에서
그 파일은 **닫히는 순간**에 도달 불가가 됩니다.

| 시점 | `filesOnCard` | 실제 도달 불가 | `filesOnCard - 128` |
|---|---|---|---|
| 128 등재 + 1 열림 | 129 | **0** | 1 |
| 그 파일이 닫힌 뒤 | 129 | **1** | 1 |

**계산값이 틀린 것이 아니라 먼저 맞는 것**입니다. 확정된 결과를 미리 보여주는
값이므로 그대로 쓰셔도 됩니다 — 다만 §3.2와 겹쳐서 **"N개를 잃었습니다"** 로
나가면, 아직 기록 중인 파일까지 잃었다고 말하게 됩니다.

### 3.4 참고 — reason 6도 같이 정확해집니다

`evtLogError(reason 6)`의 `detail`은 **카드의 파일 수**를 싣습니다(인덱스 수가
아닙니다 — 그건 정의상 항상 상한이라 빼면 0이 됩니다). 지금까지 그쪽은 이 값에서
초과분을 계산하려면 역시 128을 갖고 있어야 했습니다. **`indexCapacity`가 오면
reason 6 이벤트도 추가 작업 없이 정확해집니다.**

## 4. §4.1 — 캐시 필요 없습니다

> **다만 0x43이 SD 접근을 동반한다면** 말씀해 주십시오. 저희가 캐시로 바꾸겠습니다.

**동반하지 않습니다. 온디맨드 조회 그대로 진행하십시오.**

0x43 응답의 **모든 필드가 RAM에서 나옵니다.** 파일시스템 호출이 한 번도 없습니다.

| 필드 | 출처 |
|---|---|
| `logState` · `writeErrorCount` · `fileIndex` | RAM 카운터 |
| `bootId` | 플래시 설정 캐시 |
| `lastSeq` | flush 시점에 갱신되는 RAM 값 |
| `currentTickMs` | 타이머 레지스터 |
| `filesOnCard` · `indexCapacity` | RAM 카운터 / 컴파일 상수 |
| **`freeSpaceMB`** | **FatFs 구조체 읽기 — `f_getfree` 아님** |

마지막 줄이 유일하게 의심스러운 항목이라 근거를 답니다. `u16_SD_Log_Get_FreeMB()`는
`f_getfree()`를 부르지 않고 FatFs가 유지하는 free-cluster 카운트를 **구조체에서
직접 읽습니다.** 저희 주석 그대로입니다.

> `f_getfree`는 같은 값을 돌려주지만 FSINFO가 낡았을 때 FAT 전체를 스캔한다 —
> 2 s 워치독을 상대로 수 초 블로킹이고, **쓰기 중 전원 차단이 남기는 것이 정확히
> 그 낡은 FSINFO다.**

즉 이 설계는 **처음부터 0x43을 논블로킹으로 유지하려고** 한 것입니다. 폴링 빈도에
제약을 두지 않으셔도 됩니다. `LOG_STATUS_PROBE_INTERVAL_MS = 5 s`도, 사용자 조작에
따른 온디맨드도 모두 여유입니다.

**한 가지만**: 0x43은 백필(0x44) 전송 중에도 같은 UART를 씁니다. 회수 중에 초당
여러 번 때리시면 청크 처리량이 그만큼 줄어듭니다. 화면 열기·새로고침 수준이면
문제 없습니다.

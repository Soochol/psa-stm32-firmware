## 1. §1 B 채택 — 확인. 두 보수적 결정에 동의합니다

**(1) BOOTING/HEALING에서 힐링 재무장하지 않기**

저희 권고보다 그쪽 판단이 낫습니다. 근거로 드신 것이 정확합니다 —
**"재무장이 무해한가"가 아니라 "누가 재무장할 권한을 갖는가"**가 맞는 질문입니다.

`armHealingCycle()`이 대입만 한다는 사실에서 "멱등"을 도출하면 안 되고,
`forceUpTimestamp`/`healingDone`이 0으로 돌아가 램프가 재시작된다는 결과를 봐야
합니다. 저희가 §2.3 표를 만들 때 **호출 형태만 보고 결과를 안 본** 경우입니다.

**(2) 탐침 25초**

`MODE_BOOTING_TOUT = 20000`을 그렇게 쓰신 것이 적절합니다. 다만 이 근거는
**STM32와 ESP32가 함께 부팅한 경우에만** 성립합니다 — §4에서 다시 다룹니다.

## 2. §2 히터 분류 — 저희 오분류입니다. 수용합니다

`PWM_ESP_HEATER`(GPIO 8)는 STM32 코드 어디에도 없습니다. 저희가 관리하는 히터는
`v_TIM2_Ch1_Out()`으로 구동하는 별개 채널이며, 그쪽 핀의 존재를 알지 못합니다.

따라서 **ESP32 재부팅 시 STM32가 대신 세워줄 수 없다**는 지적이 그대로 맞습니다.
§2.3 표의 "STM32가 스스로 관리 → 불필요"는 **철회합니다.**

> 돌려주신 지적도 그대로 받습니다. 저희가 ESP32 코드를 보지 않고 이름으로
> 분류한 경우가 맞습니다. §3.3에서 같은 유형을 하나 더 발견했으니, 이 함정이
> 양방향으로 계속 작동하고 있다고 보는 편이 맞겠습니다.

### 3.2 `0x15` initPWMCoolFan — 즉시 반영되고 되돌아오지 않습니다

```c
case ESP_CMD_INIT_PWM_COOLFAN:
    v_Mode_Set_CoolFan_Now(pu8_data[0]);   // x_modeCoolfan.u16_now = 값
    v_Mode_Set_CoolFan_Max(pu8_data[1]);
```

`x_modeCoolfan.u16_now`에 쓰는 곳은 **이 세터 하나뿐**입니다. 모드 로직은
`u16_on`(ON/OFF)만 관리하고 속도에는 관여하지 않습니다. 그리고
`v_Mode_CoolFan_Handler()`가 **매 루프 반복마다** 그 값을 PWM에 반영합니다.

즉 역할이 이렇게 갈려 있습니다.

| | 결정 주체 |
|---|---|
| 팬을 돌릴지 말지 | **STM32** (모드 로직) |
| 얼마나 빠르게 | **ESP32** (`0x15`) |

**결론**: 세션 중 재전송하면 그 속도가 **영구히 적용**됩니다. 모드 로직이
다른 값으로 되돌리지 않습니다.

**권고**: 항상 동일한 값(10/10)만 보내신다면 실질적으로 무해합니다.
세션 중 다른 값을 보내는 경로가 있다면 **복구 목록에서 제외**하십시오.

### 3.3 `0x22` — 두 가지 문제가 겹쳐 있습니다

**첫째, 이름이 대응하지 않습니다.**

| ESP32 | STM32 |
|---|---|
| `initWearableFanPWM` | `ESP_CMD_INIT_PWM_BLOWFAN` |

"wearable fan"과 "blow fan"이 같은 대상인지 **저희 쪽에서 확정할 수 없습니다.**
커맨드 코드가 같으므로 같은 것으로 취급하고 있으나, §2에서 서로 지적한 것과
정확히 같은 유형입니다. **코드로 대응을 확정해 주십시오.**

**둘째, 동작은 `0x15`와 동일합니다.**

```c
void v_Mode_Set_BlowFan_Now(uint16_t u16_now){
    ...
    x_modeBlowFan.u16_now = u16_now;
}
```

`x_modeBlowFan.u16_now`에 쓰는 곳도 이 세터 하나뿐이고, 매 루프 반영됩니다.
§3.2와 같은 판정입니다.

### 3.4 🔴 `0x12` — 미전송의 결과가 서술과 다릅니다

**가장 중요한 항목입니다.**

문서 §3의 4번 보충에 이렇게 쓰여 있습니다.

> 복구 경로는 `0x12`를 아예 보내지 않고, **STM32가 보유한 강도 기반 값(72/64/54)이
> 그대로 유지**됩니다.

**이 결과는 보장되지 않습니다.**

STM32에는 **"힐링 목표"와 "강도 목표"를 구분하는 개념이 없습니다.**
`0x12`는 단일 변수 하나에 값을 씁니다.

```c
case ESP_CMD_INIT_TEMP_FORCEUP:
    v_Mode_Set_Temp_ForceUp(typ);      // f_tempReqForceUp = 클램프(typ)
```

그리고 이 커맨드는 **가열을 시작하지 않습니다.** 설정값만 저장합니다.
가열 시작은 모드 전이(FORCE_UP 진입)이며, 그것은 `0x12`와 무관합니다.

따라서 `0x12`를 보내지 않으면 **직전에 보내신 값이 그대로 남습니다.**

| 직전에 보낸 `0x12` | 복구 후 STM32 보유값 |
|---|---|
| 강도 64 | 64 ✅ 서술대로 |
| **힐링 80** | **80** ❌ 서술과 다름 |

즉 **힐링 사이클 도중에 ESP32가 재부팅하면 `f_tempReqForceUp`은 80으로 남아 있고**,
그 상태에서 FORCE_UP에 진입하면 80을 목표로 가열합니다.

**확인 요청**: 복구 시점에 직전 `0x12` 값이 80일 수 있는 경로가 있습니까?
있다면 `0x12`를 "보내지 않음"이 아니라 **"강도값으로 명시 전송"**이 맞습니다.
저희 쪽에서는 어느 쪽이든 수용 가능하지만, 의도한 결과가 나오는지는
ESP32 측 상태로만 판단할 수 있습니다.

### 3.5 `0x21` initMode — 의심이 맞습니다. 그리고 표기가 오해를 부릅니다

```c
MODE_AI_ESP = 0,
MODE_AI_STM,        // = 1
```

**`0`은 "AI"가 아니라 `MODE_AI_ESP`입니다.** 표의 `0 (AI)` 표기는 "AI 모드"로
읽히지만 실제 의미는 **"AI를 ESP32가 담당"**입니다.

이 값이 하는 일은 [mode.c:379](../User/Edit/src/mode.c:379)에 있습니다.

```c
static void v_Mode_GyroAI_Handler(){
    if(e_mode_ai != MODE_AI_STM){return;}   // ← 즉시 종료
```

`e_mode_ai`가 `MODE_AI_STM`이 아니면 **STM32의 기울기→모드 전환이 통째로
비활성화**됩니다. 기울기로 FORCE_UP/FORCE_DOWN에 진입하는 경로가 사라집니다.

**판정**: 즉시 동작 변경 맞습니다. 다만 **항상 0만 보내신다면 실질 멱등**입니다.
관건은 **세션 중 1(`MODE_AI_STM`)을 보내는 경로가 있는가**입니다.

- 없다 → 재전송 무해, 목록 유지 가능
- 있다 → **복구가 사용자의 IMU 모드를 빼앗습니다. 목록에서 제외하십시오**

이 판단은 ESP32 측 코드로만 가능합니다.

### 3.6 값 자체에 대한 확인 두 건

**(1) `0x10` initTempSleep = 32**

STM32 헤더 기본값은 `MODE_TEMP_SLEEP = 38.0f`입니다. 그쪽이 32를 보내시므로
**런타임 값은 32**가 됩니다.

이것이 **보고 #05 §5의 승온율 산출에 영향을 줍니다.** 저희는 SLP 유지온도를
38 °C로 가정해 약 9.8 °C/s를 산출했는데, 실제 출발이 32 °C였다면
약 **12.1 °C/s**가 됩니다. 보고 #05 §5의 수치는 **이 확인 후 갱신하겠습니다.**

**(2) `0x16` initTout = 5/60/60/250 — 보고 #05 §8의 질문(Q33)이 해소됐습니다**

보고 #05에서 "런타임 타임아웃이 헤더 기본값과 다르다"며 값을 문의드렸는데,
그쪽 표에 이미 있었습니다.

| | 헤더 기본값 | ESP32 전송값 | 로그 관측 |
|---|---|---|---|
| FORCE_UP | 10 s | **5** | 5 s ✅ |
| FORCE_ON | 60 s | 60 | 60 s ✅ |
| FORCE_DOWN | 30 s | **60** | 60 s ✅ |
| WAITING | 300 s | **250** | — |

셋 다 일치합니다. **Q33은 종결합니다.**

`0x19` initGyroAct = 20도 마찬가지입니다(헤더 초기값 10). 이 역시 런타임 값이
우선합니다.

> 이 세 건 모두 "소스의 `#define`을 읽어 동작을 판단하면 틀린다"는 같은 교훈입니다.
> 보고 #05 §8에 적은 내용이며, 양측 문서에서 값을 인용할 때는 **출처가 헤더인지
> 런타임인지 명시**하는 편이 좋겠습니다.

## 4. §5 미검증 분기 — 불필요하지 않습니다. 유지하십시오

"설계상 도달 곤란"으로 세 분기를 묶으셨는데, **BOOTING과 나머지 둘은 성격이
다릅니다.**

### BOOTING(8) — 조건부로만 도달 곤란

25초 탐침 > 20초 부팅 타임아웃이라는 근거는 **양측이 함께 부팅한 경우**에만
성립합니다.

STM32가 **ESP32보다 늦게** 재부팅하면 성립하지 않습니다. 예를 들어 ESP32 부팅
후 20초 시점에 STM32가 리셋되면, 25초 탐침 시점에 STM32는 부팅 5초차로
**BOOTING(8)입니다.**

STM32 단독 리셋 경로는 실재합니다 — `v_Mode_WakeUp()`이 `HAL_NVIC_SystemReset()`으로
끝나므로 STOP 복귀 때마다 리셋이 발생합니다.

### WAKE_UP(9) / OFF(10) — 도달 곤란하지 않습니다

이 둘은 **부팅 타이밍과 무관**합니다. 25초 지연이 아무 보호도 제공하지 않습니다.
ESP32 재부팅은 비동기 사건이므로, 탐침 시점에 STM32가 어느 상태든 있을 수 있습니다.

두 상태의 지속 시간은 각각 1초 내외로 짧아 **확률이 낮을 뿐 구조적으로 도달
가능**합니다. 그리고 하필 그때 도달하면 결과가 나쁩니다.

| 상태 | 탐침이 도달하면 |
|---|---|
| OFF(10) | STM32가 STOP으로 진입 중. 보낸 것이 처리되지 않고, 곧 무응답이 됨 |
| WAKE_UP(9) | 1초 뒤 `SystemReset`. 설정이 리셋으로 날아감 |

**두 경우 모두 "복구 연기"가 정확한 처리**입니다. 그쪽 구현이 맞습니다.

### 결론

**세 분기 모두 유지하십시오.** "관측되지 않았다"와 "도달 불가능하다"는 다르며,
이 경우는 전자입니다. 낮은 확률로 도달하는 분기를 제거하면 **재현이 어려운
현장 결함**이 됩니다.

정직하게 미검증으로 남겨주신 것에 감사드립니다 — 그 표시가 없었다면 저희도
검증된 것으로 넘어갔을 겁니다.

## 5. 부수 발견 — 벤치가 `MODE_AI_ESP` 상태입니다

§3.5를 확인하는 과정에서 나온 것으로, 저희 계측 해석에 영향이 있어 공유합니다.

`0x21 initMode = 0`이 전송되므로 **STM32의 기울기 제어는 비활성 상태**입니다.
저희가 벤치에서 관측한 모드 전이는 기울기가 아니라 버튼 조작에 의한 것이었고,
`[I/TILT]` 로그가 한 건도 없는 것이 그 증거입니다.

계측 해석에 두 가지 영향이 있어 **보고 #05를 발송 전에 수정했습니다.**

| 보고 #05 | 수정 내용 |
|---|---|
| §6 잔열 재진입 | 진입 트리거를 기울기로 특정한 서술 → 트리거 무관으로 일반화 |
| §5 승온율 | `initTempSleep` 값에 따라 9.8 또는 12.1 °C/s — 잠정 표기 |

잔열 재진입의 **결론은 유지됩니다.** 판정이 `temp >= f_temp_lmt` 하나이므로
기울기·버튼·AI 중 무엇이 진입시켜도 동일하게 성립하며, **ESP32가 AI로 진입을
결정하는 정상 경로에서도 재현**됩니다.

**확인 요청**: ESP32의 AI가 FORCE_UP 진입을 결정할 때 **직전 사이클의 냉각
완료 여부를 고려**합니까? 고려하지 않는다면 보고 #05 §6의 조건이 실사용에서
재현됩니다.

| Q39 | AI의 FORCE_UP 진입 판단이 직전 사이클 냉각을 고려합니까? | §5 |

Q35~Q37은 모두 같은 형태입니다 — **"항상 같은 값만 보내는가"**입니다.
같은 값만 보내신다면 세 항목 모두 재전송해도 무해하며, 목록을 그대로 두셔도
됩니다. 다른 값을 보내는 경로가 하나라도 있으면 그 항목만 제외하시면 됩니다.

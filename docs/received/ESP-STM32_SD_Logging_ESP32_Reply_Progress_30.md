## 1. §2 — 개수를 다시 넣되, 구형도 견디게

세 경로가 모두 카드 파일 수를 말하게 되었으므로 **이벤트만으로 초과분이
나옵니다.** 표시를 다시 열었습니다.

```
[LOG] INDEX FULL (event): 141 file(s) on the card, 13 beyond the 128 it can list
      - still recording, but those cannot be backfilled until it is cleared
```

### 1.1 다만 조건을 붙였습니다

`detail`이 한도보다 **클 때만** 개수를 인용합니다. 그렇지 않으면 이렇게
찍습니다.

```
[LOG] INDEX FULL (event, detail=128): the card holds files beyond the 128 it
      can list - see filesOnCard on the status reply for how many
```

이유는 **구형 펌웨어가 섞일 수 있기 때문**입니다. 수정 전 빌드가 올라간 장치는
세션 중 `detail = 인덱스 수`를 보내고, 그러면 다시 "초과분 0"이 됩니다.
조건을 두면 **어느 빌드에서도 틀린 숫자를 말하지 않습니다.**

### 1.2 ⚠️ 새 빌드로는 검증하지 못했습니다

한도가 128로 돌아왔고 카드에 파일이 아홉 개뿐이라 **이벤트를 발생시킬 수
없습니다.** 축소 빌드였다면 확인했겠지만 그 시점에는 아직 이 수정이 없었습니다.

**산술과 분기만 검토했고 실물 확인은 없습니다.** 다음에 축소 빌드를 쓰실 일이
있으면 그때 같이 보겠습니다. 급한 항목은 아닙니다 — 상태 쪽이 정확한 값을
계속 주고 있고, 그쪽이 권위라는 구조는 그대로입니다.

> 권위는 상태 쪽이라는 구조는 유지하시길 권합니다

동의합니다. 이벤트에 개수가 실려도 **"놓치면 모르고 재시작하면 사라진다"**는
성질은 변하지 않습니다. 표시만 풍부해졌을 뿐 관계는 그대로 두었습니다.

## 2. §4 무응답 — 종결

```
** Verified OK **
** Resetting Target **     → 콜드 부팅 → modeOFF → 1초 뒤 STOP
```

STOP에서 CPU가 멈추므로 UART로 아무것도 나가지 않는다 — 기전이 명확합니다.
**결함이 아닌 것으로 종결합니다.**

적재 시 알려주시겠다는 것으로 충분합니다. 저희 쪽에서는 "적재 중"과 "정말
죽었다"가 구분되지 않고, 실제로 이번에 80회의 타임아웃을 겪은 뒤에야 물어본
것이 그 때문입니다.

이 건이 보고 #25부터 세 라운드에 걸쳐 있었습니다. **저희가 매번 "재현되면
알리겠다"고만 하고 적재 시점과 대조해 볼 생각을 하지 않은 것**이 늦어진
이유입니다. bootId가 56 → 95로 뛴 것을 보고도 그것을 단서로 쓰지 않았습니다.

## 3. §5 — 같은 계열이라는 지적

> "보냈다"와 "받아들여졌다"를 구분하지 않은 것

맞습니다. 그리고 그쪽 `flags` 비트0이 정확히 그 구분을 위해 있다는 대응이
인상적입니다 — **"STAT을 만들었다"가 아니라 "TX 큐에 들어갔다"**로 기록했기
때문에 저희가 4.5%를 찾을 수 있었습니다.

저희 `close_log_file()`은 그 구분이 없었고, 그래서 STM32가 죽은 상태에서
네 번 연속 "성공"을 보고했습니다. 같은 실수를 반대편에서 한 셈입니다.

## 4. §6 플래시 복구 — 공유 감사합니다

증상이 하드웨어 고장처럼 보인다는 점이 특히 유용합니다. 전압은 정상인데
아무것도 안 읽히면 케이블이나 칩을 먼저 의심하게 되고, 그러면 실제 원인
(지워지다 만 플래시가 부팅 즉시 폴트를 내고 디버그 포트까지 방해)에
도달하기까지 한참 걸립니다.

```
reset_config srst_only srst_nogate connect_assert_srst
```

`docs/fixtures/rtt.sh reset`에 들어 있다는 것도 기록해 두겠습니다. 저희가 쓸
일은 없지만, 같은 증상을 저희가 먼저 보게 되면 이 절차를 안내하겠습니다.

## 1. 세 갈래로 갈랐습니다

지난 측정은 두 갈래였습니다 — 식은 뒤 첫 읽기와, **같은 파일의 다음 구간**. 뒤엣것은
장치가 이미 열어둔 파일이라 **캐시 냉각과 `f_open`이 섞여** 있었습니다. 이번엔
가운데를 하나 넣었습니다.

```
① 파일 A 첫 읽기    232 ms   식은 캐시 + f_open
② 파일 B 첫 읽기    180 ms   따뜻한 캐시 + f_open   ← 다른 파일이라 f_open 발생
③ 파일 A 이어 읽기  183 ms   따뜻한 캐시 + 이미 열림

①−② = +51 ms   유휴가 물린 비용
②−③ =  −3 ms   f_open 자체 비용
```

### 1.1 `f_open`은 사실상 공짜입니다

**−3 ms**입니다. 다른 파일을 새로 여는 것과 이미 열린 파일을 이어 읽는 것의 차이가
잡음에 묻힙니다. 보고 #27에서 주신 **파일당 3.0 ms**와 정합합니다.

이게 중요한 이유는 **비용이 파일당이 아니라 유휴 구간당**이라는 뜻이기 때문입니다.
카드에 파일이 60개든 128개든, 백필 한 번에 한 번만 뭅니다.

### 1.2 바닥 180 ms는 카드와 무관합니다

세 측정 모두 180 ms 위에 얹혀 있습니다. 이건 요청이 도는 경로 전체의 왕복
비용입니다 — BLE 쓰기 → ESP32 → UART → STM32 → 카드 → 되돌아오는 길. 카드
특성을 보려면 **차이만** 봐야 하고, 그래서 위 두 뺄셈이 답입니다.

## 3. 🔴 이전 보고(+112 ms)를 철회합니다

앞서 저희가 `① 134 ms / ② 22 ms / 차이 +112 ms`로 보고드렸습니다. **그 숫자를
믿지 마십시오.** 저희 쪽 오염이었습니다.

### 무슨 일이 있었나

그 측정 직후 다시 재보니 **카드를 아예 안 건드리는 요청(`0x20`, RAM 인덱스)** 이
236~1165 ms로 나왔습니다. 카드가 아니라 릴레이 경로가 느려진 것이라, 콘솔을
캡처해 원인을 찾았습니다.

```
18초에 경고 370줄, 20 ms 간격
[W][data.cpp:127] biosigDataClass buffer overflow prevented, index: 600
[W][data.cpp:185] accel buffer overflow prevented, accelIndex: 100
```

**저희 쪽 링 버퍼 경고**였습니다. 두 버퍼 모두 가득 차면 한 칸씩 밀어내는 구조라
`index >= LEN`이 정상 운영의 정상 상태인데, 거기에 `ESP_LOGW`가 걸려 있어
**샘플마다** 찍히고 있었습니다. 보고 #23에서 잡은 것과 같은 부류입니다.

### 조치

경고를 제거하고 **펌웨어를 적재한 뒤** 이번 측정을 했습니다. 결과지에 콘솔 상태를
함께 찍어 조건을 기록으로 남겼습니다.

```
콘솔: 238줄 중 경고/오류 0줄 ← 오염 없음
```

**그쪽에 조치를 요청드릴 것은 없습니다.** 저희 쪽 문제였고 저희가 고쳤습니다.
다만 지난 보고의 숫자로 무언가를 판단하셨다면 이 회신으로 갱신해 주십시오.

## 5. BLE 동시 접속 — 준비는 끝났습니다

PSA 유닛이 1대뿐이라 여전히 못 잽니다. 다만 그동안 **PC 앱 쪽 준비**를 마쳤습니다.

- 유닛마다 자기 클라이언트·자기 저장소·자기 작업자 라벨
- **스캔 직렬화** — 한 유닛의 재연결 스캔이 다른 유닛의 링크를 깎지 않도록
- 손실 계측(`missed=`)이 유닛별로 이미 붙어 있어 별도 도구 불필요

유닛이 확보되면 **기준선 1대 → 2대 → 3대**를 같은 조건으로 재고 결과를
공유하겠습니다.

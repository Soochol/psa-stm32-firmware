## 1. Q75 — 이견 없습니다

저희가 IWDG를 계산하지 않았습니다. 제안서에 "디렉터리 순회 + `f_unlink`"라고만
적었고, 그것이 **한 호출 안에서 끝난다고 암묵적으로 가정**했습니다.

산수를 확인했습니다.

```
150개 × 20 ms = 3.0 s   >  IWDG 2.0 s
150개 × 50 ms = 7.5 s
```

그리고 이 사양은 처음부터 그 예산 위에 서 있습니다 — 부팅 스캔이 128개에서
멈추는 이유가 **390 ms로 5배 여유를 두기 위해서**였습니다(보고 #27). 같은
제약을 저희가 새 명령에서 잊었습니다.

### 1.1 시간 기준이 맞습니다

> 카드마다 `f_unlink` 소요가 다릅니다. "20개씩"으로 끊으면 느린 카드에서 다시
> 워치독에 닿습니다

**개수로 끊으면 상한이 카드 속도에 좌우됩니다.** 시간으로 끊으면 어떤 카드에서도
예산이 지켜집니다. 저희가 개수를 요청했는데(Q74) 그것을 **진행 표시**로
돌리고 분할은 시간으로 하신 것이 더 정확합니다.

### 1.2 `f_readdir` 중 `f_unlink`

> FatFs가 보장하지 않습니다. 이름을 먼저 모으고 디렉터리를 닫은 뒤 지웁니다

수용합니다. 저희가 "디렉터리 순회하며 지운다"고 적은 것이 부정확했습니다.

### 1.3 실패 형태에 대한 지적이 정확합니다

> 지우다 만 상태로 재부팅하고, PC는 결과를 못 받고, 다시 걸면 또 중간에
> 리셋됩니다. **파일이 많을수록 확실히 실패**하므로 §1.1의 문제가 형태만 바꿔
> 남습니다

이 한 문장이 제안을 고쳐야 하는 이유 전부입니다. 저희가 지적한 결함("가장
필요할 때 실패한다")을 저희 해법이 그대로 물려받을 뻔했습니다.

## 2. 🔴 진행이 멈추면 루프가 끝나지 않습니다

`f_unlink`가 **특정 파일에서 실패**하면 어떻게 됩니까?

```
0x58 → 결과 6, 개수 0     그 파일이 남음
0x58 → 결과 6, 개수 0     다음 f_opendir에서 또 걸림
0x58 → 결과 6, 개수 0     ...
```

지워진 항목은 건너뛰므로 수렴한다고 하셨는데, **지워지지 않은 항목은 건너뛰지
않습니다.** 손상 섹터나 읽기 전용 속성 하나로 루프가 영원히 돕니다.

### 2.1 제안 — 실패는 결과 4로 즉시 반환

```
f_unlink 실패 → 결과 4 (삭제 실패)로 즉시 반환, 부분 삭제 상태로 종료
```

이미 있는 코드이고, PC는 "일부 지웠고 실패했다"를 알 수 있습니다. 나머지를
계속 지우는 것보다 **멈추고 사람이 보는 편**이 낫다고 봅니다 — 카드가 이상한
상태일 수 있으니까요.

### 2.2 PC 쪽에도 안전장치를 둡니다

프로토콜과 별개로, 저희도 **진행 없는 호출이 이어지면 중단**하겠습니다.

```
결과 6인데 개수 0이 연속 3회 → 중단하고 사용자에게 보고
```

양쪽에 두는 이유는, 되돌릴 수 없는 작업에서 **무한 루프가 가장 나쁜 실패**이기
때문입니다. 사용자는 진행률이 멈춘 채 기다리게 되고, 그동안 로깅은 꺼져
있습니다.

---

## 3. 진행률 표시 — 하겠습니다

> 되돌릴 수 없는 작업이 한 번에 끝나는 것보다, 몇 개씩 지워지는 것이 보이는
> 편이 안전합니다

동의합니다. 분할 실행이 UI에 부담이 아니라 **이점**이 됩니다.

```
카드 비우기 — 61개 중 50개 삭제됨…          ← 누적 개수
```

한 번에 끝나면 "눌렀다"와 "끝났다" 사이에 아무것도 없어서, 멈춘 것과 도는
것을 구분할 수 없습니다. 개수가 올라가면 그 구분이 화면에 있습니다.

`0x56 stop → 0x58 반복 → 0x56 start`는 저희가 묶어 처리하고, 사용자에게는
버튼 하나로 보이게 하겠습니다.

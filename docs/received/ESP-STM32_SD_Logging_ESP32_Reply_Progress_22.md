## 1. Q54 — `boot=48`이었습니다

원시 캡처에 그대로 남아 있습니다.

```
[LOG] state=1 boot=48 lastSeq=52420 tick=5252459 free=30524MB file=1 errs=0 mode=SLEEP
```

**`boot=45`를 회수하던 시점에 장치는 `boot=48`을 기록 중이었습니다.** 45번은 세
부팅 전에 닫힌 세션입니다.

따라서 그쪽 §5의 `FR_LOCKED` 설명과 모순되지 않습니다. **저희는 기록 중인 파일에
닿은 적이 없습니다.** 세 번의 계측 캡처 전부 `-> 3` 거부가 0건이었던 것도
같은 이유입니다.

`boot=45`에서 갭 재요청 6회가 났던 것은 파일 종류와 무관하며, 원인은 미특정으로
남깁니다.

## 2. 🔴 그런데 — 현재 세션이 목록에 아예 없습니다

Q54를 확인하다 발견했습니다. **§5의 우려는 다른 형태로, 더 크게 존재합니다.**

### 2.1 관측

같은 시각에 장치에 두 가지를 물었습니다.

```
파일 목록(0x20) → 18개 파일, 최신이 boot=45
장치 상태(0x43) → boot=48 lastSeq=68340 file=1
```

| | 값 |
|---|---|
| 목록의 최신 세션 | **boot=45** (file 0·1·2, 총 82,281건) |
| 실제 현재 세션 | **boot=48** (lastSeq **68,340**, 현재 file=1) |
| **목록에 있는 boot=48 파일** | **0개** |

**현재 bootId의 파일이 하나도 목록에 없습니다.** 열려 있는 file 1뿐 아니라,
**로테이션으로 이미 닫힌 file 0(36,001건)도 없습니다.**

### 2.2 무엇을 뜻하는가

**오늘 기록된 약 68,000건(약 2시간)이 백필로 접근 불가입니다.**

`FR_LOCKED`는 열린 파일 하나를 거부하는 것인데, 관측되는 것은 **세션 전체가
목록에서 빠지는 것**입니다. 닫힌 file 0까지 빠지므로 잠금만으로는 설명되지
않습니다.

이것이 저희 §5 지적의 실제 결과입니다. 다만 방향이 반대입니다.

| | 그쪽 §5 예상 | 실제 |
|---|---|---|
| 증상 | `-> 3` 거부가 반복됨 | **애초에 요청 대상이 되지 않음** |
| 저희 "최신 우선" | 정면 충돌 | **충돌하지 않음** (닿을 수 없으므로) |
| 결과 | 회수 실패 | **회수 시도조차 못 함** |

저희 "최신 세션부터" 변경이 안전한 이유는 안전하게 설계해서가 아니라
**현재 세션에 닿을 방법이 없기 때문**입니다.

### 2.3 현장 시나리오에 직접 걸립니다

작업자가 작업 중 BLE가 끊겨 라이브 CSV에 구멍이 생기고, 작업을 마친 뒤
백필로 그 구간을 메우려 합니다. **그 구간은 현재 세션에 있으므로 목록에
없습니다.** 장치를 재부팅해 세션을 닫기 전에는 회수할 수 없습니다.

현장에서 "작업 끝나고 백필"이 성립하려면 이 조건이 풀려야 합니다.

### 2.4 Q56 — 확인 부탁드립니다

| # | 질문 |
|---|---|
| Q56-a | 현재 bootId를 목록에서 제외하는 것이 **의도된 동작**입니까? |
| Q56-b | 로테이션으로 닫힌 파일(예: `boot=48` file 0)은 목록에 올릴 수 있습니까? |
| Q56-c | 열려 있는 파일을 안전하게 읽을 방법이 있습니까? (플러시 후 읽기 등) |

**b만 되어도 실용적으로는 대부분 해결됩니다.** 1시간 로테이션이므로 한 시간 전
데이터까지는 회수 가능해지고, 현장 작업 시간과도 맞습니다.

c는 저희가 요구하지 않겠습니다 — 읽기·쓰기 동시 접근의 위험을 저희가 판단할
위치에 있지 않습니다.

## 3. Q51 — 완료. 예고가 정확했습니다

### 3.1 저희 클라이언트 경로

`boot=9 seq=35950 cnt=128`을 걸었습니다. 결과는 **128/128, 수집률 100%,
CRC 실패 0, 불변식 위반 0**입니다.

다만 장치 로그를 보면 **저희 클라이언트는 경계를 넘는 요청을 하지 않습니다.**

```
backfill read boot=9 seq=35950 count=51    ← 파일 끝까지만
backfill read boot=9 seq=36001 count=77    ← 다음 파일부터
backfill read boot=9 seq=36048 count=1     ← 갭 재요청
```

PC가 파일 목록을 갖고 있으므로 **요청을 파일 단위로 미리 쪼갭니다**(51 + 77 = 128).
그래서 그쪽이 예고하신 "128 요청 → 51건에서 멈춤" 경로가 이 시험에서도
실행되지 않았습니다.

### 3.2 🟢 그래서 직접 걸었습니다

플래너를 우회해 **경계를 가로지르는 단일 요청**을 원시로 보냈습니다.

```
요청  : 0x21 boot=9 seq=35950 count=128
응답  : 레코드 51건
END   : result=0  lastSeqSent=36000
```

**그쪽 §4의 예고와 정확히 일치합니다.** 파일 끝에서 멈추고, `result=0`으로
"가진 만큼 보냈다"를 알리며, `lastSeqSent`가 36000입니다. 이 경로는 이제
실측으로 확인됐습니다.

### 3.3 정정 — 보고 #19의 연속성 설명

그쪽 §4에서 보고 #19의 `seq=35995 cnt=12` 시험을 이렇게 설명하셨습니다.

> STM32가 36000에서 한 번 멈추고 PC가 자동 재요청해 두 번째 응답이 36001~36006을
> 채운 결과

**기전이 다릅니다.** 그때도 PC가 미리 6 + 6으로 쪼개 보냈습니다. 보고 #19에서
"2 배치"라고 적은 것이 그 분할입니다. 단축 응답도, 자동 재요청도 없었습니다.

결과가 같아 구분되지 않았던 것이고, §3.2의 원시 요청이 **처음으로** 단축 응답
경로를 실행한 시험입니다.

## 4. Q55 — 지연 구간의 장치 시각

`[T:]`는 ESP32의 millis이므로 그대로는 카드와 대조되지 않습니다. 같은 로그의
`[LOG] state=... tick=` 줄을 앵커로 STM32 tick으로 환산했습니다. **전부
`boot=48`입니다.**

| 펌웨어 | STM32 tick 구간 | 지연 | 누락 |
|---|---|---|---|
| `0a208a2` (조치 전) | 5,207,523 ~ 5,208,810 | 1,287 ms | 11 |
| `0a208a2` | 5,213,318 ~ 5,214,611 | 1,293 ms | 11 |
| `0a208a2` | 5,219,029 ~ 5,220,088 | 1,059 ms | 9 |
| `0a208a2` | 5,231,554 ~ 5,232,795 | 1,241 ms | 11 |
| `767c84b` (조치 후) | 5,404,620 ~ 5,405,624 | 1,004 ms | 9 |
| `767c84b` | 5,501,723 ~ 5,502,729 | 1,006 ms | 9 |
| `767c84b` | 5,534,125 ~ 5,535,541 | 1,416 ms | 13 |

**환산의 한계를 밝힙니다.** 캡처당 앵커가 1개뿐이라 두 시계의 드리프트를
보정하지 못했습니다. 100초 구간이므로 오차는 수십 ms 수준으로 보지만,
**단일 점 추정**입니다.

### ⚠️ 그쪽 §2.6 제안이 지금은 실행되지 않습니다

"해당 구간을 백필로 회수해 `tick` 연속성과 `flags` 비트0을 확인하라"고
제안하셨는데, **그 구간이 전부 `boot=48`이고 §2에 따라 목록에 없습니다.**
저희가 회수할 수 없습니다.

- Q56-b가 해결되면 그때 저희가 회수해 대조하겠습니다
- 그전에는 **그쪽에서 카드나 RTT로 직접 보시는 편이 빠릅니다** — 위 tick 구간을
  쓰시면 됩니다

## 5. 그쪽 §1·§2에 대하여

**§1 자체 철회 확인했습니다.** 저희 수치가 틀렸으니 그 위에 세운 논거가 함께
무너지는 것이 맞습니다. 아티팩트를 저희가 먼저 잡았어야 했습니다.

**§2 수용합니다.** 특히 §2.4가 결정적이라고 봅니다 — 165,588 레코드에
`txFail=0`이고 tick 간격 최대가 100 ms이면, 생성과 큐 투입 단계는 배제됩니다.
SD 52 ms + TX 큐 159 ms = 약 211 ms 상한도 관측값 1,416 ms와 7배 차이입니다.

§2.5에서 `cyc=12us`의 한계를 먼저 밝혀 주신 것도 판단에 도움이 됐습니다.

**남은 구간은 TX 큐 진입 이후 ~ ESP32 처리 완료 사이**입니다. 저희 쪽에서
계속 보겠습니다.

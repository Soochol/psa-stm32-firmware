## 1. 23 B 경로 — 실장치로 끝냈습니다

보고 #44에서 *"실기 확인은 아직"* 이라고 적었던 항목입니다. 끝냈습니다.

```
PC 앱  ──0x25──▶  ESP32  ──0x43──▶  STM32
       ◀─0xB4──         ◀─23 B──
```

화면 문구까지 확인했습니다.

```
회수 71/?    Connected — samples=55 errors=0 age=0.1s | missed=0
```

**분모가 `?` 인 것이 지금 정확한 표시입니다.** 그쪽이 아직 23 B로 답하므로
`indexCapacity`가 오지 않고, 저희는 그것을 128로 메우지 않습니다. 이 `?` 하나가
Q77 전체의 목적이었습니다 — 예전 코드였다면 여기에 아무도 확인해 주지 않은
`128`이 자신 있게 떴을 것입니다.

### 1.1 프레임 원본

```
← 0xB4, 24 B
b4 01 00 00 00 7f 00 00 0a db 00 04 6b da 77 0a 00 00 00 00 01 01 00 47
   │  └ boot 127┘ └ seq 2779┘ └ tick    ┘ └free┘ └idx┘ └err┘ │  │  └ 71 ┘
   └ logState                                          fmt ──┘  └ mode
```

`1 + 23 = 24 B`입니다. 25 B가 되면 뒤에 2 B가 붙고, **저희 중계와 파서는 이미
그것을 통과시킵니다.** 화면 코드만 분모를 `?`에서 실제 값으로 바꿉니다.

### 1.2 덤 — 저희 결함 하나를 실기로 잡았습니다

그쪽에 영향은 없지만, 실기가 무엇을 잡아내는지의 사례라 적어 둡니다.

`0x43`을 중계할 때 "요청 중" 표시를 세우는데, 그 표시를 지우는 코드가 **응답
파서 안에만** 있었습니다. 응답이 없으면 그 파서는 실행되지 않으므로, 무응답이
한 번 나면 표시가 영구히 남고 그 뒤 앱 요청이 UART로 나가지 못했습니다.

**그쪽 전원을 껐을 때 로그가 `0x43 FAILED after 4 attempts`로 가득 찬 것을 보고
찾았습니다.** 고친 뒤 같은 방법으로 확인했습니다 — STM32만 끄고 요청하면 20초
뒤 "장치가 답하지 않음"이 앱까지 올라옵니다.

> 코드만 읽었으면 못 봤을 것입니다. 그쪽이 `sdmax` 버킷을 나눠 두지 않았으면
> 부팅 스캔과 평시 플러시가 구분되지 않았을 것이라고 하신 것(#43 §2.3)과 같은
> 종류의 이야기입니다.

## 2. §6.2의 "1 큼"을 같은 부팅 안에서 봤습니다

보고 #46 §4에서 그쪽 `indexed 68 of 68`과 저희 `onCard=69`의 차이를 **부팅 스캔
시점 대 로깅 시작 후**로 설명드렸습니다. 이번에 **같은 장치가 시간에 따라
바뀌는 것**을 봤습니다.

| 시점 | `bootId` | `filesOnCard` | `mode` | `lastSeq` |
|---|---|---|---|---|
| 어제 | 124 | **69** | WAITING | 559 |
| 오늘 부팅 직후 | **127** | **70** | **BOOTING** | **0** |
| 오늘 로깅 중 | 127 | **71** | WAITING | 2,779 |

**가운데와 아래는 같은 부팅입니다.** 파일이 하나 새로 생긴 것이 아니라,
`BOOTING` 동안 닫혀 있던 상태에서 로깅이 시작되며 **파일이 열린 것**입니다.
`lastSeq`가 0에서 2,779로 간 것이 그 사이에 일어난 일을 말해 줍니다.

> v1.7 §6.2: *"`filesOnCard`는 기록 중인 파일을 포함하므로 `total`보다 통상
> 1 큽니다."*

문서로만 있던 문장이 한 장치에서 시간축으로 재현됐습니다. **`0x43`을 언제
찍었는지에 따라 값이 1 달라진다**는 뜻이라, 양쪽이 숫자를 비교할 때는
`bootId`와 `mode`를 함께 보는 편이 안전하겠습니다.

### 2.1 카드는 계속 늘고 있습니다

`bootId 124 → 127`, **3회 부팅**입니다. 오늘 저희가 펌웨어를 올리고 전원을
조작한 횟수입니다. 파일은 **69 → 71**.

#43 §1.1에서 *"로깅 시간이 아니라 부팅 횟수로 는다"* 고 하신 것 그대로입니다.
저희 쪽 시험이 그쪽 카드를 채우고 있다는 것도 같이 확인됐습니다 — 상한
128까지 **57개** 남았습니다.

## 3. 요청 — `9bd5679` 적재

**하나뿐입니다.**

| | 상태 |
|---|---|
| STM32 구현 | ✅ 완료 (#43 §1.3) |
| STM32 빌드 | ✅ `stm32_debug` SUCCESS, FLASH +16 B |
| **STM32 적재** | ⬜ **"아직 어느 장치에도 굽지 않았습니다"** (#44 §1.2) |
| ESP32·PC | ✅ 코드·시험·실기 완료 |

**25 B 응답을 아직 아무도 본 적이 없습니다.** 저희가 시험한 25 B는 전부 저희가
만든 프레임입니다. 그쪽 실물이 보내는 것을 받아야 이 건이 닫힙니다.

굽고 알려 주시면 저희는 **아무것도 바꾸지 않고** 화면이 `회수 71/128`로 바뀌는
것만 확인하면 됩니다. 그때 90 % 경고와 초과 경고도 처음으로 살아납니다 —
지금은 분모를 몰라 띄우지 않습니다.

### 3.1 reason 7은 급하지 않습니다

Q79(`SD_LOG_ERR_DELETE = 7`, `detail = FRESULT`)는 보고 #46에서 동의했고,
**저희 수신 코드는 이미 들어가 있습니다.** 그쪽이 언제 넣으셔도 됩니다.

받으면 이렇게 표시합니다.

```
[LOG] DELETE FAILED: FR_DENIED (FRESULT=7)
      - that one file could not go; the rest of the card is unaffected

[LOG] DELETE FAILED: FR_DISK_ERR (FRESULT=1)
      - treat as card or filesystem trouble; stop and check it
```

#41 §1.3의 두 층 분류를 그대로 썼습니다. **파일 단위 코드를 나열하고 나머지를
전부 카드 문제로** 취급합니다 — 처음에는 반대로 짰다가, 그러면 `FR_TIMEOUT`이
"파일 하나 문제"로 표시된다는 것을 보고 뒤집었습니다. *"모르는 코드는
보수적으로"* 가 정확히 그 경우를 막는 규칙이었습니다.

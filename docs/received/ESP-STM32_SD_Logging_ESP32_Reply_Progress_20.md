## 1. Q49 — 지연 경로가 있습니다

**결론부터: 있습니다. 그리고 그쪽 §3.3의 추정이 정확했습니다.**

### 1.1 위치

백필 중계와 STAT 처리가 **같은 수신 루프, 같은 태스크**입니다.

```c
// src/uartMaster.cpp:535
if (currentMessage.command == statLogChunk)
{
    handleLogChunkMessage();   // BLE 알림 큐가 차면 여기서 블로킹
}
else
{
    handleStatusMessage();     // STAT 처리 + ACK 송신
}
```

`handleLogChunkMessage()`는 레코드를 BLE 알림으로 올립니다. 큐가 가득 차면
공간이 날 때까지 재시도합니다.

```c
// src/bleSensorHub.cpp:445
for (int attempt = 0; attempt < BACKFILL_NOTIFY_ATTEMPTS; attempt++)  // 8회
{
    if (s_txCharacteristic->notify()) { return true; }
    vTaskDelay(pdMS_TO_TICKS(BACKFILL_NOTIFY_RETRY_MS));              // 4 ms
}
```

**프레임 하나당 최대 32 ms입니다.** 그동안 같은 루프는 STAT을 파싱하지도,
ACK를 보내지도 못합니다. 혼잡이 이어지면 이 32 ms가 연달아 쌓입니다.

### 1.2 계측 — 그쪽 관측을 재현했습니다

STAT은 10 Hz로 고정 도착하므로, **ESP32가 실제로 처리한 STAT의 초당 건수**가
루프 기아를 직접 보여줍니다. 110초를 연속 캡처하고 중간 45초에 백필을 걸었습니다.

| 구간 | STAT 처리율 |
|---|---|
| 백필 전 (5~35 s) | **10.00 Hz** |
| **백필 중 (38~77 s)** | **9.05 Hz** |
| 백필 후 (83~108 s) | **10.00 Hz** |

백필이 없을 때는 **정확히 10.00 Hz**이고, 백필 중에만 떨어집니다.

더 중요한 것은 분포입니다.

| STAT 공백 | 시점 |
|---|---|
| **1,401 ms** | 43.4 s (백필 중) |
| 1,001 ms | 67.7 s (백필 중) |
| 1,001 ms | 70.3 s (백필 중) |
| 1,001 ms | 74.5 s (백필 중) |
| 1,001 ms | 76.9 s (백필 중) |

상위 5건이며 **총 6회**입니다. 백필 구간은 35~80 s인데 **6회 전부 그 안에
있습니다.** 그쪽 경고는 1,000 ms
기한에서 찍히므로([comm_esp.c:938](../User/Edit/src/comm_esp.c:938)),
이 6회가 그대로 그쪽 카운트로 들어갔을 것입니다.

### 1.3 🟢 드롭 횟수와 공백 횟수가 일치합니다

같은 캡처에서 `backfill frame dropped`(8회 재시도를 모두 소진하고 버린 경우)가
**6건**입니다. **1초 이상 공백도 6건**입니다.

이 일치가 기전을 설명합니다 — 알림 큐가 가득 찬 구간에서는 프레임마다 32 ms를
모두 소모하고, 그런 프레임이 연달아 30개쯤 이어지면 약 1초가 됩니다. 마지막
하나가 결국 버려지면서 드롭으로 기록됩니다. **드롭 1건 = 약 1초의 루프 기아**가
같은 사건의 양면입니다.

드롭률 자체는 낮습니다 — 45초에 650 레코드 중 6건(약 0.9%)이고, 버려진
레코드는 PC가 seq 불연속으로 감지해 재요청하므로 **데이터 유실로 이어지지
않습니다.**

### 1.4 이 재시도는 저희가 의도적으로 넣은 것입니다

원래는 `notify()`의 반환값을 무시했고, 그 결과 배치 96건에서 29건이 조용히
사라졌습니다. 재시도를 넣어 유실을 0으로 만들었는데, **그 대가가 지금 보시는
지연**입니다. 유실과 지연을 맞바꾼 셈이고, 저희가 지연 쪽을 인지하지 못한 채
바꿨습니다.

### 1.5 조치 방향

| 안 | 내용 | 평가 |
|---|---|---|
| A | 재시도 횟수·간격 축소 (8×4 ms → 3×2 ms) | 한 줄. 드롭이 늘지만 PC가 재요청하므로 유실 아님 |
| B | **중계를 별도 태스크로 분리** | 근본 해결. 수신 루프가 절대 막히지 않음 |
| C | 재시도 사이에 UART 수신 여부 확인 후 양보 | 중간. 루프 구조를 건드림 |

**B가 옳다고 봅니다.** A는 증상을 줄일 뿐이고, 큐 혼잡이 심해지면 다시 나타납니다.
다만 §9.5 동시 구간을 다시 계측해야 하므로, 그쪽 일정과 맞추는 편이 낫겠습니다.

**어느 쪽을 선호하시는지 알려주시면 그에 맞춰 진행하겠습니다.** 저희 단독 조치가
가능한 항목이라 그쪽 조치 요청은 없습니다.

## 2. §3.2 기저 76회 — 재현하지 못했습니다

백필이 없는 65초 구간에서 STAT 처리율은 **정확히 10.00 Hz**였고, 1,000 ms 이상
공백은 **0건**이었습니다. ESP32 로그에도 대응하는 흔적이 없습니다.

다만 **이것을 근거로 기저 발생을 부정하지는 않습니다.** 그쪽 수치는 780구간
(약 3,900초)에 76회이므로 초당 약 0.019회이고, 65초라면 기댓값이 1.3회입니다.
**0건이 나오는 것이 이상하지 않은 표본 크기**입니다.

기저 쪽은 더 긴 캡처가 필요합니다. 필요하시면 30분 캡처를 돌려 같은 방식으로
집계하겠습니다 — 다만 우선순위는 §1의 조치가 먼저라고 봅니다. 조치 후에도 남는
발생분이 곧 기저이기 때문입니다.

## 3. Q48 — 통과했지만 파라미터가 달랐습니다

보고 #19에서 경계 통과를 보고드렸는데, 요청하신 것과 값이 다릅니다.

| | 요청 (§4) | 실제 시험 |
|---|---|---|
| bootId | 9 | 9 |
| startSeq | 35950 | **35995** |
| count | 128 | **12** |

경계(36000 → 36001)는 실제로 가로질렀고 seq가 끊김 없이 35995~36006으로
이어졌으므로 **검증 대상 자체는 충족**한다고 봅니다. 다만 128건 요청이 경계를
넘을 때 STM32가 두 파일에 걸쳐 어떻게 나누는지는 그쪽 로그로만 보이므로,
**원하시면 `boot=9 seq=35950 cnt=128`로 다시 걸겠습니다.** 1분이면 됩니다.

## 5. ⚠️ 주의 — 백필 대상이 "기록 중인 파일"로 바뀝니다

그쪽 §2.3에서 "백필의 읽기는 로깅 쓰기를 방해하지 않는다"를 확인해 주셨는데,
그 계측은 `boot=12`·`boot=9` 등 **이미 닫힌 파일**을 읽은 것이었습니다.

저희 PC 측 백필이 **최신 세션부터 가져오도록 바뀌었습니다.** 현장에서 메우고 싶은
것은 방금 끊긴 구간인데, 오래된 세션부터 받으면 카드 전체를 훑은 뒤에야 거기에
닿기 때문입니다(현재 카드 기준 한 시간 이상).

즉 **앞으로 백필은 STM32가 지금 쓰고 있는 파일을 읽습니다.** 저희 쪽 관측으로는
닫힌 파일보다 재요청이 잦습니다.

| 대상 | 회수 | 갭 재요청 |
|---|---|---|
| `boot=27` (닫힌 파일) | 1,280건 | **0회** |
| `boot=39` (닫힌 파일) | 300건 | **0회** |
| **`boot=45` (기록 중)** | 2,000건 | **6회** |

재요청으로 전부 회수되므로 병합 결과는 100%입니다. 다만 같은 파일에 대한
읽기·쓰기 동시 접근이라는 조건 자체가 새로운 것입니다.

**그쪽에서 확인해 주실 것은 없습니다.** 다만 §9.5를 다시 계측하실 때 이 조건이
달라졌다는 점을 알려드립니다 — 동일 파일에 대한 읽기·쓰기 동시 접근은 이전
계측에 포함되지 않았습니다.

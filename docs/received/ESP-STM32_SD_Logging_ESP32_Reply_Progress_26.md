# 진행 보고 #26 — ESP32 팀 조치 통보

> **성격**: 조치 통보 (`ctrlLogEnable(0x56)` 사용 개시)
> **ESP32 펌웨어**: `7365e76`
> **판정**: **세션 종료 시 `0x56`으로 파일을 닫습니다. 실물 검증 완료** (§1)
> **STM32 측 조치 요청**: 없음. 다만 **§3의 인덱스 한도**는 확인 부탁드립니다

---

## 0. 요약

| 항목 | 내용 |
|---|---|
| **`0x56` 사용 개시** | 세션 종료마다 stop → start. 파일이 닫히고 등재됨 — §1 |
| **효과** | 오늘 작업 구간을 **당일 회수 가능** — §1.3 |
| 로깅 중단 없음 | stop 직후 곧바로 start — §2 |
| ⚠️ **인덱스 한도** | `SD_LOG_IDX_MAX = 128`, 초과분은 **조용히 누락** — §3 |
| 관측 | 카드가 2개 파일로 초기화된 듯합니다. 로테이션도 1시간으로 복구 — §4 |

## 1. `0x56`을 쓰기 시작했습니다

### 1.1 왜

파일은 **닫혀야 목록에 오릅니다.** 그래서 마지막 로테이션 이후 기록분 전체가
백필로 닿지 않았고, 한 시간보다 짧은 작업이면 **그날 기록한 전부**가 여기
해당했습니다.

현장 시나리오가 여기서 막혀 있었습니다 — 작업 중 링크가 끊겨 생긴 구멍을
작업 후에 메우려는데, 그 구간이 열린 파일 안에 있어 요청조차 안 됐습니다.
우회는 장치 재부팅이나 1시간 대기뿐이었고 둘 다 현장에서 쓸 수 없습니다.

### 1.2 무엇을 보내나

앱에서 **수집을 종료할 때** 한 번 보냅니다.

```
Stop Collect
  → BLE 0x22 (PC → ESP32, 저희 쪽 명령)
  → setLogEnable(false)   → 0x56  → flush + close + 등재
  → setLogEnable(true)    → 0x56  → 새 파일로 재개
  → BLE 연결 해제
```

`v_SD_Log_SetEnabled(false)`가 `v_SD_Log_Close()` → `v_log_rotate("close")` →
`v_log_close_and_index()`로 이어지므로, **보고 #24에서 합쳐주신 그 경로를
그대로 탑니다.** 저희가 새로 만든 길이 아닙니다.

### 1.3 실물 검증

| 단계 | 관측 |
|---|---|
| 기록 중 | `boot=100 lastSeq=20419` |
| Stop Collect | `0x56` stop/start 전송, 확인 응답 `0x22 0xFD` |
| **목록** | **`boot=100 seq 0..20433 (20434 records) file=0`** |
| 장치 상태 | `boot=100` 그대로, **`file=1`로 로깅 계속** |
| 회수 | 마지막 400건 → **수집률 100%**, 갭·CRC·불변식 위반 0 |

**재부팅도 로테이션도 없이** 방금 기록한 구간이 목록에 올라왔습니다. 1시간
로테이션은 36,000에서 걸리는데 **20,433에서 닫혔으므로**, 이 명령이 닫은
것이 분명합니다.

## 2. 로깅은 곧바로 다시 켭니다

`0x56` stop만 보내면 로깅이 꺼진 채로 남습니다. 저희는 **바로 이어서 start를
보냅니다.**

**카드가 무선과 무관하게 기록한다 — 이것이 이 시스템의 안전판**이고, 명령
하나를 아끼자고 그것을 PC 의존으로 바꾸지 않겠습니다. PC가 늦게 붙거나 앱이
죽은 구간도 카드에는 남아야 합니다.

start 전송이 실패하면 로깅이 꺼진 채 남으므로, 그 경우 ESP32 콘솔에
`RESTART COMMAND NOT SENT, logging is off`를 찍고 PC에 실패로 답합니다.
지금까지 발생한 적은 없습니다.

## 3. ⚠️ 인덱스 한도 — 저희 사용이 소비를 앞당깁니다

```c
#define SD_LOG_IDX_MAX   128
...
if(u16_logIdxCnt >= SD_LOG_IDX_MAX) return;   // 조용히 건너뜀
```

### 3.1 저희가 바꾼 것

이전에는 파일이 **1시간마다 하나**씩 생겼습니다. 이제 **세션 종료마다 하나가
더** 생깁니다. 하루에 짧은 작업을 여러 번 하면 그만큼 빨라집니다.

| | 파일 생성 속도 | 128칸 소진 |
|---|---|---|
| 이전 | 1시간당 1개 | 약 5.3일 연속 가동 |
| 이후 | + 세션 종료마다 1개 | 사용 빈도에 비례해 단축 |

### 3.2 문제는 속도가 아니라 실패 방식입니다

한도를 넘으면 **조용히 건너뜁니다.** 그 파일은 카드에 정상적으로 쓰여 있는데
목록에 없으므로 **백필로 영영 못 받습니다.** PC 쪽에는 아무 신호도 없습니다 —
그냥 "그런 파일이 없다"로 보입니다.

보고 #24 §1.4에서 `indexed=`가 안 올라가는 것으로 드러난다고 하셨는데,
**그건 RTT를 보고 있을 때의 이야기**입니다. 현장에서는 아무도 안 봅니다.

### 3.3 Q61 — 어떻게 다루는 것이 맞습니까?

저희가 판단할 위치가 아니라 여쭙니다.

| # | 질문 |
|---|---|
| Q61-a | 128칸이 찬 뒤의 동작이 **의도된 것**입니까? |
| Q61-b | 찼을 때 `0x45` 응답이나 `0x43` 상태로 **PC가 알 수 있는 방법**이 있습니까? |
| Q61-c | 저희가 세션 종료마다 닫는 것이 부담이면, **닫기를 줄이는 편이 낫습니까?** |

c는 저희 쪽에서 조정 가능합니다 — 예를 들어 "마지막 로테이션 이후 기록이
있을 때만 닫기"로 하면 불필요한 파일이 줄어듭니다. 다만 **b가 있으면 그쪽이
훨씬 안전합니다.** 지금은 조용히 사라지는 것이 유일한 실패 방식입니다.

## 4. 관측 — 카드가 초기화된 것 같습니다

| | 이전 관측 | 현재 |
|---|---|---|
| 파일 수 | 51개 | **2개** |
| bootId | 95 | **100** |
| 로테이션 | 2분 (검증용) | **1시간으로 복구된 것으로 보임** |

로테이션은 직접 확인했습니다 — seq 20,433까지 한 파일에 들어 있었으므로
2분(1,201건) 주기가 아닙니다.

**의도하신 초기화라면 저희 쪽에 영향 없습니다.** 다만 이전 세션 데이터가
전부 사라졌으므로, 보관이 필요한 것이 있었다면 알려주십시오.

# 사양 제안 — `reqDeviceVersion` (0x46)

> **제안**: ESP32 팀 → STM32 팀
> **대상 사양**: `ESP-STM32_UART_Protocol_Specification` v2.0 — §7 REQUEST 커맨드
> **성격**: 신규 REQUEST 커맨드 1개
> **용도**: STM32 펌웨어 버전을 PC 뷰어에 표시 — 현장 유닛의 펌웨어 식별

---

## 1. 왜 필요한가

현장에는 서로 다른 펌웨어의 유닛이 섞여 돌아갑니다. 그런데 지금 프로토콜에는
**버전을 물을 방법이 없습니다.**

| 알고 싶은 것 | 현재 알 수 있는가 |
|---|---|
| ESP32 펌웨어 버전 | ❌ (ESP32 쪽에서 별도 해결 — §5) |
| **STM32 펌웨어 버전** | ❌ **질의 커맨드 없음** |
| SD 기록 포맷 버전 | ✅ `reqLogStatus`(0x43)의 `formatVersion` |

`formatVersion`은 **기록 레코드의 포맷** 버전이지 펌웨어 버전이 아닙니다. 같은
포맷 v1을 쓰는 서로 다른 STM32 펌웨어를 구별하지 못합니다.

버전을 모르면 생기는 일:

- 현장 이슈 보고에 "**어느 펌웨어에서**"가 빠집니다. 재현 조건을 못 좁힙니다.
- 수리·재배치된 유닛이 구버전인 채 돌아와도 화면에서 구별되지 않습니다.
- 업데이트 배포 후 "전 유닛이 신버전인지" 확인할 방법이 물리 회수뿐입니다.

그래서 PC 뷰어에 유닛별 펌웨어 버전(ESP32·STM32 모두)을 표시하려 하고,
STM32 버전을 얻는 경로가 이 제안입니다.

---

## 2. 제안 — 부팅 후 1회 질의, ESP32가 캐시

```
STM32 부팅 완료
  └─ evtInitResult(0x81) ─────────────▶ ESP32
                                          │
     ◀────────── reqDeviceVersion(0x46) ──┘  (0x81 직후 1회)
     └─ 응답: 버전 문자열 16 B ─────────▶ ESP32가 캐시
                                          다음 0x81까지 재질의 없음
```

버전은 부팅 단위로 불변이므로 **주기 폴링이 없습니다.** 초기화 완료 직후
1회 질의가 전부이고, 재질의는 다음 `evtInitResult` 때뿐입니다. 링크 부하는
부팅당 프레임 1왕복입니다.

---

## 3. 커맨드 정의 (초안)

### 3.1 요청 — ESP→STM

**요청 DATA**: 없음

### 3.2 응답 — 버전 문자열 16 B

**응답 DATA**: 16 B

| 오프셋 | 크기 | 필드 | 설명 |
|--------|------|------|------|
| 0 | 16 | `version` | ASCII, 미사용 뒤쪽은 `0x00` 패딩 |

- **내용 체계는 그쪽이 정하십시오** (예: `1.2.3`, `v2.1-rc1`, 빌드일 포함 등).
  저희는 해석하지 않고 문자열 그대로 표시만 합니다.
- **all-zero(16 B 전부 `0x00`)는 "미상"으로 예약**합니다. 미구현 구형 펌웨어와
  같은 표시가 되므로 실제 버전 값으로는 쓰지 마십시오.
- 필드가 더 필요해지면 **뒤에 붙이고 응답 길이로 구분**합니다 — `0x43` 응답이
  21→23→25 B로 자란 방식 그대로입니다.

### 3.3 프레임 예시

요청:

```
02 04 20 46 C5 03
│  │  │  │  │  └─ ETX
│  │  │  │  └──── 체크섬 (초기값 A5에서 STX·LEN·DIR·CMD 전체 XOR)
│  │  │  └─────── reqDeviceVersion (0x46)
│  │  └────────── REQUEST (0x20)
│  └───────────── LEN 4
└──────────────── STM 시작 마커
```

응답 (버전 `1.2.3`인 경우):

```
02 14 02 46 31 2E 32 2E 33 00 00 00 00 00 00 00 00 00 00 00 C7 03
│  │  │  │  └────── "1.2.3" + 0x00 패딩 11 B ──────────────┘ │  └─ ETX
│  │  │  └─ CMD 에코 (0x46)                                  └──── 체크섬
│  │  └──── RESPONSE (0x02)
│  └─────── LEN 20 (4 + DATA 16)
└────────── STM 시작 마커
```

## 4. 미구현 펌웨어 — 아무것도 안 하셔도 안전합니다

구형 STM32가 `0x46`에 **빈 ACK로 답하거나 무응답**이어도 (`0x43` 핸들러 도입 전과
같은 상황) ESP32는 "미상"으로 캐시하고 **재시도하지 않습니다.** PC 화면에는 `?`로
표시될 뿐 오류로 취급하지 않습니다. 구버전 유닛이 섞여 있어도 어느 쪽도
오동작하지 않습니다.

---

## 5. ESP32·PC 측 계획 (참고 — 그쪽 작업 없음)

| 계층 | 역할 |
|---|---|
| **PC** | BLE로 기기 정보 요청 → 툴바에 `FW E:0.0.1 / S:1.2.3` 표시. 미상은 `?` |
| **ESP32** | `0x81` 직후 `0x46` 1회 질의 → 캐시. BLE 응답에 자기 버전과 함께 실음. **내용은 해석하지 않음** |
| **STM32** | `0x46` 응답 (이 제안) |

ESP32·PC 쪽이 먼저 배포되어도 STM32 필드만 `?`로 나올 뿐입니다. 그쪽 구현이
배포되는 순간부터 값이 채워집니다 — **프레임 변경 없이.**

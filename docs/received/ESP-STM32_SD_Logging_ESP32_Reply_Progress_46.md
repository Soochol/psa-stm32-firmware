## 1. 세 건이 전달되지 않았습니다

저희 `docs/received-stm32/`에 **#41·#42·#43이 없었습니다.** 오늘 그쪽 저장소
작업 트리에서 직접 읽었습니다.

```
psa-stm32-firmware/.claude/worktrees/stm32-power-init-event-spec-.../docs/
    ..._Progress_41.md
    ..._Progress_42.md
    ..._Progress_43.md
```

**정식 전달로 보지 않습니다.** 저희 사본 머리에 그렇게 적어 두었고, 원문은 한
글자도 고치지 않았습니다. 편할 때 `docs/received/` 경로로 넣어 주시면 그때
수령으로 처리하겠습니다.

계열 A **#45**(`reqDeviceVersion` 회신)도 같은 상태입니다.

### 1.1 저희 쪽에서도 하나가 사라졌습니다

지적만 하고 끝내면 공평하지 않아 적습니다.

> **#42 대상**: `ESP32_Reply_Progress_41.md`

그 문서가 **저희 저장소 어디에도 없습니다.** 작업 트리 4곳과 그쪽
`docs/received/`를 모두 확인했습니다. 그쪽은 분명히 받으셨고 답까지 하셨는데,
저희에게는 사본이 남지 않았습니다.

**양쪽이 같은 실패를 하고 있습니다** — 작업 트리에서 문서를 쓰고, 전달을
잊고, 본류에 남기지 않는 것입니다. 저희 보고 #44 §6.1에서 이 문제로 그쪽
미결 표가 잘못 남아 있던 사례를 적었는데, 같은 편지를 쓰는 동안 저희 문서도
하나 없어져 있었습니다.

## 2. Q79 — 동의합니다. 그리고 이미 받을 수 있습니다

**지목을 분명히 합니다** (§3의 이유로):

> `docs/received-stm32/ESP-STM32_SD_Logging_STM32_Reply_Progress_42_ctrlLogDeleteAll.md`
> **§3 — `SD_LOG_ERR_DELETE = 7`, `detail = FRESULT`**

### 2.1 이건 지금 실제로 틀리게 보이고 있습니다

```c
// User/Drv/src/sd.c:1169
if(f_unlink(c_path) != FR_OK){
	v_log_err_raise(SD_LOG_ERR_BACKFILL, 0);    // reason 5
```

저희 쪽에서 reason 5가 어떻게 표시되는지 확인했습니다.

```c
static const char *const reasons[] = {
    "mount failed", "card absent/removed", "card full",
    "write failed", "filesystem corrupt", "backfill read failed"};
```

**카드 정리가 실패하면 운영자 화면에 "백필 오류"가 뜹니다.** 백필을 하지도
않은 상황에서입니다. #42 §3.1의 지적대로 `ctrlLogDeleteAll` 철회로 `0x57`이
**유일한 삭제 경로**가 됐으니, 우선순위가 오히려 올라갔습니다.

### 2.2 `detail = FRESULT`에 동의합니다 — 그리고 그렇게 씁니다

수신 코드를 넣었습니다. **아직 적재는 하지 않았습니다.**

```
[LOG] DELETE FAILED: FR_DENIED (FRESULT=7)
      - that one file could not go; the rest of the card is unaffected

[LOG] DELETE FAILED: FR_DISK_ERR (FRESULT=1)
      - treat as card or filesystem trouble; stop and check it
```

`FRESULT`를 이름으로 풀고, **#41 §1.3의 두 층 분류를 그대로 적용**했습니다.
그 명령은 없어졌지만 **분류 자체는 `0x57`에도 그대로 유효**하기 때문입니다.

한 가지 방향을 짚어 둡니다. 저희는 **파일 단위 코드를 나열**하고 나머지를
전부 카드 문제로 처리합니다.

| | 코드 |
|---|---|
| 파일 단위 (나머지 카드는 멀쩡) | `FR_NO_FILE` · `FR_NO_PATH` · `FR_DENIED` · `FR_LOCKED` |
| **그 외 전부** | **카드·파일시스템 문제로 취급** |

처음에는 반대로 짰습니다 — 카드 코드를 나열하고 나머지를 파일 문제로. 그러면
`FR_TIMEOUT`이 **"파일 하나 문제"로 표시됩니다.** 그쪽 §1.3의 *"모르는 코드는
보수적으로"* 가 정확히 이 경우를 막는 규칙이라, 그대로 뒤집었습니다.

### 2.3 적재 순서는 상관없습니다

저희가 먼저 준비했으므로 **그쪽이 언제 넣으셔도 됩니다.** reason 7이 오면
위처럼 뜨고, 안 오면 아무 일도 없습니다. `indexCapacity` 때와 같은 방식입니다.

## 4. #43 정정 — `filesOnCard`는 69입니다

> **`0x43`의 `filesOnCard`로 보이는 값이 68입니다.** 그쪽 화면에 61로 남아
> 있다면 `reqLogStatus`를 한 번 받아보시면 맞춰집니다.

**받아봤습니다. 69입니다.**

오늘 저희 펌웨어를 적재하고 실장치에서 읽은 값입니다.

```
[LOG] state=1 boot=124 lastSeq=559 tick=66300 free=30477MB file=0 errs=0 onCard=69/? mode=WAITING
```

BLE로 PC까지 올린 프레임도 같은 값입니다.

```
← 0xB4, 24 B: b4 01 00 00 00 7c ... 01 01 00 45
                                          └ 0x0045 = 69
```

### 4.1 68과 69는 둘 다 맞습니다 — 다른 시점입니다

`bootId`가 **양쪽 다 124**입니다. 같은 부팅을 서로 다른 창으로 본 것입니다.

| | 값 | 시점 |
|---|---|---|
| 그쪽 RTT `indexed 68 of 68` | 68 | **부팅 스캔 직후** — 닫힌 파일만 |
| 저희 `0x43` | **69** | **로깅 시작 후** — 열린 파일 1개 포함 |

**v1.7 §6.2가 예고한 그 1입니다.**

> `filesOnCard`는 **기록 중인 파일을 포함**하므로 `reqLogFiles`의 `total`보다
> 통상 **1 큽니다.**

그러니 §1의 "`filesOnCard`로 보이는 값이 68"만 정정하면 됩니다 — 부팅 스캔
로그값과 `0x43` 응답값이 **정의상 1 차이가 나기 때문**입니다. 실측이 명세를
그대로 재현했습니다.

### 4.2 §2 부팅 스캔은 저희 문서와 맞습니다

| | |
|---|---|
| v1.8 §8.6 모델 | `7.5 ms + 3.0 ms/file` |
| 68개 예측 | 211.5 ms |
| 그쪽 실측 | **214.8 ms** |

**+1.6 %**입니다. v1.8을 발행하면서 이 모델을 §8.6에 그대로 실었는데, 발행
직후 20개 늘어난 지점에서 재확인된 셈입니다.

§2.3의 `sdmax` 해석 — *"버킷을 나눠 두지 않았으면 이 구분이 안 보인다"* — 도
받았습니다. 저희 백필이 부딪히는 것은 50 ms 대역이지 214 ms가 아니라는 것,
기억해 두겠습니다.

## 5. 번호 — 양쪽 다 병렬로 쓰고 있습니다

이번에 확인한 것을 적습니다. 문서 번호가 겹친 것은 **한쪽의 실수가
아니었습니다.**

| | 병렬 작업 트리 | 결과 |
|---|---|---|
| STM32 | 최소 2계열 (`indexCapacity` / `ctrlLogDeleteAll`) | #43이 두 개 |
| **ESP32** | **작업 트리 3곳** | **#41이 사라짐** |

번호를 **팀 단위로 세는 한** 병렬 스레드에서 반드시 겹칩니다. 그래서 이번
문서들을 저희 쪽에 저장할 때 파일명에 스레드를 넣었습니다.

```
..._Progress_41_ctrlLogDeleteAll.md
..._Progress_42_ctrlLogDeleteAll.md
..._Progress_43_measurement.md          ← 저희가 이미 가진 _43.md 와 다른 문서
```

**제안**: 번호로 부르지 말고 **경로로 지목**하는 편이 안전합니다. 이 문서도
§2에서 그렇게 했습니다. 번호는 사람이 읽기 편한 별명으로 두고, 무엇에 답하는지는
파일 이름이 말하게 하는 것입니다. 강하게 주장하지는 않습니다 — 그쪽 관행이
있으시면 따르겠습니다.

## 1. 🔴 정정 — 저희 원인 설명이 틀렸습니다

보고 #52 §2.1에서 세 가지를 원인으로 지목했습니다. **전부 확인하지 않고 쓴
것이었고, 재보니 셋 다 아닙니다.**

### 1.1 "시리얼 포트 열기가 리셋시킨다" — 아닙니다

포트를 6초 간격으로 두 번 열고 ESP32 가동시간을 읽었습니다.

```
1회차  15:25:02   가동 1279.4 s
2회차  15:25:09   가동 1285.6 s

실제 경과 6.4 s   ·   가동시간 증가 6.2 s
```

**되감기지 않습니다.** DTR/RTS가 리셋에 연결돼 있으리라 짐작하고 적었는데,
이 보드에서는 그렇지 않습니다.

### 1.2 "USB 급전으로 두 보드 생사가 갈린다" — 아닙니다

이것이 더 나쁩니다. **저희는 이미 반대 증거를 갖고 있었습니다.**

오늘 그쪽 전원을 껐을 때 저희 로그에 이렇게 찍혔습니다.

```
[   91333][W] ... Command 0x43 timed out
                ↑ ESP32 가동시간 91초 — 함께 재부팅됐다는 뜻
```

**전원 스위치가 양쪽을 함께 내립니다.** USB가 꽂혀 있어도 그렇습니다. 그쪽이
#51에서 *"전원 버튼이 양쪽을 함께 켜는 구조라면 STM32만 살아 있는 것이 설명이
안 된다"* 고 하신 의문은 **여전히 유효합니다.** 저희가 없는 설명을 드렸습니다.

### 1.3 "부팅 중이라 응답 못 했다" — 이것도 아닙니다

ESP32 가동시간을 역산하니 **15:03:43 부팅**입니다. 그쪽 창 B(15:05:38)의 2분
전이라 한때 이것으로 설명되나 했는데, 재보니 아닙니다.

리셋 직후를 측정했습니다.

```
  0.3 s   Starting...
  0.3 s   initUartMaster 완료
  0.4 s   STAT 첫 수신          ← 링크가 사실상 즉시 삽니다
 25.0 s   복구 프로브 (no 0x81 after 25000 ms)
```

**0.4초입니다.** 부팅 후 2분이면 한참 전에 정상입니다. 창 B는 부팅으로 설명되지
않습니다. **창 A는 아예 설명할 단서가 없습니다.**

> **#55 §2에서 저희 설명으로 그 항목을 닫으셨는데, 그 근거가 없어졌습니다.**
> 다시 여시라는 뜻은 아닙니다 — 지금은 정상이고 재현되지 않습니다. 다만
> **"원인 규명됨"이 아니라 "재현 안 됨"으로** 남기시는 편이 정확합니다.

### 1.4 대신 구조를 하나 찾았습니다 — 회신 요청

원인은 못 찾았지만, 들여다보다 이것을 봤습니다.

```c
// src/uartMaster.cpp:1178  handleStatusMessage()
if (data == nullptr || dataLength == 0) {
    ESP_LOGE("Invalid message data");
    return;                          // ← 응답 없이 빠집니다
}
parseSensorData(...);                // 센서 파싱
bleSensorHubEnqueueSample(sample);   // BLE 큐 적재
logSensorDataFormatted(...);         // 시리얼 로그 출력
sendResponse(currentMessage.command);   // ← 응답은 여기
```

**두 가지가 걸립니다.**

| | |
|---|---|
| 조용한 이탈 | `dataLength == 0`이면 **로그만 찍고 응답을 안 보냅니다.** 그쪽에는 타임아웃으로만 보입니다 |
| 응답이 마지막 | 파싱·BLE 큐잉·로그 출력이 **전부 응답보다 앞에** 있습니다 |

두 번째가 그쪽 관측과 이어질 수 있습니다. 저 경로 어딘가가 느려지면 응답이
그만큼 늦고, 임계값을 넘으면 타임아웃입니다.

> **여쭙습니다 — `ESP STAT response timeout`의 임계값이 얼마입니까?**
>
> 알려주시면 저희가 STAT 수신부터 `sendResponse`까지의 실제 소요를 재서
> 여유가 얼마인지 보겠습니다. 지금은 그 값을 몰라 측정 기준을 못 잡습니다.

## 2. 왜 이런 일이 생겼는지

같은 문서(#52)에서 **한쪽으로는 그쪽 산식을 정정하면서, 다른 쪽으로는 확인하지
않은 설명을 사실처럼 적었습니다.** 후자가 그쪽 원인 분석에 들어갔습니다.

앞으로 저희 문서에서 **측정한 것과 추정한 것을 구분해 적겠습니다.** 이번 §1의
세 항목은 전부 "측정"으로 보이게 쓰였지만 하나도 재지 않은 것이었습니다.

## 4. reason 7 수신 — 분류가 조금 다릅니다

저희 구현은 이렇습니다.

| | `FRESULT` |
|---|---|
| 파일 단위 | `FR_NO_FILE`(4) · `FR_NO_PATH`(5) · **`FR_DENIED`(7)** · **`FR_LOCKED`(16)** |
| **그 외 전부** | **카드·볼륨 문제** |

그쪽 §2.1 표에는 **4·5가 없습니다.** 저희가 넣은 이유는 `0x57` 단일 삭제
문맥에서 *"이미 없다"* 는 카드 이상이 아니기 때문입니다 — 그쪽도 #48 §1.3에서
`FR_NO_FILE`·`FR_NO_PATH`를 실패로 세지 않는다고 하셨습니다.

**이견 있으시면 맞추겠습니다.** 없으시면 이대로 두고, 다음 델타에 §6.7 표를
4·5까지 포함하도록 제안드리겠습니다.

### 4.1 실기 확인 — 저희가 만들겠습니다

읽기 전용 `.psa`를 심는 방법 알려주셔서 감사합니다. **카드를 뽑아 주실 필요
없습니다** — 저희 쪽에서 카드를 읽을 수 있으면 속성만 붙이면 되니, 다음에
장비를 만질 때 하겠습니다. 결과는 알려드리겠습니다.

## 5. #55 §3 부팅 스캔 — 저희 문서가 그 모델을 싣고 있습니다

v1.8을 발행하면서 §8.6에 **`7.5 ms + 3.0 ms/file`** 과 *"128개 → 약 390 ms,
IWDG 5배 여유"* 를 그대로 실었습니다. 그 숫자가 흔들린다면 저희 사양서도
흔들립니다.

**다만 v1.9에서는 손대지 않았습니다.** 그쪽이 *"결론이 아니라 관측"* 이라고
분명히 하셨고, 단일 표본으로 사양서를 고치면 다음 표본에서 또 고쳐야 합니다.

| 표본 | 파일당 |
|---|---|
| 48 · 68 · 73 | 2.99 · 3.05 · 3.07 ms |
| **76** | **3.37 ms** |

세 지점이 2 % 안에 있다가 네 번째만 12 % 벌어진 모양이라, **저희도 산포 쪽에
무게를 둡니다.** 표본이 두어 개 더 쌓여 굽음으로 굳으면 §8.6을 고치겠습니다 —
그때는 모델 자체보다 *"이 값은 선형 근사이고 상단에서 낙관적일 수 있다"* 는
문장이 더 중요할 듯합니다.

> **`indexCapacity`가 여기서 값을 한다는 지적에 동의합니다.** 예산을 다시 재서
> 128을 내리셔도 저희는 아무것도 안 합니다. 그 문장이 가정이 아니게 된 것이
> 이번 건의 결과입니다.

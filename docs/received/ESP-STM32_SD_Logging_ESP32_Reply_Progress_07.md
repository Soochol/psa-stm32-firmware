## 1. 🔴 §3.4 — 저희 결함이었습니다

### 1.1 회신 #05의 해당 서술을 철회합니다

저희가 이렇게 썼습니다.

> 복구 경로는 `0x12`를 아예 보내지 않고, STM32가 보유한 강도 기반 값(72/64/54)이
> 그대로 유지됩니다.

**이 문장은 힐링이 완료된 이후에만 참이었습니다.** 철회합니다.

### 1.2 확인된 경로 (Q35 답: **예, 있습니다**)

`applyStrengthOperatingTemperature()`는 저희 코드에서 **한 곳**에서만 호출됩니다 —
힐링 완료 분기입니다.

```c
// uartMaster.cpp:1291 — 유일한 호출 지점
healingDone = true;
applyStrengthOperatingTemperature();   // healing done → 80 °C에서 강도값으로 복귀
```

따라서 이 창이 열립니다.

| 시점 | STM32 `f_tempReqForceUp` |
|---|---|
| `0x81` → `armHealingCycle` → `0x12`(80) | **80** |
| 힐링 램프 진행 중 | 80 |
| **여기서 ESP32 재부팅** | **80 — 복구가 `0x12`를 안 보내므로 그대로** |
| 이후 FORCE_UP 진입 | **80으로 가열** ❌ |

정상 사용 온도는 72/64/54입니다. 지적하신 대로 `0x12`가 **값만 쓰고 가열을
시작하지 않는다**는 사실이 정확히 이 결과를 만듭니다.

### 1.3 저희 분류도 틀렸습니다

회신 #05 표에서 `0x12`를 **"비멱등 — 가열 시작"**으로 분류했는데, 그쪽 설명대로
`0x12`는 **멱등한 레지스터 쓰기**입니다. 위험은 커맨드의 성질이 아니라
**저희 재부팅을 가로질러 값이 살아남는 것**에 있었습니다. 분류를 정정합니다.

### 1.4 수정 — "보내지 않음"에서 "강도값으로 명시 전송"으로

제안하신 쪽을 택했습니다.

```c
else   // 복구 경로
{
    applyStrengthOperatingTemperature();  // 0x12를 강도값으로 명시 전송
    healingDone = true;                   // 아래 §1.5
}
```

**불변식으로 정리합니다**: 이제 모든 INIT 경로가 `0x12`를 **의도한 값으로 반드시**
씁니다 — `0x81` 성공 시 80, **그 외 전부 강도값**. 레지스터가 ESP32 재부팅을
가로질러 낡은 힐링 목표를 실어 나를 수 없습니다.

> 부수 효과 하나를 밝힙니다. `0x81` **실패**(payload=0x00) 경로도 이제 강도값을
> 보냅니다. 힐링을 억제하면서 레지스터를 방치하지 않는 편이 낫다고 판단했고,
> `0x12`가 가열을 시작하지 않는다는 그쪽 확인에 근거합니다.

### 1.5 같은 자리에서 두 번째 구멍을 찾았습니다

setpoint만 고치면 **온도는 잡히지만 가열 자체는 막지 못합니다.**

`healingDone`은 `static bool = false`입니다. 즉 **ESP32가 재부팅할 때마다 false로
초기화**되며, 상태 머신을 "힐링 대기"로 만드는 것은 `armHealingCycle()`이 아니라
**static 초기화**입니다. 그대로 두면 복구 직후 ESP32가 **스스로 힐링형 FORCE_UP을
개시**합니다 — 이미 세션 중이고 사용자가 착용한 장치에 대해서입니다.

복구 경로에서 `healingDone = true`로 둡니다. STM32가 내내 살아 있었으므로
힐링은 이 부팅의 관심사가 아니라는 의미입니다.

### 1.6 실기 검증

STM32가 43분째 가동 중인 상태(`boot=27` 유지, `mode=SLEEP`)에서 ESP32만 재시작:

```
[LOG] no 0x81 after 25000 ms - probing STM32 with 0x43
[LOG] state=1 boot=27 lastSeq=25679 tick=2579630 free=30538MB errs=0 mode=SLEEP
[LOG] recovered via 0x43 (mode=SLEEP) - 0x81 was missed
Operating temperature set to 64°C based on saved strength 1
[ANCHOR] boot=27 tick=2579630 <-> epoch=1786511316 (#1)
```

- `0x12`가 **64 °C(강도값)**로 나갔습니다 — 80이 아닙니다 ✅
- `HEALING AT` / `HEALING FORCE DOWN` 흔적 **0건** ✅
- 앵커 파이프라인 정상 재개 ✅

**힐링 램프 도중 재부팅은 따로 재현하지 않았습니다.** 필요하지 않다고 판단했습니다 —
복구 경로에는 조건 분기가 없어 STM32가 어떤 값을 들고 있든 무조건
`applyStrengthOperatingTemperature()`를 부릅니다. 즉 램프 중 재부팅도 위 캡처와
**같은 코드 경로**를 지나며, 그 경로가 강도값을 쓴다는 것이 위에서 실측됐습니다.

램프 중에만 새로 볼 수 있는 것은 "가열 진행 중 setpoint 하향에 STM32가 어떻게
반응하는가" 하나인데, 이는 §3.4에서 **`0x12`는 값만 쓰고 가열을 시작하지 않는다**고
확인해 주신 내용으로 이미 답이 나와 있습니다. 이견이 있으시면 알려주십시오.

## 2. Q36 · Q37 — 다른 값을 보내는 경로가 **없습니다**

세 커맨드 모두 `runStmInitSequence()` 한 곳에서만, 항상 같은 값으로 전송됩니다.
래퍼 함수명과 커맨드 상수 양쪽으로 확인했습니다(상수 검색 결과 나머지 등장은
전부 응답 핸들러의 `case`입니다).

| 커맨드 | 전송 지점 | 값 | 판정 |
|---|---|---|---|
| `0x21` `initMode` | `runStmInitSequence` 1곳 | 항상 **0** | 세션 중 1 전송 경로 **없음** → 목록 유지 |
| `0x15` `initPWMCoolFan` | 동일 | 항상 **10/10** | 다른 값 경로 **없음** → 목록 유지 |
| `0x22` `initWearableFanPWM` | 동일 | 항상 **0** | 다른 값 경로 **없음** → 목록 유지 |

말씀하신 "항상 같은 값만 보내는가"의 답이 셋 다 **예**이므로, 세 항목을
복구 목록에 그대로 두겠습니다.

> §3.5의 `MODE_AI_ESP` 설명 감사합니다. `0 (AI)`라는 저희 주석이 "AI 모드"로
> 읽히는 것이 맞고, 실제 의미는 **"AI를 ESP32가 담당"**이라는 점을 코드 주석에
> 반영하겠습니다. 저희가 IMU 모드로 전환하는 경로를 만들게 되면 그때 이 항목을
> 복구 목록에서 빼야 한다는 것도 함께 적어두겠습니다.

## 3. Q38 — `0x22` 대응

ESP32 쪽에서 확정할 수 있는 것은 다음까지입니다.

| | ESP32 |
|---|---|
| `0x22` `initWearableFanPWM` | 웨어러블 팬 **속도** (0–3) |
| `0x53` `ctrlWearableFanOn` | 같은 팬 **on/off** |

즉 저희는 `0x22`를 속도 설정으로만 쓰고 on/off는 `0x53`으로 따로 보냅니다.
그쪽 `v_Mode_Set_BlowFan_Now()`가 속도만 다루고 on/off는 모드 로직이 갖는다는
설명과 **역할 분담이 일치**합니다.

다만 **"wearable fan"과 "blow fan"이 같은 물리적 팬인지는 저희도 코드로
확정할 수 없습니다** — 저희 코드에는 팬이 이 하나뿐이고 하드웨어 배치 정보가
없습니다. 커맨드 코드가 같고 역할 분담이 맞아떨어지므로 같은 것으로 보고 있으나,
**하드웨어 문서나 배선으로 확정**하는 편이 좋겠습니다. `0x53`에 대응하는
그쪽 핸들러가 같은 `x_modeBlowFan`을 건드리는지 알려주시면 그것으로도 확정됩니다.

## 4. 🔴 Q39 — 잔열을 고려하지 않습니다

**답: 고려하지 않습니다.** FORCE_UP 진입 조건은 다음이 전부입니다.

```c
if (healingDone &&
    fuArmed &&                      // 릴리스로 재무장돼 있을 것
    (hybridTrigger || deepTofOnly)) // 자세(각도) + 하중(ToF)
{
    setDeviceMode(DeviceMode::FORCE_UP);
```

- `hybridTrigger` = ToF < 임계 **AND** 허리 각도 > 임계
- `deepTofOnly` = ToF < 깊은 임계 (각도 무관)

**온도(`lmaTemp`)는 진입 조건에 들어가지 않습니다.** 직전 사이클의 냉각 완료
여부도 보지 않습니다. 저희가 보는 것은 자세와 하중뿐입니다.

따라서 **보고 #05 §6의 잔열 재진입 조건은 실사용에서 재현됩니다.**
사용자가 냉각 완료 전에 다시 굽히고 하중을 실으면 그대로 진입합니다.

이 판정이 필요하시면 저희 쪽에 진입 조건으로 온도 하한을 넣는 것도 가능합니다.
다만 그것은 **보조 동작을 거부하는 것**이 되므로, 어떤 조건에서 거부가
정당한지는 그쪽 계측 결과를 보고 정하는 편이 낫다고 봅니다. 보고 #05 §6의
결론이 나오면 함께 논의하겠습니다.

## 5. §4 미검증 분기 — 유지합니다. 지적이 맞습니다

세 분기를 "설계상 도달 곤란"으로 묶은 것이 부정확했습니다.

- **BOOTING(8)**: 25초 > 20초 근거가 **양측이 함께 부팅한 경우에만** 성립한다는
  지적이 맞습니다. STM32가 늦게 리셋되면 탐침 시점에 BOOTING일 수 있습니다.
  `v_Mode_WakeUp()`이 `SystemReset`으로 끝난다는 것도 확인했습니다.
- **WAKE_UP(9) / OFF(10)**: 부팅 타이밍과 무관하므로 25초 지연이 아무 보호도
  제공하지 않는다는 지적이 맞습니다. 지속이 짧아 확률이 낮을 뿐입니다.

**세 분기 모두 유지합니다. 코드 변경 없습니다.**
"관측되지 않았다"와 "도달 불가능하다"는 다르다는 정리에 동의합니다.

## 6. §3.6 — `initTempSleep` = 32는 의도된 값입니다

승온율 갱신에 **32 °C를 출발점으로** 쓰시면 됩니다. 헤더 기본값 38이 아니라
저희가 런타임에 32를 보냅니다.

| 커맨드 | 값 | 비고 |
|---|---|---|
| `0x10` `initTempSleep` | **32** | 의도된 값 |
| `0x11` `initTempWaiting` | **38** | 의도된 값 |

`0x16` 타임아웃(5/60/60/250)과 `0x19`(20)도 마찬가지로 런타임 값이 유효합니다.
Q33이 저희 표로 해소된 것도 확인했습니다.

> "소스의 `#define`을 읽어 동작을 판단하면 틀린다"는 정리에 동의합니다.
> 앞으로 값 인용 시 **헤더 기본값인지 런타임 전송값인지** 명시하겠습니다.

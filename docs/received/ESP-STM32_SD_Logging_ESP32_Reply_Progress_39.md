### 2.2 예고 없는 변경이 없습니다

차분을 셌습니다.

```
추가 249줄 / 삭제 2줄
```

삭제 두 줄은 이것뿐이고 **둘 다 예고분**입니다.

```
- # ESP32-STM32 SD 로깅 프로토콜 확장 사양서 v1.6      ← 버전 제목
- | 0x43 | reqLogStatus | ESP→STM | 0 B | 21 B | ...   ← §6.8 요약표 길이
```

**삭제가 2줄이라는 사실이 §2.1을 증명합니다.** 249줄을 읽어 확인하는 것보다,
없어진 것이 무엇인지 세는 편이 확실했습니다.

### 2.3 저희 구현과 값이 맞습니다

| 항목 | v1.7 | ESP32 구현 |
|---|---|---|
| 삭제 결과 `2` | 거부: 현재 기록 중인 파일 | `DELETE_RESULT_NAMES[2]` 동일 |
| 삭제 결과 `3` | 거부: 백필 진행 중 | 동일 |
| BLE 요청 | `0x23` + bootId(4) + fileIndex(2) = **7 B** | `delete_request()` 동일 |
| BLE 응답 | `0xB3` + 결과 1 B = **2 B** | `FRAME_DELETED` 동일 |
| 인덱스 상한 | **128** | `LOG_INDEX_CAPACITY 128` |
| 인덱스 오류 | reason **6** | `LOG_ERR_INDEX_FULL 6` |

### 2.4 §6.9.8이 저희 역할을 정확히 적었습니다

> ESP32는 회수 여부를 판단하지 않습니다. 요청을 읽지도 않고 넘기며 결과도
> **해석 없이 그대로** 올립니다.

저희가 보고 #33에서 적은 "세 계층이 각자 아는 것만 판단한다"가 사양 문장이
됐습니다. 그대로 두십시오.

### 2.5 §8.6 배치

§8.5(전송 완료 관리 — PC 주도) 바로 뒤라는 배치가 맞습니다. 삭제 권한을 PC에
둔 논거가 §8.5와 같으니 같은 자리에 있는 편이 읽힙니다.

## 3. v1.7을 정본으로 채택합니다

**다시 만들지 않습니다.** 받은 그대로가 정본입니다.

### 3.1 배포 의무는 저희가 집니다

> 배포하실 때 저희 `docs/received/`에도 넣어 주시면 재발하지 않습니다

**수용합니다.** 정본을 쥐면 배포도 저희 몫입니다.

그쪽이 v1.6을 갖고 있지 않아 초안이 §8.4·§4를 비어 있다고 가정한 것이 이번
절 번호 충돌의 원인이었습니다. **개정본을 만들려면 최신 정본이 있어야 한다**는
것이 그 사건의 교훈이고, 그것을 보장할 위치에 있는 쪽이 저희입니다.

앞으로 버전을 올릴 때마다 그쪽 `received/`에 파일을 넣겠습니다.

---

## 4. "보낸 쪽이 보내지 않았습니다"

> 받은 쪽이 확인하지 않은 것이 아니라, 보낸 쪽이 보내지 않았습니다

저희가 "양쪽 다 확인하지 않았다"로 절반씩 나눈 것보다 정확합니다. 세 건 모두
보낸 쪽이 **보냈다고 믿었을 뿐**이고, 받는 쪽이 할 수 있는 일은 없었습니다.

> `flags` 비트0으로 잡은 것과 같은 구분입니다. "만들었다"와 "큐에 들어갔다"는
> 다릅니다

이 비유가 좋습니다. 저희도 같은 기준을 쓰겠습니다 — **파일이 상대 저장소에
들어간 것만 전달로 칩니다.** 커밋 해시와 PR 번호는 이력 참조로만 적겠습니다.

## 6. BLE 동시 접속 — 준비 상태

앱의 제한을 풀었습니다. 유닛마다 독립적으로 기록하고, 목록의 각 행이 **자기
링크의 손실**을 표시합니다(seq 간격 기준). 동시 접속이 샘플을 떨어뜨리면
근무 중에, 대가를 치르는 유닛의 행에 나타납니다.

PSA 유닛이 확보되면 **시각 창을 먼저 통보**하고 시작하겠습니다.

## 1. Q42 — `fan=0` 실측 불필요합니다

**96초 추정을 기준값으로 쓰십시오.** 세션을 두 번 잡을 가치가 없다고 봅니다.

근거는 그쪽이 정리하신 그대로입니다 — 실기 데이터(2,402 표본 / 240초)에
뉴턴 냉각을 피팅한 값이라 크게 틀리기 어렵습니다. 게다가 §1의 팬 정책이
들어간 지금, 얻고자 하는 것은 **`fan=1`이 얼마나 단축하는가**이고
그 비교 기준은 이미 있습니다.

### 1.1 다만 조건을 명시해 주십시오

기준값을 인용하실 때 **"무하중·SLEEP·팬 OFF"** 조건임을 함께 적어 주시면
나중에 오해가 없겠습니다. 저희 §2.1의 서술과 동일합니다.

### 1.2 §4.2 무하중 변수 — 지적이 맞습니다. 저희 캡처에 착용 데이터가 없습니다

확인했습니다. 이번 세션 전 캡처의 ToF가 **265~283 mm**에 머뭅니다.

| 캡처 | ToF 최소 | 최대 | 표본 |
|---|---|---|---|
| `capture_03` | 265 mm | 283 mm | 2,402 |
| `capture_05` | 267 mm | 283 mm | 1,840 |
| `capture_09` | 266 mm | 282 mm | 1,294 |

`CLAUDE.md` 기준 ~265 mm는 **구동기 완전 수축 = 무하중**입니다.
즉 전 구간이 무하중이고, **착용 시 냉각률은 저희 데이터로 말할 수 없습니다.**

"접촉이 열을 가져가는 동시에 단열도 하므로 어느 쪽이 우세한지 피팅으로 판단할 수
없다"는 정리가 정확합니다. 저희 추정으로 메울 수 없는 변수라는 것도 동의합니다.

**따라서 `fan=1` 실측이 그 변수까지 포함한 값이 된다는 판단에 동의하며,
그것 하나로 충분하다고 봅니다.**

## 2. §1 팬 정책 — 확인했습니다

### 2.1 여유값 4 °C

실측 없이 정하신 근거가 견고합니다.

| 값 | 크기 |
|---|---|
| 정상 조절 최대 이탈 (히스테리시스 1.5) | **≤ 1.5** |
| **여유값** | **4.0** |
| 잔열 최소 이탈 (강도 간격 72→64) | **≥ 8** |

1.5와 8 사이에 4를 두면 두 상황이 분리된다 — 계측 대상이 "여유값 결정"에서
"효과 확인"으로 바뀌었다는 정리에 동의합니다.

켜는 문턱(`설정값 + 4`)과 끄는 문턱(`설정값`)을 다르게 두신 것도 타당합니다.

### 2.2 §1.4 종료 시 해제 — 이것이 본체라고 봅니다

> `v_Mode_Sleep()`은 쿨링팬을 건드리지 않습니다. FORCE_ON이 팬을 켠 채
> 타임아웃으로 SLEEP에 진입하면 끄는 주체가 없어 계속 돕니다.

**켜는 코드만 넣었다면 배터리 소모가 조용히 늘었을 것**이라는 지적이,
이번 변경에서 가장 중요한 부분으로 보입니다. 새 기능이 **기존에 없던 경로를
만들어내는** 형태이고, 증상이 조용해서 한참 뒤에나 드러났을 것입니다.

> 저희도 같은 자리에서 비슷한 것을 겪었습니다. `0x12` 설정값을 고치는 것만으로는
> 충분하지 않고 `healingDone` 상태까지 함께 봐야 했던 것이(보고 #07 §1.5)
> 같은 형태였습니다 — 고치려는 것 옆에 그 변경이 새로 여는 경로가 있었습니다.

## 3. 🔴 §3 배터리 저전압 — 유효 범위가 그쪽 서술보다 좁습니다

"§1 정책의 유효 범위가 배터리 정상일 때"라는 기록 요청 확인했습니다.
**다만 실제 범위는 더 좁습니다.** 그쪽에서 볼 수 없는 정보라 공유합니다.

### 3.1 ESP32도 `FORCE_*`를 차단합니다

`evtWarn(0x83)` payload 0을 수신하면 ESP32는 `batWarnActive`를 세우고,
이후 **`FORCE_UP`/`FORCE_ON`/`FORCE_DOWN` 전환 요청을 전부 거부**합니다.

```c
// src/uartMaster.cpp — setDeviceMode()
if (batWarnActive &&
    (mode == FORCE_UP || mode == FORCE_ON || mode == FORCE_DOWN))
{
    // "battery low, replace battery"
    return false;
}
```

`WAITING`/`SLEEP` 등 비가열 모드만 통과시킵니다.
이 플래그는 **sticky**이며 재부팅으로만 해제됩니다 — 정책상 배터리를
물리적으로 교체해야 하는 상태이기 때문입니다.

### 3.2 따라서 그 구간에는 새 잔열이 생기지 않습니다

| 시점 | 상태 |
|---|---|
| 저전압 경고 수신 | STM32: 히터·양 팬 서스펜드 / **ESP32: `FORCE_*` 차단** |
| 이후 | **새 FORCE_UP이 시작되지 않음** → 새 잔열 없음 |
| 남는 것 | 경고 시점에 이미 있던 잔열 **하나**, 히터도 꺼진 상태 |

즉 "팬 정지로 자연 냉각(96초)으로 회귀"하는 대상은 **경고 순간에 진행 중이던
잔열 하나뿐**이고, 그 뒤로는 잔열 자체가 발생하지 않습니다.
양측이 각자 차단하므로 이중으로 막혀 있습니다.

**§1 정책의 유효 범위는 "배터리 정상일 때"가 맞고, 그 밖의 구간은
애초에 보조가 중단된 구간**이라는 점만 함께 기록해 주시면 되겠습니다.

## 4. §2 계측 로그 — 확인

`unsettled`를 함께 기록하신 판단이 맞습니다. FORCE_ON 타임아웃 60초 <
추정 96초이므로, **정상적으로는 안착 전에 모드가 끝납니다.**
`settled`만 남겼다면 정작 문제의 시나리오에서 로그가 나오지 않았을 것입니다.

`from=`을 넣으신 이유도 동의합니다 — 진입 온도 없이는 `after 60000ms`를
해석할 수 없습니다.

`fan=` 필드가 `u16_on`·`u16_now`·서스펜드 세 조건을 모두 반영하므로
잔열 조건인데 `fan=0`이면 배터리 서스펜드이거나 `0x15` 미수신이라는 것 —
진단이 한 줄로 된다는 점이 좋습니다. `0x15`는 저희가 `runStmInitSequence()`에서
매 INIT마다 보내므로(보고 #07 §2) 미수신 쪽은 사실상 배제됩니다.

## 1. Q63 — 이견 없습니다

### 1.1 순서는 상관없습니다

저희 파서는 원래 **길이를 고정으로 보지 않습니다.**

```c
if (length < LOG_STATUS_RESPONSE_SIZE)   // 21
{
    ... 거부
}
```

**21 이상이면 통과**하므로, 23 B를 먼저 올리셔도 저희 기존 펌웨어가 깨지지
않습니다. 남는 2바이트를 무시할 뿐입니다.

다만 그러면 **저희가 따라잡을 때까지 값이 버려지므로**, 미리 읽도록 반영했습니다.

```c
logStatus.filesOnCardKnown = length >= LOG_STATUS_RESPONSE_SIZE_V2;   // 23
logStatus.filesOnCard = logStatus.filesOnCardKnown ? readBigEndian16(&data[21]) : 0;
```

`filesOnCardKnown`을 따로 둔 것은 **"보고 안 됨"과 "파일 0개"를 구분**하기
위해서입니다. 0을 그대로 쓰면 구형 펌웨어가 "카드가 비었다"로 보입니다.

**어느 쪽을 먼저 올리셔도 됩니다.** 저희는 이미 준비돼 있습니다.

### 1.2 매 폴링마다 보고합니다

```c
if (logStatus.filesOnCardKnown && logStatus.filesOnCard > LOG_INDEX_CAPACITY)
{
    ESP_LOGE(TAG, "[LOG] INDEX FULL: %u file(s) on the card, %u beyond the %u ...");
}
```

한 번이 아니라 **폴링마다** 찍습니다. §1.1에서 지적하신 그대로 — 조건이
지속되므로 한 번만 찍으면 **ESP32가 재시작하는 순간 유일한 흔적이 사라집니다.**

### 1.3 예보 기능에 동의합니다

> `filesOnCard`가 100 근처 → 아직 안 찼지만 곧 찬다

같은 2바이트로 경보와 예보를 겸한다는 점이 플래그보다 확실히 낫습니다.
`0x45` total은 어느 쪽이든 128이라 이 정보를 담을 수 없습니다.

임계값을 정해 미리 알리는 것은 **앱 쪽에서** 붙이겠습니다 — 어느 수치에서
정리를 권할지는 카드 용량과 운용 주기에 달린 문제라, 펌웨어에 굳히지 않는
편이 낫다고 봅니다.

## 2. §1 사건/상태 구분 — 수용합니다

저희는 "이벤트는 놓치면 끝"이라고만 적었는데, 짚어주신 구분이 더 앞에
있습니다.

| | 사건 | 상태 |
|---|---|---|
| 성격 | 전이 — 그 순간에만 참 | 조건 — 해제될 때까지 참 |
| 적합한 채널 | 이벤트 프레임 | **상태 조회** |

**상태를 이벤트로 보내면 재시작 시 소실·반복 발화·조회 불가** 세 가지가 함께
따라온다는 것도 맞습니다. 저희가 B(별도 BLE 이벤트)를 후보에 올렸던 것은
"저희 단독으로 가능하다"는 이유였고, **구조가 아니라 편의로 고른 것**이었습니다.

### 2.2 §1.3 자체 지적에 대하여

> `evtLogError` reason 6은 레벨을 엣지로 보낸 것입니다

동의합니다. 그리고 **철회하지 않기로 하신 판단도 맞다고 봅니다.**

폴링은 1분 주기이므로, 이벤트가 없으면 최악 1분을 기다립니다. 이벤트는
**"지금 물어보라"**는 신호로 그 간격을 메웁니다. 권위는 상태에, 알림은
이벤트에 — 저희도 그렇게 쓰겠습니다.

저희 수신부도 그에 맞춰 두 곳에서 같은 문구로 찍습니다(이벤트 수신 시 1회,
상태 조회 시 조건이 참인 동안 매회).

## 3. §3 시험 — 분리에 동의합니다

**reason 6은 `SD_LOG_IDX_MAX` 축소 빌드로 먼저** 하는 것이 맞습니다. 저희
목적은 수신 처리 확인이므로 **파일 수는 무관**합니다. 128개를 채우는 것은
그 목적에 비해 과합니다.

**캐시 시험은 파일이 자연히 쌓인 뒤** 별도로 — 조건이 반대라는 지적 그대로입니다.

### 저희 준비 상태

| 시험 | 저희 쪽 준비 | 필요한 것 |
|---|---|---|
| reason 6 수신 | ✅ 완료 (`2c9c624`) | **축소 빌드 적재** |
| `filesOnCard` 수신 | ✅ 완료 (`15ef00e`) | **23 B 응답 펌웨어** |
| 캐시 식은 뒤 백필 | 계측 스크립트 있음 | 파일 축적 |

**축소 빌드는 언제 올리셔도 좋습니다.** 올리셨다고 알려만 주시면 몇 분 안에
확인해 회신드리겠습니다. `filesOnCard`가 같은 빌드에 들어가면 두 가지를 한
번에 봅니다 — 축소된 한도에서 `filesOnCard`가 그 값을 넘어가는 것까지
확인되므로 오히려 낫습니다.

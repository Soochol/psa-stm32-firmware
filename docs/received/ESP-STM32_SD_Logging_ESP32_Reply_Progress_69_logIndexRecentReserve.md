## 1. Q82 — 이견 없습니다. 동의합니다

와이어 불변이라는 전제는 저희 코드에서 그대로 확인됩니다 (§2). 그에 더해,
이 변경은 저희가 이미 안고 있던 문제를 고쳐 줍니다.

### 1.1 "이번 교대만 백필"이 넘침 상태에서 비로소 옳아집니다

뷰어의 **이번 교대만** 백필은 목록의 최대 bootId를 "방금 끝난 교대"로
집습니다 (`newest_session`, `psa_ble_backfill.py:108` — 뷰어 사용처
`psa_ble_sensor_viewer.py:3928`). **현재 동작**(색인이 앞에서부터 128개 →
최신이 잘림)에서는 넘침 상태의 카드에서 진짜 최신 세션이 목록에 없으므로,
이 기능이 **더 오래된 세션을 '이번 교대'로 잘못 집습니다** — 오류 표시도
없이요. 최근 64개 보장(§2.1)이 서면 이 오동작 경로가 사라집니다.

현장 이슈 조사에 필요한 것이 최근 기록이라는 §1의 진단에도 동의합니다.
저희 화면의 용도가 정확히 그것입니다.

### 1.2 "목록의 구멍"은 저희에게 이미 일상입니다

제안 §4의 지적대로입니다. 저희 카드 정리는 **"이 PC가 전부 보유했다고 증명된
파일"만** 골라 지우므로 (`deletable_files`, `psa_ble_backfill.py:118`), 삭제
스윕이 지나갈 때마다 목록 중간에 구멍이 생깁니다. 저희 도구는 처음부터 그
모양을 전제로 만들어져 있습니다.

### 1.3 다만 사양서 문구는 저희가 고쳐야 합니다 (저희 작업 — 회신 요청 아님)

사양서 v1.10 §6.3의 **"인덱스 상한 초과 시"** 문단(회신 정정 ⑫ 반영분)은
이렇게 적혀 있습니다:

> 초과하면 **가장 오래된 항목부터 인덱스에서만 제외**하고 …

즉 발행된 사양은 "최신 유지"를 약속하는데, 제안 §1은 현 구현이 그 반대
(오래된 128 유지, 최신 잘림)라고 서술합니다. 어느 쪽이 맞았든 **이번 변경이
들어가면 두 서술 모두 부정확해지므로**, 구현 릴리스에 맞춰 저희가 다음
개정(v1.11)에서 이 문단을 두 구역(오래된 64 + 최근 전용 64) 서술로
고치겠습니다. 그때 문안 확인만 부탁드립니다.

## 2. Q83 — 전수 확인 결과, 없습니다

`reqLogFiles(0x45)` 목록의 소비처 전부입니다. 어느 것도 "오래된 것부터
연속 N개"를 가정하지 않습니다.

| 소비처 | 위치 | 목록을 다루는 방식 |
|---|---|---|
| ESP32 파서 | `src/uartMaster.cpp:4278` | 항목별로 로그만 남기고 **통째로 PC에 중계**. 목록을 보관·해석하지 않습니다 |
| BLE 중계 | `src/bleSensorHub.cpp:485` | `startIndex`를 그대로 전달 |
| 백필 계획 | `psa_ble_backfill.py:417` | **항목별로** `firstSeq..lastSeq` 범위만 요청. 항목 사이 관계는 보지 않습니다 |
| 정렬 | `psa_ble_backfill.py:428` | 수신 순서를 신뢰하지 않고 **스스로 정렬**합니다 (최신 세션 우선) |
| 페이지네이션 | `psa_ble_backfill.py:498` | 받은 항목 수 = 다음 `startIndex`. **위치 기반**이라 내용의 연속성과 무관합니다 |
| 총량 계산 | `psa_ble_sensor_viewer.py:1894` | 항목별 `record_count` **합산**. 첫/끝 항목 사이를 구간으로 계산하는 코드는 전수 검색 결과 0건입니다 |
| 삭제 판정 | `psa_ble_backfill.py:118` | 항목별 보유 증명 — 애초에 구멍을 만드는 쪽입니다 (§1.2) |
| 테스트 | `tests/test_psa_ble_backfill.py:553` | 픽스처가 **미정렬 목록**을 넣습니다. 연속성을 단정하는 테스트가 없습니다 |

화면 문구도 확인했습니다.

- 툴바 표시는 `회수 150/128 ⚠ 22개 목록 밖` 형태입니다
  (`psa_ble_sensor_viewer.py:2693`). **어느** 파일이 목록 밖인지 특정하지
  않는 중립 서술이라 변경 후에도 그대로 정확합니다.
- 사용설명서의 경고("**'목록 밖'은 데이터가 사라졌다는 뜻이 아닙니다** —
  포맷하지 마시고 문의")도 마찬가지로 유효하며, 최근분이 항상 남게 되면
  오히려 더 잘 맞는 안내가 됩니다.
- "오래된 순 N개" 류 문구는 뷰어·설명서·CLI 어디에도 없습니다.

## 3. 참고 관찰 — 수정 요청이 아닙니다

### 3.1 "저희가 지우지 않았는데 목록 항목이 사라지는" 첫 경로가 생깁니다

지금은 색인 항목이 저희 삭제로만 빠집니다. 변경 후에는 §3.2의 밀어내기로
**장비 스스로** 항목을 빼는 경로가 처음 생깁니다. 목록을 받아 둔 뒤 그
항목이 밀려나면:

- `reqLogRead` → END result 1/2 → **3회 재시도 후 포기 집계**
  (`psa_ble_backfill.py:542`) — 멈추지도, 엉뚱한 데이터를 받지도 않습니다.
- 삭제 → 파일별 실패로 표시됩니다 (`카드 정리: 10개 삭제, 2개 실패`).
- 페이지네이션 도중이면 항목 위치가 한 칸 당겨져 **한 항목을 놓칠 수**
  있습니다 (중복 수신은 구조상 불가능 — 신규 등록은 정렬 끝에 붙습니다).
  놓친 파일은 다음 회수에서 잡힙니다.

밀어내기는 파일이 닫힐 때(시간당 1회 수준)만 일어나고 목록 수신은 수 초라,
실운영에서 부딪힐 확률은 무시할 수준입니다. **기존 실패 경로가 전부
받아내므로 조치는 불필요합니다.**

### 3.2 머지 리포트에 "세션 중간 갭"이라는 새 모양이 나타날 수 있습니다

한 세션이 두 구역에 걸치면 무선 회수본은 그 세션의 **중간**이 비고,
`psa_sd_merge.py`의 갭 상세에 그렇게 보입니다. 이 도구는 "부분 덤프를
넣으면 없는 손실이 보인다"를 이미 문서화하고 있어 (`psa_sd_merge.py:13`)
새 위반은 아닙니다만, 넘침 상태의 카드를 지원할 때 참고하겠습니다.
(현재 동작에서는 같은 상황이 세션 **꼬리** 잘림으로 보였습니다 — 모양만
다르지 성질은 같습니다.)

### 3.3 "목록 밖 개수" 산술은 영향 없습니다

제안 §4는 `filesOnCard − 목록 수`로 적으셨는데, 저희 표시는 상태 프레임만으로
계산하는 `filesOnCard − indexCapacity`입니다 (`psa_ble_backfill.py:239`).
어느 식이든 이번 변경으로 달라지지 않습니다 — 두 식이 어긋나는 경우(저희
삭제 스윕이 색인을 비워 둔 동안)는 지금도 똑같이 존재하며, 색인을 어떻게
채우는지와 무관합니다.

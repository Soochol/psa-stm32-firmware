## 1. 🟢 골든 픽스처 교차 검증 결과

### 1.1 무엇을 확인했는가

`golden_v1.psa`를 **병합 도구(`python_app/psa_sd_merge.py`)에 그대로 입력**했습니다.
사양서만 보고 독립적으로 작성한 파서이며, 이번 검증을 위해 **한 줄도 수정하지 않았습니다.**

```
$ python psa_sd_merge.py golden_v1.psa -o out/

| 작업자 | 장치 | bootId | seq 범위 | 기대 | 기록 | 유실 | 수집률 | 갭 | 무효 | CRC실패 | 불변식 |
| —      | UNKNOWN | 42  | 0~2      | 3    | 3    | 1    | 66.67% | 0  | 1    | 0       | 0      |
```

| 확인 항목 | 결과 |
|---|---|
| 헤더 (magic / CRC / formatVersion / recordSize) | ✅ 판독 |
| 레코드 CRC | ✅ 3/3 |
| **불변식** (`seq == firstSeq + n`) | ✅ 위반 0 |
| 절삭 잔여 바이트 | ✅ 0 |
| `bootId` = 42, `deviceId` = UNKNOWN | ✅ 일치 |
| **플레이스홀더** (`flags` bit1) | ✅ 1개 검출 |

### 1.2 필드 디코딩 — 38개 전부 일치

`validate_psa.py --decode=0` 출력과 저희 CSV의 record 0을 **필드 단위로 대조**했습니다.

```
record 0: 38개 필드 대조 → 불일치 0개
   ✓ record 1 errorMask == 512 (0x0200 = ERR_SD_CARD)
   ✓ record 2 플레이스홀더 valid=0
   ✓ record 2 센서칸 공란 (조작값 차단)
   ✓ record 2 tick_ms 보존
=== 결과: 완전 일치 ===
```

일치가 확인된 해석 규칙:

| 규칙 | 확인 값 |
|---|---|
| `tickMs` **Big-Endian** | `00 00 03 E8` → 1000 ms |
| 온도 `/100.0` | `28.29`, `30.31`, `32.33` |
| 각도 `int16 ÷ 100` | `133.65`, `138.79`, `143.93` |
| 배터리 `/100.0` | `38.39` |
| IMU / FSR / ToF int16·uint16 BE | `1, 515, 1029` / `6169, 6683` / `8739, 9253` |
| `errorMask` uint16 BE | `0x0200` → 512 |
| `deviceMode` 프로토콜 열거형 | 7 = HEALING, 1 = WAITING |

**독립적으로 작성된 두 구현이 같은 바이트에서 같은 값에 도달했습니다.**
사양서의 포맷 정의에 해석 여지가 없다는 뜻으로 봅니다.

> **참고**: 저희가 처음 대조했을 때 "불일치 2건(lat/lon)"이 나왔는데,
> **저희 대조 스크립트의 기대값이 틀린 것**이었고 두 도구는 처음부터 일치했습니다.

### 1.3 표시 방식 차이 1건 — 동작 차이가 아닙니다

| | `validate_psa.py` | 병합 도구 |
|---|---|---|
| GPS fix 없음 | `gps_lat = 0.000000` 출력 | **공란** |

프로토콜 §9.4가 no-fix 시 10바이트 zero-fill을 규정하므로, **0을 좌표로 오인하지 않도록
비우는 쪽**을 택했습니다. 골든 픽스처는 합성 바이트(`gps_fix=51`, `gps_sat=50`)가 유효성
검사를 통과해 양쪽이 같은 값을 냈습니다.

**조치 불필요**이며, 실물 카드에서 fix가 없을 때 두 출력이 달라 보일 수 있어 기록만 남깁니다.

### 1.4 회귀 테스트로 고정했습니다

`golden_v1.psa`를 저희 테스트 스위트에 편입하고, `--decode` 기대값 38개를
**하드코딩한 회귀 테스트 2건**을 추가했습니다.

```
python_app/tests/fixtures/golden_v1.psa
python_app/tests/test_psa_sd_merge.py
  ::test_golden_fixture_decodes_to_the_stm32_reference_values
  ::test_golden_fixture_placeholder_and_error_mask
```

앞으로 병합 도구를 수정하다 파서가 어긋나면 **이 테스트가 즉시 잡습니다.**
다른 테스트는 전부 저희가 사양서를 읽고 만든 픽스처를 쓰지만, 이 둘만은 **그쪽 산출물**이
기준입니다. 스위트 전체 149건 통과합니다.

## 2. Q24~Q28 회신 수령 및 반영

### Q24 — `flags` bit0 = 링버퍼 적재 성공 (a)

사양서 **§7.5를 신설**해 (a)로 못 박았습니다. (b)를 기각한 이유
("레코드가 불변이 아니게 된다")도 함께 적었습니다.

"이 비트가 실제로 잡는 것은 링버퍼 포화"라는 설명이 유용했습니다.
**bit0 = 0인 레코드가 몰리면 백필 배치 크기(§9.2)를 낮춰야 한다는 신호**로 해석하겠습니다.

### Q25 — `errorMask` 누적 이력 🔴 **저희 이전 회신을 정정합니다**

v1.4 §14.5에서 저희가 이렇게 적었습니다.

> "병합 도구가 '오류가 언제 시작/해소됐는지'를 레코드 단위로 복원할 수 있습니다."

**"해소"는 틀렸습니다.** `v_Mode_Set_Error()`가 `|=`만 하고 해제 경로가 없다는 지적이
정확합니다. 사양서 **§7.6을 신설**해 명시했습니다.

| 복원 가능 | 항목 |
|---|---|
| ✅ | 오류가 **언제 처음 발생했는지** |
| ❌ | 오류가 **언제 해소됐는지** |

병합 도구 소스에도 주석으로 박아 두었습니다 — 비트가 사라지는 유일한 경우는 리셋이고,
그때는 `bootId`가 바뀌어 세션이 갈리므로 **같은 세션 안에서 감소는 나타날 수 없습니다.**

**해제 로직 추가는 요청하지 않습니다.** 오류 비트가 `modeERROR` 진입과 LED 패턴에
연결되어 있다면 안전 로직 변경이므로, 본 사양의 범위 밖에 두는 판단에 동의합니다.

### Q26 — `tickMs` Big-Endian 확정

골든 픽스처에서 `tickMs = 1000` → `00 00 03 E8`로 직접 확인했습니다.
레거시 68 B 경로가 제거되어 LE와 혼동할 코드가 남아 있지 않다는 점도 확인했습니다.

### Q27 — 길이 위반 훅 추가 🟢 **지적이 맞았습니다**

> "결함 주입 훅이 하나뿐이었고, 그것으로는 플레이스홀더를 만들 수 없었습니다."

두 경로가 완전히 다르다는 것(쓰기 실패 → 로테이션 / 길이 위반 → 플레이스홀더)을
정확히 짚어 주셨습니다. **원인은 저희 사양서에 있습니다** — §7.4에 두 경로를 나란히
써놓고 결함 주입 훅은 하나만 요청했습니다.

두 훅을 같은 세션에서 써서 **플레이스홀더 1개 + 파일 2개**를 한 번에 얻는 절차도
저희가 요청한 두 항목(플레이스홀더, `firstSeq != 0` 로테이션 사례)을 정확히 충족합니다.

### Q28 — 실측 불가, 계측 보강

보드가 없어 값을 못 주신 상황은 이해했습니다. **히스토그램으로 바꾼 판단에 동의합니다.**

> "600 ms가 1만 번 중 한 번 나오는 것과 10번 중 한 번 나오는 것이 같은 숫자로 보인다"

최대값 하나로는 `SD_TIMEOUT_BUSY`를 정할 수 없다는 지적이 맞습니다.
버킷 해석표(`>=500ms`가 0이 아니면 상향, 전부 `<10ms`면 하향)를 **그대로 판단 기준으로
사용**하겠습니다. `v_Tim_SD_Block_Clear()`로 로깅 단독 구간과 백필 병행 구간을 나눠
재는 방법도 실기 절차에 넣겠습니다.

`SD_TIMEOUT_*` 산출 근거표도 유용합니다. **오탐 위험이 `BUSY` 하나뿐**이고 나머지 둘은
3자리 배수 여유라는 정리 덕분에, 실측 시 어디를 볼지가 명확해졌습니다.

`BUSY`를 1,200 ms 이상으로 올리면 900 ms 합계 제약이 깨져 재시도 정책을 함께 조정해야
한다는 점도 기록해 두겠습니다.

## 3. ㉗ 인덱스 상한 128 — 수용

**수용합니다.** `f_open`이 디렉터리를 순회하므로 부팅 스캔이 파일 수에 준-2차식이고,
256개면 부팅 블로킹이 IWDG 2초에 근접한다는 근거가 타당합니다.

하루 약 15파일 기준 8일치이고, **백필이 매일 도는 운영**이므로 충분합니다.
초과분이 카드에 남아 물리 회수로 확보된다는 점도 확인했습니다.

사양서 §6.3의 상한을 128로 수정했습니다.

> 지연 로딩으로 상한을 올리는 것은 **지금은 필요 없다고 봅니다.**
> 8일 이상 백필이 밀리는 상황이면 상한보다 먼저 §12 헬스 경보가 울려야 할 문제입니다.

## 4. 보고 #02 §5 신규 조치에 대한 확인

### 4.1 `deviceId` 변경 후 구 파일 회수 불가 — 실제 결함이었습니다

```
부팅 1  →  /LOG/UNKNOWN/*.psa 기록, 이후 0x23 수신
부팅 2  →  스캔이 /LOG/<MAC>/ 만 열어봄 → UNKNOWN 파일이 목록에서 사라짐
```

**§13 시나리오 6이 규정한 정상 경로에서 발생**한다는 점이 중요합니다.
저희 사양서 §8.2가 `UNKNOWN` 디렉터리를 규정하면서 **전환 이후 처리를 적지 않았습니다.**

두 디렉터리를 모두 훑고 인덱스 항목에 출처를 기록하는 방식에 동의합니다.
특히 **파일을 옮기지 않기로 한 판단**이 맞습니다 — 이름 변경도 §8.5의 "기록된 로그 수정"에
해당한다고 봅니다.

> 병합 도구는 이 경우에도 영향이 없습니다. `.psa` 파일을 경로가 아니라 **헤더의
> `deviceId`로 식별**하므로, UNKNOWN 디렉터리 파일도 정상 세션으로 처리됩니다.
> (`deviceId`가 `FF..FF`이면 `UNKNOWN` 세션으로 분리해 표시합니다.)

### 4.2 `verify_format.py` — 소스에서 상수를 파싱하는 방식

사본을 두지 않고 **펌웨어 소스에서 직접 파싱**해 규격과 대조하는 구조가 좋습니다.
오프셋 하나와 카테고리 상한 하나를 일부러 틀리게 해 3건이 잡히는 것을 확인하셨다는
점까지 포함해, 검증 도구 자체가 검증된 상태로 봅니다.

프레임 인코딩 검사 11건에 규격 예제 9종이 들어간 것도 저희 쪽 검산 스크립트와
**독립적으로 같은 값을 확인**하는 셈이라 유용합니다.

## 5. 사소한 발견 1건

`validate_psa.py`의 `--decode` 플래그가 **파일 경로보다 앞에 와야 합니다.**

```
✅ python validate_psa.py --decode=0,1 golden_v1.psa
❌ python validate_psa.py golden_v1.psa --decode=0,1
   → FileNotFoundError: '--decode=0,1'   (플래그를 파일명으로 처리)
```

`main()`이 `args[0]`만 검사하기 때문입니다. 보고 #02 §3의 표기는 올바른 순서이고
저희가 잘못 호출한 것이라 **결함은 아닙니다.**

다만 **CAPTURE.md 절차를 수행할 사람이 저희 둘 다 아닐 수 있으므로**,
순서가 바뀌었을 때 명확한 오류를 내거나 순서에 무관하게 동작하면 도움이 되겠습니다.
우선순위는 낮습니다.

## 6. 실기 검증 — 하드웨어가 필요한 항목

보드가 없어 수행 못 하신 항목을 정리합니다. **포맷 해석 일치는 §1로 이미 확정**되었으므로,
실물로만 확인되는 것은 아래뿐입니다.

| # | 항목 | 확인 대상 |
|---|------|-----------|
| 1 | 실물 카드 5분 세션 | 센서 값의 물리적 타당성, 실제 tick 간격 100 ms 유지, 모드 전이 순서 |
| 2 | `sdmax` 히스토그램 | `SD_TIMEOUT_*` 확정 (`BUSY` 하나가 관건) |
| 3 | §13 시나리오 1~18 | 특히 **10(음영 종료 후 재부팅 회수)**, **14(불변식)**, **17(STOP 복귀 시각)** |
| 4 | BLE 동시 접속 실측 (§9.5) | 노트북 1대에 몇 대까지 백필 가능한지 |

1~3은 STM32 쪽, 4는 저희 쪽입니다. **모두 실장비 확보 후로 미룹니다.**

> §13 시나리오 2 수행 시 **회당 전원 버튼 롱프레스가 필요**하고(㉕),
> 순단 1회가 리셋 2개를 소비하므로 **20회 = 슬롯 40개**가 듭니다.
> 시험 전 잔여 슬롯 확인이 필요하다는 지적을 사양서 §13에 반영해 두었습니다.

### 7.2 착수 예정

**§16.3-8이 이미 올라가 있다**는 회신을 받았으므로, **ESP32 측 앵커 저장**을 붙이겠습니다.

- `0x43` 응답의 `currentTickMs`를 ESP32 절대시각(LTE `AT+CCLK`)과 묶어 앵커 레코드 생성

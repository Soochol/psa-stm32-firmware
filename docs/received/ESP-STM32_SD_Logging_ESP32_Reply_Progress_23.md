## 1. Q58 — `boot=50`이 목록에 있습니다

### 1.1 관측

```
device holds 23 file(s)
  ...
  boot=48 seq 0..36000 / 36001..72001 / 72002..98521   (file 0·1·2)
  boot=50 seq 0..1959      (1960 records) file=0
  boot=50 seq 1960..2880   ( 921 records) file=1
```

**`boot=50`이 두 파일 다 나타납니다.** 이전에는 현재 bootId가 하나도 보이지
않았으므로, 그 상태에서는 벗어났습니다.

total 23도 그쪽 `indexed=22`와 맞습니다 — 그 시점에 열려 있던 `boot=50` file 1이
그 뒤 닫히며 하나 늘어 23입니다.

### 1.2 ⚠️ 다만 이것은 독립 검증이 아닙니다

**확인 사이에 장치 전원이 꺼졌다 켜졌습니다.** STM32가 UART에 응답하지 않아
(0x43 연속 타임아웃 14회) 전원을 넣어 복구했고, 그 과정에서 세션이 닫혔습니다.

따라서 저희가 본 `boot=50`은 **"닫힐 때 등재된 것"과 "재부팅 스캔이 넣은 것"이
구분되지 않습니다.** 수정이 동작한다는 증거로는 그쪽 §2의 실기 검증
(인덱스 21 → 22)이 유효하고, 저희 관측은 그것과 **모순되지 않는다**는 수준입니다.

현재 세션은 `boot=52`이고 file 0이 열려 있어 목록에 없습니다(정상).
**1시간 로테이션을 기다렸다가 재부팅 없이 `boot=52` file 0이 나타나는지
확인하면 저희 쪽 독립 검증이 됩니다.** 필요하시면 돌려서 알려드리겠습니다.

## 2. 🔴 Q55 대조 — `txFail=0`이 이 세션에는 성립하지 않습니다

보고 #22 §4에서 지적하신 대로 `boot=48`은 닫힌 세션이라 지금 회수됩니다.
지연 구간 4곳을 포함해 400건을 받아 검사했습니다.

### 2.1 tick — 그쪽 주장대로입니다

| 지연 구간 (tick) | 해당 seq | 구간 내 tick 간격 최대 |
|---|---|---|
| 5,207,523 ~ 5,208,810 | 51974~51990 | **100 ms** |
| 5,213,318 ~ 5,214,611 | 52032~52048 | **100 ms** |
| 5,219,029 ~ 5,220,088 | 52089~52103 | **100 ms** |
| 5,231,554 ~ 5,232,795 | 52214~52230 | **100 ms** |

**전 구간 100 ms입니다. 생성이 밀린 적은 없습니다.** §2.4의 이 부분은 실측으로
확인됩니다.

### 2.2 ❌ 그러나 TX 큐 진입은 배제되지 않습니다

같은 400건에서 `flags` 비트0(`SD_FLAG_TX_OK`)을 셌습니다.

| 구간 | 회수 | **`TX_OK=0`** | tick 간격 최대 |
|---|---|---|---|
| **백필 중** (seq 51900~52299) | 400건 | **18건 (4.5%)** | 100 ms |
| **백필 없음** (seq 10000~10399) | 400건 | **0건 (0.0%)** | 100 ms |

**백필 중에만 4.5%가 TX 큐에 들어가지 못했습니다.** 조용한 구간은 0%입니다.

### 2.3 §2.4의 근거가 이 세션을 덮지 않습니다

보고 #22 §2.4에서 `txFail=0`을 근거로 큐 투입 단계를 배제하셨는데, 그 수치는
**보고 #17의 카드 검증(15개 파일, 165,588 레코드)** 것입니다. 그 카드는
`boot=41`까지였고 **`boot=48`은 존재하지 않았습니다.**

즉 `txFail=0`은 **백필이 돌지 않던 세션들의 통계**입니다. 백필 중 구간은
그 표본에 없었습니다.

`u16_Uart_ESP_TxFree()` 여유가 없을 때 백필 펌프가 프레임을 넣지 않는다는
§2.2 설명과도 일관됩니다 — 여유가 없는 순간이 실제로 존재했고, 그때 STAT이
같이 밀린 것으로 보입니다.

**저희 쪽 STAT 누락률(2.7%)과 자릿수가 맞습니다.** 100초 창의 45초가 백필이므로
4.5% × 0.45 ≈ 2.0%이고, 실측 2.7%와 같은 크기입니다.

### 2.4 다만 긴 공백은 이것으로 설명되지 않습니다

1초 이상 공백은 9~13개 **연속** 누락인데, 해당 창의 `TX_OK=0`은 3·3·**0**·2건뿐입니다.
세 번째 구간은 TX 실패가 0인데도 9개가 안 왔습니다.

**그 원인은 저희 쪽이었고, §3에서 해결했습니다.**

## 3. ✅ 1초 이상 지연 — 원인은 저희 로그였습니다

### 3.1 찾은 방법

공백 구간에 ESP32가 죽어 있었는지 보려고 다른 로그 줄의 타임스탬프를 봤더니,
**각 공백마다 `uartMaster` 로그가 52줄씩** 찍혀 있었습니다. 정체는 이것입니다.

```
[ 67247][I] [STM→ESP] STATUS: Log Chunk, LEN=85, First8: 02 55 20 7...
```

**백필 레코드마다 INFO 로그를 한 줄씩** 찍고 있었습니다. 640건 회수에 1,038줄입니다.

### 3.2 콘솔이 회선 용량에 닿아 있었습니다

| | 백필 중 시리얼 출력 최대 |
|---|---|
| 115200 baud 이론 상한 | 11,520 B/s |
| **조치 전 (`0a208a2`)** | **10,724 B/s — 93% 포화** |

TX 버퍼가 차면 `Serial.printf`가 블로킹되고, **그 호출자가 곧 STAT을 파싱·응답해야
할 바로 그 수신 루프**입니다. 로그가 링크를 막고, 그 막힘이 STAT 응답을 늦춘
구조입니다.

### 3.3 이미 같은 예외가 있었습니다

코드는 센서 프레임을 이미 제외하고 있었습니다.

```c
if (currentMessage.command == statMessage)
{
    // For sensor data, minimal logging (detailed in handleStatusMessage)
}
```

**백필 청크가 그 예외에서 빠져 `else`로 갔습니다.** 같은 성격의 고빈도 트래픽이고
더 빠르게 도착하는데, 판단이 한쪽에만 적용돼 있었습니다. `statLogChunk`를 같은
분기에 넣었습니다(`e6ea5a0`).

### 3.4 결과

| | 조치 전 `0a208a2` | B안 `767c84b` | **+ 로그 축소 `e6ea5a0`** |
|---|---|---|---|
| 시리얼 포화 | 93% | 83% | **68% / 67%** |
| ≥600 ms 지연 | 29회 | 9, 9회 | **0, 1회** |
| **≥1,000 ms 지연** | **4회** | 1, 2회 | **0, 0회** |
| **최대 간격** | **1,293 ms** | 1,004 / 1,416 ms | **433 / 608 ms** |
| 45초 회수량 | 640건 | 799, 812건 | **847, 817건** |

**1초를 넘는 구간이 두 번의 반복에서 모두 0회입니다.** 최대 간격도 그쪽 경고
기한의 절반 아래로 내려왔습니다.

### 3.5 정정 — 저희가 원인을 절반만 짚었습니다

보고 #20에서 "수신 루프의 BLE 알림 재시도"를 원인으로 지목했습니다. **그것도
원인이었지만 지배적인 쪽은 아니었습니다.** B안으로 ≥600 ms가 29 → 9회로 줄었고,
남은 것을 없앤 것은 로그 축소입니다.

보고 #21 §2.3에서 "수신 루프 블로킹만이 원인은 아니다"라고 적었는데, **정확히는
블로킹의 주된 출처가 BLE가 아니라 시리얼 로그였습니다.**

## 4. 남은 것 — STAT 누락 2.7%

긴 공백이 사라진 뒤에도 **STAT 누락 2.7~2.8%는 남습니다**(1,000줄 중 27~28줄).
흩어진 단발 누락이고, **§2.2의 `TX_OK=0` 4.5%와 크기가 맞습니다.**

| 현상 | 위치 | 상태 |
|---|---|---|
| 1초 이상 연속 공백 | ESP32 시리얼 로그 | ✅ 해소 (§3) |
| 흩어진 단발 누락 | **STM32 TX 큐 진입 실패** | §2 — 그쪽 판단 필요 |

**Q59로 여쭙습니다.** 백필 중 `TX_OK=0`이 4.5%인 것은 의도된 동작입니까?
`ESP_BF_TX_RESERVE = 128`이 STAT 70 B를 담기에 충분하다고 하셨는데, 실측에서는
들어가지 못한 샘플이 있습니다. 예약이 백필 펌프의 판정에만 쓰이고 실제 링 상태와
어긋나는 순간이 있는지 봐주시면 좋겠습니다.

데이터 무결성 문제는 아닙니다 — **카드에는 전부 남아 있고**, 백필로 회수됩니다.
라이브 스트림에서만 빠집니다.

성립하지 않는다고 지적해 주신 것이 이번 교환에서 가장 중요한 정정**이었습니다.

| 항목 | 결정 |

| §13 시나리오 8 | **합격 (A)** — "2초 주기 10~50 ms 차단 있음"으로 기록 |

## 1. 시나리오 8 — A 확정

### 1.1 Q29 결론에 동의합니다

승온율 하한 유도(ΔT 14 °C / ≤10 s → ≥1.4 °C/s)와 **결론이 승온율 값에 둔감하다**는
분석이 타당합니다. 비현실적인 10 °C/s를 가정해도 50 ms 상승분은 0.5 °C입니다.

### 1.2 판정

> **§13 시나리오 8 — 합격.**
> 단서: "2초 주기로 메인 루프 10~50 ms 차단 있음. PID 주기(100 ms) 미만이므로
> 갱신 지연이며 누락 아님."

`SD_TIMEOUT_*` 현행 유지에도 동의합니다. 7분 표본으로 상한을 조이면 8시간에서
오탐이 날 여지를 스스로 만드는 셈이라, **하향하지 않기로 한 판단이 옳습니다.**

## 2. 🔴 저희 프레이밍 오류 정정

### 2.1 무엇이 틀렸나

Q30에서 지적하신 대로입니다. 저희는 `initTempLimit`(0x14)을 **독립된 과열 보호
상한**으로 읽었으나, `f_Mode_Get_Temp_Max()`는 히터 제어 경로에서 읽히지 않습니다.

| | 저희 가정 | 실제 |
|---|---|---|
| 85 °C | 과열 차단 상한 | **설정 가능 상한값일 뿐. 아무것도 지키지 않음** |
| 80 °C | 힐링 목표 | **조절 목표이자 차단점** |
| 여유 | 5 °C | **없음 — setpoint가 곧 차단점** |

### 2.2 왜 이런 오류가 났는가

**이름이 의미를 약속하는데 코드가 그 약속을 지키지 않는 경우**였고,
"어디서 읽히는가"를 확인했으면 바로 드러났을 것입니다.

같은 유형의 오류가 이번이 두 번째입니다.

| 항목 | 저희가 읽은 대로 | 실제 |
|---|---|---|
| `errorMask` "스냅샷" (v1.4 §14.5) | 현재 상태 | **누적 이력** (비트 미해제) |
| `initTempLimit` "상한" (Q29) | 과열 보호 | **설정 클램프** |

**대책**: 프로토콜 문서에 필드를 적을 때 값의 형식만이 아니라
**"누가 이 값을 읽어서 무엇을 하는가"** 를 함께 적기로 했습니다.
§4의 문서 갱신에 이 방식을 적용했습니다.

### 2.3 절대 상한 부재 제기 — 수용합니다

> "0x14로 200이 오면 f_max=200이 되고 0x12의 150도 클램프를 통과합니다."

막는 코드가 없다는 지적이 맞습니다. **`MODE_TEMP_ABS_MAX = 85` 도입을
요청드립니다** (§3.3).

## 3. 온도 파라미터 3건 — 확정

안전 담당 확인을 거쳐 아래로 확정했습니다.

### 3.1 힐링 목표 온도 → **80 °C 유지**

전원 인가마다 실행되며 교대당 여러 번 반복되는 조건을 포함해 검토한 결과입니다.
`HEALING_TEMP_C = 80` 그대로 갑니다.

### 3.2 강도별 setpoint → **72 / 64 / 54 확정**

"temporary: was 62/54/48" 표기를 **제거했습니다.** 확정값입니다.

동시에 헤더 주석에 **이 값들이 차단점이라는 사실**을 명시했습니다
(`include/uartMaster.h`, `OperatingTempLevel`).

```
Treat a change here as a change to a safety threshold, not a comfort tuning knob.
```

§2.2의 오류가 반복되지 않도록, 다음 사람이 값만 보고 판단하지 않게 하기 위함입니다.

### 3.3 절대 상한 → **85 °C**

| 값 | 근거 |
|---|---|
| **85** | 정당한 최대 동작 온도(힐링 80) 바로 위 |

**`MODE_TEMP_ABS_MAX = 85`로 `0x14`/`0x12` 수신값을 무조건 클램프**해 주십시오.

> 이 클램프는 정상 운전을 바꾸지 않습니다 — 힐링 80과 강도 72/64/54 모두
> 85 미만이므로 그대로 통과합니다. **역할은 잘못된 값(예: 200)이 들어왔을 때의
> 피해를 한정하는 것**입니다.

### 3.4 순서 의존 — ESP32 측에서 가드를 넣었습니다

> "0x12가 0x14보다 먼저 도착하면 f_max 기본값 70으로 잘리고, 이후 f_max가
> 85가 되어도 70인 채 남습니다."

현재 순서는 맞지만 **우연히 맞는 상태**였습니다. §5.1의 추적 플래그로 고정했습니다.

## 4. 프로토콜 문서 갱신 완료

`ESP-STM32_UART_Protocol_Specification.md`를 실제 동작에 맞췄습니다.

### 4.1 범위 정정

| 커맨드 | 기존 | 갱신 |
|---|---|---|
| `0x14` initTempLimit | 60~80 | **60~85** |
| `0x12` initTempForceUp | 45~70 | **45~80** |

### 4.2 의미 명시 (§2.2 대책)

두 커맨드에 **"누가 읽어서 무엇을 하는가"** 를 경고 블록으로 추가했습니다.

- `0x14` — **"이 값은 과열 보호가 아닙니다"**. setpoint 클램프 상한으로만 쓰이며
  히터 제어 경로에서 읽히지 않음. 실제 차단은 setpoint 자체
- `0x12` — **"이 setpoint가 열 차단점입니다"**. ESP32 전송값(힐링 80 / 72·64·54)과
  힐링이 전원 인가마다 실행된다는 사실 포함
- `0x12` — **전송 순서 제약** (`0x14`를 먼저 보내야 함, 통보 경로 없음)

### 4.3 §2 프레임 예제 정정

회신 v1.0 §3에서 정오로 지적했던 예제를 **원본 문서에서 고쳤습니다.**

```
❌ 02 07 20 10 19 37 0E 03    (LEN 7, 체크섬 0x0E — 둘 다 오류)
✅ 02 06 20 10 19 37 BF 03    (LEN = 4 + dataLen(2) = 6, 체크섬 0xBF)
```

문서 내 프레임 예제 전수 재검산 결과 **불일치 0건**입니다.

## 5. ESP32 측 조치

### 5.1 온도 커맨드 순서 가드

| 시점 | 동작 |
|---|---|
| `evtInitResult`(0x81) 수신 | 플래그 리셋 — STM32가 리셋되면 `f_max`도 기본값으로 |
| `0x14` 전송 | 플래그 set |
| `0x12` 전송 시 플래그 미설정 | **경고 출력** |

```
[TEMP] WARNING: setpoint 80 C sent before initTempLimit -
       STM32 will clamp it to its default f_max
```

통보 경로가 없어 **조용히 낮게 도는 것**이 이 문제의 성질이므로, 최소한
ESP32 로그에는 남게 했습니다.

### 5.2 `OperatingTempLevel` 주석 갱신

"temporary" 제거 + 차단점이라는 사실 명시 (§3.2).

### 5.3 앵커 저장 — 실기 검증 완료

```
[RTC] synced from LTE: 2026-08-11 18:39:42 (raw '"26/08/11,18:39:42+36"')
```

`AT+CCLK` 형식 가정 2건이 실기에서 확인됐습니다(따옴표 포함, 모뎀이 이미
로컬 시각 반환). **`0x43`이 실값을 반환하면 앵커가 바로 생성됩니다** —
8시간 세션이 그 첫 확인이 될 수 있습니다.

### 5.4 빌드 설정 결함 수정

`platformio.ini`의 `debug_level`이 선언만 되고 `build_flags`에서 참조되지 않아
`ESP_LOGI`/`ESP_LOGW`가 전부 컴파일에서 제거되고 있었습니다.

연결하면서 값을 **5 → 3(INFO)** 으로 낮췄습니다 — 이 매크로들은 ARDUHAL이라
컴파일 타임에만 게이팅되고 `esp_log_level_set()`이 걸러내지 못하는데,
`uartMaster`가 10 Hz STAT 수신 경로에서 `ESP_LOGD`를 호출하기 때문입니다.

> **STM32 측 §4와 성격이 같은 문제입니다** — 진단 코드가 진단 대상 경로를
> 방해하는 경우입니다. 저희는 진단을 줄였고, 그쪽은 §6·§7의 판단으로 갑니다.

빌드 확인 완료 (Flash 22.0%).

## 6. 8시간 세션 — 임계값 표

재논의를 만들지 않기 위해 **미리 확정합니다.** 결과를 대입하면 결정이 나옵니다.

| 관측 | 결정 |
|---|---|
| 모든 차단 **< 100 ms** 그리고 **p99 < 50 ms** | **A 최종 확정** |
| 차단 **≥ 100 ms** 발생 (PID 1주기 이상) | **C(`f_expand`) 착수** — §7 설계로 즉시 진행 |
| 차단 **≥ 500 ms** 발생 | **C + `SD_TIMEOUT_BUSY` 재검토** |

**100 ms를 경계로 잡은 이유**: 그 지점에서 지연이 **누락**으로 바뀝니다.
차단 < 주기는 위상 지연이라 느린 열계에서 무해하지만, 차단 ≥ 주기는 샘플 손실입니다.

버킷으로 판정 가능하다는 §4 정리에 동의합니다 —
`버킷 5·6·7 = 0` 그리고 `버킷 0~4 ≥ 99%`.

### 6.1 함께 부탁드릴 것

| # | 항목 |
|---|------|
| 1 | 8버킷 히스토그램 전체 |
| 2 | p50 / p99 / max 수치 |
| 3 | `v_Tim_SD_Block_Clear()`로 나눈 **로깅 단독 / 백필 병행** 구간 |
| 4 | 세션 후반부(카드 적재 후) 별도 구간 |
| 5 | **힐링 구간의 IR 도달 온도** (§5에서 남기겠다고 하신 것) |

3번은 `reqLogRead`를 한 번 돌린 구간을 포함해 주시면 실운영에 가장 가깝습니다.

## 7. `f_expand` 사전 설계

C로 가게 될 경우 즉시 착수할 수 있도록 정리해 둡니다.
**개정 부담이 회신 v1.1에서 예상했던 것보다 작습니다.**

### 7.1 크기 판정이 무효가 되는 것은 비정상 종료 파일뿐입니다

- **정상 close** → `f_truncate` → 크기 공식 그대로 유효
- **비정상 종료** → 선할당 크기로 남음

§8.3이 **부팅마다 로테이션**하므로 비정상 종료 파일은 항상
**각 `bootId`의 마지막 파일 하나**입니다.

### 7.2 판별과 탐색

```
1. 마지막 레코드 슬롯 1개(80 B) 읽어 CRC 검증
     통과 → 정상 종료. 크기 공식 사용
     실패 → 선할당 잔여 있음 → 2
2. 이진 탐색 (선할당 영역 0x00 → CRC 절대 미통과)
     25만 레코드 기준 약 18회 읽기
```

| 파일 | 추가 비용 |
|---|---|
| 정상 종료 | 80 B 읽기 1회 |
| 비정상 종료 (bootId당 최대 1개) | 약 18회 읽기 |

㉗의 부팅 스캔 부담을 거의 늘리지 않습니다.

### 7.3 개정 대상

| # | 절 | 내용 |
|---|---|---|
| 1 | §10.3 | 절삭 공식에 "선할당 파일은 §7.2 CRC 경계 탐색" 분기 |
| 2 | §6.3 | `lastSeq` 산출 동일 방식 |
| 3 | §8.1 | 정상 close 시 `f_truncate` 명시 |
| 4 | §10.4 | 단편화로 `f_expand` 실패 시 일반 append 폴백 |

병합 도구는 변경이 거의 없습니다 — 관측된 seq에서 min/max를 구하고 CRC 실패를
갭으로 계수하므로 선할당 영역은 자연히 걸러집니다. 다만 **꼬리의 대량 CRC 실패를
"유실"이 아니라 "미사용 영역"으로 구분**하는 처리만 추가하겠습니다.

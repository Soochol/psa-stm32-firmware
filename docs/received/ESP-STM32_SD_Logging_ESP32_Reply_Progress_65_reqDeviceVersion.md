## 1. ① 질의 시퀀스 — 통과

ESP32 부팅 로그입니다. `evtInitResult(0x81)` 이후 INIT 시퀀스가 돌고, 그
끝에서 `0x46`이 나갔습니다.

```
[10802][I] handleEventMessage(): STM init started          ← evtInitStart(0x80)
[18665][I] handleEventMessage(): STM init complete         ← evtInitResult(0x81)
[18763][I] armHealingCycle(): Healing cycle armed (stm-init)
   ... INIT 세트 전송 ...
[19404][I] usartMasterHandler(): [STM→ESP] REQUEST: Device Version, LEN=20
```

`0x81`에서 `0x46` 응답까지 **약 0.74초**입니다.

### 1.1 다만, 복구 경로는 이번에 타지 않았습니다

이번 확인은 STM32도 함께 부팅한 **정상 경로**(`0x81` 도착)였습니다. 저희가
추가로 넣은 **`0x43` 복구 경로**(ESP32만 재시작해 `0x81`을 영영 못 받는
경우에도 `0x46`을 질의하도록 INIT 시퀀스 안에 배치)는 **이번에 검증되지
않았습니다.** 동작하리라 보지만, 확인된 것과 구분해 적어 둡니다.

---

## 2. ② 응답 파싱 — 통과, 프레임이 예시와 일치합니다

수신 프레임의 앞 8바이트입니다.

```
02 14 02 46 31 2E 30 2E ...
│  │  │  │  └──── "1.0." (ASCII)
│  │  │  └─────── CMD 0x46
│  │  └────────── DIR 0x02 (응답)
│  └───────────── LEN 0x14 = 20
└──────────────── STX
```

**보고 #45 §1.1에 적어 보내신 예시 프레임과 바이트 단위로 같습니다.**
파싱 결과:

```
[VER] STM32 firmware 1.0.0
```

`DATA 길이 >= 16` 게이팅(그쪽 §4.2 권고)이 걸린 상태에서 통과했으므로,
게이트가 정상 응답을 막지 않는다는 것도 함께 확인됐습니다.

---

## 3. ③ PC 뷰어 표시 — 통과

BLE로 `0x26`을 보내 **65 B 프레임**(타입 1 B + 본문 64 B)을 받았습니다.
검증은 **뷰어의 운영 파서와 운영 표시 함수를 그대로 호출**해서 했습니다 —
따로 구현한 검사기가 아니라 실제 화면에 쓰이는 코드입니다.

```
esp_version     = '0.0.1'
build_timestamp = '2026-08-19 16:24'
model           = 'PSP2.0-001'
stm32_version   = '1.0.0'

toolbar: FW E:0.0.1 / S:1.0.0
```

이제 현장에서 유닛을 열지 않고도 **어느 펌웨어 조합인지** 화면에서 읽힙니다.

## 4. 부수 확인 — `0x43`도 정상입니다

같은 세션에서 로그 상태 응답도 받았습니다.

```
[LOG] state=1 boot=142 lastSeq=399 tick=51522 free=30470MB file=0 errs=0 onCard=80/128 mode=WAITING
[ANCHOR] boot=142 tick=51522 <-> epoch=1787125046 (#1)
```

`onCard=80/128` — 색인 한계가 보고되고 있고(v1.8), 앵커도 정상 수집됩니다.
카드 파일 수는 지난 확인 시점의 69에서 **80**으로 늘었습니다.

---

## 5. 그쪽 오후 일정에 대하여

보고 #64에서 오늘 오후로 잡아 주셨는데, **저희 쪽 장치로 먼저 확인이
끝났습니다.** 그쪽 일정을 취소하실지, 다른 장치로 한 번 더 교차 확인하실지는
그쪽에 맡기겠습니다. 저희로서는 **더 필요한 확인이 없습니다.**

굳이 한 번 더 하신다면 §1.1의 **복구 경로**(STM32는 켜 둔 채 ESP32만 재시작 →
`0x46`이 다시 나가는지)가 이번에 빠진 유일한 경로입니다.

## 1. 시험 결과

CLI에 `--delete-recovered`를 붙여 돌렸습니다(`7c1e2a7`). 판정 기준은 **보유**입니다 —
장치가 말한 그 파일의 **모든 seq**를 PC가 갖고 있어야 목록에 오릅니다.

### 1.1 정상 삭제

```
device holds 17 file(s); 1 fully recovered here
  boot=104 file=3 seq 15379..15490 (112 records)
  boot=104 file=3: deleted
      ↓
device holds 16 file(s)
```

**`file=3`만 사라지고 0·1·2·4·5·6은 그대로**입니다. 인덱스가 구멍을 메우면서
순서를 유지한다는 §3.5 설명과 일치합니다.

### 1.2 개수 감소 (시험 5)

두 번째 삭제로 확인했습니다.

| | 삭제 전 | 삭제 후 |
|---|---|---|
| `0x45` total | 16 | **15** |
| `filesOnCard` | 17 | **16** |

**둘 다 정확히 1씩** 줄었습니다.

> 이 확인을 하려다 저희 쪽 문제를 하나 찾았습니다 — `filesOnCard`를 파싱만 하고
> **한도 초과일 때 말고는 찍지 않고 있었습니다.** 그쪽이 실어준 값이 평상시에는
> 보이지 않는 상태였습니다. 상태 줄에 넣었습니다(`961e685`).
>
> ```
> [LOG] state=1 boot=108 ... errs=0 onCard=17 mode=SLEEP
> ```

## 2. 🔴 발견 A — 결과 2는 도달 불가로 보입니다

시험 2에서 **기대는 2였는데 1이 나왔습니다.**

| 지목 대상 | 결과 |
|---|---|
| 이미 지운 파일 | 1 |
| 없는 세션 (`boot=999`) | 1 |
| **현재 기록 중인 파일** | **1** |

### 이유

**인덱스 등재가 파일을 닫을 때 일어나므로, 인덱스에 있는 파일은 정의상 기록 중이
아닙니다.** 기록 중인 파일은 목록에 없고, 그것을 지목하면 "인덱스에 없음"이
먼저 답합니다.

```
v_log_close_and_index()   ← 닫힐 때 등재
  ⇒ 인덱스에 있다 = 닫혔다
  ⇒ "인덱스에 있으면서 기록 중" 인 파일은 존재할 수 없음
```

`0x45`에 없는 것은 지목할 수 없으므로, **결과 2에 닿는 경로가 없어 보입니다.**

### 확인 부탁

- 저희 추론이 맞습니까? 맞다면 **사양서에 그렇게 적어두는 편**이 낫겠습니다 —
  "구현되어 있으나 현재 구조에서는 발생하지 않음", 또는 검사 순서를 바꿔
  발생하게 하거나.
- 저희가 못 만든 조건이 있다면 알려주십시오. 다시 시험하겠습니다.

**동작에는 문제가 없습니다.** 기록 중인 파일은 어느 코드로든 거부되고, 그것이
목적입니다. 다만 **사양에 있는 코드가 실물에서 안 나오면** 나중에 "왜 안 나오지"로
시간을 씁니다.

## 3. 🔴 발견 B — `onCard`는 목록보다 항상 1 큽니다

시험 5 직전 상태입니다.

```
0x45 total : 16
onCard     : 17          ← 1 차이
현재 상태  : boot=108 file=0 기록 중
```

**차이는 기록 중인 파일입니다.** 그 파일은 카드에 존재하므로 `onCard`에 세어지고,
닫히지 않았으므로 목록에는 없습니다.

### 왜 짚어두는가

`§8.4`의 계산이 **한 칸 어긋납니다.**

```
초과분 = filesOnCard − 128
```

인덱스가 128로 찼고 파일 하나가 열려 있으면 `onCard = 129`이므로 **초과분 1**로
읽힙니다. 그런데 그 1은 **아직 회수 불가가 아닙니다** — 열려 있어서 원래 목록에
없는 것이고, 닫힐 때 비로소 등재에 실패합니다.

| 시점 | `onCard` | 실제 회수 불가 | 계산값 |
|---|---|---|---|
| 128 등재 + 1 열림 | 129 | **0** | 1 |
| 그 파일이 닫힌 뒤 | 129 | **1** | 1 |

즉 **경계에서 한 주기 앞서 보고**합니다. 값이 틀렸다기보다 **예보**에 가깝고,
그 자체는 나쁘지 않습니다. 다만 `"1 beyond"`를 **"이미 1개를 잃었다"**로 읽으면
오해입니다.

### 제안

사양서 §8.4에 한 줄이면 충분해 보입니다.

> `filesOnCard`는 기록 중인 파일을 포함하므로, 목록(`0x45` total)보다 통상 1
> 큽니다. 초과분 계산은 그만큼 앞서 보고합니다.

저희 표시 문구도 이에 맞춰 다듬을지 그쪽 의견을 듣고 정하겠습니다.

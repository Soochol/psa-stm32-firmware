## 1. 정정 — ESP32도 모릅니다

§2.1의 논거는 정확합니다.

> STM32는 그 파일이 회수됐는지 모릅니다. **모르는 쪽이 삭제를 판단하면, 이
> 시스템 전체가 막으려던 것을 저희가 하게 됩니다.**

**같은 이유로 ESP32도 판단 주체가 될 수 없습니다.** 저희도 중계일 뿐입니다.

### 1.1 저희 코드가 그렇게 적혀 있습니다

```c
// src/uartMaster.cpp:4108
// Relay the record untouched. CRC and the placeholder flag (§6.5) are
// checked by the PC, which is also the only side that knows which
// records it already holds.
```

| 아는 것 | ESP32 | PC |
|---|---|---|
| 레코드를 BLE로 올렸다 | ✅ | — |
| **CRC가 맞았다** | ❌ | ✅ |
| **`.psa`로 저장됐다** | ❌ | ✅ |
| **병합에서 수집률 100%였다** | ❌ | ✅ |
| 어느 seq를 이미 갖고 있다 | ❌ | ✅ |

저희는 프레임을 올린 뒤 그것이 도착했는지조차 확인하지 않습니다. 알림 큐에
넣었을 뿐입니다.

### 1.2 그래서 사슬이 하나 더 깁니다

```
PC   : "boot=9 file=0 — 병합 완료, CRC 실패 0, 불변식 0. 지워도 된다"
ESP32: 중계
STM32: f_unlink → 인덱스 제거 → filesOnCard 감소 → 결과
```

§9.1이 백필을 PC 주도로 정한 것과 같은 구조입니다. **`0x45`로 목록을 받고
`0x21`로 범위를 요청하는 그 주체가, 다 받았다고 말하는 주체이기도 해야
합니다.**

BLE 쪽 명령은 저희가 붙이겠습니다 — `0x20`·`0x21`·`0x22` 옆에 **`0x23`**을
쓰면 자연스럽습니다. **그쪽 형식은 그대로 두시면 됩니다.**

## 2. 삭제 정책 — 자동으로 하지 않겠습니다

§4에서 "언제 지울지는 ESP32/PC 정책"이라고 하셨으므로 저희 판단을 밝힙니다.

### 2.1 조건

| 조건 | 확인 방법 |
|---|---|
| 해당 파일의 모든 레코드를 PC가 보유 | `.psa`가 디스크에 있음 |
| 병합에서 **수집률 100%** | `psa_sd_merge` 리포트 |
| **CRC 실패 0, 불변식 위반 0** | 같은 리포트 |

**셋 다 만족할 때만** 삭제 대상이 됩니다. 하나라도 아니면 그 파일은 아직
회수되지 않은 것입니다.

### 2.2 그래도 사용자 확인을 받겠습니다

되돌릴 수 없는 동작이고, **지우고 나면 PC의 사본이 유일본**이 됩니다. 검증
로직에 결함이 있으면 그때 잃습니다.

임계값을 넘겼다고 앱이 알아서 지우는 형태는 만들지 않겠습니다. **"카드 정리"를
누르면 지울 목록과 근거(각 파일의 수집률·CRC 결과)를 보여주고 확인을 받는**
쪽으로 하겠습니다.

> 자동 삭제는 결함이 있을 때 조용히, 그리고 전부에 대해 작동합니다. 확인
> 한 번이 그 성질을 없앱니다.

### 2.3 §4의 "미리 지워라"에 동의합니다

> 닿은 뒤에는 이미 몇 개가 목록에서 빠져 있고, **빠진 것은 지목할 수도
> 없습니다**

이 지적이 결정적입니다. 한도에 닿으면 **삭제로도 복구되지 않는 구간**이
생깁니다 — `0x45`에 없으니 지울 대상조차 되지 못하고, 카드를 뽑는 수밖에
없습니다.

`filesOnCard`가 개수인 덕분에 **닿기 전에 움직일 수 있다**는 설계 의도가
여기서 완결됩니다. 앱이 임계값에 다가가면 정리를 권하겠습니다.

## 3. 나머지 — 전부 동의합니다

| 항목 | 회신 |
|---|---|
| `0x57` 배정 | ✅ 저희 헤더에서도 비어 있음을 확인 (`0x50`~`0x56` 사용 중) |
| 요청 6 B (`bootId` 4 + `fileIndex` 2) | ✅ `0x45` 응답 항목과 같은 식별자 — 새 개념 없음 |
| 응답 1 B, 코드 0~4 | ✅ |
| **거부 2·3** (열린 파일·백필 중) | ✅ **구조적 안전만 보는 것이 맞습니다** |
| 단건 처리 | ✅ 부분 실패의 모호함을 피하는 판단에 동의 |
| 재스캔 안 함 | ✅ |

### §1.1 — §10.4와 구분하신 것

> §10.4를 만들 때 전제는 "지우면 데이터를 잃는다"였습니다. 인덱스 한도에서는
> **이미 회수·검증이 끝난 파일**이 자리를 차지하고 있을 수 있고, 그것은 지워도
> 잃는 것이 없습니다.

맞습니다. 그리고 그 전제가 성립하려면 **"회수·검증이 끝났다"를 누가 보증하는지가
정해져야** 하는데, 그것이 §1의 정정입니다. 보증하는 주체가 PC이므로 요청도
PC에서 출발해야 합니다.

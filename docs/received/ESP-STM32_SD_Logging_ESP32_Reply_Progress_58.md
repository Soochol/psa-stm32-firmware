## 1. 임계값 — 값보다 §1.2가 중요했습니다

**1000 ms 감사합니다.** 그런데 저희가 물어본 이유였던 "측정 기준"은 값이 아니라
**거는 방식**에 있었습니다.

```
경고 조건 = 1초 동안 STAT 계열 수신 0건
          ≠ 한 응답이 1초를 넘김
```

> `handleStatusMessage()`가 800 ms 걸려도 경고는 안 뜹니다

**이 문장이 §1.4의 계획을 무의미하게 만듭니다.** 저희는 "STAT 수신 →
`sendResponse`" 한 건의 소요를 재서 1000 ms와 비교하려 했는데, 그렇게 재면
**여유가 실제보다 열 배 빡빡하게 나옵니다.** 재야 할 것은 한 건의 지연이 아니라
**연속으로 응답을 못 낸 구간의 길이**입니다.

물어보길 잘했습니다. 값만 받고 계획대로 쟀으면 틀린 결론을 냈을 것입니다.

## 2. 지목하신 조건 — 저희 코드에는 없습니다

> BLE 큐가 가득 차 블로킹된다면 그 조건이 될 수 있습니다

**확인했습니다. 블로킹하지 않습니다.**

### 2.1 큐는 대기 없이 가장 오래된 것을 버립니다

```c
// src/bleSensorHub.cpp:571
bool bleSensorHubEnqueueSample(const PsaSensorTelemetrySample &sample)
{
    if (xQueueSend(s_sampleQueue, &sample, 0) == pdTRUE)   // ← 대기 시간 0
        return true;

    PsaSensorTelemetrySample dropped = {};
    xQueueReceive(s_sampleQueue, &dropped, 0);             // 오래된 것 버림
    s_droppedSamples++;
    return xQueueSend(s_sampleQueue, &sample, 0) == pdTRUE;
}
```

**세 호출 모두 대기 0입니다.** 큐가 가득 차도 이 함수는 즉시 돌아옵니다 —
샘플 하나를 버리고 새 것을 넣습니다. 버린 수는 `s_droppedSamples`로 셉니다.

BLE가 느리거나 클라이언트가 없어도 **STAT 응답 경로는 그만큼도 늦지
않습니다.** 그쪽이 지목하신 조건은 저희 쪽에서 성립하지 않습니다.

> 백필 프레임 큐도 같습니다 — `BACKFILL_ENQUEUE_WAIT_MS = 0`이고, 넣지 못하면
> 프레임을 버리고 PC가 seq 간격으로 재요청합니다. **UART 수신 루프가 BLE를
> 기다리지 않는다**는 것이 그 설계의 목적이었습니다.

### 2.2 남은 후보는 시리얼 로그인데, 산수가 안 맞습니다

응답보다 앞에 있는 셋 중 남는 것은 `logSensorDataFormatted`입니다. `Serial`
TX 버퍼가 차면 블로킹할 수 있습니다.

```
STAT 로그 한 줄  ≈ 130 B
115200 bps       ≈ 11.5 kB/s
한 줄 전송        ≈ 11 ms   (10 Hz 주기 100 ms 대비 11 %)

1초를 채우려면   ≈ 11.5 kB/s 를 1초간 지속
```

**1초 내내 막히려면 초당 11 kB 이상을 쏟아야 합니다.** 저희 최악 구간(그쪽
전원이 꺼져 `0x43 FAILED`가 몰릴 때)에도 초당 8줄 남짓, 약 1.2 kB입니다.
**열 배 모자랍니다.**

### 2.3 그래서 지금은 계측을 넣지 않겠습니다

재현되지 않는 현상을 위해 STAT 처리 경로에 계측을 넣으면, **그 계측 자체가
경로를 늦춥니다.** 지금 상태에서는 이득보다 위험이 큽니다.

**다시 관측되면** 그때 §1.2 기준(연속 무응답 구간)으로 재겠습니다. 그쪽도
#51 §4를 결함이 아니라 관측으로 올리셨고, 지금은 같은 자리에 두는 것이
맞다고 봅니다.

## 3. Q80 — 안 A에 동의합니다

> `FR_NO_FILE` → 인덱스에서 제거하고 **결과 0**

**동의합니다.** 호출자가 원하는 것은 "그 파일이 카드에 없는 상태"이고, 이미
그렇습니다. 안 B(결과 4 유지)는 저희 쪽에서 다음처럼 읽힙니다.

```
결과 4 수신  →  "삭제 실패"로 표시하고 재시도 대상으로 봄
             →  그런데 인덱스에서 빠져 목록에 안 나옴
             →  재시도할 대상을 찾을 수 없음
```

**실패로 보고하면서 다시 시도할 방법을 없애는 조합**이라 안 B는 피하는 편이
낫습니다.

### 3.1 저희 화면에 미치는 영향 — 무해합니다

저희 앱은 결과 0을 "지웠다"로 셉니다.

```python
if result == 0:
    deleted += 1        # 화면: "N개 삭제 완료"
```

안 A면 **"이미 없던 파일"이 삭제 수에 포함**됩니다. 엄밀히는 부정확하지만,
사용자가 원한 상태(그 파일이 없음)는 달성됐으므로 **틀린 정보는 아닙니다.**
이것을 구분하려면 결과 코드를 하나 더 만들어야 하는데, **그럴 값어치는
없다고 봅니다.**

### 3.2 다만 `filesOnCard`는 정해 주셔야 합니다

**안 A에서 `filesOnCard`를 감소시키십니까?**

| | 감소시킴 | 감소 안 시킴 |
|---|---|---|
| 카드에 파일이 원래 없었다면 | **이중 감산** — 실제보다 작아짐 | 정확 |
| 부팅 스캔이 그 파일을 셌다면 | 정확 | 실제보다 큼 |

**어느 쪽이 맞는지는 `u16_logFilesOnCard`가 언제 갱신되는지에 달렸고, 그건
그쪽만 압니다.** 저희 화면(`회수 N/M`)의 N이 그 값이라 결과가 바로 보입니다.

어긋나더라도 다음 부팅 스캔이 교정하므로 **위험은 낮습니다.** 다만 정하지
않으면 구현하는 사람이 임의로 고를 자리라 여쭙니다.

## 4. 그쪽 결함 2건 — `"retrying"`은 저희가 오해하고 있었습니다

> 재시도하는 코드가 없습니다. 플래그만 내리고 로그를 찍습니다

**저희가 그 로그를 재시도로 읽고 있었습니다.** 보고 #47 §1.2에서 그쪽 전원이
꺼졌을 때의 로그를 인용하며 저희 결함을 설명했는데, 그때 `"retrying"`이라는
낱말을 **양쪽에 재시도 메커니즘이 있는 것처럼** 다뤘습니다.

이제 알겠습니다 — **링크 복구는 그냥 다음 STAT이 나가고 그것에 응답이 오는
것**입니다.

`ESP_COMM_TIMEOUT` 상수 미사용 건도, `sd.c:1169`의 reason 5와 같은 종류라는
그쪽 표현이 정확합니다. **이름이 있는데 코드가 안 보는 것**이 이 두 건의
공통점입니다.

> 저희도 하나 있었습니다. `LOG_INDEX_CAPACITY`는 이름도 있고 코드도 봤지만,
> **그 값을 아는 주체가 아닌 쪽에 있었습니다.** 없애고 나서야 그게 문제였다는
> 게 분명해졌습니다.

## 5. #55 §2 정정 접수

**"재현 안 됨"으로 정정해 주셔서 감사합니다.** 다시 열지 않는 판단에도
동의합니다.

> 저희가 #51 §4를 "결함"이 아니라 "관측"으로 올린 것이 이번에 도움이 됐습니다

**맞습니다.** 그쪽이 원인을 지목하지 않으셨기 때문에 저희 철회가 그쪽 문서를
두 번 뒤집지 않았습니다. 저희가 #56 §2에서 "측정과 추정을 구분하겠다"고 적은
것과 같은 이야기를, 그쪽은 이미 **문서 성격을 나누는 방식**으로 하고
계셨습니다.

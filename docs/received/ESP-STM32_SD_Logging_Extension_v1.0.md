## 1. 배경 및 목적

### 🎯 운영 환경

작업자 여러 명이 PSA 장치를 여러 대 착용하고 현장에서 작업하며, 작업 중 센서 데이터를
지속 수집합니다. **BLE 통신 범위를 벗어나는 작업 영역이 많습니다.**

### 🔍 현재 구조의 문제

ESP32 측 BLE 스트리밍은 연결이 유지될 때만 데이터가 존재하는 구조입니다.

- BLE 연결이 끊기면 송신 큐를 비우고 스트리밍을 중단 → **음영 구간 100% 유실**
- 샘플에 순번(seq)이 없어 **유실 여부조차 사후에 알 수 없음**
- LTE(MQTT) 경로는 1분 집계만 발행하므로 원시 데이터 백업 경로가 아님
- LTE Cat.M1로 원시 데이터를 올리는 것은 대역폭상 비현실적 (아래 §1 데이터량 참조)

### 🏗️ 채택한 아키텍처

| 계층 | 역할 | 유실 허용 |
|------|------|-----------|
| **Tier 1: STM32 → SD 카드** | **원본 기록 (system of record)** | ❌ 불가 |
| Tier 2: ESP32 → BLE | 실시간 모니터링 (관측용) | ✅ 허용 |
| Tier 3: LTE 1분 리포트 | 집계 + **로깅 헬스 상태** | ✅ 허용 |
| 오프라인 | 교대 종료 후 SD 수거 → 병합 | — |

**핵심 원칙**: BLE는 데이터 전송 수단이 아니라 **관측 수단**입니다. 데이터 완전성은
전적으로 SD 카드가 보증합니다. 따라서 이 문서의 요구사항은 대부분 STM32 측에 집중됩니다.

### 📊 데이터량 근거

| 항목 | 계산 | 결과 |
|------|------|------|
| STAT(0x70) 원시 | 70 B × 10 Hz | 700 B/s |
| 제안 SD 레코드 | 80 B × 10 Hz | **800 B/s = 2.9 MB/h** |
| 8시간 교대 1대분 | | **약 23 MB** |
| 32 GB 카드 기준 | | **약 1,100 시간분 (140 교대)** |

용량은 어떤 시나리오에서도 문제가 되지 않습니다. **문제가 되는 것은 용량이 아니라
전원 차단 내성과 식별 체계입니다.**

## 2. 범위 / 비범위

### ✅ 범위

- SD 로깅 세션 식별 / 상태 조회 / 에러 이벤트 커맨드 (신규 4종)
- SD 레코드 바이너리 포맷 및 파일 헤더
- 파일 명명 / 로테이션 규칙 (= 병합 도구와의 계약)
- 전원 차단 내성(내구성) 요구사항
- seq / bootId 생성 및 리셋 규칙

### ❌ 비범위 (사유 포함, §14 참조)

| 항목 | 제외 사유 |
|------|-----------|
| 실시간 갭 백필 프로토콜 | UART 115200 8N1 = 11.5 kB/s 상한. 8시간분(23 MB) 회수에 약 33분 소요. 벌크 회수는 **물리적 SD 수거**가 정답 |
| UART 보드레이트 상향 | 위 항목이 비범위이므로 필요성 소멸 |
| STAT(0x70)에 seq 추가 | SD 기록이 완전하므로 병합에 불필요 (§14.1) |
| STM32 RTC 추가 | 앵커 방식 채택으로 STM32에 시계 불필요 (§5) |

> **오디오 기능은 이 문서와 무관합니다.** 오디오 자산은 STM32 내장 플래시에 있으며
> SD 카드는 데이터 로깅 전용입니다. 따라서 저장 매체 공존 문제는 존재하지 않습니다.

## 3. 기존 문서 정오 사항 ⚠️

**v2.0 사양서의 일부 기술이 실제 구현과 다릅니다.** 구현 시 아래를 진실로 삼아 주십시오.
(근거: ESP32 측 `src/uartMaster.cpp` / `include/uartMaster.h`)

### 3.1 체크섬 알고리즘 — 문서 §2가 틀림

| 구분 | 내용 |
|------|------|
| ❌ 문서 §2 기술 | `CHKSUM = DIR ⊕ CMD ⊕ DATA[0..n]` |
| ✅ **실제 구현** | **초기값 `0xA5`에서 시작하여 `STX`, `LEN`, `DIR`, `CMD`, `DATA` 전체를 XOR** |

문서 §9.3(STAT)에만 올바르게 기술된 이 방식이 **모든 메시지에 적용**됩니다.

```c
uint8_t chk = 0xA5;
chk ^= STX;  chk ^= LEN;  chk ^= DIR;  chk ^= CMD;
for (i = 0; i < dataLen; i++) chk ^= DATA[i];
```

문서 §12의 수신측 예제(`for i=2; i<length-2`)와 `sendAckResponse()`의
`command ^ 0x02` 역시 같은 이유로 잘못된 기술입니다.

### 3.2 LEN 필드 — 문서 §2 예제가 틀림

**LEN = `4 + dataLen`** 입니다 (DIR 1 + CMD 1 + CHK 1 + ETX 1 + DATA n).
STAT(0x70)의 `LEN = 0x44 = 4 + 64` 도 이 규칙과 일치합니다.

문서 §2의 `initTempSleep` 예제는 **LEN과 체크섬 두 곳 모두 오류**입니다.

```
❌ 문서 표기:  02 07 20 10 19 37 0E 03
               │  └ LEN=7 (오류: "7 = 1+1+2+1+1+1" 로 항을 하나 더 셈)
               └────────────────  체크섬 0x0E (오류)

✅ 정      답:  02 06 20 10 19 37 BF 03
               │                 └ 체크섬 0xBF
               └ LEN = 4 + dataLen(2) = 6

계산: A5^02=A7 ^06=A1 ^20=81 ^10=91 ^19=88 ^37=BF
```

> 이 예제를 그대로 참조해 구현하면 **LEN 불일치로 프레임 파싱이 실패**합니다.
> 본 문서의 모든 프레임 예제는 위 두 규칙으로 검산된 값입니다.

### 3.3 커맨드 코드 점유 현황 — 문서보다 코드가 최신

| 코드 | 문서 | 실제 |
|------|------|------|
| `0x54` | deprecated `ctrlFanPWM` | **`ctrlSpkPlay`** (MP3 트랙 1~33 재생)으로 재사용 중 |
| `0x83` | 미기재 | **`evtWarn`** 점유 (LEN=1, payload=warn_type, 0=배터리 저전압) |
| `0x22` | `initPWMFan` | `initWearableFanPWM` |
| 카테고리 범위 | INIT 0x10-0x22 등 | INIT **0x10-0x29** / REQ **0x30-0x49** / CTRL **0x50-0x69** / STAT 0x70-0x79 / EVT 0x80-0x89 / ERR 0x90-0x99 |

**현재 비어 있는 코드**: INIT `0x23-0x29`, REQUEST `0x43-0x49`,
CONTROL `0x56-0x69`, STATUS `0x71-0x79`, EVENT `0x84-0x89`, ERROR `0x91-0x99`

본 문서의 신규 커맨드는 이 빈 구간에서 선택했습니다.

## 4. 데이터 식별 체계

### 🔑 병합 키 = `(deviceId, bootId, seq)`

교대 종료 후 여러 작업자·여러 대의 SD 데이터를 하나로 병합하려면 각 레코드가
**전역적으로 유일하게 식별**되어야 합니다.

| 요소 | 크기 | 생성 주체 | 설명 |
|------|------|-----------|------|
| `deviceId` | 6 B | **ESP32** | WiFi STA MAC. AWS IoT thing name과 동일 근거이므로 서버 기록과 대조 가능 |
| `bootId` | 4 B | **STM32** | 전원 인가마다 1씩 증가하는 **비휘발성 카운터** |
| `seq` | 4 B | **STM32** | 해당 부팅 세션에서 0부터 시작하는 샘플 순번 |

### ⚠️ bootId가 반드시 필요한 이유

작업자는 하루에도 여러 번 장치를 껐다 켭니다. seq는 부팅마다 0으로 리셋되므로
**seq만으로는 같은 장치의 오전 데이터와 오후 데이터를 구분할 수 없습니다.**
bootId 없이는 교대 종료 병합이 원천적으로 불가능합니다.

### 📌 deviceId 전달 경로

STM32는 자신의 deviceId를 알 수 없으므로 ESP32가 신규 커맨드 `0x23`으로 전달합니다
(§6.1). STM32는 이를 파일 헤더와 디렉터리명에 기록하여 **SD 파일 자체가 자기 식별적**이
되도록 합니다 — 카드만 뽑아서 봐도 어느 장치 것인지 알 수 있어야 합니다.

### 🔒 설계 원칙: SD 로깅은 ESP32에 의존하지 않는다

**ESP32와의 통신이 전혀 없어도 SD 로깅은 정상 동작해야 합니다.** ESP32 미부팅,
UART 단선, deviceId 미수신 상황에서도 STM32는 bootId/seq로 기록을 계속하며,
deviceId만 `UNKNOWN`으로 표기합니다 (§8.3).

## 5. 시각 기준 — 앵커 방식

### 🕐 STM32에 RTC를 요구하지 않습니다

절대시각이 필요한 것은 병합 단계이지 기록 단계가 아닙니다. 따라서:

| 주체 | 책임 |
|------|------|
| **STM32** | `seq`와 **부팅 후 경과 시간(`tickMs`)** 만 기록. 절대시각 불필요 |
| **ESP32** | `(deviceId, bootId, currentTickMs ↔ 절대시각)` **앵커 쌍**을 주기적으로 자체 기록 |
| **병합 도구** | 앵커 쌍으로 각 레코드의 `tickMs`를 절대시각으로 환산 |

ESP32는 LTE 망 시각(`AT+CCLK`)으로 절대시각을 확보하며, 앵커는 `reqLogStatus`(§6.2)
폴링 응답의 `currentTickMs`로부터 생성합니다.

> **앵커 기준이 `lastSeq`가 아니라 `currentTickMs`인 이유**
> `lastSeq`는 **flush 완료된** seq이므로 실제 샘플링 시점보다 최대 2초(§9.1) 뒤처집니다.
> 이를 앵커로 쓰면 모든 레코드에 최대 2초의 **계통 오차**가 실립니다.
> 반면 `currentTickMs`는 응답 생성 시점의 STM32 시계이고, 모든 레코드가 같은 시계의
> `tickMs`를 이미 갖고 있으므로 **두 값을 직접 대응시키면 오차는 UART 왕복 지연
> (수 ms) 수준**으로 떨어집니다. 이것이 이 필드를 응답에 넣는 유일한 목적입니다.

이 방식의 이점: **STM32 하드웨어 변경이 전혀 필요 없고**, 시계 배터리 방전이나
RTC 드리프트가 데이터 품질에 영향을 주지 않습니다.

## 6. 신규 커맨드 정의

> 모든 프레임은 §3.1의 체크섬 규칙(초기값 `0xA5`)을 따릅니다.
> 멀티바이트 정수는 STAT(0x70)의 관례와 동일하게 **Big-Endian**입니다.
> 모든 DATA는 64 B 제약을 준수합니다.

### 6.1 `initLogIdentity` (0x23) — ESP→STM

장치 식별자를 STM32에 전달합니다. **ESP32는 `evtInitResult`(0x81) 수신 직후, 다른
INIT 파라미터 재전송과 함께 이 커맨드를 전송합니다.**

| 오프셋 | 크기 | 필드 | 설명 |
|--------|------|------|------|
| 0 | 6 | `deviceId` | WiFi STA MAC 6바이트 |

**DATA 크기**: 6 B · **응답**: ACK

```
요청: 02 0A 20 23 A1 B2 C3 D4 E5 F6 B9 03
      │  │  │  │  └──── deviceId = A1:B2:C3:D4:E5:F6
      │  │  │  └─────── CMD 0x23
      │  │  └────────── DIR 0x20 (REQUEST)
      │  └───────────── LEN 10 = DIR(1)+CMD(1)+DATA(6)+CHK(1)+ETX(1)
      └──────────────── STX
체크섬: A5^02=A7 ^0A=AD ^20=8D ^23=AE ^A1=0F ^B2=BD ^C3=7E ^D4=AA ^E5=4F ^F6=B9

응답: 02 04 02 23 82 03
체크섬: A5^02=A7 ^04=A3 ^02=A1 ^23=82
```

**동작 요구사항**
- 수신 전에도 로깅은 진행되어야 하며, 수신 시점에 이미 파일이 열려 있으면
  **현재 파일은 그대로 두고 다음 로테이션부터 반영**합니다 (파일 헤더 소급 수정 금지).
- 값은 비휘발성으로 보관하여 다음 부팅 시 ESP 통신 전에도 사용할 수 있게 합니다.

---

### 6.2 `reqLogStatus` (0x43) — ESP→STM

로깅 상태를 조회합니다. ESP32는 이를 **1분 주기로 폴링**하여 (a) 시각 앵커 생성,
(b) LTE 헬스 리포트 필드 확보에 사용합니다.

**요청 DATA**: 없음

**응답 DATA (20 B)**

| 오프셋 | 크기 | 필드 | 설명 |
|--------|------|------|------|
| 0 | 1 | `logState` | 0=중지, 1=기록중, 2=오류 |
| 1 | 4 | `bootId` | 현재 부팅 세션 ID (uint32 BE) |
| 5 | 4 | `lastSeq` | 마지막으로 **SD에 기록 완료된(flush 완료)** seq (uint32 BE) |
| 9 | 4 | `currentTickMs` | **응답 생성 시점의** 부팅 후 경과 ms (uint32 BE) — 시각 앵커용 |
| 13 | 2 | `freeSpaceMB` | 잔여 용량 MB (uint16 BE, 65535 초과 시 65535 고정) |
| 15 | 2 | `fileIndex` | 현재 파일 인덱스 (uint16 BE) |
| 17 | 2 | `writeErrorCount` | 부팅 후 누적 쓰기 실패 횟수 (uint16 BE) |
| 19 | 1 | `formatVersion` | 레코드 포맷 버전 (=1) |

> - `lastSeq`는 **flush가 완료된** seq여야 합니다. 버퍼에만 있는 값을 보고하면
>   ESP32가 실제로 존재하지 않는 데이터를 기록된 것으로 집계합니다.
> - `currentTickMs`는 §7 레코드의 `tickMs`와 **동일한 시계**여야 합니다.
>   이 대응이 시각 복원의 유일한 근거입니다 (§5).

```
요청: 02 04 20 43 C0 03
체크섬: A5^02=A7 ^04=A3 ^20=83 ^43=C0

응답 예 (기록중, bootId=42, lastSeq=123456, tick=12345678ms, 여유 7500MB,
         파일#3, 오류0, fmt=1):
02 18 02 43 01 00 00 00 2A 00 01 E2 40 00 BC 61 4E 1D 4C 00 03 00 00 01 B6 03
 │  │        │  └─ bootId ─┘ └─ lastSeq ┘ └ currentTick┘ └free┘ └idx┘ └err┘ └fmt
 │  │        └ logState=1
 │  └ LEN = 4 + 20 = 24 (0x18)
 └ STX                                                                  chk ─┘
체크섬 = 0xB6 (초기값 A5에서 STX·LEN·DIR·CMD·DATA 20B 전체 XOR)
전체 프레임 길이: 26 B
```

---

### 6.3 `ctrlLogEnable` (0x56) — ESP→STM

로깅을 시작/중지합니다. **중지 시에는 반드시 flush 후 파일을 닫아야 합니다** —
카드를 안전하게 뽑기 위한 커맨드입니다.

| 매개변수 | 타입 | 범위 | 설명 |
|---------|------|------|------|
| `enable` | uint8 | 0-1 | 0=중지(flush+close), 1=시작 |

**DATA 크기**: 1 B · **응답**: ACK

```
중지 요청: 02 05 20 56 00 D4 03
체크섬: A5^02=A7 ^05=A2 ^20=82 ^56=D4 ^00=D4
```

**기본 동작**: 이 커맨드를 받지 않아도 **부팅 시 자동으로 로깅을 시작**합니다.
ESP32 미부팅 시에도 기록이 남아야 하기 때문입니다 (§4 설계 원칙).

---

### 6.4 `evtLogError` (0x84) — STM→ESP

로깅 이상을 **즉시** 통보합니다. 1분 주기 폴링을 기다리지 않고 push합니다.
`0x83`은 `evtWarn`이 점유 중이므로 `0x84`를 사용합니다 (§3.3).

| 오프셋 | 크기 | 필드 | 설명 |
|--------|------|------|------|
| 0 | 1 | `reason` | 사유 코드 (아래 표) |
| 1 | 2 | `detail` | FatFs 오류코드 등 상세값 (uint16 BE, 없으면 0) |

**DATA 크기**: 3 B · **DIR**: `0x20` (자발 메시지) · **응답**: ESP32가 ACK

| `reason` | 의미 | STM32 후속 동작 |
|----------|------|-----------------|
| 0 | 마운트 실패 | 주기적 재마운트 시도 |
| 1 | 카드 미삽입 / 런타임 탈거 | 재삽입 감지 시 새 파일로 재개 |
| 2 | 용량 부족 | 로깅 중지, `logState=2` |
| 3 | 쓰기 실패 | 재시도 후 실패 시 재마운트 |
| 4 | 파일시스템 손상 | 로깅 중지, `logState=2` |

```
용량 부족 이벤트: 02 07 20 84 02 00 00 06 03
체크섬: A5^02=A7 ^07=A0 ^20=80 ^84=04 ^02=06 ^00^00=06
```

> **중요**: 어떤 로깅 오류가 발생하더라도 **자세 제어·안전 기능은 정상 동작을 유지해야
> 합니다.** 로깅은 부가 기능이며 장치 주기능을 중단시켜서는 안 됩니다.

|------|------|------|------|------|

## 7. SD 레코드 포맷

### 📦 고정 80바이트 레코드

**고정 크기가 핵심 요구사항입니다.** 전원이 쓰기 도중 끊겨도 레코드 경계를 계산으로
찾을 수 있어야 부분 손상에서 복구가 가능합니다.

| 오프셋 | 크기 | 필드 | 인코딩 | 설명 |
|--------|------|------|--------|------|
| 0 | 4 | `seq` | uint32 BE | 부팅 세션 내 샘플 순번, 0부터 단조 증가 |
| 4 | 4 | `tickMs` | uint32 BE | STM32 부팅 후 경과 시간 (ms) |
| 8 | 64 | `statPayload` | — | **STAT(0x70)의 DATA 64 B를 그대로 복사** |
| 72 | 1 | `deviceMode` | uint8 | 0=SLEEP ~ 4=FORCE_DOWN |
| 73 | 1 | `flags` | uint8 | bit0: 이 샘플의 STAT UART 송신 성공 여부, bit1-7 예약 |
| 74 | 2 | `errorMask` | uint16 BE | `errInit`(0x90) 비트마스크 스냅샷 |
| 76 | 2 | `reserved` | — | 0x0000 |
| 78 | 2 | `crc16` | uint16 BE | 오프셋 0~77에 대한 CRC-16/CCITT-FALSE |

**합계: 80 bytes** · 10 Hz 기준 800 B/s

### 💡 `statPayload` 64 B를 그대로 복사하는 이유

STAT(0x70) 페이로드 레이아웃은 v2.0 사양서 §9.2에 이미 정의되어 있습니다. 이를 그대로
재사용하면:

- STM32는 이미 만들어 둔 버퍼를 복사만 하면 됨 (추가 직렬화 코드 불필요)
- 병합 도구·분석 스크립트가 **동일한 파서 하나**로 UART/SD 양쪽을 처리
- 향후 STAT 페이로드가 확장되면 `formatVersion`만 올리면 됨

### 🔐 CRC-16/CCITT-FALSE 규격

```
다항식: 0x1021, 초기값: 0xFFFF, 반전 없음, XorOut: 0x0000
검증값: "123456789" → 0x29B1
```

CRC는 **레코드 단위 무결성**을 보장합니다. 전원 차단으로 중간이 깨진 레코드를
병합 시 확실히 걸러내기 위한 것으로, 파일 전체 재검증 없이 레코드별 판정이 가능합니다.

## 8. 파일 헤더 / 명명 / 로테이션

> **이 절은 병합 도구와의 계약입니다.** 여기서 정한 규칙대로 파일이 만들어져야
> 교대 종료 후 자동 병합이 동작합니다.

### 8.1 파일 헤더 (512 B, 섹터 정렬)

| 오프셋 | 크기 | 필드 | 설명 |
|--------|------|------|------|
| 0 | 4 | `magic` | ASCII `"PSA1"` = `50 53 41 31` |
| 4 | 2 | `formatVersion` | =1 (uint16 BE) |
| 6 | 2 | `recordSize` | =80 (uint16 BE) |
| 8 | 6 | `deviceId` | 미수신 시 `FF FF FF FF FF FF` |
| 14 | 4 | `bootId` | uint32 BE |
| 18 | 4 | `fileIndex` | uint32 BE |
| 22 | 4 | `firstSeq` | 이 파일 첫 레코드의 seq (uint32 BE) |
| 26 | 4 | `sampleRateMilliHz` | =10000 (10.000 Hz, uint32 BE) |
| 30 | 2 | `headerCrc` | 오프셋 0~29의 CRC-16/CCITT-FALSE |
| 32 | 480 | `reserved` | 0x00 채움 |

레코드는 오프셋 512부터 시작합니다.
→ **유효 파일 크기 = 512 + 80 × N**

### 8.2 파일 명명 규칙

```
/LOG/<deviceIdHex>/<bootId:08X>_<fileIndex:04X>.psa

예: /LOG/A1B2C3D4E5F6/0000002A_0003.psa
    /LOG/UNKNOWN/0000002B_0000.psa      ← deviceId 미수신 상태로 부팅
```

- `deviceIdHex`: 대문자 12자리 hex, 구분자 없음

> ⚠️ **이 명명은 LFN(Long File Name) 지원을 전제합니다.**
> 기본형 `0000002A_0003.psa`는 basename 13자, 디렉터리명 `A1B2C3D4E5F6`는 12자로
> **FAT 8.3 제약을 초과**합니다. FatFs 사용 시 `FF_USE_LFN >= 1` 설정이 필요합니다.
>
> LFN을 쓸 수 없는 구성이라면 아래 8.3 호환 대체안을 사용합니다
> (어느 쪽을 채택할지는 **§13 Q4** 회신으로 확정):
>
> ```
> /LOG/<bootId 하위4자리><fileIndex 4자리>.PSA
> 예: /LOG/002A0003.PSA        ← basename 8자 + 확장자 3자
> ```
> 이 경우 `deviceId`와 `bootId` 상위 비트는 **파일 헤더(§8.1)에만** 존재하므로,
> 병합 도구는 파일명이 아니라 헤더를 신뢰합니다. 파일명 충돌을 피하려면 카드를
> 장치 간에 돌려 쓰지 않아야 합니다.

### 8.3 로테이션 규칙

새 파일을 여는 조건 (셋 중 하나라도 만족 시, `fileIndex`를 1 증가):

| 조건 | 값 | 근거 |
|------|-----|------|
| **부팅** | 매 부팅 | `bootId`가 바뀌면 반드시 새 파일 (`fileIndex`는 0부터) |
| **경과 시간** | 1시간 | 손상 시 피해를 1시간분으로 제한 |
| **파일 크기** | 32 MB | 상동 (1시간 ≈ 2.9 MB이므로 사실상 시간 조건이 먼저 걸림) |

**파일 하나가 손상되어도 교대 전체를 잃지 않도록 하는 것이 로테이션의 목적입니다.**

## 9. 내구성 요구사항

> **배터리가 쓰기 도중에 방전되는 것은 예외 상황이 아니라 일상입니다.**
> 이 절의 항목들이 "데이터를 잃지 않는다"는 목표의 실질적인 본체입니다.

### 9.1 flush 정책

| 항목 | 요구사항 |
|------|----------|
| flush 주기 | **최대 2초** (또는 20 레코드) 마다 `f_sync()` 상당 수행 |
| 최대 손실 상한 | 전원 차단 시 **20 샘플 (2초)** 이내 |
| 파일 닫기 | `ctrlLogEnable(0)` 수신 시 즉시 flush + close |

2초 주기 근거: 8시간 교대에서 전원 차단이 20회 발생해도 최대 손실은 400 샘플
(전체의 0.14%)입니다. 이보다 짧게 하면 SD 수명과 CPU 부하가 불리해집니다.

### 9.2 부분 레코드 처리

레코드가 고정 80 B이므로 복구는 산술로 처리합니다.

```
유효 레코드 수 N = (파일크기 - 512) / 80
잔여 바이트 (파일크기 - 512) % 80 → 마지막 불완전 레코드로 간주하여 절삭
```

- **재부팅 시 이전 파일을 수리하려 하지 마십시오.** 항상 새 파일을 열고,
  절삭·검증은 병합 도구가 오프라인에서 수행합니다.
- CRC 불일치 레코드는 병합 도구가 폐기하되, 해당 `seq`는 **갭으로 계수**하여
  유실률 통계에 반영합니다.

### 9.3 매체 이상 시 동작

| 상황 | 요구 동작 |
|------|-----------|
| 부팅 시 카드 없음 | `evtLogError(1)` 후 **정상 동작 지속**, 주기적 재감지 |
| 런타임 탈거 | `evtLogError(1)`, 재삽입 감지 시 **새 파일**로 재개 (`fileIndex` 증가) |
| 쓰기 실패 | 재시도 → 실패 지속 시 재마운트 → `evtLogError(3)` |
| 용량 부족 | `evtLogError(2)`, 로깅 중지. **오래된 파일 자동 삭제 여부는 §13 Q6** |

**모든 경우에 자세 제어·히터·안전 로직은 영향을 받지 않아야 합니다.**

## 10. 에러 처리

### 10.1 기존 `errInit`(0x90) 비트와의 역할 분담

| 신호 | 의미 | 용도 |
|------|------|------|
| `ERR_SD_CARD` (0x0100) | SD 매체 자체의 이상 | 부팅 시 자가진단 결과 |
| **`evtLogError` (0x84)** | **런타임 로깅 이상** | 즉시 통보, 사유 구분 가능 |
| `ERR_MP3_FILE` (0x0200) | 오디오 자산 오류 | **STM32 내장 플래시 관련. SD와 무관** |

> `ERR_MP3_FILE`은 오디오 자산이 STM32 내장 플래시에 있으므로 **SD 카드 상태와 혼동하지
> 않아야 합니다.** ESP32 측 헬스 리포트도 이 둘을 별도 필드로 분리해 전송합니다.

### 10.2 ESP32 측 처리

- `evtLogError` 수신 즉시 ACK 후 다음 LTE 리포트에 사유 코드 포함
- `logState=2`가 연속 관측되면 경고 상태로 승격

## 11. 헬스 리포팅

**교대 완료를 기다리지 않고 로깅 실패를 당일 즉시 발견하기 위한 경로입니다.**
09:00에 카드가 죽은 장치를 18:00에 알게 되면 하루치를 통째로 잃습니다.

ESP32는 기존 1분 주기 MQTT 리포트에 `reqLogStatus` 응답을 그대로 실어 보냅니다.

| 필드 | 출처 | 경보 조건 |
|------|------|-----------|
| `logState` | 0x43 응답 [0] | ≠ 1 이면 경보 |
| `lastSeq` | 0x43 응답 [5..8] | 1분 전 대비 증가량이 600 미만이면 경보 (10 Hz × 60 s) — **아래 단서 참조** |
| `freeSpaceMB` | 0x43 응답 [13..14] | < 500 MB 경고 |
| `writeErrorCount` | 0x43 응답 [17..18] | 증가 시 경보 |
| `lastLogErrorReason` | 0x84 최근값 | 존재 시 경보 |

> ⚠️ **seq 증가율 경보는 `deviceMode`로 게이팅합니다.** SLEEP 모드에서 샘플링이 멈추면
> `lastSeq`가 정체되어 오경보가 발생합니다. ESP32는 `evtMode`(0x82)로 모드를 추적하고
> 있으므로 SLEEP 구간에서는 이 경보를 억제합니다.
> **단, SLEEP 중 샘플링 지속 여부는 §13 Q9의 회신에 따라 확정됩니다.**

이 5개 필드만으로 **"현재 몇 대가 정상 기록 중인가"** 를 관제할 수 있습니다.

## 12. 수용 기준 및 검증 시나리오

| # | 시나리오 | 합격 기준 |
|---|----------|-----------|
| 1 | **8시간 연속 기록** | seq 0 ~ 287,999 (10 Hz × 8 h) **연속성 100%, 갭 0**. CRC 전수 통과. (SLEEP 중 샘플링이 멈추는 사양이면 → **비-SLEEP 구간 연속성 100%**. §13 Q9) |
| 2 | **전원 순단 20회** | 부팅마다 새 파일 생성, `bootId` 중복 없이 증가. 절삭 후 잔존 레코드 CRC 100% 통과. 회당 손실 ≤ 20 샘플 |
| 3 | **카드 미삽입 부팅** | 자세 제어 정상. `evtLogError(0 또는 1)` 수신. `logState`=0 또는 2 보고 |
| 4 | **런타임 카드 탈거·재삽입** | `evtLogError(1)` 수신. 재삽입 후 새 `fileIndex`로 기록 재개. 기존 파일 무손상 |
| 5 | **용량 소진** | `evtLogError(2)` 수신. 장치 주기능 정상 유지 |
| 6 | **deviceId 미수신 부팅** | `/LOG/UNKNOWN/` 에 기록. 이후 0x23 수신 시 다음 로테이션부터 정상 경로 |
| 7 | **UART 단선 상태 부팅** | ESP32 통신 없이도 SD 기록 정상 진행 |
| 8 | **제어 루프 영향도** | 로깅 활성/비활성 간 100 Hz 제어 루프 지터 유의미한 증가 없음 |

### 🔍 유실률 검증 방법

```
유실률 = 1 - (CRC 통과 레코드 수) / (max(seq) - min(seq) + 1)
```

시나리오 1에서 이 값이 **0%** 여야 합니다.

## 13. ❓ STM32 팀 결정 요청 항목

> 아래는 STM32 팀의 회신이 필요한 항목입니다. ESP32 팀이 임의로 결정하지 않았습니다.

**Q1. 현행 SD 로깅 현황을 공유해 주십시오. (최우선)**
현재 이미 SD에 데이터를 기록 중인 것으로 알고 있습니다. 아래를 알려주시면 본 사양서에서
**이미 충족된 항목을 제거**하여 작업량을 줄일 수 있습니다.
- 레코드 포맷 (바이너리/텍스트, 필드 구성, 크기)
- 기록 주기
- 파일 명명 및 로테이션 규칙 유무
- flush 주기 및 전원 차단 시 동작
- seq / CRC / 파일 헤더 유무

**Q2. `bootId` 소스는 무엇으로 하시겠습니까?**
후보: RTC 백업 레지스터 / 내장 플래시 카운터 / 외부 EEPROM.
요구사항은 **전원 완전 차단 후에도 유지되고 부팅마다 증가**하는 것뿐입니다.

**Q3. `seq`의 기준을 확인해 주십시오.**
본 문서는 "STM32 센싱 루프가 생성한 샘플 순번"으로 가정했습니다. 즉 UART 송신 성공
여부와 무관하게 증가합니다. 이 해석이 맞습니까?

**Q4. SD 카드 및 파일시스템 사양은? 특히 LFN 지원 여부.**
용량 / 규격(SDHC·SDXC) / 파일시스템(FAT32·exFAT) / 라이브러리(FatFs 버전 등).
**`FF_USE_LFN`이 활성화되어 있습니까?** §8.2 기본 명명은 LFN이 필요하며,
비활성이면 8.3 호환 대체안으로 확정해야 합니다.

**Q5. 로깅이 100 Hz 제어 루프에 주는 부하가 우려됩니까?**
SD 쓰기 지연(수십~수백 ms 스파이크)이 제어 주기를 침범할 가능성이 있다면 DMA/버퍼링
구조를 함께 검토하겠습니다.

**Q6. 용량 소진 시 정책은?**
(a) 로깅 중지 (본 문서 기본안) / (b) 가장 오래된 파일부터 순환 삭제.
운영상 (b)가 안전할 수 있으나 미회수 데이터가 지워질 위험이 있습니다.

**Q7. 카드 회수·교체 운영 방식은?**
교대마다 카드를 뽑는지, 장치에 고정하고 USB 등으로 덤프하는지에 따라
`ctrlLogEnable(0)`(안전 제거) 사용 시점이 달라집니다.

**Q8. 신규 커맨드 코드 `0x23 / 0x43 / 0x56 / 0x84`에 STM32 측 충돌이 없습니까?**
ESP32 측 기준으로는 비어 있으나, STM32 내부에서 사용 중인 코드가 있는지 확인 부탁드립니다.

**Q9. SLEEP 모드에서도 샘플링과 SD 기록이 계속됩니까?**
이 답에 따라 두 가지가 달라집니다.
- **계속되는 경우**: seq는 교대 내내 끊김 없이 증가 → §12 시나리오 1(연속성 100%)을
  그대로 적용
- **멈추는 경우**: SLEEP 구간은 정상적인 seq 정체이므로 §11 경보를 `deviceMode`로
  게이팅해야 하고, §12 시나리오 1의 합격 기준을 "비-SLEEP 구간 연속성"으로 수정해야 함

또한 SLEEP 진입 시 **파일을 flush/close 하는지**도 알려주십시오.
(권장: SLEEP 진입 시 flush, 복귀 시 같은 파일에 이어쓰기 또는 새 `fileIndex`)

## 14. 향후 확장 (비범위)

### 14.1 STAT(0x70)에 `seq` 추가 — 현재 불필요

BLE로 실시간 수신한 샘플과 SD 데이터를 대조하려면 STAT에도 seq가 필요합니다. 그러나
**SD 기록이 완전하므로 병합에는 불필요**하며, STAT DATA는 이미 64 B로 포화 상태라
추가 시 v2.1 하드 컷오버가 발생합니다.

향후 실시간 유실 가시성이 요구되면 그때 협의합니다.

### 14.2 실시간 갭 백필 프로토콜

ESP32가 누락 구간을 STM32 SD에서 끌어와 BLE로 재전송하는 방식입니다.
UART 115200 기준 실시간의 약 14배 속도이므로 1시간 갭 복구에 약 4분이 걸립니다.
**짧은 갭에는 유효하지만 교대 단위 회수에는 부적합**하여 이번 범위에서 제외했습니다.

### 14.3 UART 보드레이트 상향

14.2가 도입될 경우에만 의미가 있습니다.

## 1. §2 로테이션 — 저희가 백필로 하려던 확인이 카드로 닫혔습니다

`firstSeq = 36001`이 세 쌍 모두 앞 파일 마지막 seq + 1이라는 것,
그리고 세 번 다 정확히 36,001 레코드 / span 3600 s라는 것 확인했습니다.
우발이 아니라 결정적 동작이라는 판단에 동의합니다.

§2.2에서 지적하신 위험 서술이 정확합니다.

> `firstSeq`가 1이라도 어긋나면 이후 모든 요청이 한 칸씩 밀린 레코드를 반환합니다.
> 그것도 조용히 — 반환된 레코드 자체는 CRC가 맞는 정상 레코드이기 때문에

받은 20개가 `boot=9`의 seq 0~19였다는 지적도 맞습니다. 로테이션은 36000에서
일어나므로 그 시험에 포함되지 않았습니다.

## 2. Q47 `step min=3 ms` — 발생 위치를 특정했습니다

**추적은 불필요하다고 봅니다. 원인 구간이 좁습니다.**

받은 백필 데이터가 마침 `00000009_0000`의 시작 부분(seq 0~19)이라
해당 구간을 그대로 갖고 있었습니다.

| seq | tick_ms | Δ |
|---|---|---|
| 0 | 10378 | — |
| **1** | **10381** | **3 ms** ← 이상치 |
| 2 | 10481 | 100 ms |
| 3 | 10581 | 100 ms |
| … | … | 100 ms |

**`seq 0 → 1` 한 번뿐이고, 그 뒤로는 전부 정확히 100 ms입니다.**
파일 전체 최소가 3 ms인 것은 이 한 쌍 때문입니다.

### 2.1 해석

샘플링 자체는 정확합니다 — 165,586개 간격이 100 ms이고 어긋난 것은 **로깅이
시작되는 첫 쌍 하나**입니다. 다른 파일의 최소가 41~67 ms인 것도 같은 성격의
시작 아티팩트가 덜 극단적으로 나타난 것으로 보입니다.

즉 "10 Hz 주기가 흔들린다"가 아니라 **"파일의 첫 레코드가 직전 샘플과 가깝게
찍힌다"**입니다. 로깅 armed 시점에 이미 확보돼 있던 샘플이 즉시 기록되고,
다음 정규 샘플이 곧바로 뒤따르는 형태로 설명됩니다.

### 2.2 영향

**병합 도구에는 실질적 영향이 없습니다.** 어긋나는 것은 파일당 첫 레코드
하나의 타임스탬프가 최대 100 ms 이내에서 밀리는 것뿐이고, 앵커 보간은
`tick ↔ epoch` 쌍에 기반하므로 이 한 쌍이 다른 레코드의 시각을 흔들지 않습니다.

§5.4 앵커 진행률 검사도 발동하지 않습니다 — 앵커 간 간격은 60 s이고
이 아티팩트는 파일 시작 100 ms 안에서 끝납니다.

**추적 불필요에 동의하며, 이 문서를 근거로 종결하시면 되겠습니다.**
데이터 무결성 문제가 아니라는 판단도 그대로 맞습니다.

## 3. Q46 32 MB 로테이션 — 제외에 동의합니다

산술이 명확합니다.

```
10 Hz × 80 B × 3600 s = 2.88 MB  ≪  32 MB
```

시간 조건이 먼저 걸리는 한 크기 조건은 도달하지 않으며, 도달하려면 샘플링이
10배 이상 빨라져야 합니다. **검증 목록에서 제외하는 데 이견 없습니다.**

다만 코드는 그대로 두는 편에 동의합니다 — 샘플링 주기가 바뀌거나 레코드
크기가 늘면 그때 살아나는 경로입니다. 그런 변경이 생기면 저희가 먼저
알리겠습니다(setpoint 상한 통지와 같은 성격입니다).

## 4. §2.2 — 카드가 닫은 것과 아직 남은 것

### 4.1 두 가지는 다른 확인입니다

카드 검증이 닫은 것은 **데이터가 옳다**입니다 — `firstSeq`가 실제로 연속입니다.
남은 것은 **탐색 로직이 옳다**입니다 — 경계를 넘는 `reqLogRead`가 실제로
올바른 파일을 골라 올바른 레코드를 반환하는가.

전자가 후자의 **전제**이므로 위험은 크게 줄었습니다. 다만 `u8_SD_Log_Backfill_Start()`가
seq로 파일을 고르는 부분은 여전히 실행된 적이 없습니다.

### 4.2 🔴 시도했으나 카드가 없었습니다

저희 백필 클라이언트에 세션·구간 지정을 추가하고 경계를 넘는 요청을
준비했습니다.

```
--boot 9 --start-seq 35995 --limit 12 --batch 12
```

`boot=9`의 file 0이 36000에서 끝나고 file 1이 36001에서 시작하므로,
이 요청 하나로 탐색 로직이 확인됩니다.

**실행했더니 `0 file(s)`이 돌아왔습니다.** 원인을 추적하니 헬스 리포트가
`free=65535`였고, `u16_SD_Log_Get_FreeMB()`의 `if(!b_SdMount) return 0xFFFFU`
경로였습니다. 즉 **카드 회수로 장치가 미마운트 상태**입니다. 상황을 몰라
한동안 카드 결함으로 의심했습니다.

**카드를 장치에 되돌리시면 알려주십시오.** 그때 위 요청 한 번으로 §2.2가
완전히 닫힙니다. 별도 세션이 필요 없고 30초면 됩니다.

### 4.3 참고 — `state=1`은 카드 없이도 나옵니다

추적 과정에서 확인한 것입니다. `u8_SD_Log_Get_State()`는 `b_logFault`와
`b_logEnabled`만 보고 **마운트 여부를 보지 않습니다.** 그래서 카드가 없어도
`state=1 errs=0`이 나가고, 미마운트를 알리는 신호는 `free=65535` 하나뿐입니다.

헬스 리포트만 보는 쪽에서는 "정상 기록 중"으로 읽힙니다. 저희도 그렇게 읽었습니다.
`lastSeq`가 0에서 멈춰 있는 것이 두 번째 단서였습니다.

수정을 요청드리는 것은 아니고, **판독 시 주의점으로 기록**해 두시면 좋겠습니다.
(원하시면 `logState`에 마운트 상태를 반영하는 쪽도 가능하나, 프로토콜 의미가
바뀌므로 굳이 권하지는 않습니다.)

## 5. §6 88분 세션 — 유용합니다

`bootId 27`이 52,681 레코드 / 약 87.8분이라는 것, 그리고 그것이 파일 구조
측면의 장시간 동작을 이미 증명한다는 정리에 동의합니다.

차단 히스토그램이 RTT에만 있고 카드에는 없다는 구분도 정확합니다.
장시간 세션의 남은 목적은 **차단 분포**이지 파일 구조가 아니므로,
그 관점에서 우선순위를 잡으시면 되겠습니다.

## 1. Q77 — 감사합니다. 그리고 상수를 지웠습니다

받자마자 파서를 연결했습니다. **§3.2에서 "확정 후에 넣겠습니다"라고 한 그
한 줄**입니다.

```python
index_capacity = struct.unpack(">H", body[23:25])[0] if len(body) >= 25 else None
```

### 1.1 한 줄이 아니라 상수 하나가 사라졌습니다

솔직히 말씀드리면 파싱보다 **지운 쪽이 중요했습니다.**

| 언어 | 있던 것 | 지금 |
|---|---|---|
| C++ | `#define LOG_INDEX_CAPACITY 128` | **삭제** |
| Python | `LOG_INDEX_CAPACITY = 128` | **삭제** |

두 곳 다 없앴습니다. 폴백으로 남겨 둘까 생각했는데 **남기면 결국 쓰게
됩니다** — 값이 안 왔을 때 "모름"을 표현할 자리가 없어지고, 그러면 이 제안이
없애려던 상태로 되돌아갑니다.

그래서 계산도 함께 바꿨습니다.

```
초과분 = filesOnCard - indexCapacity     둘 다 있을 때만
       = 모름                            한쪽이라도 없으면
```

**0이 아니라 "모름"입니다.** 0은 "초과분 없음"이라는 답인데, 그건 저희가 알 수
없는 사실입니다. 그쪽이 #43 §2.2에서 *"0은 '상한 0'이라는 유효한 값"*이라고
쓰신 것과 같은 이유입니다.

### 1.2 §1.2의 지적이 정확합니다

> **펌웨어가 따로 올라갑니다.** 별도 조회 커맨드로 부팅 때 한 번만 받으면,
> 저희가 먼저 업데이트된 구간에서 그쪽이 들고 있는 값은 낡은 값입니다.

이 논거는 저희 §3.4에 없던 것입니다. 저희는 "펌웨어를 교체하면 상수도
바뀐다"까지만 썼는데, **교체 시점이 서로 다르다**는 지점이 더 강합니다.
v1.8 §6.2에 그 취지를 반영했습니다.

`SD_LOG_IDX_MAX`를 리터럴이 아니라 매크로로 반환하신 것도 확인했습니다.
축소 빌드가 자동으로 따라오는 구조라, #29 같은 상황에서 **저희가 할 일이
정말 없습니다.**

## 2. #44 §2.1 — 23 B 행이 빠진 것은 표가 아니라 코드였습니다

**가장 중요한 지적이었습니다.** 표에 한 줄이 없다고 하셨는데, 확인해 보니
**코드가 그 상태를 표현할 수 없었습니다.**

### 2.1 무엇이 잘못돼 있었는가

```python
@property
def index_capacity(self) -> int:
    return LOG_INDEX_CAPACITY      # ← 무조건 128
```

분모가 **함수로 위장한 상수**였습니다. 그래서

- 23 B 응답에도 `회수 61/128`이 나왔습니다 — 모르는 값을 아는 척했습니다
- 21 B 응답에도 분모가 `128`이었습니다 — 그쪽이 §2.1에서 지적하신 그대로입니다
- **분모를 모르는 상태에서 경고가 떴습니다** — 90%도, 초과도

마지막이 특히 나쁩니다. 저희가 §2.2에서 *"분모가 틀리면 멀쩡한 장비가 정리를
재촉한다"*고 써 놓고, **정확히 그 코드를 들고 있었습니다.**

### 2.2 고친 결과

| 응답 | 화면 | 경고 |
|---|---|---|
| 조회 중 | `회수 …` | — |
| **21 B** | **`회수 ?/?`** | 없음 |
| **23 B — 지금 현장의 전부** | **`회수 61/?`** | **없음** |
| 25 B | `회수 61/128` | — |
| 〃 90% | `회수 115/128 ⚠ 정리 필요` | 있음 |
| 〃 초과 | `회수 150/128 ⚠ 22개 목록 밖` | 있음 |
| 거부 | `회수 —` | — |

**경고 사다리 전체를 분모 유무에 걸었습니다.** 분모가 없으면 숫자만 보이고
아무 권고도 하지 않습니다.

시험으로 고정한 것 중 하나를 적어 둡니다 — `SD_LOG_IDX_MAX = 4`인 장치가
6개를 들고 있으면 `회수 6/4 ⚠ 2개 목록 밖`입니다. **128이 아니라 그 장치의
값으로 재는지**를 보는 시험입니다.

### 2.3 §2.3 네 번째 근거 — 몰랐습니다

> `0x45`의 `totalCount`는 **1바이트**입니다. 인덱스 상한을 255 위로 올리면
> 그 필드부터 넘칩니다.

확인했습니다. 저희 파서도 `data[0]`를 1바이트로 읽고 있습니다. **목록은 애초에
카드 전체를 셀 수 있는 그릇이 아니다**라는 정리가 저희 세 근거보다 깔끔합니다.

## 3. #43 §3 — 세 건 다 반영했습니다

### 3.1 §3.1 라벨 — `SD`를 뗐습니다

> 이 라벨은 **카드가 128개까지 담긴다**로 읽힙니다. 그렇지 않습니다.

맞습니다. 그리고 저희가 그렇게 읽히게 써 놓았습니다.

```
전 :  SD 61/128        ← 카드 용량으로 읽힘
후 :  회수 61/128      ← 무선으로 꺼낼 수 있는 파일 수
```

**"카드가 얼마나 찼는가"는 이 줄에서 뺐습니다.** 그쪽 지적대로 그건
`freeSpaceMB`의 축이고, 저희는 지금 그 값을 화면에 쓰지 않습니다. 합치지 않고
비워 두었습니다 — 나중에 넣더라도 **별도 줄**입니다.

부팅 스캔 예산(파일당 약 3 ms, 128개 ≈ 390 ms)이라는 설명이 결정적이었습니다.
저희는 128을 "카드가 감당하는 수"로 이해하고 있었습니다.

### 3.2 §3.2 "손실" — 화면이 맞았고 문서가 틀렸습니다

#44 §2.2에서 정리해 주신 그대로입니다. 화면 문구 `⚠ 22개 목록 밖`은 그대로
두고, **제안서 §2.2 산문을 고쳤습니다.**

```
전 :  회수 불가 경고 · 데이터 손실을 보고합니다
후 :  원격 회수 불가 — 카드에는 정상 기록되어 있고,
      잃는 것은 무선으로 꺼낼 수 있는가뿐입니다
```

`ESP_LOGE`는 그대로 뒀습니다(운영자가 봐야 할 상태가 맞습니다). 다만 **문구를
고쳤습니다** — "backfilled"에서 "pulled over the radio"로, 그리고 "still
recording and the card holds them all"을 앞에 붙였습니다.

### 3.3 §3.3·§3.4 — reason 6도 보고된 한도로 잽니다

`filesOnCard - indexCapacity`가 열려 있는 동안 1 크다는 것, **확정된 결과를
먼저 보여주는 값**이라는 설명 받았습니다. 그대로 씁니다.

§3.4 말씀대로 `evtLogError(reason 6)` 처리도 함께 정확해졌습니다. 다만 **한
가지를 추가로 처리해야 했습니다.**

> 부팅 스캔 이벤트가 **첫 0x43 응답보다 먼저 도착**할 수 있습니다.

그때는 한도를 모르므로 초과분을 계산할 수 없습니다. 세 갈래로 나눴습니다.

| 상황 | 로그 |
|---|---|
| 한도 미보고 | "얼마나 많은지는 여기서 알 수 없음 — 다음 폴링이 채움" |
| 한도 < detail | `detail - indexCapacity`개 초과 |
| 한도 >= detail | 구형 펌웨어가 인덱스 수를 실은 경우 — 상태 조회를 보라 |

### 3.4 §4 — 캐시 넣지 않았습니다

> 0x43 응답의 **모든 필드가 RAM에서 나옵니다.**

`freeSpaceMB`가 `f_getfree`가 아니라 FatFs 구조체 직접 읽기라는 것, 그리고
**그 선택이 낡은 FSINFO에서 FAT 전수 스캔으로 빠지는 것을 피하려는 설계**라는
설명까지 감사합니다. 저희가 물은 것보다 한 겹 깊은 답이었습니다.

캐시는 넣지 않았고, 조회 주기도 낮추지 않았습니다.

## 4. Q78 — 1분 폴링은 백필 중에도 돕니다

> "백필 중 보내지 않습니다"가 **1분 주기 폴링에도** 적용됩니까?

**아닙니다.** 표가 두 줄로 갈라져 읽히지 않은 것이 맞습니다. 정확히 적습니다.

| 주체 | 주기 | 백필 중 |
|---|---|---|
| **ESP32 펌웨어** | 1분 (`LOG_STATUS_POLL_INTERVAL_MS`) | **무조건 돕니다 — 억제 없음** |
| **PC 앱** | 30초 | **건너뜁니다** |

억제한 것은 **앱의 30초 폴링 하나뿐**입니다. 펌웨어의 1분 폴링에는 백필
게이팅이 애초에 없습니다.

### 4.1 억제 이유가 부하가 아닙니다

> 억제를 넣으신 이유가 부하라면, 그 전제가 #43 §4에서 없어졌습니다.

**부하가 이유가 아니었습니다.** BLE 계층의 문제입니다.

백필·삭제·상태 조회가 **같은 characteristic**을 쓰고, 거부는 모두
`0xBF + 이유 1 B`로 옵니다. 그 1바이트는 **어느 요청을 거부한 것인지 말하지
않습니다.** 그래서 앱은 "지금 전송이 돌고 있는가"로 구분합니다.

```
전송 중  →  0xBF 는 전송의 것
전송 없음 →  0xBF 는 상태 조회의 것
```

이 구분이 성립하려면 **전송 중에 상태 조회를 끼워 넣지 않아야** 합니다.
끼워 넣으면 상태 조회의 거부가 백필 세션에 프로토콜 오류로 들어갑니다.

UART 부하와는 무관하고, **그쪽 답(SD 미접근)으로 풀리는 종류의 제약이
아닙니다.** 요청에 식별자를 붙이면 없앨 수 있지만, 프레임 하나 아끼려고
프로토콜을 늘릴 일은 아니라고 봅니다.

### 4.2 §3.2 우려는 해소됩니다

> §4.4에서 무응답 타이머를 두지 않으신 근거가 **1분 주기 폴링의 다음
> 응답**입니다. 그 폴링이 백필 동안 멈춘다면 —

멈추지 않습니다. **1분 폴링은 무조건 돌므로 §4.5의 전제는 그대로**입니다.
표시가 어긋나도 늦어도 1분 안에 풀립니다.

덧붙여, 백필 중에는 카드 파일 수가 변하지 않습니다(백필은 읽기만 합니다).
삭제는 끝난 직후 `0x43`을 한 번 더 보냅니다 — **그쪽이 확인해 주신 "삭제 즉시
감소" 덕분에 재부팅 없이 정확해집니다.**

## 5. v1.8 발행했습니다

`docs/ESP-STM32_SD_Logging_Extension_v1.8.md` — **정본 소유 이후 첫
개정**입니다(#39 §3). #43 §2 델타 5건만 반영하고 나머지 본문은 손대지
않았습니다.

| # | 델타 | 반영 |
|---|---|---|
| 1 | §6.2 오프셋 표 — `indexCapacity` (23, 2 B) | ✅ |
| 2 | §6.2 머리말 `응답 DATA` 21 B → **25 B** | ✅ v1.7 누락분 포함 |
| 3 | 길이 게이팅 21 / 23 / 25 | ✅ |
| 4 | **§6.2 예시 프레임 정정** | ✅ **§2.3 계산 그대로** |
| 5 | §8.6 — 상수로 갖지 말 것 | ✅ |

### 5.1 예시 프레임은 그쪽 계산을 그대로 실었습니다

`LEN=0x1D`, 체크섬 `0x0F`, 전체 31 B. **저희가 다시 계산하지 않았습니다** —
체크섬 알고리즘은 그쪽 구현이고, 21 B 예시의 `0xB6`가 재현된다는 검증도 그쪽이
하신 것입니다. 23 B 중간 단계(`LEN=0x1B`, `0x89`)도 정정 이력에 적어 두었습니다.

v1.7부터 밀려 있던 건이라, **왜 틀려 있었는지**(filesOnCard 추가 때 예시 갱신
누락)를 인용문으로 남겼습니다. 같은 종류의 누락을 다음에 알아보게 하려는
것입니다.

### 5.2 §8.6에는 두 문장을 넣었습니다

델타는 "상수로 갖지 말 것" 한 줄이었는데, **§3.1에서 알려 주신 것**을 함께
적었습니다 — 이 숫자가 카드 용량이 아니라 부팅 스캔 예산이며, 표시할 때 두
축을 합치지 말라는 내용입니다. 저희가 정확히 그 실수를 했으므로, 다음 사람이
같은 곳에서 넘어지지 않게 문서에 남기는 편이 맞다고 봤습니다.

## 6. ESP32 보고 #38·#39·#40 — 전달이 누락돼 있었습니다

그쪽 `docs/received/`에 저희 보고가 **#37까지만** 있는 것을 확인했습니다.
#38 이후 3건이 파일로 간 적이 없습니다.

**#38~#39에서 합의한 바로 그 문제를 저희가 냈습니다.** 이번에 함께 넣습니다.

| 파일 | 내용 |
|---|---|
| ESP32 보고 #38 | v1.7 본문이 도달하지 않았다는 보고 — 전달 문제를 처음 제기한 문서 |
| ESP32 보고 #39 | **v1.7 검토 완료·이견 없음** + 정본 소유 이관 합의 |
| ESP32 보고 #40 | `ctrlLogDeleteAll` Q75 회신 |
| **ESP32 보고 #44** | 이 문서 |
| **사양서 v1.8** | §5 |
| **제안서 개정본** | §2·§3에서 고쳤다고 한 그 문서입니다 — 고쳤다는 말만 보내면 그쪽이 든 사본은 그대로입니다 |

제안서에는 **절 번호 이동 안내**를 머리에 달았습니다. §4.3(라벨)을 신설하면서
#43·#44가 인용하신 §4.3·§4.4가 각각 §4.4·§4.5로 밀렸습니다.

#39 §2대로 **커밋 해시나 PR 번호를 전달의 근거로 쓰지 않습니다.** 파일로
넣었습니다.

### 6.1 손해가 하나 드러났습니다

#43·#44 미결 표에 이 줄이 있습니다.

```
| v1.7 내용 검토 | ESP32 | 본문 수령 완료 (#39 §1) |
```

**그 검토는 #39에서 끝났습니다.** 문서 머리에 *"v1.7 검토 완료. 이견
없습니다"*, 조치 요청 *"없습니다"* 라고 적혀 있습니다. 그런데 #39가 전달되지
않아 **그쪽 표에는 끝난 항목이 열린 채 남아 있었습니다.**

전달 누락이 무엇을 만드는지 보여주는 실물이라 적어 둡니다 — 끝난 일이 안 끝난
것으로 남고, 양쪽 미결 표가 조용히 갈라집니다. 저희 잘못이고, 앞으로는 보고를
쓰는 그 자리에서 바로 넣겠습니다.

### 7.1 실기는 양쪽 다 아직입니다

정확히 적어 둡니다.

| 쪽 | 상태 |
|---|---|
| STM32 `9bd5679` | 빌드 완료, **어느 장치에도 굽지 않음** (#44 §1.2) |
| ESP32 · PC 앱 | 빌드·단위시험 통과, **실기 확인 없음** |

지금까지 시험한 것은 **프레임 파싱, 길이 게이팅(21/23/25 B), 초과분 계산,
화면 문구**입니다. 25 B 경로는 저희가 만든 프레임으로만 확인했으므로,
**그쪽 실물이 보내는 25 B를 아직 본 적이 없습니다.**

굽는 대로 알려 주시면 저희도 맞춰 올리겠습니다. 그때가 이 건의 실제
종료입니다.

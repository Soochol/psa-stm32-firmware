### ESP32 측에서 이미 수정 완료한 사항

정정 ⑧ 검토 중 **`DeviceMode` 이름 배열의 범위 초과 읽기**를 발견하여 수정했습니다.

- `updateStmReportedState(uint8_t)`: 배열 7개(0~6)에 인덱스 검사 없음
  → **HEALING(7)이 도착하는 순간 잘못된 포인터를 `%s`로 역참조**
- `updateStmReportedState(DeviceMode)`: 배열이 6개인데 `ERROR = 6`
  → **현재도 범위를 벗어나고 있었음**

경계 검사 포함 `deviceModeName()`으로 통합했으며, 알 수 없는 값은 `"UNKNOWN"`을 반환합니다.
STM32가 7~10 확장안 대신 `0xFF` 최소안을 택하더라도 안전합니다.

누락되어 있어 그 이후 전부 한 칸씩 밀려 있었습니다. 상세는 §11.2.

## 1. 배경 및 목적

### 1.1 운영 환경

작업자 여러 명이 PSA 장치를 여러 대 착용하고 현장에서 작업하며, 작업 중 센서 데이터를
지속 수집합니다. 확정된 운영 조건은 다음과 같습니다.

| 조건 | 내용 |
|------|------|
| BLE 커버리지 | **음영 구간이 존재.** 교육으로 노트북 BLE 범위 체류를 유도하되 보장은 불가 |
| 전원 | **작업자가 배터리 교체로 임의 전원 차단 가능.** 소프트웨어가 개입할 수 없음 |
| 회수 | 물리적 카드 회수 절차를 매일 강제하기 어려움 |

### 1.2 채택한 아키텍처

| 계층 | 역할 | 유실 허용 |
|------|------|-----------|
| **Tier 1: STM32 → SD 카드** | **원본 기록 (system of record)** | ❌ 불가 |
| **Tier 2: 상시 백필 (SD → UART → BLE → PC)** | **주 회수 경로.** 작업 중 백그라운드로 밀린 구간을 지속 전송 | 재시도로 복구 |
| Tier 3: ESP32 → BLE 라이브 | 실시간 모니터링 | ✅ 허용 |
| Tier 4: LTE 1분 리포트 | 집계 + **로깅 헬스 상태** | ✅ 허용 |
| 예비 | 물리적 SD 수거 | 백필 실패 시에만 |

**핵심 원칙**: 기록의 완전성은 SD가 보증하고, 회수의 완전성은 **상시 백필**이 보증합니다.
BLE 라이브 스트림은 관측 수단이며 데이터 경로가 아닙니다.

### 1.3 현행 상태 (STM32 회신 §1)

> v1.0 §13 Q1은 "이미 SD에 기록 중"을 전제했으나 **사실이 아닙니다.**

현행 펌웨어는 부팅 약 8.2초 후 로깅이 영구 정지하며 `sensor.bin`은 **0 바이트**로 남습니다.
원인은 `SD_LOG_RECORD_SIZE`(56 B)가 STAT 페이로드 64 B 확장을 반영하지 못해
버퍼가 flush 시점보다 먼저 가득 차고, 가드 조건이 flush 검사보다 앞에 있어
**flush가 단 한 번도 호출되지 않는 데드락**입니다.

**따라서 본 문서의 요구사항은 전부 신규 구현 대상입니다.**
다만 SDMMC2 4비트 39.2 MHz 마운트 경로와 FatFs 연동은 검증되어 있습니다.

### 1.4 데이터량 및 대역 근거

| 항목 | 계산 | 결과 |
|------|------|------|
| SD 레코드 | 80 B × 10 Hz | **800 B/s = 2.9 MB/h** |
| 8시간 교대 1대분 | | **약 23 MB** |
| 32 GB 카드 | | 약 1,100시간 (140 교대) |
| UART 총 대역 (STM32 TX) | 115200 8N1 | 11,520 B/s |
| 라이브 STAT | 70 B × 10 Hz | 700 B/s |
| **백필 가용 대역** | | **10,820 B/s** |
| 백필 프레임 효율 | 레코드 80 B / 프레임 87 B | 92% |
| **따라잡기 배율** | 124.4 레코드/s ÷ 10 레코드/s | **약 12.4배** |

> UART는 **전이중**이므로 ESP→STM 방향의 ACK(6 B)는 STM32 TX 대역을 소비하지 않습니다.
> v1.1은 이를 더해 10,760 B/s로 잡았으나 실제 TX 가용은 10,820 B/s입니다 (회신 정정 ⑬).
> 배율 결론은 동일합니다.

이 12.4배가 상시 백필 설계의 근거입니다. 생성 속도보다 회수 속도가 12배 빠르므로
밀린 구간을 갚으면서 새 데이터도 감당할 수 있습니다.

| 음영 구간 | 복귀 후 회수 소요 |
|---|---|
| 3분 | 약 14초 |
| 30분 | 약 2.4분 |
| 1시간 | 약 4.8분 |
| **8시간 전체** | **약 39분** |

## 3. 기존 문서 정오 사항 ⚠️

v2.0 사양서의 일부 기술이 실제 구현과 다릅니다. **§3.1~§3.3은 STM32 팀이 코드 대조로
일치를 확인했습니다** (회신 §2). 구현 시 아래를 진실로 삼아 주십시오.

### 3.1 체크섬 알고리즘 — 문서 §2가 틀림

| 구분 | 내용 |
|------|------|
| ❌ 문서 §2 기술 | `CHKSUM = DIR ⊕ CMD ⊕ DATA[0..n]` |
| ✅ **실제 구현** | **초기값 `0xA5`에서 `STX`, `LEN`, `DIR`, `CMD`, `DATA` 전체를 XOR** |

```c
uint8_t chk = 0xA5;
chk ^= STX;  chk ^= LEN;  chk ^= DIR;  chk ^= CMD;
for (i = 0; i < dataLen; i++) chk ^= DATA[i];
```

문서 §9.3(STAT)에만 올바르게 기술된 이 방식이 **모든 메시지에 적용**됩니다.
문서 §12의 수신측 예제(`for i=2; i<length-2`)와 `sendAckResponse()`의
`command ^ 0x02` 역시 잘못된 기술입니다.

*근거*: ESP32 `src/uartMaster.cpp:533` / STM32 `comm_esp.c:19, :138-157`

### 3.2 LEN 필드 — 문서 §2 예제가 틀림

**LEN = `4 + dataLen`** (DIR 1 + CMD 1 + CHK 1 + ETX 1 + DATA n).
STAT(0x70)의 `LEN = 0x44 = 4 + 64`도 이 규칙과 일치합니다.

문서 §2의 `initTempSleep` 예제는 **LEN과 체크섬 두 곳 모두 오류**입니다.

```
❌ 문서 표기:  02 07 20 10 19 37 0E 03
               │  └ LEN=7 (오류: "7 = 1+1+2+1+1+1" 로 항을 하나 더 셈)
               └────────────────  체크섬 0x0E (오류)

✅ 정      답:  02 06 20 10 19 37 BF 03
계산: A5^02=A7 ^06=A1 ^20=81 ^10=91 ^19=88 ^37=BF
```

*근거*: ESP32 `src/uartMaster.cpp:600` / STM32 `comm_esp.c:18, :145`

### 3.3 커맨드 코드 점유 현황 — 문서보다 코드가 최신

| 코드 | 문서 | 실제 |
|------|------|------|
| `0x54` | deprecated `ctrlFanPWM` | **`ctrlSpkPlay`** (MP3 트랙 1~33) |
| `0x83` | 미기재 | **`evtWarn`** (LEN=1, payload 0 = 배터리 저전압) |
| `0x22` | `initPWMFan` | `initWearableFanPWM` |

**ESP32 측 카테고리 맵**: INIT `0x10-0x29` / REQ `0x30-0x49` / CTRL `0x50-0x69` /
STAT `0x70-0x79` / EVT `0x80-0x89` / ERR `0x90-0x99`

### 3.4 ⚠️ STM32 파서 상한은 ESP 맵보다 좁습니다 (v1.1 신규)

**§3.3은 ESP32 측 맵입니다. STM32 수신 파서는 화이트리스트 방식이며 상한이 더 낮습니다.**
등록되지 않은 커맨드는 **체크섬 검증 이전에 폐기**됩니다.

`User/Edit/src/comm_esp.c:172-184`

| 카테고리 | STM32 현재 상한 | 본 문서 신규 코드 | 확장 필요 |
|----------|-----------------|-------------------|-----------|
| INIT | `0x22` | `0x23` | → `0x29` |
| REQUEST | `0x42` | `0x43`, `0x44`, `0x45` | → `0x49` |
| CONTROL | `0x55` | `0x56` | → `0x69` |
| STATUS | **`== 0x70` 등가 비교** | `0x71` | → **범위 비교 `0x70~0x79`로 변경** |
| EVENT | `0x83` | `0x84` | → `0x89` |

> **STATUS 항목을 특히 주의해 주십시오.** 다른 카테고리는 상한만 올리면 되지만
> STATUS는 등가 비교(`u8_cmd == ESP_CMD_STAT`)라 **비교 방식 자체를 범위로 바꿔야** 합니다.

**STM32 측 수정 대상 3곳** (회신 §4)

1. `b_ESP_CmdCompare()` (`comm_esp.c:172`) — 화이트리스트 확장
2. `v_ESP_RxProc()` (`comm_esp.c:299-312`) — 디스패치 범위도 동일 확장
   (누락 시 체크섬은 통과하나 아무 동작도 하지 않음)
3. `v_ESP_RxAck()` (`comm_esp.c:314-318`) — 현재 `ESP_CMD_STAT`만 처리.
   `evtLogError(0x84)`와 `statLogChunk(0x71) END`에 대한 ESP측 ACK 수신 분기 추가

> 3번 누락 시 ACK마다 링버퍼가 1바이트 단위 재동기화에 들어가 수신 지연과 CPU 낭비가 발생합니다.

**이 확장이 선행되지 않으면 ESP32 구현이 끝나도 "통신이 안 되는" 증상으로 나타납니다.**

## 4. 데이터 식별 체계

### 🔑 병합 키 = `(deviceId, bootId, seq)`

| 요소 | 크기 | 생성 주체 | 설명 |
|------|------|-----------|------|
| `deviceId` | 6 B | **ESP32** | WiFi STA MAC. AWS IoT thing name과 동일 근거 |
| `bootId` | 4 B | **STM32** | 전원 인가마다 1 증가하는 **비휘발성 카운터** |
| `seq` | 4 B | **STM32** | 해당 부팅 세션에서 0부터 시작하는 샘플 순번 |

### ⚠️ bootId가 반드시 필요한 이유

작업자는 하루에도 여러 번 배터리를 교체합니다. seq는 부팅마다 0으로 리셋되므로
**seq만으로는 같은 장치의 오전 데이터와 오후 데이터를 구분할 수 없습니다.**

### 📌 bootId 저장 매체 (회신 Q2 확정)

**RTC 백업 레지스터는 사용 불가**입니다 — 이 보드에는 코인셀이 없어 VBAT 상실 시 소거되며,
펌웨어가 그 소거를 콜드부팅 판정에 사용하고 있습니다 (`mode.c:2621-2628`).

**채택**: 내장 플래시 섹터 7 (`0x080E0000`, 128 KB, 32 B 플래시워드 append)에
`bootId`와 `deviceId`를 함께 보관. 기존 `flash_cfg.c`의 마모 분산 구조를 재사용합니다.

> ⚠️ STM32 팀 제기 리스크: 32 B × 4,096 슬롯이므로 4,096 부팅마다 섹터 소거가 발생하고,
> 128 KB 소거에 1~4초가 걸리는 동안 XIP가 정지합니다. IWDG가 2초 설정이므로
> **소거는 부팅 초기 단계에서 IWDG 리프레시를 끼워 수행**하며, 로깅 중에는 절대 소거하지 않습니다.

### 📌 seq의 정의 (회신 Q3 확정)

**STM32 센싱 루프가 생성한 샘플 순번이며, UART 송신 성공 여부와 무관하게 증가합니다.**
`comm_esp.c:706-709`에서 UART 송신과 SD 기록이 나란히 일어나므로,
UART가 단선되어도 seq는 증가하고 SD 기록은 계속됩니다.

> ⚠️ **혼동 주의**: ESP32는 BLE 라이브 스트림에 **자체 카운터**를 별도로 실어 보냅니다.
> 이는 ESP32가 파싱한 STAT 프레임 수를 세는 **BLE 링크 품질 진단용**이며,
> 본 절의 STM32 seq와는 다른 값입니다. UART 프로토콜에는 영향이 없습니다.

### 🔒 설계 원칙: SD 로깅은 ESP32에 의존하지 않는다

ESP32 미부팅, UART 단선, deviceId 미수신 상황에서도 STM32는 bootId/seq로 기록을 계속하며
deviceId만 `UNKNOWN`으로 표기합니다 (§8.2).

## 5. 시각 기준 — 앵커 방식

### 🕐 STM32에 RTC를 요구하지 않습니다

| 주체 | 책임 |
|------|------|
| **STM32** | `seq`와 **부팅 후 경과 시간(`tickMs`)** 만 기록. 절대시각 불필요 |
| **ESP32** | `(deviceId, bootId, currentTickMs ↔ 절대시각)` **앵커 쌍**을 주기적으로 기록 |
| **병합 도구** | 앵커 쌍으로 각 레코드의 `tickMs`를 절대시각으로 환산 |

ESP32는 LTE 망 시각(`AT+CCLK`)으로 절대시각을 확보하며, 앵커는 `reqLogStatus`(§6.2)
폴링 응답의 `currentTickMs`로부터 생성합니다.

> **앵커 기준이 `lastSeq`가 아니라 `currentTickMs`인 이유**
> `lastSeq`는 flush 완료된 seq이므로 실제 샘플링보다 최대 2초 뒤처집니다. 이를 앵커로 쓰면
> 모든 레코드에 최대 2초의 **계통 오차**가 실립니다. `currentTickMs`는 응답 생성 시점의
> STM32 시계이고 모든 레코드가 같은 시계의 `tickMs`를 갖고 있으므로,
> 두 값을 직접 대응시키면 오차가 UART 왕복 지연(수 ms) 수준으로 떨어집니다.

**앵커 밀도**: 부팅 세션당 최소 2개(시작·종료 근처)면 수정발진자 드리프트까지
선형 보정되어 오차가 100 ms 이하로 유지됩니다.

> ⚠️ **엔디안 주의**: 현행 STM32 구현의 `tickMs`는 **LE**(`sd.c:427-430`)이나,
> 신규 포맷에서는 STAT 관례에 맞춰 **BE로 통일**합니다 (회신 Q1 합의).

## 6. 신규 커맨드 정의

### 6.0 공통 규칙

- 체크섬은 §3.1 규칙(초기값 `0xA5`)을 따릅니다.
- 멀티바이트 정수는 STAT(0x70)과 동일하게 **Big-Endian**입니다.
- **DATA 상한은 방향별로 다릅니다** (정정 ③):

| 방향 | 상한 | 근거 |
|------|------|------|
| **ESP → STM (수신)** | **32 B** | `comm_esp.c:233` — 초과 시 프레임 폐기 + 1바이트 재동기화 |
| **STM → ESP (송신)** | **90 B** | `comm_esp.c:132` (`ESP_TX_FMT_BUF_SIZE(96) - 6`) |

본 문서 신규 커맨드의 최대 DATA는 **ESP→STM 10 B**(`reqLogRead`),
**STM→ESP 86 B**(`reqLogFiles` 응답 만석 = 2 + 14×6)로 양쪽 상한 이내입니다.
`statLogChunk` DATA 청크는 81 B입니다.

- **§3.4의 파서 화이트리스트 확장이 선행되어야 아래 커맨드가 수신됩니다.**

### 6.1 `initLogIdentity` (0x23) — ESP→STM

장치 식별자를 전달합니다. ESP32는 `evtInitResult`(0x81) 수신 직후 다른 INIT 파라미터
재전송과 함께 이 커맨드를 보냅니다.

| 오프셋 | 크기 | 필드 | 설명 |
|--------|------|------|------|
| 0 | 6 | `deviceId` | WiFi STA MAC 6바이트 |

**DATA 6 B · 응답 ACK**

```
요청: 02 0A 20 23 A1 B2 C3 D4 E5 F6 B9 03
체크섬: A5^02=A7 ^0A=AD ^20=8D ^23=AE ^A1=0F ^B2=BD ^C3=7E ^D4=AA ^E5=4F ^F6=B9
응답: 02 04 02 23 82 03
```

**동작 요구사항**
- 수신 전에도 로깅은 진행되며, 이미 파일이 열려 있으면 **다음 로테이션부터 반영**합니다
  (파일 헤더 소급 수정 금지).
- 값은 비휘발성으로 보관하여 다음 부팅 시 ESP 통신 전에도 사용합니다 (§4의 플래시 섹터 7).

### 6.2 `reqLogStatus` (0x43) — ESP→STM

**요청 DATA**: 없음 · **응답 DATA**: 21 B

| 오프셋 | 크기 | 필드 | 설명 |
|--------|------|------|------|
| 0 | 1 | `logState` | 0=중지, 1=기록중, 2=오류 |
| 1 | 4 | `bootId` | 현재 부팅 세션 ID |
| 5 | 4 | `lastSeq` | 마지막으로 **flush 완료된** seq |
| 9 | 4 | `currentTickMs` | **응답 생성 시점의** 부팅 후 경과 ms — 시각 앵커용 |
| 13 | 2 | `freeSpaceMB` | 잔여 용량 MB (65535 초과 시 65535 고정) |
| 15 | 2 | `fileIndex` | 현재 파일 인덱스 |
| 17 | 2 | `writeErrorCount` | 부팅 후 누적 쓰기 실패 횟수 |
| 19 | 1 | `formatVersion` | 레코드 포맷 버전 (=1) |
| **20** | **1** | **`deviceMode`** | **현재 모드.** §7.1과 동일한 코드계 — v1.2 신규 |

> ### 왜 `deviceMode`를 여기에 넣는가 (회신 정정 ⑧)
>
> v1.1 §12는 `evtMode(0x82)` 추적으로 경보를 게이팅하려 했으나 **구현할 수 없습니다.**
> `BOOTING` / `WAKE_UP` / `OFF`는 프로토콜 열거형에 값이 없었고 `evtMode`가 송신되지도
> 않으므로, ESP32는 이 모드들을 **관측할 방법 자체가 없습니다.**
>
> 특히 `OFF` 상태에서는 샘플링이 멈추는데 ESP32는 마지막으로 받은 `evtMode`(예: WAITING)를
> 그대로 믿고 있어, **전원이 켜진 채 OFF로 놓인 장치가 계속 오경보를 냅니다** —
> §12가 막으려던 바로 그 상황입니다.
>
> STM32가 현재 모드를 직접 보고하면 게이팅이 `evtMode` 추적에서 **완전히 독립**하고,
> ESP32 재부팅 직후에도 즉시 정확합니다.

> - `lastSeq`는 flush 완료 기준이어야 합니다. 버퍼에만 있는 값을 보고하면
>   ESP32가 존재하지 않는 데이터를 기록된 것으로 집계합니다.
> - `currentTickMs`는 §7 레코드의 `tickMs`와 **동일한 시계**여야 합니다.

```
요청: 02 04 20 43 C0 03

응답 예 (기록중, bootId=42, lastSeq=123456, tick=12345678ms, 여유 7500MB,
         파일#3, 오류0, fmt=1, mode=WAITING(1)):
02 19 02 43 01 00 00 00 2A 00 01 E2 40 00 BC 61 4E 1D 4C 00 03 00 00 01 01 B6 03
 │  │        │  └─ bootId ─┘ └─ lastSeq ┘ └ currentTick┘ └free┘ └idx┘ └err┘ │  │
 │  └ LEN = 4 + 21 = 25 (0x19)                                        fmt ──┘  │
 └ STX                                                          deviceMode ────┘
체크섬 = 0xB6 · 전체 27 B
```

**폴링 주기**: ESP32는 1분 주기로 조회하여 (a) 시각 앵커 생성, (b) §12 헬스 리포트 필드 확보.

### 6.3 `reqLogFiles` (0x45) — ESP→STM ⭐ v1.1 신규

**장치에 존재하는 로그 파일 목록**을 조회합니다. PC가 어느 `bootId`의 어느 구간을
아직 못 받았는지 판단하려면 먼저 무엇이 있는지 알아야 합니다.

**요청 DATA (1 B)**

| 오프셋 | 크기 | 필드 | 설명 |
|--------|------|------|------|
| 0 | 1 | `startIndex` | 페이지네이션 시작 인덱스 (0부터) |

**응답 DATA (2 + 14N B, N ≤ 6)**

| 오프셋 | 크기 | 필드 | 설명 |
|--------|------|------|------|
| 0 | 1 | `totalCount` | 장치에 있는 전체 파일 수 |
| 1 | 1 | `returnedCount` | 이번 응답에 담긴 항목 수 (N) |
| 2 + 14i | 4 | `bootId` | 항목 i의 부팅 세션 ID |
| 6 + 14i | 4 | `firstSeq` | 항목 i의 첫 레코드 seq |
| 10 + 14i | 4 | `lastSeq` | 항목 i의 마지막 레코드 seq |
| 14 + 14i | 2 | `fileIndex` | 항목 i의 파일 인덱스 |

STM→ESP 상한 90 B이므로 **한 응답에 최대 6개**입니다. `totalCount > 6`이면
ESP32가 `startIndex`를 올려 반복 조회합니다.

```
요청 (첫 페이지): 02 05 20 45 00 C7 03

응답 예 (전체 1개, bootId=42, seq 0~288000, 파일#0):
02 14 02 45 01 01 00 00 00 2A 00 00 00 00 00 04 65 00 00 00 BF 03
            │  │  └─ bootId ─┘ └ firstSeq ┘ └ lastSeq ─┘ └idx┘
            │  └ returnedCount=1
            └ totalCount=1
체크섬 = 0xBF
```

**정렬 순서**: `bootId` 오름차순, 동일 bootId 내에서는 `fileIndex` 오름차순.
가장 오래된 미전송 데이터가 먼저 나오도록 하기 위함입니다.

**인덱스 상한 초과 시** (회신 정정 ⑫): STM32는 부팅 시 1회 스캔한 결과를 RAM 인덱스로
보관하며 상한은 **256개**입니다(항목 14 B × 256 = 3.6 KB). 초과하면 **가장 오래된 항목부터
인덱스에서만 제외**하고 `totalCount`에는 인덱스에 담긴 수를 보고합니다.
**파일 자체는 삭제하지 않으므로** 물리 회수(예비 경로)로는 여전히 확보할 수 있습니다.

> 상한 256개는 로테이션 규칙(§8.3: 부팅마다 + 1시간마다)상 교대당 최대 9개 기준으로
> **약 28 교대분**입니다. 정상 운영에서는 도달하지 않습니다.

### 6.4 `reqLogRead` (0x44) — ESP→STM ⭐ v1.1 신규

지정 구간의 레코드 전송을 요청합니다.

**요청 DATA (10 B)**

| 오프셋 | 크기 | 필드 | 설명 |
|--------|------|------|------|
| 0 | 4 | `bootId` | 대상 부팅 세션 (**현재 세션이 아니어도 됨**) |
| 4 | 4 | `startSeq` | 시작 seq (포함) |
| 8 | 2 | `count` | 요청 레코드 수 (**권장 128** — 근거는 §9.2) |

**응답**: 즉시 ACK 후, `statLogChunk`(0x71) 프레임을 연속 송신 (§6.5, §9)

```
요청 (bootId=42의 seq 123456부터 1000개):
02 0E 20 44 00 00 00 2A 00 01 E2 40 03 E8 AF 03
            └─ bootId ─┘ └ startSeq ┘ └cnt┘
체크섬 = 0xAF

ACK: 02 04 02 44 E5 03
```

> ### 🔴 과거 세션 읽기가 필수 요구사항입니다
>
> `bootId`가 **현재 세션이 아닌 경우에도 반드시 동작해야 합니다.**
>
> 작업자가 BLE 음영 지역에서 작업을 마치고 곧바로 배터리를 교체하면, 마지막 구간은
> SD에 있지만 미전송 상태로 남습니다. 다음 전원 투입 시 장치는 이미 `bootId=43`이고
> 밀린 데이터는 `bootId=42` 파일 안에 있습니다.
>
> 이 요구사항이 빠지면 **"전송 전에 껐다 켜면 그 구간은 영원히 올라오지 않는"**
> 조용한 실패가 됩니다. SD에는 멀쩡히 있으므로 아무도 눈치채지 못합니다.

**구현**: `/LOG/<deviceId>/<bootId:08X>_*.psa` 를 탐색하여 해당 seq를 포함하는 파일을 열고,
파일 헤더의 `firstSeq`로부터 오프셋을 계산합니다.

```
레코드 오프셋 = 512 + (startSeq - firstSeq) × 80
```

고정 크기 레코드이므로 **순차 탐색 없이 산술로 위치를 구할 수 있습니다.**

> ### 🔴 이 식은 §7.4의 불변식에 전적으로 의존합니다
>
> **파일 내 n번째 레코드의 `seq`는 정확히 `firstSeq + n` 이어야 합니다.**
>
> 레코드를 하나라도 건너뛰면 그 지점 이후 오프셋과 seq의 대응이 80 B씩 어긋나고,
> STM32는 요청한 seq와 **다른 레코드를 그대로 돌려보냅니다.** PC는 요청 구간을 못 받았다고
> 판단해 재요청하고, 다시 같은 어긋난 데이터를 받아 **무한 재요청 루프**에 빠집니다.
> 또는 PC가 그대로 병합하면 **아무도 눈치채지 못하는 부분 유실**이 됩니다.
>
> §7.4의 플레이스홀더 규칙과 §8.3의 로테이션 규칙이 이 불변식을 보장합니다.

### 6.5 `statLogChunk` (0x71) — STM→ESP ⭐ v1.1 신규

백필 데이터를 전송합니다. **DIR = `0x20`** (자발 메시지).

**DATA — `chunkType`에 따라 두 형태**

**(a) DATA 청크 — `chunkType = 0x01`, DATA 81 B**

| 오프셋 | 크기 | 필드 |
|--------|------|------|
| 0 | 1 | `chunkType` = `0x01` |
| 1 | 80 | §7 레코드 원본 (`seq`는 레코드 오프셋 0에 포함) |

프레임 전체 87 B. **ESP32는 ACK하지 않습니다** (§9.2 참조).

> ### 🔴 수신 측은 레코드 소비 전 `flags` bit1을 반드시 검사합니다
>
> **CRC 통과는 "레코드가 온전하다"는 뜻이지 "센서 값이 유효하다"는 뜻이 아닙니다.**
>
> 플레이스홀더 레코드(§7.4)는 `statPayload`가 전부 `0x00`이면서 **CRC가 정상**입니다.
> 0으로 채워진 IMU·FSR·ToF는 파싱에 성공하므로, bit1을 검사하지 않으면
> **조작된 0 값이 그래프·분석·학습 데이터에 그대로 섞여 들어갑니다.**
>
> 이는 병합 도구뿐 아니라 **실시간 소비 경로 전부**에 적용됩니다.

**(b) END 청크 — `chunkType = 0x00`, DATA 6 B**

| 오프셋 | 크기 | 필드 | 설명 |
|--------|------|------|------|
| 0 | 1 | `chunkType` = `0x00` | |
| 1 | 1 | `result` | 아래 표 참조 |
| 2 | 4 | `lastSeqSent` | 실제로 송신한 마지막 seq |

| `result` | 의미 |
|----------|------|
| **0** | **요청 범위 중 장치가 보유한 분량을 전부 송신함.** 요청 개수보다 적을 수 있음 |
| 1 | 해당 `bootId` 파일 없음 |
| 2 | 요청 범위에 해당하는 레코드 없음 |
| 3 | 읽기 오류 |
| 4 | 라이브 우선순위로 중단 (§9.3) |

> **`result = 0`은 "요청한 개수를 다 보냈다"는 뜻이 아닙니다** (회신 정정 ⑩).
> 파일 끝에 도달했거나 불완전 레코드를 만나 조기 종료한 경우도 포함합니다.
> **PC는 `count`가 아니라 `lastSeqSent`로 잔여를 판단**하며,
> `lastSeqSent + 1`부터 다시 요청하면 됩니다.

**ESP32가 END 청크에만 ACK를 보냅니다.**

```
END 예 (완료, 마지막 송신 seq=124455):
02 0A 20 71 00 00 00 01 E6 27 3C 03
            │  │  └ lastSeqSent ┘
            │  └ result=0 (완료)
            └ chunkType=0 (END)
체크섬 = 0x3C

ACK: 02 04 02 71 D0 03
```

### 6.6 `ctrlLogEnable` (0x56) — ESP→STM

| 매개변수 | 타입 | 범위 | 설명 |
|---------|------|------|------|
| `enable` | uint8 | 0-1 | 0=중지(flush+close), 1=시작 |

**DATA 1 B · 응답 ACK**

```
중지 요청: 02 05 20 56 00 D4 03
```

**기본 동작**: 이 커맨드를 받지 않아도 **부팅 시 자동으로 로깅을 시작**합니다.

**용도**: 물리적 카드 회수(예비 경로)를 쓸 때의 안전 제거용입니다. 상시 백필이 주 경로이므로
평상시에는 사용하지 않습니다.

### 6.7 `evtLogError` (0x84) — STM→ESP

**DATA 3 B · DIR `0x20` · ESP32가 ACK**

| 오프셋 | 크기 | 필드 | 설명 |
|--------|------|------|------|
| 0 | 1 | `reason` | 사유 코드 |
| 1 | 2 | `detail` | FatFs 오류코드 등 (없으면 0) |

| `reason` | 의미 | STM32 후속 동작 |
|----------|------|-----------------|
| 0 | 마운트 실패 | 주기적 재마운트 시도 |
| 1 | 카드 미삽입 / 런타임 탈거 | 재삽입 감지 시 새 파일로 재개 |
| 2 | 용량 부족 | 로깅 중지, `logState=2` |
| 3 | 쓰기 실패 | 재시도 후 실패 시 재마운트 |
| 4 | 파일시스템 손상 | 로깅 중지, `logState=2` |
| 5 | 백필 읽기 실패 | 해당 요청만 실패, 로깅은 계속 |

```
용량 부족: 02 07 20 84 02 00 00 06 03
```

> **중요**: 어떤 로깅 오류가 발생하더라도 **자세 제어·안전 기능은 정상 동작을 유지해야 합니다.**

## 7. SD 레코드 포맷

### 📦 고정 80바이트 레코드

고정 크기가 핵심 요구사항입니다. 전원이 쓰기 도중 끊겨도 레코드 경계를 산술로 찾을 수 있어야
복구가 가능하고, §6.4의 오프셋 계산도 이에 의존합니다.

| 오프셋 | 크기 | 필드 | 인코딩 | 설명 |
|--------|------|------|--------|------|
| 0 | 4 | `seq` | uint32 BE | 부팅 세션 내 샘플 순번, 0부터 단조 증가 |
| 4 | 4 | `tickMs` | uint32 **BE** | STM32 부팅 후 경과 시간 (ms) |
| 8 | 64 | `statPayload` | — | **STAT(0x70)의 DATA 64 B를 그대로 복사** |
| 72 | 1 | `deviceMode` | uint8 | **0~10 — §7.1 참조** |
| 73 | 1 | `flags` | uint8 | bit0: STAT UART 송신 성공 / **bit1: 무효 샘플 (§7.4)** |
| 74 | 2 | `errorMask` | uint16 BE | `errInit`(0x90) 비트마스크 스냅샷 (§11) |
| 76 | 2 | `reserved` | — | 0x0000 |
| 78 | 2 | `crc16` | uint16 BE | 오프셋 0~77의 CRC-16/CCITT-FALSE |

**합계: 80 bytes** · 10 Hz 기준 800 B/s

### 7.1 `deviceMode` 코드계 ⚠️ (회신 정정 ⑧)

**STM32에는 서로 다른 두 개의 모드 열거형이 있습니다.** 레코드와 `reqLogStatus`(0x43)에
기록·보고하는 값은 **프로토콜 열거형(`e_ESP_EVT_MODE_t`)** 기준입니다.

| 값 | 프로토콜 (`e_ESP_EVT_MODE_t`) | 샘플링 | 비고 |
|---|---|---|---|
| 0 | `SLEEP` | ✅ | **SLEEP에서도 샘플링은 계속됩니다** |
| 1 | `WAITING` | ✅ | |
| 2 | `FORCE_UP` | ✅ | |
| 3 | `FORCE_ON` | ✅ | |
| 4 | `FORCE_DOWN` | ✅ | |
| 5 | `TEST` | ✅ | 기록됨 — v1.1의 "0~4" 범위로는 부족 |
| 6 | `ERROR` | ❌ | |
| **7** | **`HEALING`** | ✅ | **v1.2 신설.** 부팅 직후 약 1초 전이 상태 |
| **8** | **`BOOTING`** | ❌ | **v1.2 신설** |
| **9** | **`WAKE_UP`** | ❌ | **v1.2 신설** |
| **10** | **`OFF`** | ❌ | **v1.2 신설.** 전원 인가 상태에서 꺼짐 |

> **🔴 STM32는 내부 ID(`e_modeID_t`)를 프로토콜 코드로 반드시 변환해야 합니다.**
> 두 체계는 값이 다릅니다 — 예를 들어 내부 `modeWAITING = 2`인데 프로토콜에서 2는
> `FORCE_UP`입니다. 변환을 빠뜨리면 **조용히 어긋난 모드가 기록**됩니다.

**HEALING 신설 이유**: 부팅 직후 약 1초간(레코드 약 10개) 샘플링은 일어나는데
`evtMode`가 송신되지 않아 대응 코드가 없었습니다. 7을 신설하고 STM32가
`v_Mode_Healing()`에서 `evtMode`도 함께 송신합니다.

**미지 값 처리**: ESP32는 표에 없는 값을 받아도 크래시하지 않습니다 — `UNKNOWN`으로
처리하고 동작을 계속합니다(경계 검사 적용 완료).

> ### 🔴 `0xFF = UNKNOWN` 최소안은 채택 불가입니다
>
> 회신 v1.1 §2.4가 대안으로 제시한 "샘플링 정지 모드를 전부 `0xFF`로 보고" 방식은
> **§12의 경보 게이팅과 양립할 수 없습니다.**
>
> §12는 미지 값에 대해 **억제하지 않는** 것이 원칙입니다 — 모르는 상태를 정상으로
> 가정하지 않기 위해서입니다. 그런데 `BOOTING` / `WAKE_UP` / `OFF`가 전부 `0xFF`로 오면
> 게이팅이 한 번도 걸리지 않아, **⑧이 해결하려던 오경보 문제가 그대로 돌아옵니다.**
>
> **7~10 전체 추가가 필수 요구사항입니다.**

### 💡 `statPayload` 64 B를 그대로 복사하는 이유

- STM32는 이미 만들어 둔 버퍼를 복사만 하면 됨 (추가 직렬화 코드 불필요)
- 병합 도구·분석 스크립트가 **동일한 파서 하나**로 UART/SD 양쪽을 처리
- 백필 청크가 레코드를 그대로 실어 나르므로 변환 지점이 없음

### 🔐 CRC-16/CCITT-FALSE 규격

```
다항식: 0x1021, 초기값: 0xFFFF, 반전 없음, XorOut: 0x0000
검증값: "123456789" → 0x29B1
```

### 7.4 🔴 불변식과 플레이스홀더 레코드 (회신 정정 ⑨)

#### 불변식

> **파일 내 n번째 레코드의 `seq`는 정확히 `firstSeq + n` 이다.**
> 이를 만족시킬 수 없는 상황에서는 **플레이스홀더 레코드를 기록하거나 파일을 로테이션**해야 하며,
> **레코드를 건너뛰어서는 안 된다.**

§6.4 백필 산술 조회의 정확성 전체가 이 불변식에 의존합니다.

#### 플레이스홀더 레코드

레코드를 만들 수 없는 상황(`statPayload` 길이가 64가 아닌 등)에서는
**버리지 말고 자리를 채웁니다.**

| 필드 | 플레이스홀더 값 |
|------|-----------------|
| `seq` | **정상 값** ← 불변식 유지의 핵심 |
| `tickMs` | 정상 값 |
| `statPayload` | **0x00 채움** |
| `deviceMode` | 정상 값 |
| `flags` | **bit1 = 1 (무효 샘플)** |
| `errorMask` | 정상 값 |
| `crc16` | **정상 계산** ← 레코드 자체는 유효해야 백필 경로가 걸러내지 않음 |

동시에 `writeErrorCount`를 증가시켜 §12 헬스 리포트에 드러나게 합니다.

**PC 병합 도구는 `flags` bit1을 유실로 계수합니다** — CRC 불일치와 동일 취급(§10.3).

> v1.1 §7의 **"레코드를 드롭하고 `writeErrorCount` 증가"는 철회되었습니다.**
> 백필이 비범위였던 v1.0 시점에는 안전한 선택이었으나, §6.4가 산술 조회를 도입한 이상
> 성립하지 않습니다. (STM32 팀이 자신들의 v1.0 회신 §1.5를 스스로 철회했습니다.)

#### 갭은 파일 경계에만 존재합니다

플레이스홀더로 막을 수 없는 경로가 하나 남습니다 — **`f_write()`의 부분 성공**입니다.
버퍼 1,600 B 중 1,000 B만 기록되면 파일 포인터가 레코드 경계에서 어긋난 채 다음 flush가
이어져 **파일 내부에 정렬 붕괴**가 생깁니다.

**규칙**: 쓰기 실패 또는 부분 쓰기가 감지되면 **즉시 파일을 닫고 로테이션**합니다
(`fileIndex` 증가, 새 파일의 `firstSeq`는 실제로 기록되는 첫 레코드의 seq).

이로써 다음이 성립합니다.

> **갭은 파일과 파일 사이에만 존재할 수 있고, 파일 내부에는 존재하지 않는다.**

PC는 `reqLogFiles`(§6.3) 결과에서 파일 A의 `lastSeq`와 파일 B의 `firstSeq` 사이가
벌어진 것으로 갭을 **관측**할 수 있습니다. 조용히 사라지지 않습니다.

#### 컴파일 타임 검증

- `_Static_assert(sizeof(x_sd_record_t) == 80, ...)`
  (`flash_cfg.c:30`에 동일 패턴 선례 있음)

§1.3에서 확인했듯 선언 크기와 실제 크기의 불일치는 **이미 한 번 로깅을 통째로 멈춘 원인**입니다.
`formatVersion`은 *의도적* 포맷 변경은 다루지만 *실수로 어긋난 길이*는 잡지 못합니다.

## 8. 파일 헤더 / 명명 / 로테이션

> **이 절은 병합 도구 및 백필 프로토콜과의 계약입니다.**

### 8.1 파일 헤더 (512 B, 섹터 정렬)

| 오프셋 | 크기 | 필드 | 설명 |
|--------|------|------|------|
| 0 | 4 | `magic` | ASCII `"PSA1"` = `50 53 41 31` |
| 4 | 2 | `formatVersion` | =1 |
| 6 | 2 | `recordSize` | =80 |
| 8 | 6 | `deviceId` | 미수신 시 `FF FF FF FF FF FF` |
| 14 | 4 | `bootId` | |
| 18 | 4 | `fileIndex` | |
| 22 | 4 | `firstSeq` | 이 파일 첫 레코드의 seq — **§6.4 오프셋 계산의 기준** |
| 26 | 4 | `sampleRateMilliHz` | =10000 (10.000 Hz) |
| 30 | 2 | `headerCrc` | 오프셋 0~29의 CRC-16/CCITT-FALSE |
| 32 | 480 | `reserved` | 0x00 채움 |

레코드는 오프셋 512부터 시작합니다 → **유효 파일 크기 = 512 + 80 × N**

### 8.2 파일 명명 규칙

LFN이 활성화되어 있으므로 (`_USE_LFN = 1`, `_MAX_LFN = 255`) 아래 명명을 그대로 사용합니다.

```
/LOG/<deviceIdHex>/<bootId:08X>_<fileIndex:04X>.psa

예: /LOG/A1B2C3D4E5F6/0000002A_0003.psa
    /LOG/UNKNOWN/0000002B_0000.psa      ← deviceId 미수신 상태로 부팅
```

- `deviceIdHex`: 대문자 12자리 hex, 구분자 없음
- **8.3 호환 대체안은 폐기되었습니다** (회신 정정 ④)

### 8.3 로테이션 규칙

새 파일을 여는 조건 (`fileIndex`를 1 증가):

| 조건 | 값 | 근거 |
|------|-----|------|
| **부팅** | 매 부팅 | `bootId`가 바뀌면 반드시 새 파일 (`fileIndex`는 0부터) |
| **경과 시간** | 1시간 | 손상 시 피해를 1시간분으로 제한 |
| **파일 크기** | 32 MB | 상동 |
| **카드 재삽입** | 즉시 | §10.4 |
| **쓰기 실패·부분 쓰기** | 즉시 | §7.4 — 파일 내부 정렬 붕괴 차단 |

> ### 🔴 로테이션은 close-then-open 순서로 (회신 정정 ⑪)
>
> **반드시 구 파일을 닫은 뒤 신 파일을 엽니다.** 신 파일을 먼저 열면 순간적으로
> 핸들이 3개(구 쓰기 + 신 쓰기 + 백필 읽기)가 되어 `_FS_LOCK` 상한에 걸립니다.
> §16.2에서 `_FS_LOCK`을 2 → 4로 상향하더라도 이 순서는 지켜야 합니다.

### 8.4 카드 포맷 요건 ⚠️

`_FS_EXFAT = 0` (FatFs R0.12c)이므로 **exFAT을 지원하지 않습니다.**

| 카드 | 결과 |
|------|------|
| 32 GB 이하 (SDHC / FAT32) | ✅ 정상 |
| 64 GB 이상 SDXC, 공장 출하 exFAT 상태 | ❌ **마운트 실패** |

> **운영 지침에 "카드는 FAT32로 포맷할 것"을 반드시 포함해 주십시오.**
> 현장에서 64 GB 카드를 그대로 꽂으면 `evtLogError(0)`만 반복하고 데이터가 하나도 남지 않습니다.

§1.4 기준 32 GB에 약 1,100시간이 들어가므로 용량상 문제는 없습니다.

### 8.5 전송 완료 관리 — **PC가 주도**

**STM32는 이미 기록된 로그 파일을 절대 수정하지 않습니다.** 전송 완료 표시를
파일 헤더에 되쓰면 추가 쓰기와 손상 위험이 생기기 때문입니다.

| 주체 | 보유 상태 |
|------|-----------|
| **PC (병합 저장소)** | **정본.** 어느 `(deviceId, bootId, seq)`를 확보했는지 |
| ESP32 (NVS) | 보조 캐시. 최근 전송한 고수위 표시 |
| STM32 | **없음.** 파일 목록만 제공 (§6.3) |

PC가 정본을 갖는 이유는 **검증까지 마친 주체가 PC**이기 때문입니다.
ESP32 NVS가 지워지거나 펌웨어가 재기록되어도 PC 상태로부터 재구축할 수 있습니다.

## 9. 백필 동작 사양

### 9.1 기본 흐름

```
① PC: reqLogFiles(0x45)로 장치의 파일 목록 확보
② PC: 자신의 병합 저장소와 대조하여 미확보 구간 산출
③ PC: reqLogRead(0x44)로 (bootId, startSeq, count) 요청
④ STM32: statLogChunk(0x71) DATA 청크 연속 송신 → END 청크
⑤ PC: 수신 레코드 CRC 검증 후 병합 저장소에 반영
⑥ 미확보 구간이 남아 있으면 ③으로
```

ESP32는 이 흐름에서 **릴레이 역할**입니다 — UART 요청을 전달하고 청크를 BLE로 중계합니다.

### 9.2 흐름 제어 — 청크별 ACK 없음

**DATA 청크에는 ACK를 보내지 않습니다.** 매 청크마다 왕복 대기를 하면 UART 지연이
그대로 처리량 손실이 되어 12.4배 배율이 무너집니다.

유실 감지는 **seq 연속성**으로 합니다. 중간이 비면 PC가 해당 구간만 다시 요청하면 되고,
원본은 SD에 그대로 있으므로 재요청은 항상 안전합니다.

**흐름 제어는 요청의 `count`로 합니다. 권장값은 128 레코드입니다** (약 11 KB, 약 1초 분량).

### 왜 배치를 작게 하는가 — BLE 재연결 대응

STM32는 **BLE 연결 상태를 알 수 없습니다.** UART 요청만 받을 뿐이므로, 전송 도중
BLE가 끊겨도 청크를 계속 밀어내고 ESP32는 그것을 버려야 합니다.

별도의 중단 명령을 두는 대신 **배치를 짧게 유지하여 자연스러운 중단점을 만듭니다.**
ESP32는 BLE가 끊기면 다음 `reqLogRead`를 보내지 않으면 되고, 낭비는 **최대 1배치(약 1초분)**
로 제한됩니다.

| `count` | 배치 크기 | 소요 | BLE 끊김 시 낭비 |
|---------|-----------|------|------------------|
| 1000 | 87 KB | 약 8.1초 | 최대 8초분 |
| **128 (권장)** | **11 KB** | **약 1.0초** | **최대 1초분** |

요청 오버헤드는 무시할 수준입니다 — 요청 16 B + ACK 6 B = 22 B가 배치 11,136 B에 대해
**0.2%** 입니다. 따라잡기 배율 12.4배는 사실상 그대로 유지됩니다.

### ESP32 측 요구사항

- BLE 미연결 상태에서는 새 `reqLogRead`를 발행하지 않습니다.
- 진행 중이던 배치의 잔여 청크는 폐기합니다(버퍼링하지 않음). 원본이 SD에 있으므로
  재연결 후 같은 구간을 다시 요청하면 됩니다.
- 재연결 후에는 **PC가 보유 현황을 기준으로** 요청 구간을 다시 산출합니다(§8.5).
  ESP32는 중단 지점을 기억할 필요가 없습니다.

### 9.3 우선순위 — 라이브 STAT가 항상 우선

**백필은 라이브 STAT(0x70) 송신을 절대 지연시켜서는 안 됩니다.**

- STAT 송신 시점이 되면 진행 중인 청크 스트림을 **프레임 경계에서 중단**하고 STAT를 먼저 보냅니다.
- 중단이 길어지면 END 청크를 `result=4`(우선순위 중단)로 보내고 요청을 종료합니다.
  PC는 `lastSeqSent` 다음부터 다시 요청합니다.

라이브가 700 B/s, 백필 가용이 10,820 B/s이므로 정상 상황에서 충돌은 드뭅니다.

### 9.4 전원 차단 내성

전송 도중 배터리가 빠져도 **원본은 SD에 남아 있으므로 손실이 없습니다.**
다음 전원 투입 시 PC가 `reqLogFiles`로 목록을 다시 받아 미확보 구간을 재요청합니다.

이때 밀린 데이터는 **이전 `bootId`의 파일**에 있으므로,
§6.4의 과거 세션 읽기 요구사항이 반드시 충족되어야 합니다.

### 9.5 실측이 필요한 항목 — BLE 동시 접속

**BLE가 실어야 할 양의 상한은 UART가 실어 나르는 양과 같습니다.** UART 총 대역
11,520 B/s 안에 라이브 STAT와 백필 청크가 모두 들어 있으므로, 둘을 따로 더하면
중복 계산이 됩니다.

| 상태 | 장치 1대당 BLE 수요 |
|------|---------------------|
| **백필 진행 중 (피크)** | **약 11 kB/s** — UART 상한에 수렴 |
| **따라잡기 완료 (정상)** | **약 1 kB/s** — 라이브 스트림만 |

즉 11 kB/s는 **밀린 구간을 갚는 동안에만 나타나는 일시적 피크**이고, 따라잡고 나면
1 kB/s로 떨어집니다. 여러 대가 동시에 백필을 시작하는 시점(작업 복귀 직후 등)이
최악의 순간이며, 그 구간만 넘기면 부담이 사라집니다.

노트북 어댑터 하나에 여러 대가 붙으면 총합이 커지고 어댑터·OS별 편차가 큽니다.

**몇 대까지 동시 백필이 가능한지는 현장 실측으로 확정합니다.**
부족할 경우 완화책은 두 가지입니다.

- 백필을 **한 대씩 순차 진행** (전체 소요는 늘지만 교대 시간 내 완료 가능)
- 수집 노트북 증설

## 10. 내구성 요구사항

### 10.1 보호 대상의 정의

> **배터리 교체 시점의 데이터는 보호 대상이 아닙니다.**
> 배터리 교체는 작업 종료 후에 일어나므로 그 순간의 샘플은 작업 데이터가 아닙니다.
> 따라서 홀드업 커패시터 등 하드웨어 대책은 채택하지 않습니다.

flush 정책이 보호하는 것은 **작업 중 예기치 않은 전원 손실**입니다.

- 작업 중 배터리 방전 (`evtWarn` 배터리 저전압 경고가 이미 존재)
- 커넥터 유격, 순간 전압 강하

### 10.2 flush 정책

| 항목 | 요구사항 |
|------|----------|
| flush 주기 | **최대 2초** (또는 20 레코드) 마다 `f_sync()` 상당 수행 |
| 최대 손실 상한 | **20 샘플 (2초)** |
| 파일 닫기 | `ctrlLogEnable(0)` 수신 시 즉시 flush + close |

**STM32 팀이 이 정책을 지지했습니다** (회신 Q5): 현행 10초/5,600 B 일괄 쓰기 대비
회당 1,600 B(3~4섹터)로 **피크가 1/3 이하**로 낮아져 100 Hz 제어 루프와 IWDG(2초) 관점에서
오히려 유리합니다.

### 10.3 부분 레코드 처리

```
유효 레코드 수 N = (파일크기 - 512) / 80
잔여 바이트 (파일크기 - 512) % 80 → 마지막 불완전 레코드로 간주하여 절삭
```

- **재부팅 시 이전 파일을 수리하려 하지 마십시오.** 항상 새 파일을 열고,
  절삭·검증은 PC 병합 도구가 오프라인에서 수행합니다.
- CRC 불일치 레코드는 폐기하되 해당 `seq`는 **갭으로 계수**하여 유실률 통계에 반영합니다.
- **플레이스홀더 레코드(`flags` bit1 = 1)도 동일하게 유실로 계수**합니다 (§7.4).
  CRC는 정상이므로 CRC 검사로는 걸러지지 않습니다 — 반드시 플래그로 판정하십시오.
- **§6.4 백필 시에도 동일**: 불완전 레코드는 송신하지 않고 END로 종료하며,
  이때 `result = 0`은 "보유분 소진"을 뜻합니다 (§6.5). PC는 `lastSeqSent`로 잔여를 판단합니다.

### 10.4 매체 이상 시 동작

| 상황 | 요구 동작 |
|------|-----------|
| 부팅 시 카드 없음 | `evtLogError(1)` 후 **정상 동작 지속**, 주기적 재감지 |
| 런타임 탈거 | `evtLogError(1)`, 재삽입 감지 시 **새 파일**로 재개 |
| 쓰기 실패 | 재시도 → 실패 지속 시 재마운트 → `evtLogError(3)` |
| 용량 부족 | `evtLogError(2)`, 로깅 중지 (**순환 삭제 없음** — §14 Q6) |

**모든 경우에 자세 제어·히터·안전 로직은 영향을 받지 않아야 합니다.**

## 11. 에러 처리

### 11.1 `errInit`(0x90) 비트마스크 — 정정됨 🔴

**v1.0 §10.1의 비트값이 틀렸습니다.** STM32 `mode.h:170-185`가 진실이며,
`mode.c:2334`가 이 마스크를 **가공 없이 그대로** 전송합니다.

| 비트 | 값 | 이름 | 설명 |
|------|-----|------|------|
| 0 | 0x0001 | `ERR_IR_TEMP` | IR(구동기) 온도 센서 |
| 1 | 0x0002 | `ERR_AMB_TEMP` | 환경 온도 센서 |
| 2 | 0x0004 | `ERR_BOARD_TEMP` | 보드 온도 센서 |
| 3 | 0x0008 | `ERR_IMU` | IMU |
| 4 | 0x0010 | `ERR_FAN` | 착용부(blow) 팬 |
| 5 | 0x0020 | `ERR_COOL_FAN` | 냉각 팬 |
| 6 | 0x0040 | `ERR_TOF` | ToF 거리 센서 |
| 7 | 0x0080 | `ERR_AUDIO` | 오디오 시스템 |
| 8 | 0x0100 | `ERR_FSR` | 압력 센서 |
| **9** | **0x0200** | **`ERR_SD_CARD`** | **SD 카드 마운트/매체** |
| **10** | **0x0400** | **`ERR_MP3_FILE`** | 오디오 자산 (**STM32 내장 플래시**, SD와 무관) |
| 11 | 0x0800 | `ERR_HEATER_CURRENT` | 히터 전류 |
| 12 | 0x1000 | `ERR_ESP_COMM` | STM32측 ESP UART 링크 |

> ⚠️ v1.0대로 구현했다면 **FSR 고장이 SD 고장으로, SD 고장이 MP3 오류로** 보고됩니다.

### 11.2 ESP32 측 수정 완료 사항

정정 ① 검토 중 **ESP32 펌웨어의 맵이 bit 2부터 어긋나 있던 것**을 발견하여 수정했습니다.
회신이 지적한 범위(bit 8~9)보다 넓었습니다.

| bit | ESP32 (수정 전) | 실제 |
|-----|-----------------|------|
| 2 | `ERR_IMU` | **BOARD_TEMP** ← 여기서부터 밀림 |
| 3 | `ERR_FAN` | IMU |
| … | … | … |
| 8 | `ERR_SD_CARD` | FSR |
| 9 | `ERR_MP3_FILE` | **SD** |

ESP32에 `BOARD_TEMP`(bit 2) 항목이 없어 이후가 전부 한 칸씩 밀려 있었습니다.
**모든 STM32 에러가 엉뚱한 부품 이름으로 로깅되고 있었습니다.**

함께 수정한 것: `lastErrorCode`가 `uint8_t`라 16비트 마스크의 상위 바이트를 잘라내고 있었습니다.
**SD 오류 비트(0x0200)는 저장 자체가 불가능했으며**, 이는 §12 헬스 리포팅의 전제를 무너뜨립니다.
`uint16_t`로 변경했습니다.

### 11.3 `evtLogError`(0x84)와의 역할 분담

| 신호 | 의미 | 용도 |
|------|------|------|
| `ERR_SD_CARD` (0x0200) | SD 매체 자체의 이상 | 부팅 시 자가진단 결과 |
| **`evtLogError` (0x84)** | **런타임 로깅 이상** | 즉시 통보, 사유 구분 가능 |
| `ERR_MP3_FILE` (0x0400) | 오디오 자산 오류 | **SD와 무관.** 별도 필드로 분리 전송 |

## 12. 헬스 리포팅

교대 완료를 기다리지 않고 로깅 실패를 **당일 즉시** 발견하기 위한 경로입니다.
09:00에 카드가 죽은 장치를 18:00에 알게 되면 하루치를 통째로 잃습니다.

ESP32는 기존 1분 주기 MQTT 리포트에 `reqLogStatus` 응답을 실어 보냅니다.

| 필드 | 출처 | 경보 조건 |
|------|------|-----------|
| `logState` | 0x43 응답 [0] | ≠ 1 이면 경보 |
| `lastSeq` | 0x43 응답 [5..8] | 1분 전 대비 증가량 < 600 이면 경보 (10 Hz × 60 s) |
| `freeSpaceMB` | 0x43 응답 [13..14] | < 500 MB 경고 |
| `writeErrorCount` | 0x43 응답 [17..18] | 증가 시 경보 |
| `lastLogErrorReason` | 0x84 최근값 | 존재 시 경보 |
| `deviceMode` | 0x43 응답 [20] | 경보 게이팅용 (아래 참조) |
| `backfillBacklog` | PC 산출 | 미확보 구간이 계속 증가하면 경보 |
| `placeholderCount` | PC 산출 (`flags` bit1) | 증가 시 경보 — 센서 데이터가 비어 있는 레코드 |

### ⚠️ seq 증가율 경보는 ERROR 모드로 게이팅합니다 (정정 ②)

v1.0은 SLEEP에서 샘플링이 멈춘다고 가정했으나 **반대입니다.**
`v_Mode_Sleep()`이 `v_Mode_Sensing_Handler()`를 호출하므로(`mode.c:2055`)
**SLEEP 중에도 seq는 10 Hz로 증가합니다.**

| 샘플링 **수행** | 샘플링 **정지** |
|-----------------|-----------------|
| Healing, Waiting, ForceUp, ForceOn, ForceDown, **Sleep**, TEST | **ERROR**, BOOTING, WAKE_UP, OFF |

### 게이팅은 `reqLogStatus`(0x43)의 `deviceMode`로 합니다 — `evtMode` 추적 아님

**경보 억제 조건**: `deviceMode ∈ { ERROR(6), BOOTING(8), WAKE_UP(9), OFF(10) }`

v1.1은 이 조건을 `evtMode(0x82)` 추적으로 구현하려 했으나 **불가능했습니다** (회신 정정 ⑧).
`BOOTING` / `WAKE_UP` / `OFF`는 프로토콜 열거형에 값이 없었고 `evtMode`가 송신되지도
않으므로 ESP32가 관측할 방법이 없었습니다.

§6.2에서 `deviceMode`를 0x43 응답에 넣은 이유가 이것입니다. 이제 게이팅이:

- `evtMode` 수신 이력에 **의존하지 않습니다** — ESP32 재부팅 직후에도 즉시 정확합니다
- 헬스 필드와 **같은 응답에서 함께 오므로** 시점 불일치가 없습니다
- 표에 없는 값(`UNKNOWN`)이 오면 **억제하지 않습니다** — 모르는 상태를 정상으로 가정하지 않기 위함

## 13. 수용 기준 및 검증 시나리오

| # | 시나리오 | 합격 기준 |
|---|----------|-----------|
| 1 | **8시간 연속 기록** | **비-ERROR 구간** seq 연속성 **100%, 갭 0**. CRC 전수 통과 |
| 2 | **작업 중 전원 순단 20회** | 부팅마다 새 파일, `bootId` 중복 없이 증가. 절삭 후 잔존 레코드 CRC 100% 통과. **작업 중 순단이므로 flush 주기 내 손실만 허용 — 회당 ≤ 20 샘플.** (작업 종료 후 배터리 교체는 §10.1에 따라 보호 대상이 아니며 이 기준을 적용하지 않음) |
| 3 | **카드 미삽입 부팅** | 자세 제어 정상. `evtLogError(0/1)` 수신. `logState` = 0 또는 2 |
| 4 | **런타임 카드 탈거·재삽입** | `evtLogError(1)` 수신. 재삽입 후 새 `fileIndex`로 재개. 기존 파일 무손상 |
| 5 | **용량 소진** | `evtLogError(2)` 수신. 장치 주기능 정상 유지 |
| 6 | **deviceId 미수신 부팅** | `/LOG/UNKNOWN/`에 기록. 이후 0x23 수신 시 다음 로테이션부터 정상 경로 |
| 7 | **UART 단선 상태 부팅** | ESP32 통신 없이도 SD 기록 정상 진행 |
| 8 | **제어 루프 영향도** | 로깅·백필 활성/비활성 간 100 Hz 루프 지터 유의미한 증가 없음. IWDG 리셋 없음 |
| **9** | **백필 처리량** | 8시간분(288,000 레코드) 회수가 **45분 이내** (이론값 39분 + 여유) |
| **10** | **🔴 음영 종료 후 재부팅 회수** | 음영 상태로 30분 작업 → 전송 없이 배터리 탈거 → 재투입 후 **이전 `bootId` 구간이 전부 회수됨** |
| **11** | **백필 중 전원 차단** | 전송 도중 배터리 탈거 → 재투입 후 재요청으로 **손실 0** |
| **12** | **백필 중 BLE 끊김·재연결** | 전송 도중 범위 이탈 → 재연결 후 자동 재개, **손실 0**. 낭비는 1배치(약 1초분) 이내 |
| **13** | **라이브 우선순위** | 백필 진행 중에도 STAT(0x70) 10 Hz 주기가 유지됨 |
| **14** | **🔴 불변식 유지** | 플레이스홀더가 기록된 파일에서 `reqLogRead(startSeq=X)` 요청 시 **정확히 seq=X 레코드가 반환됨** |
| **15** | **쓰기 실패 시 로테이션** | 강제 쓰기 실패 주입 → 새 `fileIndex`로 전환. **파일 내부 갭 0**, 갭은 파일 경계에만 존재 |
| **16** | **모드 관측** | 장치를 OFF 상태로 두었을 때 0x43이 `deviceMode=10`을 보고하고 **오경보가 발생하지 않음** |

### 🔍 유실률 검증

```
유실률 = 1 - (CRC 통과 레코드 수) / (max(seq) - min(seq) + 1)
```

시나리오 1에서 이 값이 **0%** 여야 합니다.

**시나리오 10이 이번 개정의 핵심 검증 항목입니다** — 이것이 통과하지 못하면
배터리 교체 운영에서 데이터가 조용히 사라집니다.

> 리프레시하는 방식은 **채택하지 않습니다.** 그렇게 하면 카드가 멈춘 30초 동안
> 자세 제어가 정지하기 때문입니다. 로깅보다 안전 기능이 우선입니다.

### 14.3 남은 확인 항목

**Q14. `deviceMode`는 7~10 전체 추가로 확정합니다 — 선택이 아니라 필수 요구사항입니다.**
회신 v1.1 §2.4가 제시한 두 안 중 **7~10 전체 추가**를 채택했습니다 (§7.1).

`0xFF = UNKNOWN` 최소안은 **채택할 수 없습니다.** §12는 미지 값에 대해 경보를 억제하지
않는 것이 원칙인데(모르는 상태를 정상으로 가정하지 않기 위해), 샘플링 정지 모드가 전부
`0xFF`로 오면 게이팅이 한 번도 걸리지 않아 **⑧이 해결하려던 오경보가 그대로 재발합니다.**

ESP32 측 경계 검사는 크래시를 막을 뿐 이 문제를 해결하지 못합니다.
`v_Mode_Healing()`의 `evtMode` 송신도 함께 부탁드립니다.

**Q15. 쓰기 실패·부분 쓰기 감지 시 로테이션(§7.4)이 구현 가능합니까?**
`f_write()`가 요청보다 적게 기록한 경우를 감지해 즉시 close + `fileIndex` 증가로
전환하는 경로입니다. 플레이스홀더(§7.4)로는 이 경로를 막을 수 없어 별도 규정했습니다.

**Q16. `SD_TIMEOUT` 축소 시 정상 카드에서 오탐이 발생하지 않는지 확인 부탁드립니다.**
1초 이하로 줄이면 워치독 관점에서는 안전해지나, 마모 평준화 중인 카드의 쓰기 지연이
1초를 넘으면 `evtLogError(3)`이 불필요하게 발생할 수 있습니다.
§13 시나리오 8 실측 시 **오탐 빈도**도 함께 기록해 주시면 임계값을 조정하겠습니다.

## 15. 향후 확장 (비범위)

### 15.1 UART 보드레이트 상향

115200 → 460800으로 올리면 백필 배율이 12.4배 → **약 50배**가 되어
8시간분 회수가 39분 → **약 10분**으로 단축됩니다.

현재 12.4배로도 운영 요건을 만족하므로 이번 범위에서 제외하나,
BLE 동시 접속 실측(§9.5) 결과에 따라 재검토할 수 있습니다.
검토 시 STM32 측 클럭 오차 여유 확인이 선행되어야 합니다.

### 15.2 STAT(0x70)에 `seq` 추가

BLE 라이브 샘플과 SD 데이터를 직접 대조하려면 STAT에도 seq가 필요하나,
백필로 전량 회수되므로 병합에는 불필요합니다.
STAT DATA가 64 B 포화 상태라 추가 시 v2.1 하드 컷오버가 발생합니다.

STM32 팀이 회신 v1.0 §7.1에서 즉시 처리 대상으로 식별한 항목입니다.

### 16.2 백필 선행 인프라 — 이것이 없으면 백필이 성립하지 않습니다 🔴

STM32 회신 v1.1 §4에서 도출된 항목입니다. **전부 STM32 측 작업이며 ESP32 팀 조치는 불필요합니다.**

| # | 수정 | 위치 | 사유 |
|---|------|------|------|
| 1 | `SD_TIMEOUT` 30초 → **1초 이하** | `sd_diskio.c:41` | IWDG 2초 이내로 최악 블로킹 억제. **미조치 시 SD 이상이 워치독 리셋으로 나타남.** 정확한 임계값은 §14.3 Q16 실측에 따라 조정 |
| 2 | `UART_ESP_TX_ARR_SIZE` 256 B → **2 KB** | `uart.c:55` | 256 B는 115200 bps에서 22 ms분. SD 블로킹이 그보다 길면 회선이 idle로 낭비되어 12.4배 배율이 깎임 |
| 3 | `v_SD_BusyWait_Yield()`에 **TX 드레인만** 추가 + 쓰기 대기 루프에도 훅 삽입 | `tim.c:78`, `sd_diskio.c:353, 366, 400` | 블로킹 중에도 회선을 채움 |
| 4 | `_FS_LOCK` 2 → **4** | `ffconf.h:230` | 쓰기 + 백필 읽기 + 로테이션 동시 오픈 |

> ### ⚠️ 3번 구현 시 절대 하면 안 되는 것
>
> `v_SD_BusyWait_Yield()`에서 `v_Uart_Handler()`를 통째로 호출하면 안 됩니다.
> 이 훅은 `f_read()`의 busy-wait **안에서** 실행되는데,
> `v_Uart_Handler()` → `v_ESP_Handler()` → 수신 디스패치로 이어지면
> 그 순간 도착한 `reqLogRead`가 **FatFs를 재진입**시킵니다.
> `_FS_REENTRANT = 0` 환경에서는 **볼륨이 손상될 수 있습니다.**
> **TX 링버퍼 드레인 코드만 분리해서 호출**하십시오.

§13 시나리오 8·13의 합격은 1~3번에 직접 의존합니다.

# ESP32 보고 #41 — ESP32 팀 회신

> **대상**: STM32 보고 #40 (Q75·Q76 진행 중)
> **판정**: **`ctrlLogDeleteAll` 제안을 철회합니다**
> **STM32 측 조치 요청**: **없습니다 — 작업을 멈춰 주십시오**

---

## 1. 철회합니다

`SPEC_PROPOSAL_ctrlLogDeleteAll`(0x58)을 **진행하지 않기로 했습니다.**

**Q75·Q76 회신이 필요 없습니다.** §6.10 델타도 만들지 마십시오. 준비 중이셨다면
멈춰 주십시오 — 늦게 알리면 그만큼 헛일이 되므로 먼저 보냅니다.

우선순위 판단이고, 그쪽 검토 내용에 문제가 있어서가 아닙니다.

---

## 2. 대신 유지되는 것

기존 **`ctrlLogDelete`(0x57) 선택 삭제**로 계속 처리합니다. 이미 양쪽에
구현돼 있고 동작합니다.

오늘 실물로 확인했습니다.

```
카드 62개 → 삭제 후보 1개(boot=114 file=0, PC가 140건 전부 보유)
→ 확인 창 → 삭제 → 카드 61개
PC 보유분 140건 그대로
```

일상 운용에는 이것으로 충분합니다. 카드는 61개로 상한 128까지 여유가 있습니다.

---

## 3. 진단은 철회하지 않습니다

제안서 §1의 지적은 **여전히 유효합니다.**

> 상한은 RAM 인덱스의 한계이지 파일시스템의 한계가 아닙니다.
> 카드를 비우려는 상황이 곧 초과분이 생기는 조건입니다.

그리고 그쪽이 §2에서 더한 것도 유효합니다 — 일괄 삭제는 IWDG 2초를 넘고,
분할 실행이 답이라는 것.

**문제가 사라진 것이 아니라 지금 급하지 않을 뿐입니다.** 카드가 128에
가까워지면 이 문서에서 재개하면 됩니다. 제안서에 철회 표시를 남기고 논의
기록은 그대로 두었습니다.

---

## 4. 그쪽 검토에 대하여

짧게라도 남겨둡니다. 헛일이 된 검토지만 두 가지는 저희가 배운 것입니다.

**IWDG를 저희가 계산하지 않았습니다.** "디렉터리 순회 + `f_unlink`"라고 적고
그것이 한 호출에 끝난다고 가정했습니다. 이 사양이 처음부터 그 예산 위에
서 있었는데(부팅 스캔 128, 390 ms, 5배 여유) 새 명령에서 잊었습니다.

**개수가 아니라 시간으로 끊는다**는 것도 저희가 못 낸 답입니다. 카드 속도가
다르면 개수 기준은 상한을 못 지킵니다.

다음에 비슷한 명령을 제안할 때 두 가지를 먼저 확인하겠습니다.

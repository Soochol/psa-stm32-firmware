# 사양 제안 — `0x43`에 `indexCapacity` (2 B)

> **제안**: ESP32 팀 → STM32 팀
> **대상 사양**: `ESP-STM32_SD_Logging_Extension_v1.7` §6.2
> **성격**: 기존 응답에 필드 1개 추가 (23 → 25 B)
> **규모**: `filesOnCard` 추가(21 → 23 B)와 **같은 형태의 변경**

---

## 0. 요약

| 항목 | 내용 |
|---|---|
| 요청 | `0x43` 응답 끝에 `indexCapacity`(u16 BE) 추가 — 응답 23 → 25 B |
| 이유 | 지금 그 값은 **ESP32가 소스에 적어 둔 128**이고, 축소 빌드 때 실제로 어긋났습니다 |
| 선례 | `filesOnCard` 자체가 같은 방식(길이 게이팅)으로 들어왔습니다 |
| 급함 | **아닙니다.** 다만 사용자 화면에 숫자를 띄우기 전에 정하는 편이 낫습니다 |

---

## 1. 무엇을 하려는가

PC 앱에 **카드 사용량을 상시 표시**하려 합니다.

```
SD 카드    61 / 128 개
```

`filesOnCard`(§6.2, v1.7)가 이미 왼쪽 숫자를 줍니다. 저희는 그 값을 BLE로
올려 화면에 띄우기만 하면 됩니다 — **그쪽 추가 구현은 여기까지는 없습니다.**

문제는 **오른쪽 숫자**입니다.

---

## 2. 오른쪽 숫자를 지금은 저희가 지어내고 있습니다

```c
// include/uartMaster.h
// SD_LOG_IDX_MAX on the STM32 side. Kept here only to turn the reported file
// count into "how many are out of reach"; the STM32 owns the real limit.
#define LOG_INDEX_CAPACITY 128
```

주석이 스스로 인정하고 있습니다 — **한도의 주인은 STM32인데 값은 저희가
들고 있습니다.**

### 2.1 이건 가상의 위험이 아닙니다

이미 한 번 어긋났습니다.

| 시점 | STM32 `SD_LOG_IDX_MAX` | ESP32 `LOG_INDEX_CAPACITY` |
|---|---|---|
| reason 6 시험 (#29) | **4** (축소 빌드) | 128 → 수동으로 4 |
| 원복 (#30) | 128 | 128 → 수동으로 복구 |

회신 #30 §1에 *"그쪽 `LOG_INDEX_CAPACITY`도 128로 복구하셨다니 양측 표시가
맞습니다"* 라고 쓰여 있습니다. **양쪽이 각자 고쳤기 때문에 맞은 것**이지,
구조가 맞춘 것이 아닙니다.

### 2.2 화면에 띄우면 성격이 바뀝니다

지금까지 이 값은 로그 한 줄이었습니다. 앞으로는 **사용자가 보고 판단하는
숫자**가 됩니다.

| 실제 | 화면 | 사용자 판단 |
|---|---|---|
| 한도 100 · 카드 90 | `90 / 128` | "여유 있다" → **틀림. 10개 남았습니다** |
| 한도 256 · 카드 130 | `130 / 128` **초과 경고** | "정리해야 한다" → **틀림. 여유 있습니다** |

두 번째가 특히 나쁩니다. 저희 코드는 `filesOnCard > LOG_INDEX_CAPACITY`를
**ESP_LOGE + 회수 불가 경고**로 처리합니다. 분모가 틀리면 **멀쩡한 장비가
데이터 손실을 보고**합니다.

---

## 3. 제안 — `filesOnCard`와 똑같은 방식

### 3.1 필드

| 오프셋 | 크기 | 필드 | 설명 |
|---|---|---|---|
| … | … | (기존 §6.2 그대로) | |
| 21 | 2 | `filesOnCard` | v1.7 |
| **23** | **2** | **`indexCapacity`** | **`SD_LOG_IDX_MAX` (uint16 BE)** — 신규 |

**응답 23 B → 25 B.**

### 3.2 하위 호환 — 그쪽이 정한 규칙 그대로

v1.7 §6.2가 `filesOnCard`에 대해 정한 것과 같습니다.

```
길이 >= 21  →  기존 필드 파싱
길이 >= 23  →  filesOnCard 유효
길이 >= 25  →  indexCapacity 유효
```

저희 파서는 이미 이 모양입니다(`length >= LOG_STATUS_RESPONSE_SIZE_V2`).
따라서 **양측 적재 순서는 상관없습니다.** 그쪽이 먼저 나가도 저희가 무시하고,
저희가 먼저 나가도 `?`로 표시합니다.

### 3.3 값이 없을 때

저희는 `filesOnCard`와 같게 처리합니다 — **0을 "한도 0"으로 읽지 않고**
`indexCapacityKnown = false`로 두고 화면에 `61 / ?` 로 씁니다. 잘못된 분모보다
없는 분모가 낫습니다.

### 3.4 상수인데 왜 매번 보내는가

컴파일 타임 상수를 매 응답에 싣는 것이 낭비로 보일 수 있습니다. 다만

- 주기가 **1분**이라 대역 비용이 사실상 없습니다 (2 B/분)
- 별도 조회 커맨드를 신설하면 **커맨드가 하나 늘고**, 저희 쪽에 "언제
  물어봤는지" 상태가 생깁니다
- 펌웨어를 교체하면 상수도 바뀝니다. 같은 응답에 실려 오면 **버전을 맞출
  일이 아예 없습니다**

`formatVersion`을 매번 싣는 것과 같은 판단입니다.

## 4. 저희 쪽 계획 (참고 — 회신 불필요)

| 계층 | 하는 일 |
|---|---|
| PC 앱 | `filesOnCard / indexCapacity` 표시. 초과 시 "목록 밖 N개" 경고 |
| ESP32 | BLE `0x25` → UART `0x43` 중계. **응답 바이트를 그대로 올림** |
| STM32 | 필드 1개 추가 |

ESP32는 §6.9.8과 같은 원칙으로 **해석하지 않습니다.** 0x43 응답을 통째로
BLE 프레임에 실어 보내므로, 나중에 §6.2에 필드가 더 붙어도 **ESP32 수정 없이**
앱까지 도달합니다.

### 4.1 조회 주기 — 이견 있으시면 알려주십시오

앱이 화면을 열거나 사용자가 새로고침할 때 **온디맨드로 0x43을 1회** 보냅니다.
기존 1분 주기 폴링은 그대로 둡니다.

부하는 이미 검증된 범위 안이라고 봅니다 — ESP32의 복구 프로브가
`LOG_STATUS_PROBE_INTERVAL_MS = 5 s` 간격으로 0x43을 쏘고 있고, 사용자 조작
속도는 그보다 느립니다. **다만 0x43이 SD 접근을 동반한다면** 말씀해 주십시오.
저희가 캐시로 바꾸겠습니다.

## 5. 회신 요청

| # | 항목 |
|---|---|
| **Q77** | `0x43` 응답 끝에 `indexCapacity`(u16 BE) 추가, 23 → 25 B — 가능합니까? |

**Q77 하나뿐입니다.** §4.1은 이견이 있을 때만 답해 주시면 됩니다.

### 5.1 이미 답을 받은 것 — 다시 묻지 않습니다

기록을 위해 적어 둡니다.

| 확인된 사실 | 출처 |
|---|---|
| `filesOnCard`는 기록 중인 파일을 **포함** | 회신 #34, v1.7 §6.2 |
| 삭제하면 `filesOnCard` **즉시 감소** (재부팅 불필요) | v1.7 §6.9, 회신 #34 (16→15 / 17→16 실측) |
| `filesOnCard`는 부팅 스캔·상태 응답·reason 6이 **같은 값** 사용 | 회신 #30 §2.2 |

이 세 가지 덕분에 앱이 삭제 직후에도 정확한 숫자를 보여줄 수 있습니다.

---

## 6. 급하지 않습니다

현재 카드는 61개, 한도는 128로 양쪽 값이 맞아 있습니다. 지금 당장 틀린 숫자가
나오는 상황은 아닙니다.

다만 **사용자에게 숫자를 보여주기 시작하면** 그 숫자의 출처가 어디인지가
중요해집니다. 그전에 정해 두자는 제안입니다.

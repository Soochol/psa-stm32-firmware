# 사양 제안 — `0x43`에 `indexCapacity` (2 B)

> **제안**: ESP32 팀 → STM32 팀
> **대상 사양**: `ESP-STM32_SD_Logging_Extension_v1.7` §6.2
> **성격**: 기존 응답에 필드 1개 추가 (23 → 25 B)
> **규모**: `filesOnCard` 추가(21 → 23 B)와 **같은 형태의 변경**
> **저희 쪽 상태**: **코드 완료** — 빌드·단위시험 통과, **실기 확인은 아직**입니다 (§4)

---

## 0. 요약

| 항목 | 내용 |
|---|---|
| 요청 | `0x43` 응답 끝에 `indexCapacity`(u16 BE) 추가 — 응답 23 → 25 B |
| 배경 | 카드 사용량 표시를 구현했습니다. **왼쪽 숫자는 그쪽이 주신 `filesOnCard`입니다** |
| 문제 | **오른쪽 숫자(128)만 저희가 소스에 적어 둔 값**입니다 |
| 선례 | `filesOnCard` 자체가 같은 방식(길이 게이팅)으로 들어왔습니다 |
| 준비 | 25 B가 와도 **저희 중계는 이미 통과시킵니다**. 값을 쓰는 코드만 Q77 확정 후 |

**감사드립니다.** `filesOnCard`가 없었으면 이 화면은 만들 수 없었습니다. 파일
목록으로 대신하려 했다가 왜 안 되는지 확인했습니다 (§1.1).

---

## 1. 무엇을 만들었는가

PC 앱 상단, `카드 정리` 버튼 옆에 카드 사용량을 상시 표시합니다.

```
[Backfill] [카드 정리]  SD 61/128        ← 61은 예시입니다
```

정리할지 말지를 판단하는 자리에 그 판단에 필요한 숫자를 둔 것입니다.

### 1.1 파일 목록으로는 셀 수 없습니다

만들면서 확인한 것을 적어 둡니다. 목록(`0x45`)의 항목 수를 세는 방법은 **세
가지 이유로 틀립니다.**

| 방법 | 결과 |
|---|---|
| `0x45` 항목 수 | 한도에서 멈춥니다 — 128을 넘으면 **더 세지 않습니다** |
| 〃 | 기록 중인 파일이 빠집니다 (회신 #34) |
| 〃 | 숫자 하나 보려고 14 B × N을 페이지로 나눠 받아야 합니다 |
| **`0x43`의 `filesOnCard`** | **정확하고, 2 B이고, 이미 1분마다 옵니다** |

특히 첫 번째가 결정적입니다. **정리가 필요한지 알고 싶은 바로 그 구간에서
목록은 세기를 멈춥니다.**

## 2. 오른쪽 숫자를 지금은 저희가 지어내고 있습니다

```c
// ESP32 include/uartMaster.h
// SD_LOG_IDX_MAX on the STM32 side. Kept here only to turn the reported file
// count into "how many are out of reach"; the STM32 owns the real limit.
#define LOG_INDEX_CAPACITY 128
```

주석이 스스로 인정하고 있습니다 — **한도의 주인은 STM32인데 값은 저희가
들고 있습니다.** 이번에 앱에도 같은 상수가 하나 더 생겼습니다. **이제 두
곳입니다.**

### 2.1 이건 가상의 위험이 아닙니다

이미 한 번 어긋났습니다.

| 시점 | STM32 `SD_LOG_IDX_MAX` | ESP32 `LOG_INDEX_CAPACITY` |
|---|---|---|
| reason 6 시험 (#29) | **4** (축소 빌드) | 128 → 수동으로 4 |
| 원복 (#30) | 128 | 128 → 수동으로 복구 |

회신 #30 §1에 *"그쪽 `LOG_INDEX_CAPACITY`도 128로 복구하셨다니 양측 표시가
맞습니다"* 라고 쓰여 있습니다. **양쪽이 각자 고쳐서 맞은 것**이지, 구조가
맞춘 것이 아닙니다. 그때는 로그 한 줄이었고, 지금은 화면입니다.

### 2.2 화면에 뜨는 순간 성격이 바뀝니다

| 실제 | 화면 | 사용자 판단 |
|---|---|---|
| 한도 100 · 카드 90 | `SD 90/128` | "여유 있다" → **틀림. 10개 남았습니다** |
| 한도 256 · 카드 130 | `SD 130/128 ⚠ 2개 목록 밖` | "손실 났다" → **틀림. 여유 있습니다** |

두 번째가 특히 나쁩니다. 저희는 초과분을 **회수 불가 경고**로 표시합니다.
분모가 틀리면 **멀쩡한 장비가 데이터 손실을 보고**합니다.

## 3. 제안 — `filesOnCard`와 똑같은 방식

### 3.1 필드

| 오프셋 | 크기 | 필드 | 설명 |
|---|---|---|---|
| … | … | (기존 §6.2 그대로) | |
| 21 | 2 | `filesOnCard` | v1.7 |
| **23** | **2** | **`indexCapacity`** | **`SD_LOG_IDX_MAX` (uint16 BE)** — 신규 |

**응답 23 B → 25 B.**

### 3.2 하위 호환 — 그쪽이 정한 규칙 그대로

v1.7 §6.2가 `filesOnCard`에 대해 정한 것과 같습니다.

```
길이 >= 21  →  기존 필드 파싱
길이 >= 23  →  filesOnCard 유효
길이 >= 25  →  indexCapacity 유효
```

**적재 순서는 상관없습니다.** 지금 25 B로 보내주셔도 저희 중계와 파서는 이미
통과시킵니다 — 길이만 보고 아는 필드까지만 읽습니다. 다만 **그 값을 화면
분모로 쓰는 코드는 Q77 확정 후에 넣겠습니다.** 위치와 의미가 정해지기 전에
읽으면, 이 문서가 막으려는 바로 그 "틀린 분모"를 저희가 만들게 됩니다.

### 3.3 값이 없을 때

`filesOnCard`와 같게 처리합니다 — **0을 "한도 0"으로 읽지 않습니다.**

### 3.4 상수인데 왜 매번 보내는가

컴파일 타임 상수를 매 응답에 싣는 것이 낭비로 보일 수 있습니다. 다만

- 주기가 1분이라 대역 비용이 사실상 없습니다 (2 B/분)
- 별도 조회 커맨드를 신설하면 커맨드가 하나 늘고, 저희 쪽에 "언제 물어봤는지"
  상태가 생깁니다
- 펌웨어를 교체하면 상수도 바뀝니다. 같은 응답에 실려 오면 **버전을 맞출 일이
  아예 없습니다**

`formatVersion`을 매번 싣는 것과 같은 판단입니다.

## 4. 저희 쪽 구현 — 완료했습니다 (참고, 회신 불필요)

| 계층 | 한 일 | 상태 |
|---|---|---|
| PC 앱 | `filesOnCard / 128` 표시, 초과 시 "목록 밖 N개" 경고 | 코드 완료 |
| ESP32 | BLE `0x25` → UART `0x43` 중계, 응답을 **바이트 그대로** BLE `0xB4`로 | 코드 완료 |
| STM32 | 필드 1개 추가 | **Q77** |

**아직 실기에 올리지 않았습니다.** 빌드와 단위시험까지입니다 — 프레임 파싱,
길이 게이팅(21/23/25 B), 초과분 계산, 화면 문구를 시험으로 고정했습니다.
실장치 확인 결과는 나오는 대로 알려드리겠습니다.

### 4.1 ESP32는 해석하지 않습니다

§6.9.8과 같은 원칙입니다. 0x43 응답을 **길이째로** BLE 프레임에 실어 보냅니다.
필드를 뽑아 담지 않았기 때문에

> **§6.2에 필드가 더 붙어도 ESP32는 한 줄도 고치지 않습니다.**

Q77이 확정되면 저희가 손댈 곳은 **앱의 파서 한 줄**뿐입니다.

### 4.2 화면 상태 — `?`와 `0`을 구분했습니다

그쪽이 v1.7 §6.2에서 요구하신 구분을 화면까지 끌고 갔습니다.

| 장치 상태 | 화면 |
|---|---|
| 조회 중 | `SD …/128` |
| 정상 | `SD 61/128` |
| **21 B 응답 (구형 펌웨어)** | **`SD ?/128`** — "모름"이지 "0개"가 아닙니다 |
| 한도의 90% | `SD 115/128 ⚠ 정리 필요` |
| 한도 초과 | `SD 150/128 ⚠ 22개 목록 밖` |
| 장치가 거부 | `SD —/128` |

세 번째 줄이 §6.2 하위 호환 규칙의 실물입니다. 없는 필드를 0으로 읽었다면
**가득 찬 카드가 빈 카드로 보였을 것**입니다.

### 4.3 조회 주기 — 이견 있으시면 알려주십시오

| 언제 | 무엇 |
|---|---|
| 링크 연결 중 | **30초 주기**로 `0x43` 1회 |
| 삭제 직후 | `0x43` 1회 (숫자가 바뀌는 유일한 조작이라) |
| **백필 중** | **보내지 않습니다** — 전송이 끝날 때까지 건너뜁니다 |
| 기존 1분 폴링 | 그대로 유지 |

부하는 검증된 범위 안이라고 봅니다 — 복구 프로브가
`LOG_STATUS_PROBE_INTERVAL_MS = 5 s`로 0x43을 쏘는 구간이 이미 있고, 30초는
그보다 훨씬 성깁니다.

**다만 `0x43` 응답 생성이 SD 접근을 동반한다면** 말씀해 주십시오. 주기를
늘리거나 사용자 조작 시점으로만 제한하겠습니다.

### 4.4 무응답 타이머를 두지 않았습니다

`0x43`을 보내고 답이 없을 때 ESP32는 아무것도 재촉하지 않습니다. 표시가 남아도
**1분 주기 폴링의 다음 응답이 그것을 해소**하므로 중계가 잠기지 않습니다.
재요청 판단은 PC가 합니다 — 백필(§9.2)과 같은 분담입니다.

## 5. 회신 요청

| # | 항목 |
|---|---|
| **Q77** | `0x43` 응답 끝에 `indexCapacity`(u16 BE) 추가, 23 → 25 B — 가능합니까? |

**Q77 하나뿐입니다.** §4.3은 이견이 있을 때만 답해 주시면 됩니다.

### 5.1 이미 답을 받은 것 — 다시 묻지 않습니다

기록을 위해 적어 둡니다. 이 세 가지 덕분에 **추가 질문 없이 구현이
끝났습니다.**

| 확인된 사실 | 출처 |
|---|---|
| `filesOnCard`는 기록 중인 파일을 **포함** | 회신 #34, v1.7 §6.2 |
| 삭제하면 `filesOnCard` **즉시 감소** (재부팅 불필요) | v1.7 §6.9, 회신 #34 (16→15 / 17→16 실측) |
| `filesOnCard`는 부팅 스캔·상태 응답·reason 6이 **같은 값** 사용 | 회신 #30 §2.2 |

두 번째가 특히 유용했습니다. 삭제 직후 `0x43`을 한 번 더 보내는 것만으로
화면이 정확해집니다 — 재부팅을 기다릴 필요가 없습니다.

---

## 6. 급하진 않습니다만, 한 가지 달라졌습니다

현재 카드는 61개, 한도는 128로 양쪽 값이 맞아 있습니다. 지금 틀린 숫자가
나오는 상황은 아닙니다.

다만 **이제 그 숫자는 사람이 보고 판단합니다.** 이 문서를 처음 쓸 때는 "화면에
띄우기 전에 정해 두자"였는데, 그 사이에 띄웠습니다. 화면의 왼쪽은 그쪽이 주신
사실이고, **오른쪽은 아직 저희 추정입니다.**

`filesOnCard`를 주실 때 "플래그가 아니라 사실"이라고 하셨습니다(#29 §1.4).
분모도 같은 이유로 사실이면 좋겠습니다.

## 1. ① 절 번호 — 기존 번호를 밀지 않는 쪽을 권합니다

요약표를 `§6.8` → `§6.9`로 옮기는 안과, 커맨드를 `§6.9`로 신설하는 안 중
**후자**를 권합니다.

이유는 하나입니다. **이미 발송된 문서들이 §6.8을 요약표로 참조합니다.**
번호를 옮기면 그 참조들이 조용히 다른 곳을 가리키게 되고, 어느 판본을 읽었느냐에
따라 다른 절을 보게 됩니다. 보고 #16 §2.2에서 정리하신 판본 문제와 같은
성질입니다.

> 커맨드 정의가 요약표 뒤에 오는 게 어색해서

어색함은 맞습니다. 다만 요약표는 **그 시점까지의 커맨드를 모은 것**이므로 뒤에
새 커맨드가 붙는 구조 자체가 이상하지는 않습니다. 표에 `0x57` 행만 추가하면
목차상으로도 읽힙니다.

**그쪽이 §6.8을 요약표로 유지하는 편이 낫다고 판단하시면 그대로 따르겠습니다.**
저희 문서에서 §6.8을 참조한 곳은 없습니다.

## 2. ② BLE `0x23` — 아래 내용으로 §4를 채워주십시오

구현했습니다(`2534b33`).

### 4.1 `0x23` — PC→ESP32 파일 삭제 요청

| 항목 | 내용 |
|---|---|
| **요청** | `0x23` + `bootId`(4 B, BE) + `fileIndex`(2 B, BE) — **총 7 B** |
| **응답** | 프레임 `0xB3` + 결과 1 B — **총 2 B** |
| UART 매핑 | `0x57` (`bootId` 4 B + `fileIndex` 2 B) |
| 결과 전달 | UART ACK의 1 B를 **해석 없이** 그대로 올림 |

식별자는 `0x45` 응답 항목과 같습니다. **목록에서 본 것을 그대로 지목**하는
형태이므로 PC 쪽에 새 개념이 없습니다.

### 4.1.1 결과 코드

`§6.8.1`의 0~4를 그대로 전달하며, 하나를 더합니다.

| 값 | 의미 | 출처 |
|---|---|---|
| 0~4 | §6.8.1 | STM32 |
| **`0xFF`** | **장치가 답하지 않음** | **ESP32** |

`0xFF`가 필요한 경우는 셋입니다.

| 상황 | 이유 |
|---|---|
| 요청이 7 B 미만 | 형식 오류 |
| `stm32Ready == false` | 보낼 상대가 없음 |
| UART 송신 실패 | 슬롯 없음 등 |

**침묵 대신 답을 보냅니다.** PC가 자기 타임아웃까지 기다리는 것을 피하기
위해서이고, `0x22`에서 저희가 겪은 "보냈다 vs 받아들여졌다"와 같은 이유입니다.

### 4.1.2 ESP32가 하지 않는 것

**회수 여부를 판단하지 않습니다.** 요청을 읽지도 않고 그대로 넘기며, 결과도
해석하지 않습니다. 저희가 보는 것은 **형식이 맞는가**와 **보낼 상대가 있는가**
둘뿐입니다.

```c
// 요청을 넘기고 결과는 STM32의 ACK가 가져옵니다
if (deleteLogFile(bootId, fileIndex)) { return; }
```

### 4.2 사슬 전체 (그쪽 초안 그대로)

```
PC     0x23  "boot=9 file=0 지워도 된다"   ← 판단 (병합·CRC 검증 결과 보유)
  ↓
ESP32        중계                          ← 형식·연결만 검사
  ↓
STM32  0x57  f_unlink                      ← 구조적 안전만 검사
  ↑
결과   1 B   0 완료 / 1~4 거부·실패 / 0xFF 무응답
```

## 3. ⚠️ 미검증 — 적재 직후입니다

알려주신 대로 지금 STM32가 STOP이라 **시험하지 못했습니다.** 빌드와 코드
경로만 확인했습니다.

전원을 넣으면 §2에서 제안하신 순서로 확인하겠습니다.

| # | 확인 | 기대 |
|---|---|---|
| 1 | `0x56`으로 파일 몇 개 만들고 하나 지목 | 결과 **0** |
| 2 | 현재 기록 중인 파일 지목 | 결과 **2** |
| 3 | 백필 도중 요청 | 결과 **3** |
| 4 | 없는 파일 지목 | 결과 **1** |
| 5 | 삭제 후 `0x45`·`filesOnCard` | 각각 1 감소 |

**적재 알림 감사합니다.** 이번엔 무응답을 시험 실패로 오해하지 않았습니다.

## 4. 삭제 UI — 다음 작업입니다

보고 #31 §2에서 밝힌 정책대로 만들겠습니다.

```
[카드 정리]  →  지울 목록과 근거를 보여줌  →  사용자 확인  →  한 건씩 0x23
```

각 항목에 **왜 지워도 되는지**를 함께 보입니다 — 해당 `.psa` 보유, 병합
수집률 100%, CRC 실패 0, 불변식 위반 0. 하나라도 아니면 목록에 오르지
않습니다.

결과 2·3은 **일시적**이므로 재시도 대상으로 두고, 1·4·`0xFF`는 사용자에게
그대로 보입니다.

완성되면 알려드리겠습니다.

## 5. §4 §8.4 신설에 대하여

`SD_LOG_IDX_MAX = 128`이 사양서에 없었다는 지적이 맞습니다. 그리고 이 값을
적어두는 이유로 드신 것이 특히 그렇습니다.

> 이걸 적어두지 않으면 다음에 누군가 "128은 작다"며 그냥 올릴 자리입니다

**128의 근거가 RAM이 아니라 부팅 스캔 시간(파일당 3 ms, 워치독 2초)**이라는
것이 코드에는 안 보입니다. 상수만 보면 늘려도 될 것처럼 생겼습니다.

§10.4와 구분해 적으신 것도 같은 성격입니다 — 그 구분이 없으면 나중에 §10.4를
근거로 이 기능이 부정될 수 있습니다.

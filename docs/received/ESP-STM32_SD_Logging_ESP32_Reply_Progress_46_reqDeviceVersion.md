## 1. §4.2 권고 수용 — 지적이 정확했습니다

저희 파서는 원래 **16 B보다 짧은 응답도 읽었습니다.** 근거로 이런 주석까지
달아 두었습니다 — "패딩을 줄인 유닛은 고장이 아니라 자기 버전을 말하는 것".

**그 전제가 틀렸습니다.** 그쪽 구현(`comm_esp.c`)을 보니 `strncpy`로 **항상
16 B를 zero-padding**해 보내더군요. 즉 짧은 응답을 만들 수 있는 유닛이 존재하지
않습니다. 그렇다면 짧은 응답은 "패딩을 줄인 것"이 아니라 **온전히 도착하지 않은
프레임**이고, 반쪽 버전을 버전으로 읽는 것이 가장 나쁜 결과입니다.

`DATA 길이 >= 16`을 유효 조건으로 걸었습니다. 이제 세 경우가 한 경로로
떨어집니다.

| 입력 | 결과 |
|---|---|
| 빈 ACK (DATA 0 B) | 미상 |
| 16 B 미만 응답 | 미상 |
| all-zero 16 B | 미상 |
| 16 B 정상 ASCII | 버전 확정 |

어느 경우도 재시도하지 않습니다.

### 1.1 그쪽 예시 프레임 검증

`"1.0.0"` 응답의 체크섬 `C6`, 저희도 검산했습니다 — **정확합니다.**
(`"1.2.3"`의 `C7`에서 `32^30 ^ 33^30 = 0x01` 차이 → `C6`)

## 2. §4 정정 수용 — 두 층위로 기록했습니다

"빈 ACK 또는 무응답"이라고 뭉뚱그린 것은 저희 제안서의 부정확한 서술이었습니다.
사양서에 배포본별로 갈린다는 사실 그대로 적었습니다.

| 배포본 | 0x46 수신 시 |
|---|---|
| REQUEST 범위(0x30~0x49) 전체 수용 빌드 | 빈 ACK (LEN 4, DATA 없음) |
| 그 이전 빌드 | 무응답 — 프레임째 폐기 |

§4.1에서 말씀하신 "재시도하지 않는 설계 덕분에 비용이 부팅당 1프레임으로
고정된다"는 점 — 그 설계 그대로 유지합니다.

## 3. 미결 항목 처리

### 3.1 미결 #1 — 사양서 등재 완료

`ESP-STM32_UART_Protocol_Specification` **§7에 0x46을 등재**했습니다.
섹션 범위를 `0x30-0x42` → `0x30-0x46`으로 넓혔고, 응답 형식·유효 조건·구형
동작 두 층위·그쪽 예시 프레임을 함께 적었습니다.

### 3.2 미결 #2 — ESP32 질의 구현 완료

제안서 §5대로 구현했고, 한 가지를 더했습니다.

- **질의 시점**: `evtInitResult(0x81)` 직후 1회 — 정확히는 저희 INIT 시퀀스
  함수 안에 넣었습니다. 그래야 **0x43 복구 경로**(ESP32만 재시작해 0x81을
  영영 못 받는 경우)에서도 질의가 나갑니다.
- **캐시 무효화**: 질의를 보낼 때 캐시를 먼저 비웁니다. STM32가 0x46 없는
  펌웨어로 **다운그레이드**되면 응답이 없을 텐데, 그때 예전 버전이 그대로
  남아 있으면 안 되기 때문입니다.

### 3.3 참고 — PC 뷰어까지 연결했습니다

그쪽 작업은 없지만 전체 그림을 위해 적습니다. BLE에 커맨드 `0x26` / 프레임
`0xB5`를 신설해, PC가 연결하면 **1회 자동으로** ESP32 버전·빌드일시·모델과
**캐시된 STM32 버전**을 함께 받아 툴바에 `FW E:0.0.1 / S:1.0.0`으로
표시합니다. ESP32가 미리 캐시해 두므로 UART 왕복을 기다리지 않습니다.

`S:?` 표시 규칙은 그쪽 §2 설명 그대로 따랐습니다 — **`?`면 1.0.0 이전
펌웨어.** all-zero가 나올 수 없다고 확인해 주신 덕분에 이 단정이 가능해졌습니다.

다만 PC가 **STM32 부팅보다 먼저 연결하는 경합**이 있어, `S:?`일 때만 30초 후
1회 재요청합니다. 0x81(약 13초)과 저희 25초 복구 프로브가 모두 지난 뒤라,
그때도 `?`면 진짜 미지원입니다. UART로 나가는 질의는 여전히 부팅당 1회입니다.

## 4. 남은 것 — 실기 확인뿐입니다

| # | 항목 | 상태 |
|---|---|---|
| 1 | 사양서 등재 | ✅ 완료 |
| 2 | ESP32 질의 구현 | ✅ 완료 (빌드 성공, 자동 테스트 329건 통과) |
| 3 | **실기 확인 (0x81 → 0x46 시퀀스)** | ⏳ **양쪽 다 미배포** |

저희 빌드도 아직 어느 장치에도 굽지 않았습니다. 그쪽도 같은 상태라고
하셨으니, **두 펌웨어를 같은 장치에 함께 올려 한 번에 확인**하는 것이
효율적일 것 같습니다.

확인 항목은 세 가지입니다.

1. 0x81 직후 0x46 요청이 나가는가
2. 16 B 응답이 오고 `1.0.0`으로 파싱되는가
3. PC 뷰어에 `S:1.0.0`이 뜨는가

**일정은 그쪽에 맞추겠습니다.** 준비되시면 알려 주십시오.

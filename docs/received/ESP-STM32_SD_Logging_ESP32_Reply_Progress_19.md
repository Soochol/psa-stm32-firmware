## 1. §2.2 종결 — 경계를 넘는 요청이 정상 동작합니다

카드를 되돌려 주신 뒤 준비했던 요청을 실행했습니다.

```
--boot 9 --start-seq 35995 --limit 12 --batch 12
→ device holds 15 file(s)     (그쪽 검증 결과와 일치)
→ 12 records, 2 batches
```

**2 배치**입니다. `boot=9` file 0(…36000)과 file 1(36001…)에서 각각 6개씩
가져왔습니다. 결과는 다음과 같습니다.

| seq | tick_ms | Δtick |
|---|---|---|
| 35995 | 3,609,781 | — |
| 35996 | 3,609,881 | 100 |
| 35997 | 3,609,981 | 100 |
| 35998 | 3,610,081 | 100 |
| 35999 | 3,610,181 | 100 |
| **36000** | **3,610,281** | **100** ← file 0 마지막 |
| **36001** | **3,610,415** | **134** ← file 1 첫 레코드 |
| 36002 | 3,610,481 | 66 |
| 36003 | 3,610,581 | 100 |
| 36004 | 3,610,681 | 100 |
| 36005 | 3,610,781 | 100 |
| 36006 | 3,610,881 | 100 |

**seq가 끊김 없이 35995~36006입니다.** 병합 결과도 12/12, 수집률 100%,
CRC 실패 0, 불변식 위반 0입니다.

지적하신 위험 — `firstSeq`가 어긋나면 이후 모든 요청이 한 칸씩 밀린 레코드를
조용히 반환한다 — 은 발생하지 않습니다. `u8_SD_Log_Backfill_Start()`의
seq → 파일 선택이 경계에서 정확합니다.

**카드 검증이 "데이터가 옳다"를 닫았고, 이 요청이 "탐색이 옳다"를 닫습니다.**

## 2. 신규 계측 — 로테이션 기록 지연 약 34 ms

경계의 tick 패턴에 정보가 있습니다.

```
36000 → 36001 : 134 ms   (정상보다 +34)
36001 → 36002 :  66 ms   (정상보다 -34)
합계          : 200 ms   = 2 × 100 ms 정확히
```

**두 구간의 합이 정확히 200 ms입니다.** 즉 로테이션(close-then-open)이
한 샘플의 기록을 약 34 ms 늦췄고, 다음 샘플이 그만큼 당겨져 보상됐습니다.

### 2.1 샘플 유실이 아닙니다

seq가 연속이므로 **레코드는 하나도 빠지지 않았습니다.** 흔들린 것은
기록 시각뿐이고, 그것도 다음 샘플에서 회수됩니다.

보고 #17 §3의 "tick 간격 최대가 전 파일 100 ms"와도 모순되지 않습니다 —
그 계측은 파일 **내부** 간격이고, 134 ms는 파일 **경계를 가로지르는**
간격이라 파일 단위 스캔에는 잡히지 않습니다. 백필로 두 파일을 이어 붙여야
보이는 값입니다.

### 2.2 Q47과 같은 성격입니다

보고 #18 §2에서 답한 파일 시작 아티팩트(`seq 0→1`이 3 ms)와 같은 계열입니다.
둘 다 **파일 경계에서 기록 타이밍이 흔들리고 데이터는 온전한** 형태입니다.

| 지점 | 증상 | 데이터 |
|---|---|---|
| 파일 시작 (`seq 0→1`) | 3 ms (너무 짧음) | 온전 |
| 로테이션 경계 | 134 → 66 ms (합 200) | 온전 |

**둘 다 조치 불필요**로 봅니다. 다만 로테이션 지연 34 ms는 SD 차단 시간의
실측치이기도 하므로, 보고 #05의 차단 히스토그램(최대 47 ms)과 함께 두시면
일관된 그림이 됩니다 — **34 ms는 그 분포 안에 들어갑니다.**
